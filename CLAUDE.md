## What this project is

Replacing an email-and-Excel-based Purchase Request -> Purchase Order -> Invoice workflow (Hanyang ENG, a construction company) with a web app owning the full lifecycle. The core problem isn't any single step but that the three were never connected: the same order lived in a spreadsheet, an email thread, and a vendor's invoice with nothing tying them together, so reconciling what was ordered against what was billed was manual and after the fact.

## How the work flows

Site staff talk to a vendor first and get a quotation — that happens outside the app, and it is why a PR arrives with the vendor and the prices already settled. The requester raises the PR with that quotation attached and names an ordered chain of signers. Each signer approves, edits and continues, or returns it for correction to anyone earlier. Full approval generates the PO as a frozen snapshot of the items, the President signs it, and office staff send that PDF to the vendor — also outside the app, which is why the PO is the one document this system emits. The vendor's invoice comes back to office staff, who enter it and reconcile it line by line against the PO.

Three kinds of people, and the distinction is organisational rather than a privilege ladder. **Site staff** are non-Admin Employees: they raise PRs, sign, and withdraw their own. **Office staff** all run with `Is Admin: true`, so gating something to Admin scopes it to the office — invoicing is Admin because invoicing is office work, not because Admin is more trusted. The **President** signs POs; nothing else is role-specific to them. Vendors have no account and never touch the app.

What that boundary implies keeps coming up: a decision made before a PR exists cannot be helped by a form inside one (#19), and a status describing something that happens outside the app has nobody to set it (#144).

## Architecture

- Next.js (App Router, JavaScript, Tailwind), deployed on Vercel.
- Airtable as data store only (base: "Material Purchases"). All business logic lives in the backend. Airtable formulas only for pure data transforms, never workflow logic.
- Auth: magic link only, restricted to company email domain, verified. New signups always land as plain Employee (Is Admin: false) — promotion is a manual Airtable edit.

### Editing the Airtable schema

**The schema is editable by either of us, and a schema change ships in the SAME COMMIT as the code that reads it.** This replaces the earlier posture, which had Soo make every Airtable edit by hand while Claude only proposed one. The reason for the change is timing rather than preference: this is a single-developer project with no production data yet, so the moment to fix a name or a shape is now, and a proposal that waits is a proposal that decays.

**Why renaming is safe, stated as a mechanism rather than a hope.** Airtable resolves a field reference internally, not by its text: renaming a field carries every formula, rollup, lookup and view filter with it. Measured on this base — of 18 formula fields, the Metadata API renders 12 with `{fldXXXXXXXXXXXXXX}` and 6 with `{Field Name}`, which is itself the evidence that the NAME is a rendering and not the storage. `Materials."Uninvoiced Qty"` reads `{fldbIC92pdF5S1Tjm} - {fldcUDI2qSuZE0kqt}` — Committed minus Invoiced, by id.

**So the only thing a rename breaks is a string literal in this repo**, and those are enumerable: `record.get("...")`, a `filterByFormula` fragment, a `fields:` projection, a `parentLinkFieldName`. That makes the safe procedure mechanical rather than careful — rename the field, grep the old name across `lib/`, `app/` and `scripts/`, fix every hit, and put both halves in one commit so no revision of this repo names a field that does not exist. **Grep for the old name after the change, not before**: the check that matters is that nothing survives.

**What is NOT covered by that.** The Metadata API cannot write everything, and two limits are measured: an existing single select's option list cannot be PATCHed at all (see Units), and `prefersSingleRecordLink` is refused on field CREATE (422 `INVALID_FIELD_TYPE_OPTIONS_FOR_CREATE`) **and on field UPDATE** (422 `INVALID_REQUEST_UNKNOWN`, with and without `linkedTableId` alongside it). It is READABLE, though, so a check can report it — and where the app enforces single-record itself, the invariant is checked on the DATA instead, since an unenforced invariant drifts silently and no schema property would show it (`verify-overage-167.mjs` Part A).

**Deleting or retyping a field is still not the same as renaming it**, and neither is adding one. A rename preserves every value; a type change can silently drop them. The dummy-data convention below is unchanged: records in this base are not to be removed as tidying-up.

**THE GREP COMING BACK EMPTY IS NOT THE LAST STEP — READ EVERY HUNK.** This belongs to the procedure rather than to any one issue: a grep finds the string literal, and what a blanket substitution can also hit is **a different identifier that happens to share the old name**, in a codebase where the same value legitimately travels under one name through several parameters. Nothing warns about that. It is not a type error, not a lint error, and not a failing check — the code keeps running and quietly does something else.
- **Measured, on the near-miss #181 produced.** Renaming `poRecordId` → `packingListPORecordId` throughout `app/deliveries/new/actions.js` also caught `planDelivery`'s narrowing parameter, one call earlier, which takes the same PO id from the same source. On two orders for one material: with `poRecordId` the plan restricts to the named order and flags the excess (`poRecordIds: ["poB"]`, `over: 5`); with the other key it spreads across both orders and flags nothing (`["poA","poB"]`, `over: 0`). **Both return two rows**, so a row-count assertion would not have noticed, and the visible symptom would have been a PO number on a packing list that silently stopped restricting anything.
- **What actually catches it is reading the diff**, hunk by hunk, asking of each renamed identifier whether it is the one the field is named after. A second cheap guard where the renamed thing is pure: call the function both ways and compare, which is how the figures above were obtained.

**#181 ran that procedure on three fields at once and it held.** `Materials."Outstanding Qty"` → `Uninvoiced Qty` (a formula field, whose own expression Airtable rewrote), `Deliveries."PO"` → `Packing List PO` and `Delivery Items."Over Delivery"` → `Over Delivered`; then `Edit Log."Field Name"` → `Field` in a second commit. Nothing needed fixing on the Airtable side and every break was a string literal here.

### One rule, one implementation

The reason every entry above is a single module: two implementations of one judgement diverge, and catching the divergence then needs a third thing. Two cases have already cost that — the mirror-test family #147 deleted (hand-copies of production guards that passed with the guard removed) and #144's denylist/allowlist asymmetry, where the two sides of one decision guard in opposite directions, so a new status option would be refused by one and admitted by the other with no notice.

**So a duplication is not closed by "leave it as two for now."** If there is a real reason to keep two, that reason has to be a **measurable condition**, and the path to merging when it lifts has to be written down — not a preference, and not a vague intention.

**#18 is the worked example.** `PO Items."Invoiced Qty"` (an Airtable rollup) computes the same number as `getInvoicingStatusByPO`'s JS sum did. The blocking question was measurable: the callers read it immediately after linking an Invoice Item, so a rollup that lagged would silently under-count — and `createInvoiceAction` derives a line's Variance Flag from `invoicedQty > poItem.qty`, so an over-billed line would go unflagged (the header check does not catch it: over-shipped qty raises our calculated total and the vendor's stated total together, so they agree). Measured at 45 Invoice Items with zero stale reads: the rollup is correct on the first read after `create()` returns. This is narrower than `client.js`'s own note that computed fields can lag — what that note established was a *lookup filtered on via `filterByFormula`* being briefly invisible, a query-index effect, not reading a computed field off a `.find()`. `getInvoicedQtyForPOItem`, `getInvoicingStatusByPO` and `isPoOpen` all read the rollup, the subtraction is `lib/poItemQty.js`, and `client.js:sumQty` is gone. `scripts/tests/verify-materials-cache-18.mjs` re-measures the first-read property on every run rather than trusting this record of it.

## Data model (21 tables)

**Users**: User Name (primary), Email, Phone, Role (Employee/President), Is Admin, Status (Active/Inactive), Created At, Assigned Jobs (link -> Jobs, multiple, optional).

**Jobs**: Job Code (primary), Job Name, Business Unit, PIC/Manager (link -> Users) + Phone/Email (Lookups), Delivery/Alternate Address (link -> Addresses, single), Lines/Users (reverse-links).

**Lines**: child of Jobs. Line Label (primary, formula = {Job} - {Line Name}), Line Name (human-entered), Job (link, single).

**Vendors**: Vendor Name (primary), PIC Name/Phone/Email (plain text, external), Address (link, single), Purchase Orders (Lookup via PR chain).

**Purchase Requests**: PR ID (HYE-PR-YYMMDD-##), Requester/Vendor (links, single), Line (link, single), Job (Lookup via Line, read-only), Created At (datetime, UTC — timestamped per the *At convention; migrated from date-only Created Date in #105), Status (Draft/In Review/Approved/PO Signed/Withdrawn; PO Signed fires when President signs the generated PO), Withdrawn At (datetime, UTC, *At convention — stamped only when withdrawn, #122), Current Signer Step, Items Subtotal (rollup, PR Items only), Shipping Fee (optional currency; fixed once set, changeable only via Edit and continue), Total Amount (formula = Items Subtotal + Shipping Fee, blank = 0), Notes, Quotation Files (Lookup, plural).
- **Withdrawn (#122)** is the documented exception to the "no Rejected status" posture: it's the Requester's own *self-retraction* of a submitted PR (circumstances changed / submitted in error), NOT a signer's rejection — signers keep Return for correction. It's a state transition (not a delete — contrast Draft delete): the PR, signer chain, correction history, and Edit Log all stay on record. Requester-only, allowed **only from In Review** this pass, terminal (no revive — re-request = a new PR). The Status flip is the single lever needed (every actionable path is gated behind In Review); Pending signers / open Correction Requests / Current Signer Step are left untouched to preserve the audit trail, and the signer progress bar drops correction arcs off-In-Review so a withdrawn PR reads as ended. `getSubmittedPRs` returns Withdrawn PRs (they aren't Drafts) so they stay visible/filterable in the #119 list. PR withdrawal stays **In Review-only**, and there is no plan to extend it to Approved: once a PR is approved its PO exists, and "we're not ordering after all" is a decision about the *order*, so it's expressed as the PO's own terminal `Withdrawn` (#138, see Purchase Orders below) — an Approved PR really was approved and its signer chain records that. The PR-status check that was once wanted in `signPOAction` therefore no longer applies rather than being satisfied: the guard added in #138 checks **PO** status, and since a PR is never withdrawn past In Review, an Approved PR's PO can't be signed out from under a withdrawn PR.

**PR Signers** — dynamic ordered approval chain:
- Requester assigns an ordered signer list at creation, each tagged Confirmation Type (Approval/Agreement) — label only, same underlying action.
- Each turn: Approve/Agree, Edit and continue, or Return for correction (to any earlier signer/requester/self — pauses/resumes, never restarts; nested corrections are a LIFO stack, each resolve unwinds one level).
- Editing after signing does NOT invalidate approval.
- Fields: PR Signer ID, PR/Signer (link, single), Sequence Order, Status (Pending/Approved/Edited/Returned), Confirmation Type, Signed At, Notes (no input on plain Approve/Agree; Edit and continue/Return still collect it).
- PR detail page: linear progress bar (`lib/prSigning.js:getSignerChainProgress` + `app/prs/[prId]/SignerProgressBar.js`), current state only. Paused (passed through, pushed back by correction) shares neutral color with not-yet-reached, dashed border only. Correction Requests.Sent To stores only a user id (ambiguous if Requester = a Signer); progress bar defaults to signer interpretation — doesn't affect the actual state machine (uses Current Signer Step).

**PR Items**: PR Item ID, PR (link), Item Name, Size, Unit (single select, canonical list — see Units), Qty, Unit Price, Amount = live formula, Remark (free text only), Quotation (link, single -> Quotations — auto-linked when only one exists, dropdown once 2+, never silently reassigned).
- **`Item Name` and `Size` are normalized on save (#18)** — trimmed, internal whitespace runs collapsed, **case left exactly as typed** (`lib/itemNaming.js`). Applied in `prItems.js` create/update, i.e. the service layer, so the PR form and Edit and continue cannot drift apart on it. This is the origin of the whole chain — PO Items copy these values, Invoice Items copy those, Materials is keyed on them — so normalizing once here covers every table downstream. Case is deliberately untouched because this exact string is printed on the PO PDF the vendor receives, where `SCH 40 PVC` / `304SS` / `NPT` are correct as written and the stored value is the only copy; case-insensitivity is the *lookup's* job instead (`LOWER(TRIM(...))` in `getMaterialByKey`), which is reversible. **No stored match-key field**, deliberately: a second field is one more thing that can fall out of step with the write path meant to fill it. Rows created before #18 are not normalized, which is why `upsertMaterial` normalizes again on its way in.

**Correction Requests**: Correction Request ID, PR, Initiated By, Sent To, Notes, Requested At, Resolved At, Status (Pending/Resolved).

**Edit Log**: Edit Log ID, PR, Changed By, `Field` (select — exactly the seven labels the code can write: the six `ITEM_FIELD_LABELS` values plus `Shipping Fee`), Old Value, New Value, Changed At, Notes (optional). Append-only: no update function, and `editLog.js` deliberately has none.
- **`Field`, not `Field Name` (#181).** `X Name` on this base is a human-entered display name (`Item Name`, `Vendor Name`, `PIC Name`); this is one option from a closed list, and that family takes no `Name` (`Status`, `Role`, `Unit`, `PO Status`). Beside its own siblings it is also the better word — `Field` / `Old Value` / `New Value` is subject, before, after. `Edited Field` was rejected as a modifier doing no work, since `Changed By` and `Changed At` already say every row is an edit. The mapper key and the create parameter followed it to `field`, which also stops colliding with this repo's other `fieldName` — an Airtable field's name in the schema sense (`lib/airtableFormula.js`, `client.js:findByFieldValues`).
- **`Field` POINTS AT A COLUMN'S IDENTITY, NOT AT THE LABEL THAT HAPPENED TO BE IN USE — so a renamed field takes its log rows with it.** #78 renamed the PR Item field `Rate` → `Unit Price`; the three rows that still read `Rate` now read `Unit Price` and the `Rate` option is gone, so the option list is exactly the seven labels the code can write. Where a field is **deleted** and a different one takes over its job, old rows keep their old option instead: there is no identity left to follow.
  - **The test is objective — does the Airtable field id survive.** A rename preserves it, a delete-and-recreate breaks it, so the same fact that makes renaming safe at all (#167: the name is a rendering, the id is the storage) is what discriminates the two cases. This is not a judgment call about how much history to keep.
  - **Why update rather than preserve.** `Field` is a singleSelect, so it holds a *copy* of the label and a rename does not reach the copy. If the copy stands in for the identity, it has to be corrected whenever the identity survives — otherwise reading a row requires knowing the rename history, that knowledge lives in exactly one place, and the cost of carrying it accumulates for every later reader. **Nothing audited is lost:** `Old Value` and `New Value` are untouched, so the recorded fact stays as written and only the pointer moves.
  - **#181's first pass argued the opposite and was wrong, and the two mistakes are recorded so the conclusion is not flipped back.** It said "an append-only log keeps the vocabulary of its own time". First, it treated those three rows as evidence when they are dummy data. Second and worse, it read `Rate` → `Unit Price` as a **replacement** when it was a **rename**, which conflates *the label was different then* with *the subject was different then* — only the latter would justify keeping an old option. The rows were re-pointed and the option deleted by hand in the UI, because the Metadata API cannot write a select's option list at all (**measured on this field: a PATCH carrying `options.choices` returns 422 while a description-only PATCH returns 200**).
- **`typecast` is gone from `createEditLogEntry` (#181), and the two options it minted are why.** The comment defending it said auto-adding a missing choice "can't produce garbage choices" because the value is always one of a fixed set of constants. True of the names, false about the consequence: typecast gives every option it creates the same default color and nothing can recolor it, so `Unit Price` (minted when #78 landed) and `Shipping Fee` (when #69 did) sit at `blueLight2` while the original six walk a palette — visible in a schema dump and unfixable through the API. - **THE BLAST RADIUS OF THAT REFUSAL IS THE WHOLE TURN, not a log line, and it is worth knowing before adding a label.** Both call sites sit inside `editAndContinueAction`'s `try`, and its `catch` reverts every touched item, the Shipping Fee, the Quotations created that turn and the signer's own status, then returns *"Something went wrong saving your changes. Please try again."* — advice that would be wrong **forever** for this cause, since no retry can succeed until the choice exists in the Airtable UI. Two of those reverts are `.catch(() => {})`, so a failed revert is silent too.
- **Deliberately NOT made best-effort outside that rollback**, which is `lib/materialsCache.js`'s shape for stopping a derived artifact from undoing what produced it. The asymmetry is re-derivability: a materials cache rebuilds from `PO Items` and a PO PDF regenerates from its PO, but an Edit Log row records the **old value**, which stops existing the moment `updateItem` lands. Best-effort would apply a price change and lose the only record of what it changed — a hole in the evidence trail this table exists to be. **A refused turn beats an unlogged edit**, so the rollback stays and the fix is for the label set never to drift.
- **BOTH HALVES OF THE LABEL/CHOICE PAIR NOW EXIST, and `Unit` is the precedent for why one is not enough** — `offline/unit-options.mjs` proves the files agree, `verify-unit-options-18.mjs` proves the fields do, and a hand-added option passes the first while failing the second. **Purchase Orders**: strict 1:1 with PR. PO ID (HYE-PO-YYYYMMDD-## — 4-digit year, the one exception to the 2-digit convention), PR (link), Vendor (Lookup via PR), Quotation File (Lookup), Our PIC/Manager (links), Created Date, President Signed(+At), Status (Awaiting Signature/Signed/Withdrawn), Withdrawn At (datetime, UTC, *At convention — stamped in the same write as Status -> Withdrawn, #138), PO PDF File, Items Subtotal (rollup, PO Items only), Shipping Fee (plain currency, frozen copy from PR at PO-generation time), Total Amount (formula = Items Subtotal + Shipping Fee, blank = 0 — PO PDF's TOTAL line), Delivery Address Used (Primary/Alternate — internal only).

- **No `Sent to Vendor` status (#144)** — the one place that name still appears, kept as the record of the decision. The option existed on the Status field, but no code path ever wrote it and no PO record ever held it: the PO reaches the vendor by email, outside the app, so the value could only be set by hand in Airtable. It was removed rather than implemented. This does **not** mean cancelling an order that has already gone to the vendor is unreal — it just has no in-app path: the expected handling is a conversation with the vendor plus a manual Airtable correction, and what comes back is a credit memo or a corrected invoice, which makes it invoice-side work. Silence beats promising a process that doesn't exist. **Reopening condition:** if sending the PO to the vendor ever moves into the app, the status returns as a *byproduct* of that action rather than a step someone sets by hand — and withdrawal then has to be excluded from it again, deliberately. Note the asymmetry that would greet it, because the two sides guard in opposite directions. Withdrawal is an **allowlist**: `PO_WITHDRAWABLE_STATUSES = ["Awaiting Signature", "Signed"]`, so an unlisted status is refused. The invoice-side queries are a **denylist**: `{Status} != "${PO_WITHDRAWN_STATUS}"` — one shared fragment, `PO_NOT_WITHDRAWN`, read by `getPOsExceptWithdrawn` and `searchPOs` and inherited by `getOpenPOs` — so anything not named is admitted. A status option added to the field later is therefore refused by withdrawal *and* reaches the invoice picker with no code change and no notice. Recorded here, not fixed — whether that denylist should become an allowlist is its own decision.
  - **#168 narrowed that denylist from two statuses to one, and the reason was a false comment rather than a preference.** `getPOsExceptWithdrawn` — which carried a broader name before #168 renamed it — also excluded `Awaiting Signature`, justified in its own doc by "a PO that hasn't even been signed/sent to the vendor yet can't have a real vendor invoice against it". **The old name is deliberately not spelled here, because #168's second commit rebinds it to a different reader (every PO, no status filter) and a back-reference using it would read as a claim about that one.** **The base disproves it: `HYE-PO-20260805-02` is Awaiting Signature and carries an invoice**, and two ordinary paths produce that. Site staff order outside the app and the PR/PO follow as a record — the same fact #162 cites for not filtering delivery candidates on signature status, and why `Committed Qty` and `Signed Qty` are separate fields. And a corrective PO (#167) exists *because* material already arrived, so the excess invoice can precede it by construction. The exclusion was also never enforced anywhere but the picker query: `/api/invoices/detect-po` resolves by `getPOById` with no status filter, `InvoiceForm` deliberately appends a detected PO the picker's fetch missed, and `createInvoiceAction` checks only `Withdrawn`. So the same PO was unfindable by browsing and findable by uploading a PDF quoting its number. #133's Step 2, which asserted the exclusion, was a **rename guard** — it existed to catch a leftover `!= "Draft"` string — and #168 leaves no signature-status string for it to guard, so that step now asserts the new behavior instead.
  - **The gap #168 opened, deliberately and not fixed there:** an unsigned PO now appears in the invoice picker with **nothing marking it as unsigned**, so office staff can pick an order the President has not approved. Filed as its own Phase 3 issue.
- **Withdrawn (#138)** is the PO-side counterpart to PR Withdrawn: the requester decided not to order after all. Set by the **parent PR's Requester** (a PO carries no requester of its own, and needs none — nor an actor field on the withdrawal), confirmation modal, no reason capture, terminal (no revive). Eligibility is ONE shared predicate, `lib/poWithdraw.js:getPOWithdrawEligibility` — Status in {Awaiting Signature, Signed} AND no linked invoice (Invoice-PO Link join rows; the Invoice Items reverse-link is a safety net for a row stranded by a best-effort rollback). Status is tested first on purpose: a PO that fails the status test *and* has invoices must not be told to ask an Admin to unlink, since unlinking wouldn't make it withdrawable either. The two statuses are an allowlist, not an exclusion list — anything outside them is refused by default, including an option added to the field later without a matching code change. A linked invoice is evidence the order did go out, so the UI *explains* that an Admin has to unlink first rather than disabling the control. Modal copy (second person, to the actor) and page-banner copy (third person, to any viewer) sit as one pair in that same module and branch on the single condition `President Signed`. Terminal is enforced, not just labelled: `signPOAction` refuses a Withdrawn PO (without it, signing would write Status back to Signed and `syncPRStatusToPOSigned` would advance the PR), `regeneratePDFAction` refuses it — the PO PDF is the document sent to the vendor, so the line is "no new documents, existing document preserved": an already-generated PDF stays downloadable as audit trail — and `createInvoiceAction` refuses to link an invoice to one. A Withdrawn PO drops out of `getPOsExceptWithdrawn`/`searchPOs` (the invoice picker and /api/pos/search) and out of `/api/invoices/detect-po`'s candidates, where it is reported in its own `withdrawn` bucket instead: a vendor invoice quoting a withdrawn PO number means the vendor shipped anyway or the withdrawal was a mistake, which is the only place that contradiction surfaces, so it must never read as a failed detection. Partial closure of a partly invoiced PO is out of scope (there the order went out and was partly fulfilled — a different thing).

**PO Items**: frozen snapshot from PR Items at PO-generation — NOT live. PO Item ID, PO (link), Item Name, Size, Unit (single select, same list), Qty, Unit Price, Amount = static value, Remark, Invoice Items (reverse-link, multiple — partial invoicing is real). No free-text/user-facing Unit entry point; the snapshot fields are written only by lib/poGeneration.js.
- **The item axis (#18).** `Material` (link -> Materials, single) is the **one** field written after creation, by `setPOItemMaterial` from `lib/materialsCache.js` — deliberately narrow, and outside PO generation's rollback, so the frozen snapshot stays frozen and a cache failure cannot undo a PO. There is no general-purpose `updatePOItem`, on purpose.
- **Computed here, and this is where the which-POs-count rule lives:** `PO Status` (lookup via PO), `Invoiced Qty` (rollup = SUM of `Invoice Items.Qty` through the **PO Item** link, not through PO), `Committed Qty` (formula = `IF({PO Status} & "" = "Withdrawn", 0, {Qty})`) and `Signed Qty` (formula = `IF({PO Status} & "" = "Signed", {Qty}, 0)`). The rule sits in these two named fields rather than inside each Materials rollup's condition: a rollup condition is invisible in a schema dump, unreadable from code, and would have to be repeated per rollup. `Committed` minus `Signed` is the awaiting-signature quantity, so no third field is needed. The `& ""` coerces the `PO Status` lookup — an array — to text; **verified with real values across all three statuses (#18)**, since a silent coercion to `""` would have folded withdrawn quantity into the order book.
- **Rollup chain:** `Invoice Items.Qty` -> `PO Items.Invoiced Qty` -> `Materials.Invoiced Qty`; and `PO Items.Committed/Signed Qty` -> `Materials.Committed/Signed Qty`. Two levels, both measured as already settled on the first read after the write that feeds them.
- **`Delivered Qty` (#162)** — rollup, SUM of `Delivery Items.Qty` through the **`PO Item`** link (not through PO). Rolled up to the ordered line rather than to any invoice line because material often arrives before an invoice exists. Read under the same condition as `Invoiced Qty` and measured the same way: allocation subtracts it from `Qty` to decide what a line can still absorb, so a lagging value would over-allocate the NEXT arrival to a line already full — measured already correct on the first read after `create()` returned (`reads === 1`), and re-measured on every run of `verify-deliveries-162.mjs`. That script is also the only place the rollup's AGGREGATION FUNCTION is proved, since Airtable's Metadata API does not expose it: 4 + 5 = 9 distinguishes SUM from a COUNT of 2, and nothing in a schema dump can. No status condition, matching `Invoiced Qty`: allocation only selects lines whose `Committed Qty` is above zero, so a withdrawn PO's lines are never targets. **Deliberately NOT chained onto `Materials`** — #20 is Job-scoped and Materials' quantity rollups ignore Job. **#20 still reads `Delivery Items` directly, but for a different reason since #165.** The old one is gone: every row now names a line, so nothing is missing from the rollup. The new one is that this field now SUMS TWO DIFFERENT FACTS. An attached over-delivery row pushes it above the line's `Qty` — deliberately (see "Over-delivery is flagged") — so `Delivered Qty` alone cannot say how much arrived *against* the order versus *beyond* it. Only `Delivery Items` carries `Over Delivered` per row, and separating those two is exactly what a discrepancy screen is for. **#166 is the first reader to act on that**, and it reads the rows for exactly this reason: it reports "arrived against the order" and "arrived beyond it" as separate facts, which the rollup cannot decompose. It still reads `Invoiced Qty` from the rollup, because there the LINE's total across every invoice is precisely what is wanted (see "Delivery status").
- **This table has NO `PO Record ID` lookup, and the reason it is worth saying is that it used to (#19, deleted since).** The field was misconfigured: despite the name it was a lookup, through the `PO` link, of `Purchase Orders."Invoice Items"`, so it returned the PO's *invoice-item link array* rather than its record id — measured, a filter on it matched 0 of 4 expected rows and the raw value on a real line was two Invoice Item ids. It was the only one of the base's `* Record ID` lookups that was wrong; the rest resolve to a `_Record ID` RECORD_ID() formula and work. Nothing ever read it, so deleting it broke nothing, and **the standing instruction is unchanged: batch PO Items by `RECORD_ID()` via `findByRecordIds`.** The episode is kept because it is the cleanest example of the hazard the "Airtable side is outside CI" convention describes — a field that looked right from its name, was wrong in a way no file-only check could see, and sat there because nothing read it. That is also the argument against adding a lookup nobody reads: #162's two new tables need none, since every read reaches them through a reverse-link or the primary field.

**Quotations**: Quotation ID ({PR ID}-Q{seq}), Vendor Quotation Code (human-entered), Vendor/PR (links, single), File (attachment, required at creation in-app). At least one required per PR; can have more than one over its lifetime (dynamic list on PR form, or later via Edit and continue).
- **`File` is written in exactly one place: `createQuotation` (#142).** `updateQuotation` handles the code only and deliberately has no `file` parameter. The reason is measured: re-submitting an attachment url Airtable itself gave us returns success and silently empties the field once that url has expired, so every additional writer is another way to lose a file. Enforced by `scripts/tests/offline/source-shape.mjs` — one `File` property in that module, inside `createQuotation`, and none in `updateQuotation`.

**Invoices**: Invoice ID (HYE-INV-YYMMDD-##), Vendor Invoice Code (human-entered), Vendor (link), Issue/Due Date, Amount Due ("Vendor's Stated Total" — never auto-overwritten by the backend, unlike Items Subtotal/Calculated Total/Variance Flag; human edits allowed and recompute variance — #117), Shipping Fee, Tariff (optional, toggle-revealed), Items Subtotal (rollup), Calculated Total (formula = Items Subtotal + Shipping Fee + Tariff, blank = 0), Variance Flag (checkbox, backend-set), Paid(+Date), File (attachment, required).

**Invoice Items**: Invoice Item ID, Invoice + PO (links, single), PO Item (link, single), Item Name, Size, Unit (single select, same list), Qty, Unit Price, Amount = live formula, Variance Flag (checkbox, backend-set), Remark (shared, Unit Price/Qty discrepancies). Size/Unit are frozen copies from the linked PO Item, reference-only, no edit path (mismatch = wrong PO Item picked). Blank on a free-text line (no PO Item to copy from). Free-text "Other" option is currently hidden from the form UI (`SHOW_OTHER_ITEM_OPTION = false` in `app/invoices/new/InvoiceForm.js`, #96 — the backend path for a PO-Item-less line is untouched, so flipping the flag is the whole of re-exposing it).

**Materials**: **item identity** (#18). Natural key = Item Name + Size + Unit — **Vendor is deliberately NOT part of it.** `Unit` is the same 19-value single select as the three item tables (see Units). Writable: those three fields, and nothing else. Computed: `Material Label` (primary, formula = `Item Name` + `_Size` + `_Unit`, omitting blanks), `_Record ID`, the `Committed Qty` / `Signed Qty` / `Invoiced Qty` rollups and the `Uninvoiced Qty` formula. The `Material Prices` and `PO Items` links are both maintained from the far side. Not the price-history source itself — history is read from **PO Items** through the `PO Items` link (#19). USD only.
- **Why the split.** The three things Phase 4 serves have two different axes. Price is only meaningful per vendor — "what does this cost" has a different answer per supplier. Purchase history and on-order quantity are the opposite: they must aggregate *across* vendors, because "how much of this do we have on order" does not care who supplies it. One table cannot be keyed both ways, so identity + cross-vendor quantity live here and the per-vendor price lives in **Material Prices**.
- **`PO Items.Material` is what makes the item axis exist**, and the only alternative was matching on `Item Name` text — the approach `getInvoicingStatusByPO` cites "no name/similarity matching" as its own justification for avoiding. Its consequence: the quantity rollups traverse `Materials."PO Items"`, so **a PO line that is never linked contributes nothing** — invisible on the item axis while looking correct on the document axis. That is why `lib/materialsCache.js` links *every* line of a material, not just the one whose price won its dedupe.
- **Written in exactly two places (#18):** `upsertMaterial` (identity, find-or-create) and `upsertMaterialPrice` (price). Both go through `lib/materialsCache.js`, whose only caller is PO generation.
- **`Item Name` is not rewritten on a match — the first spelling recorded wins.** A name is not a latest-value field: rewriting it per PO would let one requester's capitalisation overwrite another's and change the row's label under anything referencing it. An item catalogue with a dropdown would become the authority; until then first-seen is at least stable. The lookup is case-insensitive precisely so the two need not agree.
- `Unit: ""` is not "no value" on a single select but a request to create an empty option, refused with `Insufficient permissions to create new select option ""` (measured), so the key is omitted instead, exactly as prItems.js/poItems.js do (#111). **`typecast` is deliberately not used on this path**: it would make that write succeed by inventing an option, which is how a canonical list silently gains a 20th value.
- `getMaterialByKey` interpolates the key into a `filterByFormula` string, so it escapes through `formulaString` — this company writes pipe sizes as `2"` / `4"`, and an unescaped quote closes the formula early (422 `INVALID_FILTER_BY_FORMULA`).
- **A unit-less item is skipped by the cache, not cached (#18).** Nothing is lost — the cache holds only latest values and the history is in PR Items — while a unit-less row would be unusable on #19's price screen, since a unit price without a unit compares to nothing. Reachable today only because a PR Item's `Unit` is not required at final submission; when it is, the branch becomes unreachable and the skip can be tightened into a throw. Deliberately not a throw today: a reachable throw there would fail a legitimate approval.

- **`Uninvoiced Qty` = Committed − Invoiced, and the name is the subtraction rather than a hope about it (#181).** It was `Outstanding Qty`, which named what someone wanted the figure to mean — ordered but not yet arrived — while the subtraction is the invoice one; and the same word was doing duty for a different subtraction on the delivery entry screen. **It remains an approximation of "ordered but not yet arrived", not a fact about it.** An invoice is a billing event, so goods can arrive before or after one. Packing lists would give the real arrival signal, and **when they exist this one formula is the single place that changes** — which is why the approximation is a formula over two rollups rather than a figure computed in JS at each reader. A negative value means more was invoiced than ordered and callers must surface it distinctly rather than folding it into "still uninvoiced", the same distinction `lib/poItemQty.js` makes per line.

### Material price screens (#19)

`/materials` (search, grouped by item with a row per vendor) and `/materials/[materialId]` (one item's full purchase history, newest first). Both are pages, not modals — this repo's modals are confirmation dialogs (`modalStyles.js`) and every reading surface is its own route.

- **It reads the item axis, not PR Items.** Comparison figures come from **Material Prices**, history from **PO Items**, both reached through #18's `Material` link — never by matching `Item Name` text. A PR Item is a *requested* price, and an unapproved PR's price is one nobody ever paid.
- **Any active user, no Job scoping** — what a material costs is not a per-Job secret, and site staff pricing a job need it as much as the office. **The exception is document identifiers:** PO ID, PR ID and Job are shown only to a viewer who passes `canViewPR` on the source PO's parent PR, the same gate `app/pos/[poId]` uses. Price, vendor, date, quantity and PO status are open. A refused row renders `—` and still shows its price.
  - Enforced in `lib/materialHistory.js`, which builds an `identifiers` object or `null` per row. The gated PO ID is stripped from the history row after sorting, so no ungated copy of an identifier leaves the module even as a sort key.
- **The gate costs no per-row query.** `canViewPR` is pure and takes an already-loaded user and PR, so the module fetches whole levels — Materials, Material Prices, POs, PO Items, PRs, Vendors, Jobs — keyed on ids gathered from the level above. **Measured, not argued:** 7 Airtable operations for a 1-material/2-row search and **the same 7** for a 2-material/3-row one; history is 5 selects + 1 find (the material itself) regardless of line count. `scripts/tests/verify-material-price-19.mjs` Part E re-measures it.
- **Search matching** uses #18's `normalizeItemText`, so the typed string and the stored name cannot disagree on case or spacing. Tokens are AND-ed as case-insensitive substrings of `Material Label` (`Item Name_Size_Unit`), so word order does not matter (`2" pipe` = `pipe 2"`) and each extra word narrows. A token can match the size or unit segment — a consequence of matching the label, accepted rather than fixed. Results are capped (25) and truncation is reported, because the follow-up batched queries fan out from these rows.
- **The date on a history row is the PO's `Created Date`.** A PO Item carries no date. `Created Date` is the moment the price was frozen onto the document, it is always present, and it is the same field `upsertMaterialPrice` stores as `Material Prices."Latest Date"` — so the comparison row and the history row cannot disagree about when a price happened. `President Signed At` was rejected because an Awaiting Signature PO has none, which would leave rows undated. It is calendar-only, so same-day rows tie; the tie-break is PO ID descending, monotonic within a day by construction.
- **Newest first, with the lowest price marked** rather than sorted to the top: a three-year-old price that happens to be lowest would otherwise take the most prominent row. The mark is a fact, not a recommendation — ties mark every tied row, and it is **omitted entirely when there is one vendor**, since "lowest of one" dresses a single data point as a comparison. When the rows' quantities differ the screen says the unit prices are not directly comparable and leaves the judgement to the reader.
- **Withdrawn and unsigned prices are shown with their status, not filtered.** `upsertMaterialPrice` writes at PO-generation time, so a vendor's newest price can come from an order later withdrawn — verified: a withdrawn PO's 41.00 is what the vendor's row carries. Whether a line counts toward the order book is #18's `Committed Qty`, read via `countsAsOrdered`, never re-derived from the status string; the status tag is the *label* and comes from `PO Status`. The two deliberately come from different fields, each from where the fact lives.
- **The status tag is shown only for `Awaiting Signature` and `Withdrawn`; silence means `Signed`.** Nearly every line is Signed, so tagging it puts noise on every row and buries the two states a reader actually has to account for. The rule is one pure function, `materialPriceView.js:statusTag`, shared by both screens.
- **The tag sits beside the VENDOR, not beside the PO ID it describes, and that is a measured layout decision.** In the Order column it wrapped: 168px of room against 214px needed for a PO ID plus a tag (and 228px on the history screen, where a Job code shares the cell) — visible only to a viewer who passes the identifier gate, since a refused row shows a short `—` instead. Reserving the width was the wrong fix because the majority of rows carry no tag at all. The Vendor column already had ~212px unused behind the longest vendor name, so the tag moved to where the slack was: nothing is reserved, and a tagged row is one line like every other (measured 29px throughout, with a full-length PO ID injected to reproduce the Admin view). The consequence "not counted as ordered" left the history rows for the same reason and is now stated once, as a footnote naming what the dimmed rows mean.
- **Every label therefore names its subject — `PO unsigned`, `PO withdrawn` — and that is the price of the move above, not decoration.** Beside a vendor name a bare `Withdrawn` reads as a fact about the VENDOR, i.e. a supplier we no longer buy from, which is a different and wrong claim. `Awaiting Signature` is not used verbatim because the label has to stay short enough that a long supplier name plus a tag still fits one line; the prefix costs ~18px, which is why the history screen's numeric columns were trimmed to give Vendor 272px against the 249px a 24-character name plus `PO withdrawn` needs. An **unrecognised** status renders as `PO: <status>` rather than being swallowed, so an option added to the Airtable field later shows up instead of vanishing — the failure mode #144 recorded for a denylist that admits whatever it does not name. The colon form is used there because an arbitrary option name cannot be relied on to read grammatically after a bare `PO`.
- **An empty query is a BROWSE, not an empty search.** The screen lists every indexed item under the search bar before anything is typed, so `searchMaterials` skips `filterByFormula` entirely rather than asking `andSearchAll` for a match-all — that builder's empty case is `FALSE()` on purpose, the right contract for a predicate but the wrong answer here. Browse order is alphabetical by `Material Label`, sorted **server-side** so the 25-row cap takes the first N of a stable order rather than an arbitrary N. Most-recently-priced would be more useful, but the dates live one level down in Material Prices, which is fetched *after* the cap, so ordering by them would mean capping on a figure that query cannot see.
- **That leaves two empties, and they must not read alike:** nothing matched what was typed, and nothing indexed at all. The second only renders while `Materials` is genuinely empty and explains that the list is built as new POs are generated — because "no results" here does **not** mean the item was never bought. PO lines created before #18 carry no `Material` link and were not backfilled, so an empty screen is the expected state on a base whose PO Items table is not empty.
- **The `Lowest` tag sits before the price, and that is an alignment fix rather than a preference.** With the tag *after* the price in a right-aligned cell it pushes the badged row's number left of its neighbours — measured at 596.05 against their 600.05, a visible 4px break in the column. Before the price, the tag grows leftwards into the column's slack and every row's number ends on the same edge (measured identical to 2dp across every group).
- **Both screens' tables are `table-fixed` with a declared `colgroup`, so no cell's content can decide a column's width.** The search page renders one table PER item group, and an auto-layout table sizes columns from its own rows, so three groups came out three different shapes. Declared widths make them identical across groups — measured `[352, 144, 64, 112, 160]` for all three, with every price and every quantity ending at the same x — and they also mean a status tag or a long vendor name cannot move a column. Widths were set from measured content rather than guessed: every column clears its widest realistic cell (a 24-character supplier name plus a tag, a full PO ID, a `$40,959.00`) by 11–103px, and `Unit price` is sized by its HEADER rather than its figures.
- **Column order differs between the two screens on purpose.** The search table runs `Vendor | Unit price | Qty | Date | Order`; the history table, like `app/prs/[prId]`, `app/pos/[poId]` and `app/invoices/[invoiceId]`, runs `Qty | Unit price | Amount`. Those three carry an **Amount** column, so qty-then-price reads as the equation `Qty × Unit Price = Amount` — the history table has Amount and follows them. The search table has no Amount and exists to compare prices, so the price leads and the quantity follows it as the caveat that qualifies it. Adjacency is the shared property; the order within it is decided by whether an Amount column is there to close the equation.
- **Both tables also carry `min-w-[52rem]`, and dropping it breaks them in a way that is easy to miss.** `w-full` alone lets the table shrink below the sum of its declared columns, and the one flexible column (Vendor) absorbs the shortfall — at 375px it collapsed to nothing and every vendor name wrapped, taking rows from 29px to 69px. The minimum keeps the desktop layout intact and hands the overflow to the `overflow-x-auto` wrapper each table already sits in, so the page body never scrolls sideways (measured at 375px). Consequence: below roughly a 900px viewport the table scrolls horizontally, since `max-w-4xl` minus `p-8` leaves exactly 832px.
- Reached from the home page; the app has no navigation shell, so one link there rather than inventing a nav bar.

**Material Prices**: item × vendor (#18). Natural key = Material + Vendor. `Price Label` (primary, formula over the two links), `Material` / `Vendor` (links, single), `Unit Price`, `Latest Date` (calendar), `Latest PO` (link), and `Material Record ID` / `Vendor Record ID` lookups. Those two lookups are what make a row findable at all — `filterByFormula` cannot compare a link field to a record id, the same exception already recorded for parent-link filtering. Still a latest-value cache, not history.

### Recording deliveries (#162)

`/deliveries` (list), `/deliveries/new` (entry), `/deliveries/[deliveryId]` (one arrival, with in-place edit and delete). Site staff record what arrived; **the app decides which order it belongs to** and there is no allocation-editing UI, so the only correction is to delete and re-enter.

- **The entry form is ONE page: a header that narrows, then a repeating list of items**, the same shape as the invoice form — not a job list you navigate through first, and not one item per delivery. A packing list normally names several items from one vendor on one day, so the ITEM ROWS repeat while the header (job, vendor, optional PO number, date, photo) does not, because those are properties of the arrival rather than of a line. Job → vendor → items, each narrowing the next. The single page is possible only because `getDeliveryCandidates` batches across jobs: the page hands the form every accessible job's lines in one read and the form filters client-side. Per-job fetching would have been ~6 queries each, over 200 for an Admin on 36 jobs, which is what forced the first version to navigate. Jobs offered are the viewer's `Assigned Jobs`, or all of them for President/Admin, narrowed through `accessibleJobs` so the dropdown cannot offer one `createDeliveryAction` would refuse. A single accessible job is preselected. Changing the job or the vendor resets the item rows, since each was narrowed by the old one.
- **An item already on one entry row is not offered on another** (`availableItemOptions`), the same rule as the invoice form's per-line PO Item dropdown (#91) and for the same reason: an item already on the delivery is not a second thing to add. The row's OWN selection is always kept, or the `<select>` would hold a value matching no option, render blank, and silently drop what was picked. `+ Add item` disables once every option is claimed rather than adding a row that cannot be filled. The rule is a pure function rather than inline JSX so the offline tier can pin it — what a control may offer is still a rule.
- **Two rows of ONE material would be summed, not planned twice**, and that path stays even though the dropdowns now prevent it. Allocation runs against a single snapshot of the candidate lines, so planning one material twice would let both plans claim the same undelivered quantity and double-allocate. The form is an affordance, not a guarantee — a Server Action is callable regardless of what the page rendered — so the action groups by material before planning. Different materials never compete for the same PO line, so they are planned independently.
- **Reading a delivery back collapses its rows to items, and that rule is one function** (`groupRowsByItem`), because the rows are two things at once — several items, and several order-slices per item. Keyed on `materialRecordId` when present and on the frozen name/size/unit otherwise, so a row with no `PO Item` still groups with its own item — a state #165 stopped producing but that the reading side still has to survive. In first-appearance order, which is `Delivery Item ID` order, which is the order the recorder listed them. An item is flagged when ANY of its slices is: the question a reader asks is "did more of this arrive than we ordered", not "which slice carried the excess".
- **The list summarizes as first item + a count** (`summarizeDelivery`): `Rebar D13 200 EA` then `+2` as its own chip, never appended to the label — read as text after the name, `+2` looks like a size or a grade on the item itself. It is a count rather than more names because a list row has one line and the useful thing there is "there is more here than you can see"; the detail page is where the rest belongs. The `Over-delivered` tag appears on the list too, from the same summary, so a reader does not have to open a delivery to find out. The detail page's headline uses the same function, so the row clicked and the page landed on cannot describe one delivery differently.
- **`ALLOCATION_COPY` was SWEPT BY #166 for one word per fact, and another issue reaching into this module is the point rather than an accident.** That issue put the same facts on the invoice screens; leaving them would have meant one fact called `arrived` here and `delivered` there, on a base whose table is `Deliveries` and whose rollup is `Delivered Qty` — a second name makes a reader ask what the difference is, and there is none. So: `arrived` → `delivered` throughout the banner and preview voices, and the list tag `over-delivery` → `Over-delivered`. `offline/delivery-status.mjs` fails on `arriv`, `recorded as` or the word `line` appearing in any #166 message, which is what keeps the vocabulary from drifting back.
- **#166 stopped at the repo boundary and #181 crossed it, which retires the carve-out this entry used to record.** #166 left the Airtable field named `Over Delivery` on the grounds that renaming it "breaks a lookup rather than fixing a word", by analogy with the US-English rule's exemption for values belonging outside this repo. That analogy was wrong and #167 measured why: a field's NAME is a rendering and its id is the storage, so a rename carries every formula, rollup, lookup and view filter with it and the only thing that can break is a string literal here — which is enumerable. The field is `Over Delivered` now. The US-English carve-out itself still stands, because it is about a value whose spelling another system owns (a select option, a package name), not about a field name we chose.
- **#181 also retired `outstanding` from this module.** It was one of two words for the invoice subtraction on `Materials` and this module was using it for the delivery one, so the same fact-per-word argument applied a second time: `undelivered` here, `uninvoiced` there. The copy builder `overNothingOutstanding` became `overFullyDelivered` (key `over-fully-delivered`) in the same pass, since its own message says "already delivered" and that is the better name for the branch anyway.
- **The banner names the item only when a delivery holds more than one.** With a single item the name is already the headline and repeating it is noise; with several, "3 EA arrived beyond what was ordered" does not say beyond what. One message per over-delivered ITEM rather than per flagged row, and it claims an order only when every flagged slice of that item names the same one.

- **THE ALLOCATION RULE, in `lib/deliveryAllocation.js:planDelivery`.** Candidates are that Job's PO lines for that vendor and that material, `countsAsOrdered`, with undelivered quantity left, narrowed to a supplied PO if the packing list named one. Filled **oldest order first** — PO `Created Date` asc, tie-broken by `PO ID` then `PO Item ID`, the same chain and the same reason as `sortHistoryRows` (Created Date is calendar-only). An undated line sorts LAST, since a data gap must not take priority in a FIFO queue.
- **Matched on #18's `Material` link, never on `Item Name` text.** The vendor wrote the packing list and we wrote the PO, so the strings do not agree — which is why the item comes from a dropdown rather than a text box, and why a PO line with no `Material` link is invisible to this feature. Pre-#18 lines were never backfilled, so that is the honest cause of the form's "item is not in the dropdown" message.
- **Signature status does not filter candidates**; withdrawal does. Site sometimes orders first and the PR/PO follow as a record, so an Awaiting Signature line must still receive its arrival. A withdrawn PO's line is excluded by reading #18's `Committed Qty` — the which-POs-count rule stays in that one named field, never re-derived from a status string, exactly as #19 reads it.
- **The dropdown is deliberately WIDER than the candidate set**: it lists every material the vendor supplied to this Job, including ones already fully delivered, showing `fully delivered` (`none outstanding` before #181). Narrowing to undelivered-only would make such an item VANISH, and the recorder would then land on the "not in the dropdown" message — which says it may never have been ordered here. That would be false, so the screen shows the item and says the true thing instead, then flags the entry as over-delivery.
- **Over-delivery is flagged, never refused**, and becomes its own row. **That row always NAMES a line (#165)**, and it attaches to the END OF THE FILL ORDER: the last line the arrival filled, or — when it filled nothing, because every order for the material is already complete — the last line in the same ordering, i.e. the most recent PO's.
  - **#162 left it unattached whenever the narrowed set held more than one line**, reasoning that no single order had been over-delivered and that a guess written into `Delivered Qty` would have #20 report it as fact. The cost of not attaching turned out to be the larger error: an unlinked row is in no line's `Delivered Qty`, so it is **invisible on the invoice axis**, and a delivery that arrived in full reads as less arrived than was billed — which points at withholding payment. Attaching is imprecise about *which* order absorbed the surplus; not attaching was wrong about *whether* the material arrived.
  - **The tail comes from `sortCandidates`, not a second comparator.** Both branches are positions in the one order allocation already fills in, so "most recent" is `sortCandidates(...).at(-1)` — one comparator, and the two branches read as one sentence. Consequence worth naming: that function sorts an **undated** line last so a data gap cannot take FIFO priority, so the tail picks such a line as "most recent". Coherent under the same reading — last to be filled, last to be blamed — and unreachable today (measured: 24 of 24 POs carry a `Created Date`).
  - **No longer depends on a PO holding at most one line per material.** `sortCandidates` is a total order, so both branches are defined whether a PO carries one line of a material or five — which is why #162's `narrowed.length === 1` test is *gone* rather than widened, and why this does not wait on #170. The sub-case #162 could only record at PO level (PO unambiguous, line ambiguous) now resolves to a line by fill order, so `Deliveries.PO` no longer carries that fact alone — it stays as the packing list's own reference, which is all it ever claimed to be.
  - **A supplied PO ID still hard-restricts**, unchanged: both branches draw only from the narrowed set, which is already filtered to that PO, so excess never spills onto another order.
  - **The invariant: a plan is either BLOCKED or every row it produces names a line.** There is exactly one way to have nothing to attach to — an empty narrowed set — and #162 wrote a row with no link and blank frozen name/size/unit for it. It is now refused with the reason (`lib/deliveryAllocation.js:BLOCKED`).
  - **Where `blocked` is reachable, because the first answer to this was wrong.** **Not from the entry form.** With a PO in use the form builds its item options from *that PO's own lines*, and both the PO checkbox and the PO input reset the item rows — so a recorder cannot hold a selection the typed PO does not carry, not even transiently. With no PO the options come from lines already filtered by vendor and `countsAsOrdered`, so every offered material has a candidate. The form refuses these combinations by never offering them, which is why it has **no blocked branch of its own**: an unreachable red message would imply a state the form can produce. It is reachable at **submit**, which is where the refusal lives: `createDeliveryAction` re-runs allocation from a fresh read, and a PO can be withdrawn while the form sits open, so `countsAsOrdered` drops its lines under a selection that was valid when it was made. A direct call on the Server Action is the other way in. The copy therefore belongs to the action, not to the preview, and `ALLOCATION_COPY.preview.blocked` says so.
- **A supplied PO ID is a hard restriction, not a preference.** Excess never spills onto another order, because the packing list names this one; the screen says so rather than leaving the recorder to wonder why a later order was not used.
- **Allocation is greedy at entry time and never re-runs.** So entering a backdated arrival after a newer one allocates it against whatever is still open — **order of entry decides, not order of arrival.** Accepted rather than solved: re-allocation would mean mutating existing rows, which the no-editing decision rules out. `withKeyLock` on `job::vendor::material` serializes in-process; the cross-invocation residual is the same class as #138's, and its failure mode is an over-delivery flag, which is a state the system already models.
- **The photo has TWO writers, and that is the one deliberate departure from #142's one-writer rule** — the photo is editable in place, unlike a Quotation's file. `createDelivery` writes it at creation; `replaceDeliveryPhoto` is the narrow second writer, in `setPOItemMaterial`'s shape, and **refuses any url that is not a fresh Vercel Blob upload** (`isOurBlobUrl`). That precondition is what makes #142's failure mode — re-submitting an url Airtable issued, which succeeds and silently empties the field — unreachable by construction rather than by discipline. `updateDelivery` has no `file` parameter and must not grow one. Enforced by `offline/source-shape.mjs`: exactly two writes, one in each function, `isOurBlobUrl` called in the replacer, none in `updateDelivery`.
- **Deletion is a real delete with no tombstone, following invoices rather than PRs and POs.** A withdrawn PR or PO keeps history worth preserving; a wrong delivery is a mistake with no history in it. Author plus Admin. `PO Items."Delivered Qty"` simply recomputes; **nothing on any Invoice record is touched**, so what was billed and whether it was paid are unchanged. The photo goes with the record and there is no second copy — #140 deleted the Blob object after ingest — which is why all three voices of `DELETE_COPY` say so. The three voices branch on whether the affected lines are invoiced and whether their invoice is paid, escalating lazily so an ordinary delivery pays only for the cheap question.
- **Authorization is per-record on two axes.** Job membership (or the office) for viewing, entry and in-place edits, via `lib/deliveryAccess.js`; authorship-or-Admin for deletion, inside `lib/deliveryDelete.js`. President/Admin are admitted to entry deliberately, one step beyond the issue's "anyone assigned to the Job": every other row-level rule admits them, and Admin can already delete. No role wrapper fits either axis, so all four Server Actions are `requireUser()` exemptions in the endpoint inventory, with the two axes named separately.
- **No per-row identifier gate, unlike #19's screens**, because the page gate subsumes it: allocation only picks lines from POs on this delivery's Job, and `canViewPR` clause 4 admits anyone assigned to a PR's Job. A second gate would re-derive the same answer and could drift from it.
- **Not in this issue:** nothing is written to any Invoice record and there is no `Invoices.Delivery` link; the discrepancy screen is #20; material never ordered on the Job, and consumption, are out of scope. `Materials.Uninvoiced Qty` (`Outstanding Qty` when #162 was written) is deliberately unchanged AS ARITHMETIC — its own description says packing lists will be the real arrival signal and that it is the one place to change, but what an arrival-based figure should mean is a reporting decision belonging to #20 with the screen that shows it. #181 renamed the field to the subtraction it performs, which does not settle that: it frees the word `outstanding` for #20 rather than spending it.

**Deliveries**: one recorded arrival (#162). `Delivery ID` (HYE-DL-YYMMDD-##), `Job` / `Vendor` (links, single), `Packing List PO` (link, single, optional), `Received Date` (calendar), `Recorded By` (link → Users, single), `Created At` (datetime, UTC), `Notes` (long text, optional), `Packing List File` (attachment, required at creation), `Delivery Items` (reverse-link).
- **`Job` is a direct link, not a lookup through PO**, because a delivery may name no PO at all — site orders first and the PR/PO follow as a record — and the Job is what scopes both authorization and the item dropdown, so it must be present unconditionally.
- **`Created At` was added because the ID counter needed a field nobody can backdate, and #164 then took that reader away** — the counter now counts the ID prefix and reads no date field at all (see "The daily counter counts the ID prefix"). The field stays, on its other two readers: the deliveries list's tie-break, and being the only timestamp on the record nobody typed — a packing list often carries no date at all, unlike a vendor invoice, so `Received Date` can be an unbacked guess. What #162's reasoning got right is unchanged and is why the rule generalized: `Received Date` is routinely earlier than entry (material arrives late afternoon, gets recorded next morning), so counting on it would have made the ID's date and the counted population different sets, which is exactly what `generateNextInvoiceId` was doing.
- **`Packing List PO` is the packing list's own reference, recorded even when allocation could attribute nothing to it.** Deliberately on the header and not on the lines: a line links a PO ITEM, because that is what carries quantity. The two are separate levels of attribution, and an over-delivery row claims only the level it can support. **Named `PO` until #181**, where a bare `PO` was found to read as the order the arrival was recorded against — the other level entirely.
- **`Recorded By` is load-bearing, not audit** — deletion is restricted to this user plus Admin, and deletion is the only way to correct an item or a quantity.
- Editable in place: `Received Date`, `Notes`, `Packing List File`. Nothing else. Item, quantity, vendor and the packing list PO are fixed, because changing them changes what the arrival was allocated against and there is no allocation-editing UI.

**Delivery Items**: one allocated slice of an arrival (#162). `Delivery Item ID` ({Delivery ID}-{seq}, 3 digits), `Delivery` (link, single), `PO Item` (link, single, **optional**), `Material` (link, single), `Item Name` / `Size` / `Unit` (frozen reference copies), `Qty`, `Over Delivered` (checkbox, backend-set).
- **Links to `PO Item`, never to an Invoice Item**, and the reason is that material often arrives with no invoice behind it yet — the ordered line is the only thing always there to compare an arrival against. Never matched on `Item Name` text; allocation matches on #18's `Material` link.
- **`Qty` is per row, and that is what makes the rollup correct.** A link field carries no quantity, so one row pointing at two PO lines would contribute its FULL Qty to both lines' `Delivered Qty` (a rollup counts the row once per linked parent) and double-count. Splitting 20 into 15 + 5 is structural, not cosmetic.
- **`PO Item` is never empty on a row this app writes (#165), and the field stays optional in the schema anyway.** Those are two different statements and both are deliberate. Allocation attaches every row, including the over-delivery one, and refuses to plan at all when it has no line to attach to — so `createDeliveryItem` is never called with a null link. The Airtable field is left optional because tightening it would be a schema change that buys nothing the code does not already guarantee, and because the reading side must still cope with a row whose link was removed by hand (`ALLOCATION_COPY.banner.overUnattached` renders that state rather than swallowing it). Measured at #165: 0 of the base's stored rows lack the link, so there was nothing to backfill.
- **`Item Name` / `Size` / `Unit` are never blank**, unlike Invoice Items': they come from the linked PO Item, or from the `Material` when there is no PO Item, and a Material is always linked and carries all three as its natural key.
- **`Overage PR` (link -> Purchase Requests, single) and `Former PO Item` (link -> PO Items, single) are #167's two fields**, both app-enforced as single-record: the Metadata API refuses `prefersSingleRecordLink` on field CREATE (measured 422 `INVALID_FIELD_TYPE_OPTIONS_FOR_CREATE`, another limit alongside its refusal to write a select's option list), and on field UPDATE (422 `INVALID_REQUEST_UNKNOWN`, both shapes tried), so the field is multi in Airtable and single in this app, exactly as `Invoice Items."PO Item"` already is — and the invariant is therefore checked on the stored ROWS rather than on a schema property nothing can set. Their symmetric sides are `Purchase Requests."Overage Delivery Items"` (the rows this request corrects) and `PO Items."Former Delivery Items"` (the rows that left this ordered item), and nothing writes either. **The two symmetric sides are deliberately NOT the same name**, which they were until the rename: one name for two meanings across two parents is worse than the accidental collisions #164 had to census, because it would be on purpose. The PO-side name went through `Reattached Delivery Items` first and that named THE WRONG END — the row is re-attached to the OVERAGE order's item and from this one it DEPARTED, so anyone opening the record read it backwards. `Former` says what the field it mirrors says, and beside `Delivery Items` it makes clear at a glance which of the two is the past. **`Overage PR` is the whole of "is a correction pending" — read from that PR's Status, never stored, which is what makes a withdrawal reopen the row.** **`Former PO Item` is PROVENANCE, not state:** the apply step re-points `PO Item` at the overage order, which destroys the only link back, and deriving the original through the shared Delivery breaks whenever the whole arrival was excess (#165's fully-delivered branch leaves that delivery with no other row for the material). Every reader takes `Former PO Item ?? PO Item` (`lib/overage.js:resolveOriginalPOItem`). **NAMED FOR WHAT IT STORES, WHICH IS ALWAYS A PAST VALUE** — empty on a row that never moved, the previous ordered item on one that did, and never a current one. It was briefly `Original PO Item`, chosen on the strength of that `?? PO Item` fallback, but the fallback is a property of the EXPRESSION rather than of the field: the field holds the past and the function collects an answer across both states. Named for what it holds rather than for the overage for a second reason too — a later re-attachment for some other cause belongs in the same field, and the cause is already next to it on `Overage PR`.
  - **THE FIELD AND THE FUNCTION MEAN DIFFERENT THINGS, and the premise that keeps them interchangeable is on the field's own description.** `Former PO Item` is the IMMEDIATELY PREVIOUS value; `resolveOriginalPOItem` is the FIRST. A row moved twice (A -> B -> C) would part them. Unreachable today: an overage PO Item's `Qty` equals the excess exactly, so no further excess can arise on it, and a `Delivery Items` row's `Qty` is fixed at creation, so the same row cannot become an over-delivery row a second time. If either changes, the field is the one that stays correct.
- **`Over Delivered` is its own row rather than a swollen last row** (the field was `Over Delivery` until #181 — a noun where a checkbox takes a participle; see "A checkbox takes a participle" under the naming rules), so the flagged quantity IS the excess with no arithmetic, and every unflagged row stays a within-order fact — the property #20 filters on.

### Delivery status (#166)

Whether what a vendor billed for was delivered, and what was delivered with no invoice behind it. **No new screen** — each fact goes where its own record lives, because a delivery with no invoice has no invoice row to sit on: the invoice list gains a column, the invoice detail a section, the deliveries list a column and two filters. `lib/deliveryStatus.js` judges; `lib/deliveryReconciliation.js` fetches.

- **ONE WORD PER FACT, and the sweep reached #162's module to keep it that way.** `delivered`, never `arrived` — the table is `Deliveries` and the rollup is `Delivered Qty`, so a second name for one fact only makes a reader ask what the difference is. `ordered item`, never `line` — a `Line` on this base is a child of a Job. And nothing is `recorded as` anything, since this app does not write `Recorded as paid` either. `ALLOCATION_COPY` was swept in the same pass (see "Recording deliveries" above); the Airtable field then still called `Over Delivery` was not, on the ground that it was outside this repo — **#181 crossed that boundary and it is `Over Delivered` now**, because #167 had measured that a field rename carries every formula, rollup, lookup and view filter with it and breaks nothing but a string literal here. `offline/delivery-status.mjs` fails on `arriv`, `recorded as` or the word `line` in any message here, so the vocabulary cannot drift back.
- **The join is computed, never stored.** There is no `Invoices.Delivery` link and deliberately none — whether to add one was left until this screen has been used. The one path that exists is `Invoice Items` → `PO Item` ← `Delivery Items`, so **the ordered item is where the judgment is made**, being the only thing both axes touch.
- **Two independent comparisons, not a list of cases:** delivered against invoiced, then each side against ordered. Every combination falls out of those two, including ones nobody enumerated, which is why the module returns figures plus a key rather than a hand-written case per screen.
- **Comparison 1 uses TOTAL delivered**, within-order plus beyond. "Did the billed material arrive" asks about delivery, not about whether the order covered it: 12 delivered against an order of 10 answers a bill for 12 in full, and using the within-order figure alone would report 2 as undelivered while it stands in the warehouse.
- **Comparison 2 is realized as two NAMED facts**, not as `max(delivered, invoiced) > ordered`. That form is true of both cases and distinguishes neither, and #162's `Over Delivered` flag already gives the delivery side exactly.

- **A LIST CELL IS A CHIP, NOT A SENTENCE, and that is what the density axis actually means.** `column` is a closed set of values a reader learns once and then recognizes — the way an Airtable single select reads — while `detail` is sentences with figures. The first version had short sentences and fractions in the column, which breaks the metaphor twice: a fraction changes per row so the set stops being closed, and saying WHAT it counts costs words a one-line cell does not have (`1 of 2 lines arrived` had to name a unit it could not use). So the count decides which chip it is and stays behind; the figures live on the detail. `offline/delivery-status.mjs` asserts that **no chip contains a digit**.
  - Invoice axis: `Delivered` / `Partly delivered` / `Awaiting delivery`, and `—` when every line is free text.
  - Delivery axis: `Invoiced` / `Partly invoiced` / `Awaiting invoice`, and `—` likewise.
  - `Partly`, not `Partially`, on both. The two sets share one tone vocabulary (complete / partial / none) in `app/components/DeliveryStatusMarks.js`, so a reader crossing between the lists recognizes the shape. **`—` is deliberately not a chip:** "we did not measure" is the absence of a value, not a fourth one.
- **THE INFERRED QUALIFIER IS A MARKER, NOT A CHIP** — a small `!` in a circle beside the chip. It is not another value of the closed set: it composes with any of the three and as a chip it would double them. **`title` alone would be the whole affordance on a mouse and nothing anywhere else**, since a tooltip opens on neither touch nor a keyboard, so the same sentence is also the `aria-label` and therefore the accessible name. The full explanation is an ordinary line of text on the invoice detail, which is the reading nobody has to discover. One sentence, two punctuations (`Inferred: …` for the marker, `Inferred — …` for the line), asserted equal offline so the two cannot come to give different reasons.
- **Facts, never verdicts.** At any one moment "the vendor over-billed" and "the rest has not been delivered yet" are the SAME measurement, so the copy says `more billed than delivered` and the reverse direction gets the same treatment. `offline/delivery-status.mjs` asserts that no message anywhere contains "over-billed", "short-shipped" or "missing". Deciding which it is belongs to a person; correcting it is #167.
- **THE ANSWER IS ATTRIBUTED TO ONE INVOICE, and the load-bearing rule is where computation ends and inference begins** (`allocateLineToInvoices`). Refusing to attribute leaves the invoice axis unable to answer "may this be paid", which is the question it exists for — the same call #165 made one level down when it stopped declining to attach an over-delivery row.
  - **Most of the time nothing is inferred.** Three shapes are order-independent and are computed outright: ONE bill on the ordered item (its delivered-against-billed *is* that invoice's answer — the common case), the delivery covering EVERY bill (all satisfied whatever the order), and NOTHING delivered (none satisfied).
  - **Inference is needed in exactly one shape:** two or more bills on the ordered item AND a delivered quantity covering some but not all of them. Then it is filled **oldest bill first** — `Issue Date` ascending, tie-broken by `Invoice ID` — because that is the order the bills were raised in. `Issue Date` is human-entered and backdatable, the property #164 learned the hard way; tolerable here because the consequence is a coin-flip landing the other way on a cell already marked, not a corrupted record. An undated bill sorts LAST, the same call `sortCandidates` makes.
  - **THE CONTAINMENT PREMISE IS A STATEMENT ABOUT PRACTICE, NOT A MEASURED FACT** (`CONTAINMENT_PREMISE`): one invoice is contained entirely within one delivery — a vendor does not bill for half a shipment. **Nothing in the data enforces it** — there is no delivery-to-invoice link, no field records the pairing, no write path checks it. What it buys is that 80 billed across two bills with 40 delivered satisfies ONE of them completely rather than half of each, which is what makes "this one has not been delivered" a one-in-two chance of naming the right invoice rather than a middle value in the data nowhere. If it breaks the inference does not degrade into "roughly right": it becomes wrong in a different way, handing a whole invoice a coverage that belongs to part of two.
  - One uncertain line makes the invoice's answer uncertain — it does not average out across lines.
- **THE INVOICE'S VERDICT HAS FOUR OUTCOMES, AND TWO WERE DELETED RATHER THAN DOCUMENTED.** A share's delivered quantity is CLAMPED at what its own bill billed, so `delivered > invoiced` cannot occur at invoice scope: `arrived-more` had no reader on the invoice path at all, and `nothing-invoiced` collapsed into "nothing delivered" for the same reason. This repo has been burned repeatedly by things with no caller — `upsertMaterial` carried three defects from Phase 0 to #18 — so an unreachable state is removed, not left standing with a comment. What `arrived-more` used to say is now said **on the order's own terms** (delivered > ordered) by the `Against the order:` line, which gives one fact one reader. The four: `All billed material delivered` / `N EA more billed than delivered` / `Nothing delivered yet` / `Not compared — no ordered item`.
- **An invoice summarizes by LINE COUNT, not by quantity**, and that is forced rather than chosen: its lines carry different Units, so adding their quantities produces a number of nothing. The count no longer reaches the screen — it decides the chip — but it is still what the chip is decided by.
- **"No line complete" and "nothing delivered" are different claims, and the chip keeps them apart.** `awaiting-delivery` is reserved for no quantity having been delivered at all; an incomplete line is `Partly delivered`. The first version keyed that on the completed-line count alone, so a one-line invoice billing 13 with 10 delivered read as nothing delivered. **Caught by reading seeded demo data rather than by a check**, which is why the seed exists and why `summarizeInvoiceStatus` carries `anyArrived`.
- **An invoice line with no `PO Item` is excluded from the judgment — and it is NOT a freight rule**, though that is the obvious misreading. A vendor's freight arrives on `Invoices."Shipping Fee"`, a header field; item rows are for material only. The app creates no `PO Item`-less item row at all, since the free-text "Other" option is hidden (`SHOW_OTHER_ITEM_OPTION = false`, #96), so a conforming invoice has none — the **2 of 7 on this base today are hand-entered dummy data**, which CLAUDE.md already records for `HYE-INV-260727-04`. The rule is still needed because #96 hid the UI option and left the backend path intact, so flipping that flag is the whole of re-exposing it. Excluding is right regardless of provenance: such a line names no ordered quantity, so counting it would make the invoice read as short through comparing something to nothing. **It is excluded from the JUDGMENT, not from the screen:** it gets its own box saying `Not compared — no ordered item`, where the line is, rather than a parenthetical about a line the reader cannot see.
- **`invoicedQty` comes from the `Invoiced Qty` rollup — the ordered item's total across every invoice — and never from summing the invoice in hand.** A PO line can carry two invoices; summing only one would report material as unbilled when it is billed twice over. `verify-delivery-status-166.mjs` Part D creates exactly that case: 16 billed on the line, 6 on the invoice being read, 10 delivered.
- **The delivered side reads `Delivery Items`, not the rollup**, because `Delivered Qty` sums within-order and beyond-order into one number and only the rows carry `Over Delivered`. This is the reader that made that distinction load-bearing rather than theoretical.
- **The query budget is 5 operations on the invoice axis and 3 on the delivery axis, measured, and never grows with row count.** Two of the five exist because the answer is attributed: deciding whether THIS bill was covered means reading every OTHER bill on the same ordered item and its `Issue Date`, which the caller never asked about. Refusing to attribute cost 3 and could not answer the question — `verify-delivery-status-166.mjs` Part E counts them with the same `_selectRecords` / `_findRecordById` instrument `verify-material-price-19.mjs` Part E uses, comparing one row against several (measured 5 for one invoice against 4 for three). The invoice detail is 5 too, adding the Deliveries themselves for their dates. **These are CEILINGS rather than fixed numbers:** an empty level costs no query at all, since `findByRecordIds` returns early on an empty id list — a delivery whose line has no invoice measures 2, and passing every invoice at once measures 4 because the sibling level is then already in hand. So the property to assert is "never more", not "exactly equal", and the two measurements have to be shape-matched. Recorded because the first version of the check read both asymmetries as per-row growth.
- **The invoicing column and the `unbilled` filter are President-or-Admin only, WITHHELD ON THE SERVER.** The deliveries list is Job-scoped, so site staff reach it, and whether a vendor has billed for a delivery is office information — a yes/no column still leaks *who has been billed*, so the column is gated rather than its wording softened. Gating in JSX would leave the data in the page payload, which is hiding rather than withholding, so `getDeliveryInvoicing` is **not called at all** for a non-privileged viewer and the two levels are never fetched. Same decision as `/pos/[poId]` filtering invoice-derived fields out on the server (#132). The pleasant side effect is that the extra operations are only paid for by the audience that may see them.
  - **`?unbilled=1` is treated as ABSENT for such a viewer, and that is a NAMED RULE rather than an `&&` at each of the two places that ask** (`resolveDeliveryFilters`, pinned offline). The server's initial props and the client's own state both call it, so they cannot come to disagree, and a filter over a column that was never fetched cannot silently empty the list. The over-delivery filter is deliberately not gated: that fact belongs to the delivery, which the viewer may already see.

- **THE INVOICE DETAIL IS ONE BOX PER INVOICE LINE, in the items table's own order**, with at most six lines inside it: the item, `Ordered · Billed · Delivered`, `This bill:`, the verdict, `Against the order:`, the inferred sentence, and the deliveries.
  - **The section heading carries the SAME CHIP the list showed, from the same function**, so the row a reader clicked and the page they land on cannot describe the invoice differently — #162's `summarizeDelivery` is shared between its list and its detail for exactly this reason.
  - **All three figures are the ORDERED ITEM's totals, including `Billed`**, which is every bill on it rather than this one. That is what makes them comparable with each other and with the deliveries listed under them. Usually this invoice IS the only bill, so `Billed` is also this invoice's figure.
  - **`This bill: 5 of 13` appears on EXACTLY the condition the inferred marker does**, and that identity is the point rather than a coincidence: the share line explains why the answer had to be inferred, so one without the other would either raise a question it does not answer or answer one nobody asked. Note this is NARROWER than "the ordered item carries more than one bill" — two bills whose material all arrived need no inference, so neither line appears. Asserted as an equality in `offline/delivery-status.mjs` over every input shape.
  - **COLOR ON THE VERDICT LINE ONLY.** `Against the order:` is a fact about the ORDER rather than about this bill, and the inferred sentence is a qualifier; with all three amber, as the first version had them, the color distinguished nothing. `describeInvoiceLine` returns **named slots** (`verdict` / `againstOrder` / `inferred`) rather than a list, so which one is colored is beyond a call site's reach.
  - **`Against the order:` is ONE line even when both sides exceed the order** — `3 EA more billed, 2 EA more delivered` — because it is one comparison with two terms, not two problems. The billed side comes first, being the side this screen is about.
  - **The deliveries sit INSIDE the box, labelled just `Deliveries ·`.** A box is scoped to one ordered item, so listing them there is exactly the claim the data supports; the foot-of-page section they used to live in needed the heading "recorded against the same order lines" to avoid over-claiming, and inside the box that qualification is structural. What is still not claimed: WHICH delivery brought the quantity attributed to this bill. The quantity is attributed; the delivery is not.
- **`/invoices` CARRIES THE STATUS CHIP AND NOTHING ELSE — both exception tags left that screen, for different reasons.** `beyond order` (billed > ordered) is already on the same page as the `⚠ Variance` badge in the items table, which `Invoice Items.Variance Flag` drives: one fact rendered twice on one screen. `over-delivery` (delivered > ordered) is not a fact about the invoice at all but about the ordered item, and inside a column headed `Delivery` it reads as "more arrived than this bill covers" — a different and wrong claim. Both facts are on the detail, under the ordered item they belong to. **`/deliveries` KEEPS its `Over-delivered` tag**, and the difference is whose fact it is: an over-delivery is a fact about that delivery, so it sits on the delivery's own row without changing frame.
- **The two filters follow the PR list's pattern (#119)**: the server sends rows it has already computed, a Client Component narrows them instantly with no Apply button, and the active filters are mirrored into the URL with `router.replace` — no navigation, no history entry, no server round trip — so refresh, a shared link and the back button all restore the view. They are `Not fully invoiced · oldest first` (`?unbilled=1`) and `Over-delivered` (`?over=1`); neither name says "only", because a filter is a toggle and the word is implied.
- **`Not fully invoiced` TAKES BOTH INCOMPLETE STATES, not just the empty one** (`isNotFullyInvoiced`). A delivery carrying two materials where only one has been billed is exactly "it is here and there is no invoice for it" — the thing the month-end email to every vendor stands in for — and filtering on `awaiting-invoice` alone dropped it. Verified on the seed: widening takes the worklist from 7 rows to 8, and the row it adds is that two-material delivery.
- **"Oldest first" is a property of that filter, not a separate sort control.** That list is the vendor-chasing worklist replacing the month-end email, so the longest-waiting delivery belongs at the top while the default list stays newest-first. `Received Date` ASCENDING, because the wait starts when the material arrived rather than when someone typed it in; it is human-entered and backdatable, which #164 learned the hard way when an ID counter read such a field, and the consequence here is milder — a mistyped date sits at the top of a worklist — but it is the same property. `Created At` DESCENDING as the tie-break, matching the default list's direction exactly, so only the primary key flips between the two orderings and the tie-break carries no meaning of its own. An undated delivery sorts LAST, the same call `sortCandidates` makes.
- **BOTH LIST TABLES ARE `table-fixed` WITH A DECLARED `colgroup` SUMMING TO EXACTLY 52rem**, which is what a `max-w-4xl` page minus `p-8` has (832px). A column is never appended; the budget is re-cut. Measured against each base's widest real cells, with every row one line, no wrap and no horizontal scrollbar.
  - `/deliveries` (6 columns): `8.5 + 8 + 5.5 + 17.5 + 6.75 + 5.75`. The chip is far narrower than the sentence it replaced, so **Invoiced gave room back to Delivered** — the column that needed it and the only one that was wrapping, since it carries an item label, a `+N` count and an `Over-delivered` tag on one line (measured 270px for `165-DEMO Elbow 3" 3 PCS` beside the tag).
  - `/invoices` (7 columns) got a `colgroup` it never had: an auto-layout table sized the Delivery column from the longest phrase in it, so every other column moved when one invoice's status changed. **This table has almost no slack — seven columns need 832px against 832px.** Six of the seven are bounded by construction and cannot grow: an Invoice ID is a fixed format (128px), a date is ten characters (80px), the Delivery column is a closed set plus a marker (120px), `Amount Due` is bound by its own header (78px), and Status by `Paid 2026-07-27` beside a `⚠ Variance` badge (176px — which is why **the last column drops its right padding**, there being nothing to its right to separate it from). So **Vendor is where the slack isn't**: 8rem holds this base's longest name at 16 characters with nothing to spare, and it is also the column where wrapping would be least harmful if a longer supplier is ever added. The worst case was verified by injecting it into a rendered row, the way #19 injected a full-length PO ID.
- **Not in this issue:** nothing is written anywhere, no `Invoices.Delivery` link, no new screen, and no correction of an overage — that is #167. The existing invoice visibility rules are unchanged: the invoice list and detail stay President-or-Admin, editing stays Admin, deliveries stay Job-scoped.

### Overage corrections (#167)

More arrived than was ordered, the vendor billed for it, and the record has to be squared with the money: a corrective PR and PO for the difference, after which the excess lives on its own ordered item. `lib/overage.js` judges, `lib/overagePR.js` reads and writes, `lib/invoiceItemFold.js` puts the invoice's items table back together.

- **THE EXCESS NEEDS NO ARITHMETIC, and that is #162's decision paying off.** An over-delivery is its own `Delivery Items` row whose `Qty` IS the excess, so nothing here subtracts ordered from delivered. Every figure the correction carries comes from a record rather than a calculation: quantity from the row, unit price and vendor code from the invoice line, Job/Line/Vendor from the order the excess was attached to, the chain from that order's PR.
- **A REAL DRAFT RECORD, not a prefilled `/prs/new`.** The quotation is the vendor's invoice, which means fetching Airtable's copy of the file server-side and writing a FRESH Blob object for Airtable to ingest — handing the form an Airtable attachment url to re-submit is exactly the silent data loss #142 measured. Creating the record also gives `Delivery Items."Overage PR"` something to point at immediately, which is what makes the row read as pending from the moment the button is used. The redirect goes to `/prs/new?draft=<prId>`, the existing #72 resume path, and `loadPRDraft` hydrates the signer chain — which is what makes the inactive-signer decision below possible at all.
- **JOB-SCOPED, NOT OFFICE-GATED, AND THAT NARROWS #166 ON PURPOSE.** Raising the request is site work, per the issue. But the affordance reveals that the over-delivered ordered item is billed, by which invoice, and at what unit price — and #166, one issue earlier, withheld exactly "whether a vendor has billed" from site staff on the deliveries LIST. That column stays withheld and is still not fetched for anyone else; this is a deliberate exception on the DETAIL, because none of those three facts can be hidden from someone raising a request quoted from the invoice (the vendor's invoice code lands on the Quotation they then edit). Recorded as a reversal rather than left as a contradiction between two comments. `getPOItemsForReconciliation`'s own doc comment says so too, since #166 marked it President-or-Admin only.
- **WHICH BILL CARRIES THE EXCESS IS #166'S AMBIGUITY, SO IT IS #166'S ORDERING** — `sortInvoicesOldestFirst`, imported rather than restated, and `offline/overage.mjs` asserts on the AST that `lib/overage.js` imports it and sorts nothing by `Issue Date` itself. The premise sentence is shared too (`INFERRED_PREMISE`, exported from `lib/deliveryStatus.js` for this), so the two `!` markers cannot come to explain themselves differently.
  - **What is NOT reused is `allocateLineToInvoices`'s `determinate` flag**, and the reason is that it answers a different question. There, determinacy means the outcome does not depend on the order the bills are taken in — so a delivery covering EVERY bill is determinate. Here the question is which bill's LINE the excess quantity sits in, and full coverage leaves that wide open. **Two bills on the ordered item is the whole condition.** The visible consequence: two bills whose material all arrived show no marker on the invoice screens and still mark the overage attribution as inferred. Those are different claims, not an inconsistency.
- **AN EXCESS SPANNING TWO INVOICES IS OUT OF SCOPE, and the reason is the quotation rather than the arithmetic:** two invoices means two files and a PR takes one. Under oldest-first that condition is exactly "the oldest bill's line is smaller than the excess", so it falls out of the ordering rather than needing a rule of its own — and a LATER bill large enough to absorb it does not rescue the case, because picking it would be a second answer to #166's ambiguity. The button is hidden and says why.
- **GENERATING THE PO SETTLES IT, and the apply step sits OUTSIDE PO generation's rollback**, in `lib/materialsCache.js`'s position and after it (it matches the overage row to a line of the new PO on #18's `Material` link, which the cache is what writes). Outside for #165's reason: a derived artifact must not undo the approval that produced it, and this one touches an invoice that may already be paid.
  - **So a failure leaves an ASYMMETRY, and it has to be visible with no email available.** Two signals, covering different halves. Re-attach failed → nothing moved, and the ONLY signal is the banner reading `not-applied`, because the row still points at an ordered item that IS invoiced so #166's worklist cannot see it. Split failed → the row moved, so the overage ordered item has a delivery and no invoice, which puts the delivery in `Not fully invoiced` as well. **Re-attach therefore runs FIRST**: the reachable middle state is the one two things notice rather than one.
  - **Idempotent, because there is no retry UI.** A row whose flag is already clear is skipped. `applied` is judged from the flag alone, which is trustworthy because `reattachDeliveryItemToPOItem` writes the attachment, the provenance and the flag in ONE `update()` — Airtable applies one record write atomically, so the three cannot half-happen.
- **THE INVOICE HEADER DOES NOT MOVE.** The two sides of the split sum to what the line summed to, so `Items Subtotal`, `Calculated Total`, `Amount Due` and `Paid` are all untouched and only the attribution shifts. **That is what makes splitting an ALREADY PAID invoice safe, which is the common case rather than an edge one** — the bill usually arrives and is settled before anyone corrects the record. `verify-overage-167.mjs` Part C runs the whole flow on a paid invoice for exactly that reason.
  - **A bill whose WHOLE line is the excess is re-pointed rather than split**, or it would be left at qty 0. `updateInvoiceItem` gained a `poRecordId` parameter for it: both links have to move together, or the line would name a `PO Item` belonging to a different PO.
  - **Variance is RECOMPUTED with `checkUnitPriceVariance` and `getInvoicedQtyForPOItem`**, the two functions `createInvoiceAction` uses, rather than assumed to have cleared. The split is exactly the event that resolves a qty variance on the original line, and asserting that without measuring it would be a second implementation of the rule.
  - **An `Invoice-PO Link` row is created for the overage PO.** Without it the order looks invoice-free, which would let #138 withdraw it and take the excess with it.
- **THE ITEMS TABLE FOLDS THE SPLIT BACK INTO ONE ROW, keyed on `Material` + unit price** (`lib/invoiceItemFold.js`, the invoice counterpart of `groupRowsByItem`). `Material` is what makes two rows the same item without matching `Item Name` text; the unit price is what keeps a vendor's two genuinely different prices for one material apart, since a split cannot change the price. **A row with no `Material` is never folded** and is its own group keyed on its record id — not a fallback to name matching: a split can only produce rows carrying the link, so a row without one cannot be half of one.
- **THE PO COLUMN LEFT THE ITEMS TABLE IN THE SAME COMMIT that put the order into the delivery section's boxes, and the pairing is not optional.** A folded row spans two orders, so that cell has no single value — unrepresentable rather than merely inconvenient. But removing the column alone would take "which item belongs to which order" off the page entirely, so the order moved to where it is exactly one: a box is scoped to ONE ordered item, and a split shows as two boxes each naming its own. This edits the section #166 built.
- **THE BANNER IS DERIVED FROM LINKS, on all three documents, and it outlives signature.** An overage order read on its own looks like a duplicate with no quotation of its own; worse, the invoice attached to it also bills the original order, so a payment against that invoice matches neither order's total alone. Whoever reconciles it needs telling, exactly once, there.
  - Three sites — the corrective PR (its own reverse-link), the corrective PO (one hop through its `PR`), and the ORIGINAL PO (its own ordered items' provenance reverse-link). Three states — `pending`, `applied`, `not-applied` — appended as shared entries rather than multiplied, so three × three stays 3 + 3.
  - **The caveat belongs to `applied` only.** While pending the invoice bills one order, so claiming it spans two would be false.
  - **The original PO's banner names the DELIVERY rather than claiming that order was over-delivered.** One delivery can fill two orders of the same material and #165 attaches the excess to the last one filled, so the banner is reachable from an order that was not itself exceeded — but the provenance reverse-link means only the order the excess actually came from renders it, which is what made that walk unnecessary.
- **THE INACTIVE SIGNER IS LEFT OUT, and the preview says how many.** A chain that reaches a departed signer STOPS and nothing in the app can unstick it — the turn belongs to a user who cannot log in. Arriving one signer short and saying so is better; the Draft is editable, and `createPRAction` already refuses an empty chain in its own words.
- **KNOWN GAP, recorded rather than fixed: a withdrawn overage PO.** `PO Items."Committed Qty"` is `IF({PO Status} = "Withdrawn", 0, {Qty})` but `Delivered Qty` has no status condition, so withdrawing an overage PO would drop the excess out of the order book while leaving it in the delivered figure — the excess disappears quietly. **The reachable half is handled:** `overagePRState` reads the overage PO's status one hop further and returns `none` for a withdrawn one, so a `not-applied` row reopens rather than being locked out forever by a correction that no longer exists. **The unreachable half is the gap:** an APPLIED overage carries an invoice line, and #138 refuses to withdraw a PO that has one, so today it cannot happen. If that ever changes, the fix is a status condition on `Delivered Qty` or a check in `withdrawPOAction`.
- **Not in this issue:** an excess spanning two invoices (no single quotation), any change to the invoice header, and #20. Nothing about a correction is stored as state — `Former PO Item` is provenance, not state, and every "is one pending" answer is read from the linked PR's Status.

### Purchase order list (#168)

`/pos`. Before it, a PO was reachable only through the PR that generated it, and `/api/pos/search` is Admin-only. Delivery status is **not** here — that is #169, which needed this page first.

- **`getAllPOs()` MEANS "EVERY PO, NO STATUS FILTER", AND THE NAME WAS REBOUND TO SAY SO.** Until #168's first commit it meant "every PO except Awaiting Signature and Withdrawn"; that reader is now `getPOsExceptWithdrawn`, with a filter narrowed to one status. The rename measured the old name at **zero occurrences** across the repo before this one reused it, so the two meanings never coexisted in a single tree — that measurement lives only in the renaming commit's message, since this commit re-creates the name.
- **HAVING NO FILTER IS THE CONTRACT, and `offline/source-shape.mjs` asserts it** (`getAllPOs` builds no `filterByFormula`). The failure mode is the reason: a list shows what it shows, so a status condition added here would make rows stop appearing with nothing on screen to say any were withheld. Every status belongs — `Awaiting Signature` is the President's own worklist, and `Withdrawn` is kept on record (#138) exactly as the PR list keeps withdrawn PRs (#122).
- **Access is the PR list's, not the invoice list's.** Any active session reaches the page; each row is gated per record by `canViewPR` against the PO's parent PR — the same shared rule `/pos/[poId]` uses. A refused row is simply absent, and a PO with no parent PR is refused rather than shown. `/invoices` differs because invoicing is office work; a purchase order is not.
- **Columns: `PO ID · Vendor · Job / Line · Total · Status`.** No requester column: a PO carries no requester of its own (#138) and the PR list already answers that question, so adding it would spend a column and a query on a fact belonging one document upstream. Job and Line both come from the parent PR, since a PO has neither field — `Job` through the PR's lookup and `Line` through its link, rendered as one cell separated by a middot, which is /prs's own shape for the pair.
- **SORTED BY `PO ID` DESCENDING, SERVER-SIDE, AND THERE IS NO DATE COLUMN — the same shape as `/invoices`**, which sorts by `Invoice ID` and shows only dates that are other facts. A PO ID is `HYE-PO-YYYYMMDD-##`, fixed width and zero-padded, so a plain string sort gives chronological order and the within-day sequence; `InvoiceForm.js` already states that property of this exact format. A `Created` column was there first, on the argument that a list should show the field it sorts by — **`/prs` is the counter-example that retired it**: it sorts by `Created At` and has no date column at all, and `/deliveries` hides its `Created At` tie-break too. Showing the sort key is not this repo's rule. **Consequence on the demo base:** hand-made fixture IDs like `HYE-PO-TESTQA-01` have no date segment, so `T` sorts above any digit and they head the list. Unreachable in production — `mintDailyId` (#164) can only mint the dated format — and the ID prefix is the one thing nobody can backdate, which is why it is the safer key than `Created Date` (the demo seeds backdate that field after generation).
- **A withdrawn order dims the WHOLE ROW**, in #122's classes so the two lists read alike, and its PO ID link inherits the muted color and stays clickable. Terminal but on record (#138), so dimmed rather than hidden.
- **Status renders the field verbatim and carries NO DATE**, which makes the column a closed set of three a reader learns once — the property #166 identified as the difference between a list cell and a sentence. It showed `Signed 2026-07-27` and `Withdrawn 2026-07-27` first; both went, and neither fact is lost: when a PO was signed is on `/pos/[poId]`, and the list already carries `Created` for the date it is scanned by. **There is deliberately no separate Signed column** — it would be blank for every unsigned and withdrawn row (24 of this base's 40) and the declared widths already spend all 832px, so a seventh would take its width from Vendor, the one column with nothing to spare. **`Awaiting Signature` gets no warning and no emphasis** — an unsigned purchase order is an ordinary state of one. The combination worth flagging is "unsigned AND already invoiced", which belongs to the invoice screens and is its own Phase 3 issue. `offline/po-list-view.mjs` asserts the label carries no marker. #19's `statusTag` is deliberately NOT reused: that rule shows only exceptions and stays silent for Signed, which would leave most rows blank in a column headed Status.
- **Newest first** by `Created Date`, tie-broken by `PO ID` descending, undated last — the same chain and reasons as `sortHistoryRows` (#19) and `sortCandidates` (#162). A signature-first default was rejected on #166's precedent: the default list stays newest-first and a *filter* provides the worklist ordering.
- **Three empty states, because they are three different facts.** Nothing on the base ("No purchase orders yet…"), nothing visible to this viewer ("No purchase orders to show. You see a purchase order when you can see the request behind it."), and nothing matching the filters. **The word `yet` is what would make the first false for the second case**, so only one message carries it; the check asserts that. Order is load-bearing — `filtered` is tested last, or a viewer who can see nothing would be told to adjust filters that cannot help them.
- **THE JOB FILTER'S OPTIONS COME FROM THE VISIBLE ROWS, NOT THE VIEWER'S ASSIGNMENTS, which is a deliberate divergence from `/prs`.** There the options are assigned Jobs, so a PR visible only through `canViewPR` clause 5 or 6 — a signer, or a correction recipient, neither of which implies assignment — appears in the list and cannot be filtered to. CLAUDE.md already recorded that as a known inconsistency whose fix is a UI decision; this is that fix, made where the page is new rather than by changing `/prs`. It leaks nothing: every job named is already on a row the viewer can read.
- **SIX OPERATIONS, NONE PER ROW — but stepped, not constant.** `requireUser` (1 find) + `getAllPOs` + `getAllVendors` + `getAllJobs` + `getAllLines` + `getPRsByRecordIds`. Four of those are selects, which Airtable pages at 100 rows, and the batched PR read chunks at 50 ids — so the count rises one query per 50 or 100 records and never with the number of rows rendered. `getLinkedRecords` is used nowhere here: it re-finds the parent on every call, which is why `/prs/[prId]` reads one PR five times. `#190`'s counter measures selects per PAGE for exactly this reason.
- **Table widths are declared (#166's rule) but measured for these six columns.** The invoice table's 52rem came from its own seven and does not transfer. Measured at 14px/20px Arial plus the 8px `pr-2`: Job / Line 184, PO ID 149, Vendor 124, Status 117, Total 79 — 653px of the 832px available. Three columns are bounded by construction and take what they need; **the remaining 27.5rem is split between the two nobody controls**, Vendor and Job / Line, both human-entered — 192px and 248px, the larger share going to the cell that carries two values and a separator. **PO ID was first sized by counting characters against the invoice list's ID and 38 of 40 rows wrapped**, because a PO ID carries a four-digit year (the one exception to the 2-digit convention) and renders at 141px. Five columns are bounded by construction and take what they need; **Vendor takes all the slack**, being the only column whose content nobody here controls.

### Units (PR Items / PO Items / Invoice Items / Materials / Delivery Items)

One single-select field, shared 19-value list: EA, FT, SET, LS, LOT, M, ROLL, PCS, SHEET, M/D, FIT, SQFT, IN, Lengths, KG, PSI, TUBES, PACK, ST. **Materials is the fourth table on this list (#18)** — and the one where the select does more than constrain input, since Unit is part of its natural key. **Delivery Items is the fifth (#162)**, where the value is a pure reference copy; it stayed a select rather than becoming plain text because a fifth copy of the same value flowing PR → PO → Invoice → Delivery is exactly where `ea ` or `Each` would enter unnoticed, and because a missing option fails `createDeliveryItem`'s write outright (no `typecast`) rather than mislabeling a row.

Measured: an existing select field's option list cannot be written through the Metadata API at all — a PATCH carrying `options.choices` returns 422 in every shape tried, while the same token PATCHing that field's description returns 200, so it is a platform limit and not a scope problem. `typecast` gives every option it creates the same default color and nothing can recolor it afterwards. - JS source of truth: `lib/units.js` CANONICAL_UNITS, dropdown on PRForm.js/EditAndContinueForm.js.
- **Out-of-list existing values are preserved as an extra option only in `EditAndContinueForm.js`** (`app/prs/[prId]/EditAndContinueForm.js`, the `!CANONICAL_UNITS.includes(row.unit)` branch). `PRForm.js` maps the canonical list flat, so a hydrated Draft item holding an out-of-list Unit renders with nothing selected — the value survives a save untouched (it is still in React state, and `updateItem` only fires on change) but *displays* as blank, and is overwritten if the Requester touches that dropdown. Currently unreachable: no out-of-list value exists on any of the four fields. Not fixed here — it is PR-form scope, tracked separately.
- `scripts/import/add_unit_options.py` keeps its own duplicate list (Python can't import JS). The duplication is structural and can't be removed, but agreement is checkable: `scripts/tests/offline/unit-options.mjs` compares the two lists (length, order, duplicates) and pins the script's four target tables.
- Airtable's Metadata API can't edit a select field's option list; only way to add a choice is `typecast=True` via a normal record write — the script cycles a throwaway scratch record per table.
- **A choice added by hand in Airtable is invisible to every file-only check** — the precedent is `DRUM`, a 20th option that sat on PR Items alone, held by no record and creatable by no code path here. `scripts/tests/verify-unit-options-18.mjs` (credentialed, schema-read only, creates nothing) is what compares the four live fields against the canonical list. It matters most for Materials, where a missing option fails the cache write outright rather than mislabelling a row.

## ID generation (lib/ids.js)

1. Top-level IDs (PR/PO/Invoice/Delivery): daily-reset counters, **all four sharing one rule** (#164). PO uses 4-digit year; the rest use 2-digit.
2. Child-table IDs: {Parent ID}-{seq}, resets per parent. Same **max + 1** sequence rule as the daily families (#164) — see below.
3. Vendor-issued codes (Vendor Quotation Code, Vendor Invoice Code): human-entered, scope by Vendor.

### The daily counter counts the ID prefix, never a date field (#164)

`mintDailyId` is the one implementation behind all four generators: lock on `{table}:{prefix}`, select the rows whose ID field starts with today's prefix, take the highest sequence, add one, create. **The pure part is `lib/idSequence.js`** — the four families' tokens, year widths and ID field names, the stamp, the prefix, `nextSequence` and `formatSequentialId`. That module imports nothing, which is the whole reason it exists separately: `lib/ids.js` reaches `lib/airtable/client.js` and its module-load throw, so a rule kept inside it cannot be pinned offline. Same split, same measured reason, as `lib/airtableFormula.js` (#159) and `lib/authzWrap.js` (#147); same shape as `lib/itemNaming.js`. **`lib/ids.js` is still the only place an ID is generated** — it owns the lock, the query and the create, and no counting reaches a call site.

- **The defect this replaced.** `generateNextInvoiceId` built `HYE-INV-{today}-{seq}` while counting `IS_SAME({Issue Date}, TODAY(), 'day')` — the **vendor's** date off their document, human-entered and almost never today — so the count was almost always 0 and **every invoice entered on one day got `-01`**. Measured read-only twice, on 2026-07-31 and again on 2026-08-03: that filter matched 0 of 5 invoices. It had not fired only because all five happened to be entered on their own issue date, which real vendor invoices are not.
- **All four converted, and the reason is that they share one rule** rather than that the other three were broken. PR counted `{Created At}` and PO `{Created Date}`, both app-written, both correct — **conditionally on nobody writing those fields with anything but now.** That condition has already been broken by a committed script: `scripts/demo/seed_material_prices.mjs` backdated `Created Date` inside its creation loop and produced **five POs sharing one PO ID**. The ID prefix needs no such condition — it is the population the sequence must be unique within by definition, and nobody can backdate it. `verify-invoice-ids-164.mjs` Part D reproduces that incident against the live base and shows the new rule is immune to it.
- **Not `LEFT({Invoice ID}, 13)`, the form the issue was filed with.** Measured: 0 rows, because the prefix is 14 characters, not 13. A hard-coded length is a per-family magic number (PR 13, PO 15, Invoice 14, Delivery 13) and that one was already written down wrong in two places. The predicate is `lib/airtableFormula.js:prefixMatch` → `FIND("<prefix>", {Field}) = 1`, which takes the anchor from the string itself. It lives with the escape for #19's reason — the alternative was a per-call-site exemption — and is registered in `offline/formula-escaping.mjs`, which fails closed on the call site if it is not (verified by mutation).
- **`nextSequence` is MAX + 1, not count + 1.** A count is the next free number only while nothing has been deleted, and deletion is normal here. Measured on this base: `HYE-INV-260716` holds seqs [02, 03] and `HYE-INV-260727` holds [03, 04] — three invoices have been deleted, and in **both** namespaces count + 1 is a number that already exists.
- **Child IDs use the same rule, and the boundary that once excluded them is gone.** It was recorded as deliberate — a parent's link array holds record ids rather than child IDs, so the highest sequence is not readable from it without another query — and that was true but was a statement about cost, not about correctness. The sentence above applies to children unchanged, and worse: **a child is deleted by an ordinary Draft re-save, not by anyone choosing to.** `persistPRFromForm` creates the new generation before destroying the old one, deliberately, so a failed re-save never loses saved children; the consequence is that every re-save shifts the sequence upward and frees the numbers below it. One item and one re-save leaves `[002]`. Measured on the live base: `HYE-PR-260722-09` holds exactly one PR Item, `-002`, and exactly one Quotation, `-Q02`, so under count + 1 the next child of either kind re-issued a number already on a live row — **and for the Quotation that was reachable with a mouse**, since the PR is In Review and Edit and continue creates Quotations. So `generateChildId` now reads the array, resolves it through `findByRecordIds` and takes `nextSequence`. That second query is the whole cost.
  - **Why the parent's array and not a `prefixMatch` on the child table**, which would be one query instead of two and was measured ~2× faster (112–197ms against 289–709ms). **Not because it lagged** — it was measured seeing a just-created sibling in 6 of 6 rounds. Because of what each option makes ID uniqueness *depend* on. The array depends on a link being visible on both sides immediately, which `generateChildId` already depended on, which `client.js` records as measured, and which `canViewPR` clauses 5–6 also rest on — so the fix adds no new consistency assumption. Filtering the child table would newly make uniqueness depend on the search index being read-your-writes consistent for a plain text field: a guarantee nothing else here relies on, supported only by a negative measurement of a timing window. The one thing the filter is genuinely better at — seeing an **orphaned** sibling whose parent link is gone, like the two parentless `HYE-PO-20260727-05-001` rows the #140 script left — stopped mattering when #164 made a parent's own ID no longer re-mintable, since no future parent carries a dead parent's ID.
  - Still **not** the child table's `{Parent} Record ID` lookup: that one is genuinely computed asynchronously and undercounts when siblings are created right after the parent, reproduced for PO Items. That prohibition is unchanged.
  - **The ID shape is a registry, not a call-site argument.** `CHILD_KINDS` in `lib/idSequence.js` holds all eight relations (ID field, pad width, optional `seqPrefix`), so "a Quotation is `{PR ID}-Q##`" is stated once rather than at one of eight call sites — and the ID field name, the one value a caller must not get wrong, is not a caller's to supply. A wrong field name would read `undefined` off every sibling, look exactly like a childless parent, and mint a duplicate; `generateChildId` throws on that instead. An unregistered relation throws too, and `offline/id-sequence.mjs` enumerates every call site in `lib/` rather than listing them, so a ninth child table cannot ship unregistered or still passing a shape of its own.
  - **The registry key is `Parent Table::Link Field`, and the pair is not caution — the field name alone is measurably not unique.** Counted against the live schema on 2026-08-03 (21 tables, 84 `multipleRecordLinks` fields, 50 distinct names): **7 of the 8 registered names are carried by more than one table**, and 18 of the 50 names base-wide are. Only `Correction Requests` is unique. Nothing collided because exactly one table per name is a *registered* relation — a property of which call sites exist, not of the schema, and `Materials."PO Items"` and `PO Items."Delivery Items"` are already sitting there one `generateChildId` call away from clashing. **The failure a collision causes is silent:** two identical keys in an object literal are not an error in JS, the later wins at parse time, and `Object.keys` then reports one entry — so a check that imports the object agrees with the bug. Demonstrated by mutation: a duplicated key left the imported object with 8 keys and `PO Items` carrying `Delivery Item ID`, i.e. the wrong field, which is the childless-parent read above. It is caught by counting `Property` nodes on `lib/idSequence.js`'s **AST**, which is the only place the duplicate still exists.
    - The offline enumeration resolves each call site's `TABLES.X` by parsing `lib/airtable/client.js`'s own object literal, since importing it would need credentials. A `TABLES.X` that does not exist is caught by the same step.
    - `verify-invoice-ids-164.mjs` Part A re-measures the census and asserts each registered pair still exists in Airtable. That is not cosmetic: a link field renamed in the UI makes `parentRecord.get()` return `undefined`, `generateChildId` reads it as a childless parent, and a live sequence restarts at 1.
  - **One `nextSequence` covers both shapes**, and `seqPrefix` is what makes that work: with `""` a `-Q01` is not a sibling of `-001`, and with `"Q"` the reverse. Two independent sequences under one parent, which is what the live rows show — `HYE-PR-260722-09` carries `-002` and `-Q02`, neither aware of the other. So `lib/idSequence.js` has its second consumer rather than a near-copy.
  - **No existing duplicate was repaired.** Measured across all eight child tables: 0 duplicate child IDs, 0 parentless PO Items (the two the #140 script stranded were hand-deleted in #162), and exactly the two gapped groups named above. A gap is a free number, not a wrong record.
- **The formula narrows; the pure function decides.** `prefixMatch` exists to avoid reading the whole table, but membership is re-tested in `nextSequence`, so a formula that over-matches costs rows and cannot corrupt a number. Past 99 the sequence widens to three digits rather than wrapping or colliding. The hand-made `-99` fixtures on this base sit on prefixes no generator can produce (`HYE-PR-TESTQA` has no digit date segment; `HYE-PO-20260715` is past).
- **One clock now.** The stamp comes from the JS clock while `TODAY()` evaluated in GMT — they agree on Vercel, where the process clock is UTC, and need not agree anywhere else. Airtable is no longer asked what day it is.
- **What each tier proves.** `offline/id-sequence.mjs` pins both rules and asserts, on the AST, that `lib/ids.js` names no date field in a formula, that `TODAY()`/`IS_SAME` are gone, that all four generators delegate to the one helper, and that `generateChildId` reads its siblings' IDs rather than the link array's length — so neither date counting nor length counting can come back without failing CI. It also enumerates every `generateChildId` call site in `lib/` rather than listing them, so an unregistered ninth child table fails too. It does **not** prove the queries selected the right rows, nor that a link array is populated in time to be counted: those are Airtable's properties and live in `verify-invoice-ids-164.mjs`, which creates two invoices in one run with backdated Issue Dates, creates three children and deletes the middle one, and re-measures the link array on the first read after a child is created. Both halves were confirmed by mutation against the live base — reverting either rule makes the corresponding Part fail, and the child mutation minted a real duplicate.

Naming: auto-generated -> `X ID`. Human-typed -> `X Label`/plain name. Calendar-only -> `X Date`. Time-meaningful -> `X At`.

## Querying parent/child data

filterByFormula can't match a link field against a record ID. Read the parent's reverse-link field via .find(parentRecordId) (getLinkedRecords() in client.js), never filter the child table directly. Exception: `materialPrices.js:getMaterialPrice` uses the `Material Record ID` / `Vendor Record ID` lookups — a price row is keyed by two links and nothing else, so there is no parent whose reverse-link would do.

### Client bundle safety — an import is an execution (#162)

**`lib/airtable/client.js` throws `Missing AIRTABLE_API_KEY` at MODULE LOAD.** In a Server Component that is a deliberate fail-fast. In a browser bundle it is an unconditional crash, because the variable is server-only by design. So **no `"use client"` file may import anything that reaches `lib/airtable/`, at any depth.**

The trap is not the rule, it is the reasoning that gets around it. #162 shipped a form that imported one *pure* helper from `lib/deliveryCandidates.js` — annotated as safe because "the module's Airtable readers are never called on this side". That is false: **importing a module executes it.** Nothing tree-shakes away a dependency whose evaluation has side effects, so the throw happens whether or not anything calls a reader. Selecting a job crashed in the browser.

Two consequences worth keeping:
- **The boundary is which modules the client IMPORTS, not which functions it calls.** A pure function in a credentialed module is unreachable from the client, so it has to move — which is why `buildItemOptions` and `itemOptionLabel` sit in `lib/deliveryAllocation.js`.
- **`next build` does not catch this**, because the throw is at runtime. It compiled the broken version without complaint.
- **A `"use server"` file is a boundary, not a dependency.** A Client Component importing a Server Action is the ordinary pattern: the bundler hands the client an action id over the network and never ships the module, so the server-only imports behind it are not in the bundle.

Enforced by `scripts/tests/offline/client-import-safety.mjs`, which walks the real import graph over `app/` and `lib/`, stops at `"use server"` modules, and fails any `"use client"` file that can still reach a **forbidden root** — naming the chain. There are two roots since #190: `lib/airtable/client.js`, and `lib/airtableOps.js`, which is not credentialed and does not reach client.js — client.js imports *it* — so the first root would not have caught a Client Component importing it. What makes it forbidden is its own `node:async_hooks` import, and the hazard is identical: an import is an execution, so nothing has to call `AsyncLocalStorage` for the bundle to break. Each root carries its own anti-vacuity assertion that the traversal is seen to reach it. It carries its own anti-vacuity checks: one asserting that a module which genuinely does reach the client is *seen* to, and one that a module importing nothing is not falsely reported. Those earned their place immediately — the first version used `require()` inside an `.mjs` file, so every path resolution silently failed and all 29 checks passed for the wrong reason.

### Measuring Airtable operations (#190)

**This base spent roughly 60,000 API calls between 1 and 6 August 2026 with one developer, no deployment and no users, and nothing in the repo could say where they went.** Airtable reports a per-base total and no breakdown by endpoint, token or code path. `lib/airtableOps.js` counts every operation and attributes it to a screen, a Server Action or a script; `lib/airtable/client.js` installs it on the one object every read and write in this app goes through.

- **AN OPERATION IS ONE LOGICAL REQUEST, AND AIRTABLE BILLS HTTP ATTEMPTS, SO EVERY NUMBER HERE IS A FLOOR — never the billed total.** Two things push the real figure up and neither is visible to the counter. **Retries:** on a 429, airtable@0.12.2's `run_action.js` recurses into its own module-local `runAction` rather than back through `Base.prototype.runAction`, so a request that took three attempts is counted once; wrapping the callback would not help, because the 429 branch never calls the callback. Timing cannot substitute — the backoff is `Math.random() * min(5000 * 2^n, 600000)`, so a retry can add almost no delay. **Raw `fetch()`:** seven credentialed scripts call the Metadata API directly, bypassing the SDK. One difference runs the other way: `select()` is lazy, so an un-awaited select costs 0 here and 1 at #19's layer.
- **It hooks `runAction` on our Base INSTANCE, not on the Table prototype.** `Table`, `Query` and `Record` all reach the Base through `this._base` and read `.runAction` at call time, so an own-property assignment on that one object is seen by everything created from it while mutating nothing global — a prototype patch is fine in a harness and not in production code. `runAction` is also one funnel rather than two, is called **once per PAGE** so pagination is counted, yields the table and the kind from the request itself, and appears on the library's own public functor. It carries `@deprecated`, which `PINNED_AIRTABLE_VERSION` is the answer to.
- **THE VERSION PIN EXISTS BECAUSE THE THROW CANNOT COVER ITSELF.** `installOpsCounter` throws when the funnel is missing, so a blind instrument is an app that does not boot — but that fires at client.js's module load, and **the offline tier never loads that file**, so bumping `airtable` would pass CI green and land on the first production request. `offline/airtable-ops.mjs` compares the pin against `package.json` *and* the installed version, turning a runtime mine into a build failure. **What a matching pin proves is that somebody looked, not that the wrapper still works** — only `verify-airtable-ops-190.mjs` can say that.
- **Labels: a route TEMPLATE for a page, the exported name for a Server Action, the filename for a script.** The template rather than the resolved path, so forty PR detail loads aggregate into one row instead of forty; asserted to be a string literal on the AST, which is what keeps the key space bounded. **The outermost scope wins**, so a service-layer scope cannot steal a page's operations. **Attribution is opt-in; the total is not** — unlabeled operations still count, so a partial rollout answers the question that motivated this.
- **`unlabeled` MEANS TWO THINGS AND ONLY ONE IS FINE:** a call site nobody has labeled yet, or a lost AsyncLocalStorage context, which would drop everything into that bucket and look identical to the first. The install throw does not cover it — a broken context still counts correctly, it just attributes wrongly. So it is asserted directly in both tiers: offline across an await boundary, and credentialed through a real request.
- **Counting is always on; printing is gated on `AIRTABLE_OPS_LOG`** (`summary` or `verbose`), so the gate can only lose the printout. **No HTTP surface and nothing written to Airtable** — a debug endpoint would have to join `authz-structure.mjs`'s inventory for a report the terminal already shows. On exit the process total is printed, which is what makes a verification script measurable without editing it.

**THE FILE LOG (`AIRTABLE_OPS_FILE`) EXISTS BECAUSE THE CONSOLE OUTPUT NEVER REACHED THE PERSON WHO NEEDS IT.** Verification scripts are the most expensive unit measured — 159 and 487 operations per run — and they mostly run in an agent session whose stdout Soo never sees and which is gone when the session ends. Soo also has no access to Airtable's own Usage tab; the workspace owner reporting heavy API use is what started this issue. **So this file is the only evidence available, and the only thing that can be shown to the owner.** Set it to a path, or to `1` for `.airtable-ops.jsonl` (gitignored).
- **JSONL, one object per line.** The per-table breakdown has variable arity, so there is no honest column form for it; both questions this has to answer later — how much last week, and scripts versus the dev server — are aggregations, and aggregating JSONL is a three-line script where parsing an ad-hoc text format is guesswork. The console output remains the human rendering; the file is the durable record. Two one-liners for the two questions are in the module header.
- **Two record kinds.** A `scope` line per labeled render (label, ops, tables, repeats, per-table breakdown) and a `process` line at exit. **The `process` line is the ONLY place unlabeled operations are recorded**, which is why it carries per-label detail rather than a bare total: a verification script opens no scope at all, so that one line is the whole of what the file learns about a 487-operation run.
- **ONE COMPLETE LINE PER `appendFileSync`, INCLUDING THE NEWLINE — that is the whole concurrency story.** A dev server and a script can hold the file at once. An `O_APPEND` write seeks and writes as one operation, so two writers cannot land at the same offset; what it does *not* protect against is one logical line split across two write calls, where the other process's line lands in the middle. So the mitigation is a rule about the writer rather than a lock, and `offline/airtable-ops.mjs` asserts there is exactly **one** `appendFileSync` call in the module (verified by mutation — a second call fails it). **Measured:** two processes writing 300 records each produced 602 lines, 0 unparseable, 2 distinct pids and 462 alternations, so the interleaving was real and nothing tore.
- **`process.on("exit")` DOES NOT RUN ON Ctrl-C, and that is measured rather than assumed.** Plain `node` receiving SIGINT with no SIGINT listener skips exit handlers entirely — a script that prints from one printed nothing after `kill -INT`. For `next dev` it is a **race**: our renders run in a CHILD process, the child does register SIGINT → `cleanup` → `process.exit` (`start-server.js:389`), but the parent SIGKILLs it `CHILD_EXIT_TIMEOUT_MS` after signalling — **default 100ms** (`next-dev.js:149`) — and SIGKILL cannot be caught. **The per-scope line owes nothing to either mechanism**: each render's record is on disk before the next request starts. Measured: after SIGINT, 4 of 4 scope records survived and parsed, and the `process` record was absent exactly as predicted. For a *script* there is no scope boundary, so Ctrl-C still loses its one record — an inherent gap, named rather than papered over.
- **Nothing identifying is written** — a label, table names, kinds and counts, never a record id, field value or formula. The key set is closed (`RECORD_KEYS`) and asserted, because "we only write counts" is the kind of claim that decays when someone adds a debugging field. Demonstrated by feeding a record-id-shaped path through the classifier: the id does not appear in the record.
- **Never throws, never goes quiet.** A logging failure must not take down a request, but silence is the failure this module exists to prevent. The first failure warns on stderr — naming the path, the reason, and that the file is now **INCOMPLETE**, so a later total will be short — then disables itself for the process rather than warning per render. Measured: an unwritable path produced exactly **1** warning across 6 write attempts and the process exited 0.
- **Synchronous, for two reasons rather than preference:** `process.on("exit")` can only do synchronous work, and an async append could still be queued when the process ends — which is the record most worth keeping. Cost is one short write per scope, tens of microseconds against a render that has already spent 100ms+ on the network. It is nonetheless sync I/O on the request path, so this is a **development and script facility**: off unless the variable is set, and not for a shared production instance, where it would block the event loop for concurrent requests and where Vercel has no durable writable filesystem anyway.

**A RAW CONTROL CHARACTER IN A SOURCE FILE MAKES RIPGREP SKIP IT, WHICH IS A GENERAL HAZARD AND WAS A REAL ONE HERE.** The counter keys its store on `table` + `kind` joined by NUL — a space would split wrongly on `Purchase Requests` — and the first version wrote that separator as a **literal NUL byte** in the source. Git still diffed the file as text, so nothing looked wrong, but ripgrep classifies a file containing a NUL as binary and **skips it silently**: `grep` over `lib/` returned nothing from this module. That is the one failure mode the field-rename procedure cannot survive, since its whole safety argument is "grep the old name and fix every hit". Written as the escape sequence `"\u0000"` now — same value at runtime, and six visible characters in the source instead of one invisible byte. **This paragraph deliberately spells the escape rather than containing the character**, which is the same reason it belongs in the module too: a document warning about a grep-invisible file must not become one.

### Formula injection — every interpolation escapes (#159)

**Interpolating a value into a `filterByFormula` is formula injection, not a quoting nuisance.** The one escape is `lib/airtableFormula.js:formulaString`, and **every interpolation in `lib/` and `app/` goes through it**; the one exception is a module constant, listed below. Writing a new lookup means using it — do not invent a second escape.

What injection actually is, measured read-only against this base (#18 on `getVendorByName`, #159 on the rest): a value of `" & {Vendor Name} & "` turns `{Vendor Name} = "..."` into `{Vendor Name} = {Vendor Name}`, true for every row, so the lookup returns the table's **first** record instead of the one asked for; `IF(1, "...", "x")` is evaluated as formula code. A plain unescaped `"` merely 422s — that is the benign case, not the interesting one.

**#159 was an authentication defect, not cleanup.** `authTokens.js:getAuthTokenRecord` interpolated `{Token}`, and `token` arrives as a raw query param on the **public** `/api/auth/verify` — no session, no role, no origin check in front of it. Exercised read-only on the live base: the tautology returned the table's first row out of 46. `consumeAuthToken` then takes whatever row came back, checks `Used`/`Expires At` on *that* row, and returns its `Email` — a session as whoever that row belongs to, for a caller who supplied no valid token. The row is not attacker-chosen, so it is an unauthenticated lottery over a table of live tokens rather than a reliable takeover; that is not a distinction worth relying on. The other six were route path params on an active session (`getPRById`, `getPOById`, `getInvoiceById`), `{Email}` (`getUserByEmail`), and two with no in-app caller (`getVendorByName`, `getJobByCode`).

**A value from a file is a different kind of reach, and one path has it — closed by its pattern.** `/api/invoices/detect-po` feeds `getPOById` values parsed out of an uploaded PDF, but only `PO_ID_PATTERN = /HYE-PO-\d{8}-\d{2}/g` matches, and that pattern has no metacharacters: its output cannot contain `"`, `\` or `&`. The regex is the sanitizer.

**Two characters are the complete escape set, and that is measured rather than reasoned** (#159, 17 hostile values against the live parser, each accepted and each matching nothing): backslash and double quote. Inside a double-quoted literal Airtable treats `\` as the escape and `"` as the terminator, and nothing else is special — a real newline, a tab, `{Field}`, `'`, `&`, `(`, `)`, `,`, `%`, `^` and non-ASCII all pass through as data. The backslash must be replaced first, or the quote pass re-escapes its own output into `\\"` — a literal backslash followed by a live terminator.

**Why the escape is not in `client.js` any more.** It moved to `lib/airtableFormula.js` because `client.js` throws `Missing AIRTABLE_API_KEY` at module load, which put the escape out of the offline tier's reach — and #159's whole claim is that the escape is *correct*, so it had to be testable without credentials. Same measured reason `lib/authzWrap.js` was split out of `lib/authz.js` in #147. It is deliberately **not** re-exported from `client.js`: two import paths for one rule is the same duplication in another form, and the check needs one canonical source to compare call sites against.

**A list is not a value, and that took a second escape boundary (#19).** A batched read needs `OR(<clause per id>)`, so what gets interpolated is a joined string — and `${chunk.map(...).join()}` is invisible to the check below, which failed it closed, correctly, because the AST cannot see whether anything inside was escaped. The fix was **not** an exemption saying "trust the code inside" (the weak shape #147 warned about) but moving list-building next to the escape: `orByRecordId`, `orByField` and `andSearchAll` in `lib/airtableFormula.js` each return a complete formula fragment with every value escaped. The check accepts a call to one of them by name, and verifies it was imported from that module. **`prefixMatch` (#164) is the fourth builder and arrived the same way**: the daily ID counter needs a whole predicate — `FIND("<prefix>", {Field}) = 1` — and the alternative was an exemption for `lib/ids.js`. Measured against the live parser: the `= 1` anchor is real (the same substring at position 5 matches nothing), `FIND` is case-sensitive, an unused prefix matches nothing, and a prefix carrying a quote or the `" & {Field} & "` tautology is inert. An **empty** prefix is refused rather than escaped, since `FIND("", x)` is 1 for every row — the whole-table answer the empty-list `FALSE()` exists to avoid. Two rules follow:
- A **field name is not a string literal** — it is a `{...}` reference, so escaping it would break it. Field names are always our own constants, so `orByField`/`andSearchAll` **refuse** a name containing a brace rather than trying to escape it; a caller passing one is a bug and a throw says so at the call.
- An empty id/needle list yields `FALSE()`, never an empty `OR()` (which Airtable rejects) and never a missing predicate (which would match the whole table).

**What enforces it:** `scripts/tests/offline/formula-escaping.mjs` (offline, so CI runs it on every push). Fail-closed in the `authz-structure.mjs` shape — it walks every `.js` under `lib/` and `app/`, parses with acorn, finds every `filterByFormula` property, and requires the value to be either a template literal whose every interpolation is an escape-builder call, **or** a bare call to one of the whole-formula builders (the stronger form: the entire predicate comes from the audited module), or a listed exemption with a reason. Verified by mutation: dropping the escape on the auth path, adding a new unescaped lookup, passing the formula by variable, calling a builder **indirectly**, and defining a local shadow of either `formulaString` or a builder each fail it.
- The single exemption is `PO_NOT_WITHDRAWN` (`getPOsExceptWithdrawn`/`searchPOs`) — a module constant holding the fragment `{Status} != "Withdrawn"`, built from the Airtable select option's own name, which no caller supplies. It **replaced** the narrower `PO_WITHDRAWN_STATUS` entry in #168 rather than being added beside it, so the list is still one long; a stale exemption fails this check, which is what forced the swap rather than leaving both.
- **What a pass does NOT prove.** Source shape is not execution: it proves the *text* wraps the value, not that the value reaching Airtable was escaped — `formulaString(mangle(v))` passes. It cannot judge whether the escape is *sufficient*, which is Airtable's property and lives in `scripts/tests/verify-formula-escaping-159.mjs` (credentialed, read-only, creates nothing, consumes no token, mints no session). An exemption is checked by **name** only — nothing verifies the binding is really a const.
- **Scope is `lib/` + `app/`, and the basis for excluding `scripts/` is value provenance, not "a developer typed it"** (#159 checked; none of the values there is a typed argument). `scripts/demo/` and `scripts/import/` build **no formula at all** — the Python importers query with `fields[]`/`pageSize`/`offset` and no filter, and `make-invoice-pdf.mjs` takes a PO ID from `argv` but hands it to `getPOById`, which escapes. The only formulas under `scripts/` are four in `scripts/tests/`, and every interpolated value originates *inside* the script: the run tag the fixture helper generated (`_fixtures.mjs`, through `prefixMatch`), an already-escaped value (`verify-materials-cache-18.mjs`, through `formulaString`), a predicate its own callers build (`verify-invoice-ids-164.mjs`), or a deliberately hostile literal, which is the point of the file (`verify-formula-escaping-159.mjs`). No `process.argv` reaches any of them. **Re-counted in #174**, which deleted the two scripts this sentence used to cite. So there is nothing there to catch today — but it stays a real limit: a new script is not covered, and **a script that interpolates a value read from a file or from Airtable would be a different case and should reopen the scope question.**

## Concurrency: withKeyLock()

generateChildId, upsertMaterial and upsertMaterialPrice wrap read-then-write in withKeyLock(). Serializes only within one process/invocation. Double-submit needs frontend disable-on-click guards.

**The two material locks use different keys on purpose (#18):** identity is locked on the normalized `Item Name + Size + Unit` triple, price on `material + vendor`. The contended resource differs — two vendors' prices for one material are two rows and must not serialize against each other, while two PO lines of one material from one vendor must. `lib/materialsCache.js` takes them in sequence, never nested, because the material record id is only known once the identity upsert has returned.

A service-layer function with no caller is verified by nothing: `upsertMaterial` sat unused from Phase 0 until #18 and carried three defects the whole time, so a module existing is not the same as the work being underway. Verified against the live base by `scripts/tests/verify-materials-cache-18.mjs`: three concurrent calls on one fresh key produce exactly one row and one shared record id, on both locks, and `_debugLockKeys()` shows the single queued key in flight and no leaked entry after it drains.

**`_debugLockKeys()` is a process-global count, so any check asserting `length === 1` only holds while the script is the sole thing holding a lock.** True for a standalone verification run today, and false the moment such a check runs alongside anything else concurrent — it would then be counting the other caller's key too. Recorded because the assertion looks local and is not: it is a statement about the whole process, and it should be read as "exactly one lock exists right now", not "this material's lock exists".

## File uploads (Vercel Blob -> Airtable)

Every file — quotation files, invoice files, generated PO PDFs — is written to Vercel Blob first and then handed to Airtable as an attachment URL, which Airtable fetches to keep its own copy. **Airtable's copy is the copy of record**; the Blob object exists only so Airtable has something to fetch. Four write paths, one lifecycle (#140):

| Path | Blob write | Ingested by | Cleanup scheduled in |
|---|---|---|---|
| Quotation file, PR form | client `upload()` (PRForm.js) | `createQuotation` in `persistPRFromForm` | `saveDraftAction` / `createPRAction`, after their last write |
| Quotation file, Edit and continue | client `upload()` (EditAndContinueForm.js) | `createQuotation` | `editAndContinueAction`, right after its try/catch |
| Invoice file | client `upload()` (InvoiceForm.js) | `createInvoice` | `createInvoiceAction`, after the last write |
| PO PDF | server `put()` (lib/poPdf.js) | `updatePO` | `generateAndAttachPOPdf` itself |
| Quotation file, overage PR (#167) | server `put()` (lib/overagePR.js), of bytes fetched from the invoice's own attachment | `createQuotation` | `createOverageDraftAction`, after its last write |

- **The fourth path is the only one with no client upload at all (#167).** The bytes come from Airtable's copy of the invoice file, so the reason for a server `put()` is not that we generated them but that re-submitting the url Airtable gave us is #142's silent data loss. It still ends at `createQuotation`, which stays the one writer of `Quotations.File`; the `after()` sits at the end of `createOverageDraftAction` rather than inside the module, because that action rolls back and a retry has to be able to re-submit the same url.
- `lib/blobIngest.js:confirmIngestThenDelete` owns the sequence. Call sites pass `{ table, recordId, field, blobUrl, attachmentId }` and never restate it.
- **Size limits are uneven.** The three client-upload paths go through two token routes, and only one of them sets a ceiling: `/api/invoices/upload` caps the upload at 20MB (`maximumSizeInBytes` in its `onBeforeGenerateToken` config), while `/api/quotations/upload` — used by both the PR form and Edit and continue — sets none, leaving a quotation file bounded only by Vercel Blob's own limit. Both routes do restrict content type to PDF/JPEG/PNG. The PO PDF has no ceiling either, but it is a server `put()` of our own generated bytes rather than a user upload.
- **Cleanup is scheduled at the END of the enclosing action, never straight after the attachment write.** All four actions roll their writes back on failure, and the user's retry re-submits the same Blob URL from the still-open form — deleting at ingest time would charge the user for a failure they didn't cause. The rule is "no Blob object outlives its ingest *and the action that ingested it*".
- **It is scheduled, not awaited**: all four sites wrap the call in `after()` from `next/server`, so the confirm poll runs once the response is on its way instead of adding ~1s per file to the user's wait. Ordering still holds — `after()` can only run after the writes that scheduled it succeeded — and if it never runs the result is one orphan, the same outcome as a failed `del()`. It also keeps the cleanup independent of placement: three of these actions end in `redirect()`, which throws, so an awaited call would only work while it sat above that line. `generateAndAttachPOPdf` defers too: being non-fatal to a signature doesn't take it off the clock, since `signPOAction` awaits the whole function. Consequence to know about: that function now expects a request scope.
- **Blob's `onUploadCompleted` callback is not relied on** by either client-upload token route. The client already has the Blob URL from `upload()`'s return value and carries it through the form submission, so nothing needs the callback to learn it — and in local dev it can't arrive at all, since receiving it needs a tunneling service (Vercel can't reach localhost). Nothing in that handler is load-bearing.
- **Confirmation signal**: the attachment no longer carries the URL we submitted (Airtable replaces it with its own). Deliberately not Airtable's CDN hostname (versioned) and not a populated `size`. An empty field counts as NOT ingested: an attachment write pointing at a URL Airtable can't fetch **returns success and silently leaves the field empty** (measured — a write against a deleted object was still empty 30s later).
- Observed ingest latency on this base: 825/890/913/959/943 ms (5 samples). Hence poll every 300 ms (stays inside Airtable's ~5 req/s per-base budget, ~3 polls to confirm) with a 10 s ceiling (~10x the slowest observed, so it fires on breakage rather than slowness). Targets are confirmed one at a time — a multi-quotation PR takes ~1 s per file, off the response path but still spread out rather than parallel, so three files can't burst against the per-base budget.
- **Timeout keeps the object** and logs it: a late ingest must not find a deleted URL. One orphan beats an empty attachment. Only the PO PDF path offers a user-facing retry for the not-confirmed case (`Regenerate PDF`) — the other paths have no regeneration path to offer, so they just log.
- On a *failed* attachment write the object is deleted immediately (no ingest can follow) — the two failure directions are opposite, see `generateAndAttachPOPdf`.
- Cleanup is **best-effort**: a failed `del()` is logged and nothing more, since Airtable already holds the file and failing the user's action over housekeeping would be backwards. So an orphan is still possible; this is a convention, not an absolute invariant.
- **The one orphan source that survives by design**: a file uploaded and then abandoned (form closed before submit). It was never ingested, so it has no ingest to outlive, there is no record to hang cleanup on, and finding it needs the store sweep #140 excludes.
- Airtable's own attachment URLs are short-lived signed URLs (**~2h**, confirmed empirically), so nothing durable may store one — re-read the record instead. Every in-app link (PR detail Quotations, invoice detail, PO PDF) renders Airtable's URL and can go stale on a page held open past that window. Rendering a stale one is a visible, recoverable annoyance; **re-submitting one as an attachment is data loss**, which is what #142 was (see "Draft re-save" below).

### Draft re-save (#142)

`persistPRFromForm` rebuilds a Draft's children from form state, so a re-save handed Airtable whatever url the form was carrying. For a quotation hydrated from a re-opened Draft that url is Airtable's own signed one, and past its ~2h life the attachment write **succeeds and lands empty** — re-saving a Draft the next morning deleted the quotation file, with no error anywhere. Re-submitting a real ingested attachment's own url with its signature invalidated is accepted and empties the field.

- **The rule is "an attachment that did not change is not rewritten"**, not "refresh the url just before re-submitting". Refreshing narrows the window without closing it and leaves "re-upload on every save" as the design.
- The judgement is `lib/quotationReuse.js:shouldReuseQuotation`, on three facts about one form entry: it names a Quotation record, that record is still among the PR's Quotations, and its url is not one of ours. `lib/prDraft.js` supplies the `recordId`; `PRForm.js` round-trips it in `quotationsJson`. They travel in the same object — replacing a file keeps `recordId` and swaps the url, removing an entry splices the whole object — so they cannot come to describe different records.
- **Where the judgement is wrong:** a `recordId` that has gone stale is not reusable, and that entry falls back to the create path with an expiring url — the original bug, in a corner. It does **not** need anyone editing Airtable: the same Draft open in two tabs, one of which **replaces a file** and saves, is enough, because a replacement is a destroy-and-create and the other tab's copy of that record id is dead from then on. #142 narrowed this rather than introducing it — before, every re-save rebuilt every Quotation, so a second tab's save re-submitted a stale url unconditionally. Left as-is rather than given a new error message; see the follow-up below.
- **Quotations are the only child this reconciles.** PR Items and PR Signers are still destroyed and recreated on every re-save, which is safe because neither holds an attachment. Item→Quotation links are re-pointed at the reused record, so a regenerated item keeps its quotation.
- Rollback is unchanged: only records this pass created are torn down, so a reused record — which belongs to the previous generation — survives a failure. Vendor Quotation Code edits on reused records are applied after the new generation is fully in place, for the same reason, and are best-effort (the file is safe either way).
- `editAndContinueAction` does **not** share the defect and was not changed — and it was not fixed for free either, since it doesn't call `persistPRFromForm` (that function, and `collectChildIds`/`destroyChildren`, exist only in `app/prs/new/actions.js`). It has no destroy-and-recreate generation: items are diffed and updated in place by record id, and its only `destroy` calls are its own rollback. Nor does its form hand it a stored url — `EditAndContinueForm` reads existing quotations only to build dropdown options, an item's choice is `existing:<id>`, and `newQuotationsJson` is serialised from a list that starts empty and only grows by this session's uploads. The one-writer rule above covers both paths anyway.
- `Purchase Orders."Quotation File"` is a Lookup chain (PR -> Purchase Requests."Quotation Files" -> Quotations.File) exposing attachment objects on the PO. Mapped in `recordToPO`, read by nothing — not a dependency.

## Auth (lib/auth.js, lib/session.js, lib/email.js, lib/authz.js)

- Magic link only. requestMagicLink() domain-checks then emails a token; verifyMagicLink() consumes it (withKeyLock-protected), finds-or-creates the User.

- Env vars: SESSION_SECRET, RESEND_API_KEY, ALLOWED_EMAIL_DOMAIN, EMAIL_FROM (optional). - **Resend's domain is verified — mail delivers to any address.** It was sandbox-only (account owner's address only) for most of this project's life, which is why several decisions here are written against that constraint; the constraint is gone, but the decisions that cite it were made under it and are not retroactively wrong.
- **The product is named in one place: `lib/productName.js` (#201).** `PRODUCT_NAME` is `HYE USA Portal`; `SIGN_IN_TITLE` is the one sentence carried by both the magic-link email's subject and `/login`'s `<h1>`, which is what stops those two from drifting. **Not the company's legal name** — `lib/poPdf.js:HYE_BUYER_NAME` (`HANYANGENG USA INC.`) is what a vendor sees on the purchase order, and the two have different owners and must never move together. Its own module rather than a constant in `lib/email.js` because `app/login/page.js` is a Client Component and `lib/email.js` throws at module load without `RESEND_API_KEY` — #162's trap, an import is an execution.

## Route protection (lib/authz.js)

**Operating convention:** office staff run with Is Admin: true; a non-Admin Employee is site staff. So gating an endpoint to Admin scopes it to the office, not merely to a higher privilege tier — e.g. the invoice routes are Admin because invoicing is office work, not because Admin is "more trusted."

app/admin/jobs|vendors|lines/new — Admin-only, Server Action re-checks requireAdmin(). app/invoices (list) and app/invoices/[invoiceId] (detail) — viewing is President-or-Admin. app/invoices/[invoiceId]/edit and the invoice edit/delete/Paid-toggle Server Actions — Admin-only.

**Row-scoped, not role-scoped: app/prs (list), app/prs/[prId] (detail), app/pos/[poId].** All three need only an active session to *reach*, and then decide per record through the one shared rule below. The PR list filters its rows (#119), the PO detail page gates on its parent PR (#132), and the PR detail page does the same (#143) — all three matter, since the list's rule does not apply to anyone who knows a PR ID and the PO gate reads a PR that could otherwise be opened directly. A refusal renders the ordinary not-found text on all three: never confirm that a record exists outside someone's scope.

### Row visibility — `canViewPR` (lib/prVisibility.js)

In order, first match wins:

1. **A `Draft` is visible only to its Requester** — ahead of everything, including President/Admin (#143). Every other Draft surface is already private that way (the resume prompt and the drafts list both read `getDraftsByRequester`), and nothing in the app links to someone else's Draft. An unsubmitted PR is not yet a record of anything, and its assigned signers have nothing to sign.
2. **President/Admin** see every submitted PR.
3. The **Requester** sees their own.
4. Anyone **assigned to the PR's Job** sees it.
5. A **signer on this PR's chain** sees it (#143).
6. The **recipient of a correction request on this PR** sees it (#143).

Clauses 5 and 6 are not generosity — without them the gate cuts the signing chain. Neither a signer nor a correction recipient is guaranteed to be assigned to the PR's Job, and a participant who cannot open the PR cannot take their turn, so the chain stops with nothing to explain it. Both are **status-agnostic**: a signer who already approved, one pushed back to Pending by a correction, and the recipient of an already-`Resolved` correction all keep access. Being locked out of a document you signed would be strange, and every chain action ends in `redirect()` back to this same page, so access that expired at the moment of acting would bounce the actor into a refusal.

**How 5 and 6 cost no queries.** Both sides of each relation already carry the child row ids as link arrays, so membership is a set intersection: `Users."PR Signers"` × `Purchase Requests."PR Signers"`, and `Users."Correction Requests (Sent To)"` × `Purchase Requests."Correction Requests"`. `recordToUser`/`recordToPR` expose them as `signerRowIds`/`correctionRowIds` — the same reverse-link trick `purchaseOrders` already used, and confirmed on a freshly created row to be populated on both sides immediately, with no propagation lag. So the PR list stays one pass over rows it already has, with **no per-row round trip**, and the detail page adds nothing either. The cost is that an intersection cannot read a child's fields, so clause 6 *cannot* filter on `Status` — which is free here, because status-agnostic is what we want anyway.

**`Sent To` ambiguity does not reach this.** CLAUDE.md records that it holds one user id and cannot say whether a correction went to someone *as a signer* or *as the Requester* when they are both. That is about the recipient's capacity; clause 6 only asks whether they are the recipient at all.

**`Withdrawn` takes no special path** — #122 keeps a withdrawn PR on record and in the list, so it is judged like any other submitted PR.

**A missing link array throws rather than refusing.** Once clauses 1–4 have not decided, the answer depends on `signerRowIds`/`correctionRowIds`, and a caller that omitted them is a bug rather than a denial. Refusing would look like the safe direction and would in fact be the stalled chain 5 and 6 exist to prevent — a signer locked out of the PR they are meant to sign, with no error to trace. Both mappers default the fields to `[]`, so `undefined` can only mean the object never went through one; every production caller does today, which makes the throw unreachable now and a tripwire for the next call site. It fires only where the arrays are actually needed, so a decision already reached by clauses 1–4 still works on an object without them. What it cannot catch: Airtable omits an empty link field, so "no signers" and "field not selected" are indistinguishable downstream — the mappers' `|| []` is what turns both into `[]`, and a field-limited select would pass this check while silently disabling both clauses. No such select produces a `canViewPR` input today (the only ones are in `lib/ids.js`, for sequence numbering).

**Guard wrappers (#147) — the expected way to gate a new endpoint.** `lib/authz.js` exports three: `withAdminApi` (Route Handler; refuses with requireAdminApi()'s own 401/403 Response), `withAdminAction` (Server Action; the call site passes its refusal as the first argument) and `withPresidentAction` (Server Action; requirePresident() throws, so there is nothing to pass). A wrapped export cannot run its body unauthorized, because the body is an argument the wrapper decides whether to call — the caller obligation below stops being a thing anyone can forget. The refusal shapes are deliberately NOT unified: four Admin Server Actions throw and four return `{ error }` for the caller to render inline, both on purpose, so refusal stays the call site's argument. Aligning them would change what a user sees and is its own decision, not part of #147.

None of the three passes the resolved user to the handler, because no Admin/President call site reads one — every requireAdmin() site destructured only `{ authorized }` and every requireAdminApi() site used its value only for the `instanceof Response` test. Add it as a first argument if a wrapped handler ever needs it.

**Not wrapped, and why (#147).** These are the exemptions, listed with reasons in `scripts/tests/offline/authz-structure.mjs` and enforced there. The list is meant to stay short for two reasons: every entry is a precedent a future author can copy, and an exemption is verified more weakly than a wrapper (see the scope note below).
- The three magic-link auth routes — public by design; there is no caller to authorize.
- `/api/invoices/upload`, `/api/quotations/upload` and `/api/deliveries/upload` — the gate has to run inside `handleUpload`'s `onBeforeGenerateToken` callback, which rejects by throwing rather than by returning a Response, so wrapping the export would answer 401/403 where the client currently gets the 400 `handleUpload`'s catch produces. Recorded because #147 found it: `request.json()` runs at the top of all three handlers **before** authorization, so "the gate comes before the route's work" is looser here than the phrase suggests. These three are the only places in the inventory where that is true, and the shape propagates — the deliveries route (#162) inherited it by being the same kind of endpoint, which is exactly what the note about every exemption being a precedent predicted.
  - The deliveries route carries one more looseness of its own, named in its exemption: it gates on `getActiveUser()` and **cannot** check the Job, because the upload happens before the form is submitted so the route does not yet know which Job the photo belongs to. The Job check is in `createDeliveryAction`. So any active user can put an object in the store; what they cannot do is attach it to a delivery.
- `createOverageDraftAction` (#167) — `requireUser()` plus the Job check, the same per-record axis as the other delivery actions, and **deliberately not Admin**: raising the correction is site work. It is the exception to #166's withholding described under "Overage corrections", and it re-derives eligibility from a fresh read so a correction raised in another tab lands as a refusal rather than a second Draft.
- The eight `requireUser()` Server Actions — session + per-record/per-turn ownership, not a role. `requireUser()` already cannot be dropped (it redirects), and the actual authorization is the record-by-record comparison in the body. A wrapper here would cover the half that was never at risk and leave the deciding half uncovered, while looking like coverage.

**Caller obligation:** requireRole()/requireAdmin() only *report* the decision — a caller must destructure the returned `{ authorized }` and short-circuit on false (throw, return `{ error }`, or render a refusal). Calling one without acting on the flag protects nothing (the code runs on). requirePresident() and requireAdminApi() are both preferred over the flag helpers for the cases that use them, but they are not equally undroppable, and the difference is the return: requirePresident() *throws*, so control cannot continue past a refusal and there is nothing for a caller to ignore; requireAdminApi() *returns* the 401/403 Response, which is a value the handler has to return for anything to be blocked — the call on its own refuses nothing, so leaving its result unassigned is still a way to lose the gate. What it removes versus `{ authorized }` is the flag to misread, not the caller's obligation.

**Re-authorization rule (#134):** every directly-callable endpoint re-authorizes to the level of the strictest page that renders its UI — a page being the only caller isn't a substitute, since Route Handlers and Server Actions are reachable directly. Server Actions use the wrappers above (signPOAction/regeneratePDFAction are `withPresidentAction`; generatePOAction, the PO-generation retry, is `withAdminAction` with a matching isAdmin render gate on app/prs/[prId]). withdrawPOAction (#138) is the per-record variant: requireUser() only settles "is this an active session", and the actual authorization is an ownership comparison against the parent PR's Requester inside lib/poWithdraw.js — no role helper fits, since the requester is typically neither President nor Admin. `/api/*`: the magic-link auth routes are intentionally public, /api/quotations/upload is any-active-user (matching the PR form that consumes it); /api/invoices/upload, /api/invoices/detect-po, /api/pos/search, /api/pos/[poRecordId]/items are Admin-only via requireAdminApi() (their sole consumer is the Admin-only invoice form). Any route that fetches a caller-supplied URL also restricts it to our Vercel Blob host (detect-po's SSRF guard), independent of auth.

**What enforces the rule (#147).** `scripts/tests/offline/authz-structure.mjs` is a structural check over an **enumerated** inventory — enumerated because a hard-coded path list is blind to any route added later: it walks every `app/api/**/route.js` and every `"use server"` file under `app/` and `lib/`, parses each with acorn (so a comment can satisfy nothing), and requires each export to be either wrapped by one of the three wrappers or listed as an exemption with a reason. It also flags a function-level `"use server"` directive anywhere in those trees — an inline Server Action is directly callable too, and none exist today, so one appearing should fail rather than pass by not being looked for. A file it cannot parse fails; an unparsed file is an unchecked file. A stale exemption (the export is now wrapped, or no longer exists) fails too, so the list can't rot into a blanket permission.

**What a pass proves, per case.** For a **wrapped** export: the gate cannot be skipped and cannot run late, because the handler is an argument the wrapper decides whether to call — ordering is structural, so there is nothing left for the check to assert or for an author to get wrong. For an **exempt** export: only that the named helper is called somewhere inside the exported function. **Order is not checked** — the old check's `gateIdx < workIdx` comparison has no counterpart, so an exempt route that does work before its gate still passes. That is not hypothetical: `/api/invoices/upload` and `/api/quotations/upload` both call `request.json()` before authorizing, which is why that fact is written into their exemption reasons. This is the check's exact scope rather than a defect in it, and it is the reason an exemption is worth less than a wrapper.

**It is a standing check, not issue evidence.** It runs with no env vars, no Airtable, no dev server and no module loader, writes nothing, and exits non-zero when it fails — so since #152 it sits in the offline tier that `npm test` and CI run on every push (see "Verification tiers" below). `scripts/tests/verify-authz.mjs` keeps only what genuinely needs credentials: the Blob host predicate, PO-generation idempotency against a throwaway PR+PO, and real HTTP 401/403 refusals. That one needs `.env.local`, the loader, and a dev server, and it exits 2 when a part could not run so an incomplete run never reads as a pass. Adding an endpoint without a gate fails the offline tier without anyone remembering to register it, which is the property the old check didn't have.

## Utility scripts (scripts/)

### Verification tiers (#152)

Checks are split by **cost of execution**, not by issue. A cheap check welded into a script that writes to the shared base costs credentials and fixtures to reach, so it does not get run — and a check nobody runs is not a check. #152 is the precedent: six assertions sat invalidated for weeks, in two scripts reporting `SOME CHECKS FAILED` at exit 0.

- **`scripts/tests/offline/` — the standing tier.** Plain `node`, no env vars, no Airtable, no Blob, no dev server, no module loader, creates nothing. `npm test` runs all of it; `.github/workflows/checks.yml` runs `npm test` on every push and PR.
- **`offline-checks` is a required status check on `main`**, so this tier passing is a merge condition rather than advice. The name is the **job key** in `.github/workflows/checks.yml` — renaming that job renames the check GitHub reports, while the branch protection rule keeps waiting for the old name, and a PR then sits permanently "Expected — waiting for status to be reported" with nothing failing and no obvious cause. If the job is ever renamed, update the required-check setting in the same change. Each file exports `title` and `run({ check, log, assert })` and also runs standalone (`node scripts/tests/offline/source-shape.mjs`). The runner **scans** the directory rather than listing files, so a new check is in CI automatically — same reasoning as #147's enumerated inventory: anything that has to be registered somewhere can be forgotten. Files beginning with `_` are shared helpers (`_harness.mjs`, `_ast.mjs`). `fixture-cleanup.mjs` (#171) is the newest check: it walks every `verify-*.mjs` on the AST and requires each one that creates records to go through the fixture helper, with no `Promise.allSettled` whose results are discarded, no empty `catch`, and no `process.exit` above its cleanup call. **It carries no exemption list on purpose** — a script that cannot use the helper is evidence the helper is wrong, not a line to add. `product-name.mjs` (#201) is the second check with none, and it gets there a different way: it scopes itself to `app/` + `lib/` so that every legitimate spelling of a superseded name is outside it rather than excused within it.
- **`scripts/tests/verify-*.mjs` — the credentialed tier.** Needs `.env.local` and the loader, writes throwaway fixtures to the shared base, and some need `npm run dev`. Human-initiated on purpose and deliberately not in CI: one shared base means concurrent workflow runs would create and delete records against each other. These no longer contain their offline parts — run `npm test` for those.
- **Where a new check goes:** if it needs no credentials it goes in `offline/`, otherwise it goes in the credentialed tier. The boundary is not a judgment call — `lib/airtable/client.js` throws `Missing AIRTABLE_API_KEY` at module load, so importing it, or anything that imports it, puts a check in the credentialed tier. Offline-safe today: `lib/prVisibility.js`, `lib/authzWrap.js`, `lib/units.js`, `lib/editLogFields.js`, `lib/variance.js`, `lib/prSigning.js`, `lib/itemNaming.js`, `lib/poItemQty.js`, `lib/airtableFormula.js`, `lib/materialPriceView.js`, `lib/deliveryAccess.js`, `lib/deliveryAllocation.js`, `lib/idSequence.js`, `lib/deliveryStatus.js`, `lib/overage.js`, `lib/invoiceItemFold.js`, `lib/productName.js`, `lib/airtableOps.js` (#190 — importable under plain `node` because `node:async_hooks` is a built-in; it is nonetheless server-only, and for the browser it is a forbidden root, which is a different boundary from this one), `lib/poListView.js`. **An offline-safe module must have no UNRESOLVABLE imports, which is stricter than "pure" (#19):** the tier runs under plain `node` with no loader, and node cannot resolve the extensionless intra-lib imports the rest of the app leaves to Next. So an offline-safe module either imports nothing, or spells the extension out: `lib/materialPriceView.js` imports `"./itemNaming.js"` that way, because the alternative was inlining #18's naming rule — a second implementation, which is worse than deviating from an import style. `lib/deliveryAllocation.js` is the second such case (#162), importing `"./materialPriceView.js"` for `countsAsOrdered` rather than re-typing `committedQty > 0`. **The friction there is recorded with the condition to resolve it:** an allocation module importing a *view* module is misleading about layering, and `countsAsOrdered`'s real home is `lib/poItemQty.js` (per-line quantity judgements, already offline-safe and dependency-free). Not moved now because it would edit #19's module plus two offline checks for no behavioural gain; **move it when a third consumer appears.** Not: `lib/poWithdraw.js`, `lib/blobIngest.js`, `lib/ids.js`, `lib/materialsCache.js`, `lib/deliveryCandidates.js`, `lib/deliveryReconciliation.js`, `lib/overagePR.js`. #18 is the worked example of one concern splitting across both tiers rather than picking a side: the two Unit lists are files, so comparing them is offline (`offline/unit-options.mjs`); what the Airtable fields actually hold needs the Metadata API, so that is credentialed (`verify-unit-options-18.mjs`). Neither subsumes the other — a hand-added option passes the first and fails the second.
- **Exit codes are mandatory for anything that computes a verdict**, in the shape #147 set: **0** all clear, **1** something failed, **2** no failures but a part could not run. A script that prints its verdict and returns 0 regardless makes a failure indistinguishable from a pass to anything but a reader. **A LEAK IS 1, NOT 2 (#171)** — a run that left rows on a shared base needs a hand, which is the same criterion that made 1 right for a failure, while 2 means a part could not run and needs none. Two meanings for 2 would demand two different human responses. Every script that creates records therefore carries two verdicts and two sentences: `pass` about the feature, and `fixtures.describe()` about the run's effect on the base. **One file computes no verdict about its subject and still has an exit code** — `verify-variance-15.mjs` prints variance figures for a human to compare and returns 1 for a leak and nothing else, because that is a fact about the run rather than a judgment about variance; its header says so. `verify-detect-po-92.mjs` remains the one file with no exit code at all, and it creates nothing.
- **Source-shape checks belong in `offline/source-shape.mjs`**, together, on the AST. "This call site calls X before Y" is unreachable behaviourally for a Server Action (iron-session cookie, request scope), so it has to be asserted on the source — but keep it in one file and parse it: matching on source text decays whenever an export changes shape. `_ast.mjs` documents what it still cannot prove: source order is not execution order.
- **What a green CI run does NOT mean.** It means the cheap tier passed. It does not mean authorization is enforced, and putting these checks behind a CI badge lends them an authority they haven't earned — the same correction #147 had to make about its own Part A. `source-shape.mjs` proves a gate call appears earlier in the file than the call it guards; a gate inside `if (false)`, or after an early return, satisfies it. `authz-structure.mjs` proves each endpoint export is wrapped, and for an exempt export only that its helper is named somewhere inside — order is not checked there at all. Only `authz-wrappers.mjs` proves behaviour, and only of the wrappers themselves. Everything that proves a real refusal against real data still lives in the credentialed tier and still has to be run by hand. Green means "nothing cheap regressed", not "the system is safe."
- **Airtable formulas, rollups and lookups are outside CI entirely — treat them as a third tier that no test can reach cheaply.** They are not in the repo, they are not in git history, and `npm test` cannot see them — and it makes no difference that Claude can now edit them directly (see "Editing the Airtable schema"), because the edit still leaves no diff: a formula can be rewritten between two green CI runs with nothing in the diff. `DRUM` is the precedent — a 20th Unit option appeared on PR Items, held by no record and creatable by no code path here, and every file-only check stayed green. **The convention that follows: when a judgement rule lives on the Airtable side, a credentialed check must read the live schema or the live values and compare them against what the code assumes.** Five exist now — `verify-unit-options-18.mjs` for the five Unit option lists, `verify-edit-log-fields-181.mjs` for `Edit Log."Field"`'s option list against `lib/editLogFields.js` (schema **and** rows, because whether an unwritable choice is legitimate depends on whether any row holds it — see Edit Log), `verify-materials-cache-18.mjs` Part E for `PO Items.Committed/Signed Qty` across all three PO statuses (the only thing that would notice if the `& ""` coercion stopped turning the `PO Status` lookup into text), and `verify-deliveries-162.mjs` Parts A–B for `PO Items."Delivered Qty"`, `verify-overage-167.mjs` Part A for #167's two link fields and both symmetric sides — a link field renamed in the UI makes `record.get()` return `undefined`, which every banner would then render as nothing at all — and `verify-delivery-status-166.mjs` Part A for the two reverse-links #166's join walks plus `Invoiced Qty` on the first read after an invoice line is created — that join has no stored link, so those three are the whole of what it rests on and none is visible to a file-only check. That last one is the sharpest illustration of why this tier has to exist: **the Metadata API does not expose a rollup's aggregation function at all**, so SUM and COUNT are indistinguishable from any schema dump, and the only way to know which one the field is doing is to write two rows and look at the number. None run in CI, all must be run by hand, and that is the cost of putting a rule where the UI can edit it.
- **The tier boundary is enforced, not just documented.** `run-all.mjs` catches a load failure per file and names it: a check that reaches `lib/airtable/` is reported as "is NOT offline" with the rule, and a missing `acorn`/`acorn-jsx` is reported as dev dependencies not installed. Both would otherwise surface as a raw module-resolution or `Missing AIRTABLE_API_KEY` stack, which reads as broken tooling rather than as a misplaced check — and a CI failure that looks like an environment problem is precisely what trains people to ignore CI. One unloadable file also cannot hide the other checks' results.

### Directories

- scripts/tests/ — verification. **The fixtures such a script creates are deleted within the run that created them, and since #171 that is a CONTRACT rather than a convention**, owned by `scripts/tests/_fixtures.mjs` and adopted by all sixteen scripts that create records. What it guarantees: cleanup survives a throw in the body; each record is reported by id when its delete fails; a failed CHILD delete keeps its parent, so a recoverable pair is left instead of an orphan; a failed PARENT read skips the parent, because the child list is then unknown rather than empty; a leak reaches the run's verdict and its exit code; and the deletion is MEASURED — a tag census before and a residue check after, since "found 0" is also what a query against the wrong field returns. `scripts/tests/offline/fixture-cleanup.mjs` pins the shape in CI; only the credentialed run proves a row is gone. ## Git workflow rules

- Never commit to main. One branch per issue: {issue#}-{short-desc}.
- Commit format: `{type}: {description} (#{issue#})` — feat / fix / chore / refactor / docs (project markdown/CLAUDE.md changes) / test (changes under scripts/tests/).
- PR description must include `Closes #{issue#}`. Squash merge — PR description becomes the final commit body.
- Line-wrap commit bodies + PR descriptions at 72 chars. Prompts/comments don't need wrapping.
- Wrap literal `<tag>`-looking text in backticks in PR descriptions.
- If an issue is already covered by other work, comment explaining why, then close — never silently close via Closes #.
- Milestones = Phases (0-6) or standalone cross-cutting milestones. Stay scoped to the current issue's Milestone unless told otherwise.
- **A comment or doc line that is FALSE about the current code or base is corrected on sight (#181)**, in whatever commit found it, rather than filed as a follow-up. It changes no behavior, and deferring costs more than fixing: an entry someone has to read, triage and schedule. **The boundary is falsity against improvement** — correcting a lie is maintenance, making a comment better is scope. Anything that changes behavior, moves code, or needs a judgement about what the right answer is stays out of scope as before.
- Don't open a PR unless asked. Never commit yourself — write commit-msg.txt at repo root (gitignored), user commits manually.
- All GitHub content, project markdown, and web-app-facing text is English regardless of conversation language.
- **That English is US English** — prose as well as identifiers, and in code comments as much as in user-facing copy. `behavior`, `judgment`, `canceled`, `labeled`, `catalog`, `gray`, `normalize`, `license`, `while` (not `whilst`). The rule exists because this repo's comments carry its reasoning, so the same word spelled two ways across two files reads as two authors rather than one, and because a mixed convention gives every later edit a coin to flip. It is not a claim that US spelling is better. The one thing it does NOT reach is a value that belongs to something outside this repo — an Airtable select option, a dependency's package name (`@img/colour` in `package-lock.json`), a third-party field or CSS keyword — where the external spelling is the correct one and changing it breaks a lookup rather than fixing a style.
