# Page not found

Route: `/[...address]`
Who reaches it: any signed-in user who opens an address no other screen answers — a mistyped
or outdated link, an address cut short, an old bookmark. Anyone signed out is sent to sign in
first and comes back here, as from any screen.
Which width comes first: the desk's, as every screen on the Equipment & Tools axis draws it;
the phone draws the same heading and the same way back.

## What it answers

That the address names nothing. **It is 1h's `Page not found`**, drawn in the app's frame with
the rail, the same view a kind's address that no catalog row carries reaches. Until #617 an
unknown address met the framework's own page, `404 | This page could not be found.`, with no
rail and none of the app's type.

**It catches only what no route takes.** Every screen that exists answers its own address
first; this is reached only by an address that matches none of them.

## What it always carries

**heading.** `Page not found`, centered in the column. It names the page rather than an item,
since the address carries nothing a reader can read back (#612).

**action.** `Back to Equipment & Tools`, a bordered control under the heading, leading to the
list.

Nothing else: no sentence naming the address, no search, no list of suggestions.

## What it carries only sometimes

Nothing. Every unknown address reaches the same view, signed-in readers of every kind alike.

## What must agree elsewhere

**One view for every address that names nothing on this axis.** A kind's address with a record
id no catalog row carries (`asset-categories-categoryRecordId.md`) draws exactly this, from the
same component, so the two cannot drift apart. An item's own address with a code no item
carries keeps `Item not found` and its sentence, because that address names a code a reader can
check against a label (`assets-assetId.md`).

**The words are the item screens' words**: `Page not found` is #612's and `Back to Equipment &
Tools` the item page's way back.
