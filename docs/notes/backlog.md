What remains:

- **Upload follow-ups (#140 + #142).** The Blob lifecycle is covered by "File uploads" above and the re-save rule by "Draft re-save". What remains unfiled:
  - Objects already in the store from before #140 are cleared by hand — no sweep, no orphan-detection oracle.
  - **A stale `recordId` on re-save** falls back to the create path with an expiring url, so that one entry can still land empty. Two paths reach it, and the realistic one needs no Airtable edit at all: the same Draft open in two tabs where one **replaces a file** and saves — a replacement is destroy-and-create, so that entry's record id changes under the other tab, whose later save is then holding a dead id. (The other path is someone deleting the Quotation record by hand mid-edit.) #142 narrowed the risk rather than introducing it: before, every re-save rebuilt every Quotation, so a second tab's save was always re-submitting a stale url; now only a genuine file replacement elsewhere does. Deleting the whole Draft in the other tab is **not** this case — `persistPRFromForm` throws at its `getPRByRecordId` check ("Draft record not found") before any attachment write, so the Requester gets an error rather than a silent loss. Fixing what remains means telling the Requester to re-attach, which is new user-facing copy and therefore its own decision.
  - **Quotation ID churn on re-save is reduced but not gone, and it is now churn only.** A reused record keeps its `{PR ID}-Q{seq}`, but a replaced file still burns a new sequence number, and PR Items/PR Signers still get fresh child IDs on every re-save. What changed is that the churn no longer *duplicates*: because the new generation is created before the old is destroyed, each re-save left the low numbers free while the count kept pointing at them, so the next child re-issued a live number — the defect measured on `HYE-PR-260722-09` and fixed by making `generateChildId` take the highest sequence (see "Child IDs use the same rule"). The remaining item is unchanged and is cosmetic: an unbroken re-save still walks `-001 -> -002 -> -003` for the same item, and now walks it without ever looking back, so a long-lived Draft's child numbers climb. Whether child IDs should be stable across re-saves was never decided — and the cheap version of that decision is reconciling PR Items the way #142 reconciled Quotations, which would stop the churn at its source rather than renumbering anything.
- **Row-visibility follow-ups (#143).** The rule itself is covered by "Row visibility" above. What remains unfiled:
  - **The PR list's Job filter does not cover chain-visible rows.** Its options come from `accessibleJobs` — the Jobs a user is *assigned* to — so a PR visible only through clause 5 or 6 appears in the list but cannot be narrowed to by Job, and its Job is not in the dropdown. Not a leak (the filter can only narrow within an already-gated set) but an inconsistency between what the list shows and what it can filter. Widening the options to the Jobs of visible rows is the obvious fix and is a UI decision.
  - **`Correction Requests.Sent To` holds a single user id.** Clause 6 needs nothing more, and the recorded capacity ambiguity does not reach it. But a correction that has to go to more than one person cannot be expressed, and that is a schema question rather than a code one.
- **Verification follow-ups (#152).** The tier split itself is covered by "Verification tiers" above. What remains unfiled:
  - **Pure predicates stuck behind a module-load side effect.** `getPOWithdrawEligibility`/`isPOWithdrawn` (11 checks) and `isOurBlobUrl` plus the ingest constants (8 checks) are pure, but `lib/poWithdraw.js` and `lib/blobIngest.js` import `lib/airtable/client.js`, which throws without `AIRTABLE_API_KEY`, so those checks cannot join the offline tier. Three ways out, none obviously right: split each concern module (fights the one-module-per-concern rule those two exist to satisfy), make the client's env check lazy (weakens a deliberate fail-fast-at-boot), or let the offline tier supply a dummy key (muddies "no credentials"). Not a defect, just the current boundary. **`withKeyLock`'s rejection-path check is a third case (#174)** — it is pure, needs no Airtable at all, and sits in `verify-token-and-lock-174.mjs` only because `withKeyLock` is exported from `client.js` itself; it belongs in the offline tier if that split ever happens.
    - **#159 resolved the third case of this, `formulaString`, by splitting**, and it is a precedent for exactly one of the two remaining — not both. It worked there because the escape is a self-contained rule with no table of its own, so `lib/airtableFormula.js` *is* its concern rather than a fragment of one; the split did not fight the one-module-per-concern rule, it satisfied it. `getPOWithdrawEligibility` is the opposite: `lib/poWithdraw.js` exists specifically to hold the predicate, its copy and its guarded write together, and prying the predicate out to make it importable would re-create the split that module was built to prevent. `isOurBlobUrl` sits closer to the `formulaString` case and could plausibly follow it.
    - **#164 followed that precedent a second time**, for the daily ID rule stuck behind `lib/ids.js`'s import of `client.js`. It qualified on the same test: what moved to `lib/idSequence.js` is a self-contained naming-and-population rule with no table of its own, and `lib/ids.js` kept the lock, the query and the create — so the split satisfied one-module-per-concern rather than fighting it. `lib/ids.js` itself is still not offline-safe and still not in the list above; what changed is that the part worth pinning no longer lives there.
  - **Two source-shape checks that could stop being source-shape.** `signPOAction`/`regeneratePDFAction`'s "guard before the write" is asserted on source order because a Server Action can't be called from node — but #147 established that one *can* be invoked over HTTP (`Next-Action` header + the action id from the page payload + a real session cookie). Converting those two would replace a proxy with the property itself. It needs a dev server, so it would land in the credentialed tier.
  - **`scheduleBlobCleanup`.** Ten of `source-shape.mjs`'s checks exist only because each upload path calls `after(() => confirmIngestThenDelete(...))` itself. A helper owning the `after()` would make "scheduled, not awaited" structural and delete those checks — the #147 move applied to a second concern. Whether "outside the rollback" can also be made structural depends on `after()`'s semantics, which nobody has checked.
  - **"Every PO carries a `Created Date`" is measured but not asserted.** #165 attaches an over-delivery to `sortCandidates`' last element, and that comparator sorts an undated ordered item last so a data gap cannot take FIFO priority — so the tail now carries two meanings, "no priority" and "most recent", and one blank `Created Date` would make a data defect the place surplus quietly lands (see "Over-delivery is flagged, never refused" for why the two readings coincide). Measured 24 of 24 on 2026-08-04, which is what keeps it unreachable; a line in `verify-deliveries-162.mjs` would keep it that way without anyone rereading the paragraph that records it.
- **Unfiled work with no parent issue.**
  - **`verify-blob-lifecycle-140.mjs` can orphan its own PO Items, and the two it left were found in #162.** Its cleanup deletes a PO's `PO Items` with `Promise.allSettled(...)` and then deletes the PO, discarding the settled results — so a failed item delete is invisible AND its parent goes anyway, leaving a PO Item with no `PO`. Two such rows existed ("#140 fixture item", qty 2), both carrying `PO Item ID` `HYE-PO-20260727-05-001` — the ID repeated because *both* counters were a COUNT of existing rows at the time, so deleting a PO freed its PO ID for the next run to mint again and the fresh PO's first item re-minted the same child ID. **#164 closed both halves of that**, so a repeat cannot happen the same way again: a daily ID is now max + 1 over the day's prefix and a child ID is max + 1 over its siblings. They were deleted by hand in #162 — measured since: 0 parentless PO Items and 0 duplicate child IDs anywhere. **The orphaning itself is untouched**, and it is still the live defect here: the script will strand rows again, they just will not share an ID. Neither row reached anything — no `Material` link, so no Materials rollup, and `getDeliveryCandidates` drops an ordered item whose PO cannot be resolved — but each still carried `Committed Qty` 2, because that formula reads `IF({PO Status} & "" = "Withdrawn", 0, {Qty})` and an absent PO makes `PO Status` empty rather than withdrawn. So a parentless ordered item counts as ordered. The fix is that script's cleanup reporting per-item failures instead of swallowing them, deleting items before the parent, and probably `verify-deliveries-162.mjs`'s treatment of side-effect rows as the model. **Deliberately not done in #162** — it is #140's script, so it belongs on its own branch rather than inside a deliveries commit.
  - **`/pos/[poId]` withholds invoice data more narrowly than the rule now requires, and whether to widen it is undecided (#233).** The page gates `Invoiced`, `Uninvoiced` and the invoices charging the order behind `isPrivileged`, on #132's line that the invoice pages were President-or-Admin. #211 moved that line: `lib/airtable/poItems.js` records it retiring the President-or-Admin gate on `getPOItemsForReconciliation` because what a vendor billed is readable by anyone who may read the order behind it, leaving `Paid` as the narrower replacement. So the two disagree, in the safe direction — this page shows a site employee less than the rule allows. Widening it is a product decision about who sees an order's billing, not a consequence of a layout change, which is why #233 left it. **Whoever takes it has one thing to split first:** `Paid` currently rides on the same `isPrivileged` flag as the rest of the invoice section, so widening the flag would widen payment with it, and payment is the one fact #211 deliberately kept narrow.
  - **Hand-entered test invoices carry a variance flag the app would not set.** `HYE-INV-260727-04`'s single invoice item has `Variance Flag` checked while its `PO Item` link is EMPTY, which `createInvoiceAction` cannot produce (its variance loop `continue`s on an invoice item with no PO Item) and which `updateInvoiceAction` would clear on the next save. So it was set by hand, or the invoice item's PO Item link was removed after the fact. It is why that invoice shows the amber "has variance flags" prompt with no red header banner and nothing checked on the `Invoices` row — the flag lives on `Invoice Items`. Left in place per the dummy-data convention; noted because it is the likeliest source of confusion about what the two warnings mean.
  - **The invoice detail page's two variance warnings overlap, and neither names its kind.** The red banner under the items table renders on `invoice.varianceFlag` alone and states the figures (Amount Due vs Calculated Total). The amber banner under Payment renders on `invoice.varianceFlag || items.some(varianceFlag)` — a SUPERSET — so a header variance produces both (the amber adding nothing) while a line-only variance produces just the amber, which does not say which invoice item or that it is an invoice item at all. Measured on the base: 0 flags → 0 warnings, header only → 2, line only → 1, both → 2. The per-line `⚠ Variance` badge in the table is the only thing that localizes it. Whether the amber should name the kind, or exclude what the red one already said, is a copy decision and is not #162's.
