# Open work with no issue — the lists

Governs nothing directly; this is the backlog CLAUDE.md points at. **Read this before editing there** — CLAUDE.md carries only the rules that bind code outside this area; the derivation, the evidence and the alternatives weighed are here.

Moved verbatim out of CLAUDE.md, and nothing in it was rewritten until #296, which read every entry against the code it names and is the first pass to edit the entries themselves.

**An entry here is what was true when it was written. Check it against the code before you promote it.** #296 read all fifteen against the files they name: two had already been closed — one of them for three weeks, and it had just been filed as an issue — and five more carried a figure, a measurement or a scope that had moved. Eight stood exactly as written. So the answer to "can an entry be trusted on sight" is no, and the check is the one the entry itself supplies: open the file it names, find the behavior it describes, and if it is gone, delete the entry with what closed it rather than filing it.

**AND A FIGURE IN AN ENTRY IS THE FIRST THING TO GO STALE.** Three of the five rewrites were counts — "two source-shape checks", "ten of source-shape.mjs's checks", "17 `Invoices` rows" — each true when written and each wrong now, because the thing counted grew while the sentence did not. Where a count is not the claim, name what to count instead of counting it.

What remains:
  - **Withdrawal notifications** — no email is sent on withdrawal today, and none is written yet: this belongs to the broader notification pass over state transitions. **That pass is no longer blocked** — it was waiting on Resend leaving sandbox mode plus domain verification, and both are done, so what remains is the work itself rather than a dependency. - **Upload follow-ups (#140 + #142).** The Blob lifecycle is covered by "File uploads" above and the re-save rule by "Draft re-save". What remains unfiled:
  - Objects already in the store from before #140 are cleared by hand — no sweep, no orphan-detection oracle.
  - **A stale `recordId` on re-save** falls back to the create path with an expiring url, so that one entry can still land empty. Two paths reach it, and the realistic one needs no Airtable edit at all: the same Draft open in two tabs where one **replaces a file** and saves — a replacement is destroy-and-create, so that entry's record id changes under the other tab, whose later save is then holding a dead id. (The other path is someone deleting the Quotation record by hand mid-edit.) #142 narrowed the risk rather than introducing it: before, every re-save rebuilt every Quotation, so a second tab's save was always re-submitting a stale url; now only a genuine file replacement elsewhere does. Deleting the whole Draft in the other tab is **not** this case — `persistPRFromForm` throws at its `getPRByRecordId` check ("Draft record not found") before any attachment write, so the Requester gets an error rather than a silent loss. Fixing what remains means telling the Requester to re-attach, which is new user-facing copy and therefore its own decision.
  - **Quotation ID churn on re-save is reduced but not gone, and it is now churn only.** A reused record keeps its `{PR ID}-Q{seq}`, but a replaced file still burns a new sequence number, and PR Items/PR Signers still get fresh child IDs on every re-save. What changed is that the churn no longer *duplicates*: because the new generation is created before the old is destroyed, each re-save left the low numbers free while the count kept pointing at them, so the next child re-issued a live number — the defect measured on `HYE-PR-260722-09` and fixed by making `generateChildId` take the highest sequence (see "Child IDs use the same rule"). The remaining item is unchanged and is cosmetic: an unbroken re-save still walks `-001 -> -002 -> -003` for the same item, and now walks it without ever looking back, so a long-lived Draft's child numbers climb. Whether child IDs should be stable across re-saves was never decided — and the cheap version of that decision is reconciling PR Items the way #142 reconciled Quotations, which would stop the churn at its source rather than renumbering anything.
- **Row-visibility follow-ups (#143).** The rule itself is covered by "Row visibility" above. What remains unfiled:
  - **The PR list's Job filter does not cover chain-visible rows.** Its options come from `accessibleJobs` — the Jobs a user is *assigned* to — so a PR visible only through clause 5 or 6 appears in the list but cannot be narrowed to by Job, and its Job is not in the dropdown. Not a leak (the filter can only narrow within an already-gated set) but an inconsistency between what the list shows and what it can filter. Widening the options to the Jobs of visible rows is the obvious fix and is a UI decision. **#168 made exactly that fix on `/pos`**, where the page was new, and left this one alone.
  - **`Correction Requests.Sent To` holds a single user id.** Clause 6 needs nothing more, and the recorded capacity ambiguity does not reach it. But a correction that has to go to more than one person cannot be expressed, and that is a schema question rather than a code one.
- **Verification follow-ups (#152).** The tier split itself is covered by "Verification tiers" above. What remains unfiled:
  - **Pure predicates stuck behind a module-load side effect.** `getPOWithdrawEligibility`/`isPOWithdrawn` and `isOurBlobUrl` plus the ingest constants are pure, but `lib/poWithdraw.js` and `lib/blobIngest.js` import `lib/airtable/client.js`, which throws without `AIRTABLE_API_KEY`, so those checks cannot join the offline tier. Three ways out, none obviously right: split each concern module (fights the one-module-per-concern rule those two exist to satisfy), make the client's env check lazy (weakens a deliberate fail-fast-at-boot), or let the offline tier supply a dummy key (muddies "no credentials"). Not a defect, just the current boundary. **`withKeyLock`'s rejection-path check is a third case (#174)** — it is pure, needs no Airtable at all, and sits in `verify-token-and-lock-174.mjs` only because `withKeyLock` is exported from `client.js` itself; it belongs in the offline tier if that split ever happens. **This entry carried a count of the checks in each of the two scripts and #296 removed them rather than re-deriving them**: they were #152-era figures, nothing had kept them current, and the boundary is the claim.
    - **#159 resolved the third case of this, `formulaString`, by splitting**, and it is a precedent for exactly one of the two remaining — not both. It worked there because the escape is a self-contained rule with no table of its own, so `lib/airtableFormula.js` *is* its concern rather than a fragment of one; the split did not fight the one-module-per-concern rule, it satisfied it. `getPOWithdrawEligibility` is the opposite: `lib/poWithdraw.js` exists specifically to hold the predicate, its copy and its guarded write together, and prying the predicate out to make it importable would re-create the split that module was built to prevent. `isOurBlobUrl` sits closer to the `formulaString` case and could plausibly follow it.
    - **#164 followed that precedent a second time**, for the daily ID rule stuck behind `lib/ids.js`'s import of `client.js`. It qualified on the same test: what moved to `lib/idSequence.js` is a self-contained naming-and-population rule with no table of its own, and `lib/ids.js` kept the lock, the query and the create — so the split satisfied one-module-per-concern rather than fighting it. `lib/ids.js` itself is still not offline-safe and still not in the list above; what changed is that the part worth pinning no longer lives there.
  - **The guard-before-the-write checks could stop being source-shape.** Every entry in `source-shape.mjs`'s `WITHDRAW_GUARDS` table asserts that a gate call appears earlier in the file than the side effect it protects, because a Server Action can't be called from node — but #147 established that one *can* be invoked over HTTP (`Next-Action` header + the action id from the page payload + a real session cookie). Converting them would replace a proxy with the property itself. It needs a dev server, so it would land in the credentialed tier. **The table is what to count, not this sentence:** it held two entries when this was written and holds four now, #281 having added one.
  - **`scheduleBlobCleanup`.** A block of `source-shape.mjs`'s checks exist only because each upload path calls `after(() => confirmIngestThenDelete(...))` itself — two per `scheduled` row of its `CLEANUP_SITES` table, which is the number to read off that table rather than out of this entry. A helper owning the `after()` would make "scheduled, not awaited" structural and delete them — the #147 move applied to a second concern. Whether "outside the rollback" can also be made structural depends on `after()`'s semantics, which nobody has checked.
  - **"Every PO carries a `Created Date`" is measured but not asserted.** #165 attaches an over-delivery to `sortCandidates`' last element, and that comparator sorts an undated ordered item last so a data gap cannot take FIFO priority — so the tail now carries two meanings, "no priority" and "most recent", and one blank `Created Date` would make a data defect the place surplus quietly lands (see "Over-delivery is flagged, never refused" for why the two readings coincide). Measured 24 of 24 on 2026-08-04, which is what keeps it unreachable; a line in `verify-deliveries-162.mjs` would keep it that way without anyone rereading the paragraph that records it.
- **Unfiled work with no parent issue.**
  - **`generatePOForApprovedPR`'s rollback can strand a `PO Items` row, and #206 already fixed the same shape in production.** Its `catch` runs `Promise.allSettled(createdPOItems.map(destroy))`, discards the settled results, and then deletes the PO regardless — so an item delete that fails is invisible AND its parent goes anyway, leaving an ordered item with no `PO`. **That is the defect `offline/fixture-cleanup.mjs` bans in verification scripts**, and #171 closed every instance of it in that tier while scoping itself to `verify-*.mjs`, so this one was never in its way. The model is `#206`'s: `deleteDeliveryAsUser` had the identical rollback and now destroys sequentially with a failed child throwing before the parent goes. **What a stranded row costs is not nothing:** `Committed Qty` reads `IF({PO Status} & "" = "Withdrawn", 0, {Qty})`, and an absent PO makes `PO Status` empty rather than withdrawn, so a parentless ordered item counts as ordered. It reaches little else — no `Material` link, so no Materials rollup, and `getDeliveryCandidates` drops an ordered item whose PO cannot be resolved. **Structure without a symptom: 0 of 38 `PO Items` are parentless today** (#296), and the two that once were came from the verification script #171 fixed. `lib/poGeneration.js`'s own docstring claimed this rollback left "zero trace" and was corrected in #296.
  - **An invoice's only correction path for a wrongly entered invoice item is deletion and re-entry** (#117 left adding and removing invoice items out of its Tier 1 edit). A ledger does not delete a posted document, so whether deletion stays the correction model is a decision the QuickBooks work owns, along with what a re-entered invoice does to a code already sent across. There is no QuickBooks issue yet, which is why this is here rather than filed against one.
  - **Seed scripts do not run #231's pairing, and there are now two shapes of that rather than one.** The computed pairing lives in `createInvoiceAction` (`getDeliveriesForInvoice` → `matchDeliveryToInvoice` → `setInvoiceDelivery` on `matched`), so a seed that writes `createInvoice` and `createInvoiceItem` directly skips all of it. **`seed_delivery_status_166.mjs` and `seed_overage_167.mjs` still do** — each creates an invoice with no pairing step, so an invoice whose material demonstrably arrived sits with an empty `Delivery`, which on screen reads `Awaiting delivery` and `No delivery has been matched to this invoice yet` — exactly what a genuine no-match looks like, so someone later working the invoice axis would debug their own code against data the matcher was never asked about. **`seed_full_demo.mjs` is the second shape and it fails the other way:** it calls `setInvoiceDelivery` directly, five times, without asking the matcher — so the link EXISTS and no judgment ever produced it, and a reader who finds a paired invoice there will believe the matcher ran on it. `seed_order_breakdown_237.mjs` is the one that does it properly: it calls the real matcher after its charges land and prints the answer per invoice, which is the shape a fix would take everywhere. **The same seeds skip `Invoice-PO Link` too**, which no code reads today (the invoice page derives its orders from `Invoice Items."PO"`), so a seeded invoice is half-linked in one direction and unlinked in the other. Doing this for #165/#166/#167's seeds means re-reading their intended states together rather than patching one, and it would change another issue's data. **This entry carried a 2026-08-17 census of 17 `Invoices` rows and named three of them; #296 removed all of it** — the base has been re-seeded since, none of the three invoices exists any more, and a count of rows is not what the entry is about.
  - **`AIRTABLE_OPS_FILE` appends a JSONL line per scope and nothing reads it.** `reportScope` writes `{t, pid, proc, kind, label, ops, tables, repeats, by}` to `.airtable-ops.jsonl` under that flag (#190), and the only code that touches the path is `resolveOpsFile` and the offline check pinning it — the two `node -e` one-liners in that module's own comment aggregate by `proc`, not by `label`, and are documentation rather than a reader. **That is why the day this base hit its call ceiling went unexplained**: the dev server's console had scrolled away and been restarted, and there was no reader to ask which label had spent the operations. What is needed is small — aggregate the file by `label`, giving a count and a total per label, so the expensive screen names itself. **It is a script rather than an issue**, in `scripts/` beside `wrap-72.mjs` and offline by construction (it reads a file, not the base). **And the condition this entry set for doing it has now been met** — it said the thing was worth writing only once a few days of logs existed, because against one session's file it would report what a single render already prints. Measured in #296: `AIRTABLE_OPS_FILE=1` is set and `.airtable-ops.jsonl` holds 4,270 lines.
  - **`verification.md`'s inventory of `scripts/demo/` names five scripts and the directory holds fourteen.** That file lists `seed_demo_fixtures.mjs`, `make-invoice-pdf.mjs`, `seed_material_prices.mjs`, `seed_over_delivery_165.mjs` and `seed_delivery_status_166.mjs`, each with what it seeds and why; `seed_full_demo.mjs`, `reset_demo.mjs`, `wipe_base.mjs`, `seed_overage_167.mjs`, `seed_order_breakdown_237.mjs`, `seed_po_backlog_176.mjs`, `mint_session.mjs`, `_demo_ids.mjs` and `output/` are absent from it. Nothing there is false — the paragraph does not claim to be exhaustive — but it reads as an inventory, and the two that matter most for a reader deciding what to run are the ones that DESTROY: `wipe_base.mjs` and `reset_demo.mjs` are not described anywhere in `docs/notes/`. Filling it in means reading fourteen scripts and saying what each is for, which is a pass over that file rather than a line.
