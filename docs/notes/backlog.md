**Everything here is work recorded as needing doing that has no issue tracking it.** Once an issue exists the tracker is the record and the line goes — not replaced by a "tracked as #N" annotation, which would mean a doc edit every time an issue closes. What stayed in CLAUDE.md is the third sentence that stood beside these, barring a phase or milestone status from THAT file, whose reader is someone writing into it rather than into this one.

**An entry here is what was true when it was written. - **Every money control in this app declares `step="0.01"` and no `min`, which makes the constraint measure against the wrong base (#405's finding).** For `input type=number` HTML takes the step base from `min` when present and **from the `value` content attribute otherwise**, so with no `min` the browser asks whether a figure is a whole number of cents away from whatever that attribute holds. Measured on the two invoice screens: `/invoices/new` binds its four header controls to React state, which keeps the attribute on the current value, so the base follows the figure and `checkValidity()` is true for anything typed — the constraint is vacuous. `/invoices/[invoiceId]/edit` renders its four with `defaultValue`, so the base is the stored figure, and **on an invoice storing `1.005` the browser accepts `1.005` and `2.005` and refuses `1.01`, `1.00` and `12.34`** — it admits the off-cent value and blocks every repair. Proved by moving the base: `min="0.005"` on that same control, with the value and the step untouched, makes the mismatch disappear, and removing it brings it back.
  - **NOTHING IS UNSAFE TODAY, which is why this is an entry rather than part of #405.** That issue put the judgment in both actions and both service writers, so no off-cent figure is written whatever a control does. What is left is a control that misleads a reader and, on the one record worth repairing, obstructs them.
  - **THE FIX IS A `min` AND THE JUDGMENT ATTACHED TO IT IS WHETHER THESE FIGURES MAY BE NEGATIVE.** `min="0"` pins the base at zero and makes `step="0.01"` mean whole cents on every screen, and it also bars a negative — which is a product question nobody has asked: a credit note, a corrected overcharge and a refunded tariff are all reasons a vendor document might state one, and this app has never had to say. `min` can be set without `0` as its value only by choosing another base, so the two decisions cannot be separated.
  - **THE SCOPE IS WIDER THAN THESE EIGHT CONTROLS, counted rather than guessed:** `app/` declares `step="0.01"` in **15** places and `min` in exactly **two**, neither of them a money field (`min="1"` on a tool-registration count and on a delivery quantity). So every currency control in the app has the same unbased constraint. Whoever takes this should grep for it rather than fix the two screens #405 happened to measure.

- **A quantity of zero is a figure the app cannot mean, and nothing refuses it (#409's finding).** `lib/variance.js:isWholeQty` is `Number.isInteger`, which admits `0`, and it is the only judgment any quantity meets: `assertWholeQty` guards `createItem`/`updateItem`, `createPOItem` and `createInvoiceItem`/`updateInvoiceItem`, and none of them asks whether the figure is positive. So an invoice item charging `0`, a request item ordering `0` and an ordered item of `0` are all writable. This is the same family as the two entries above — #308 and #405 held these figures to a SHAPE (a whole number, a whole number of cents) and neither asked what values the shape may take — and it is the quantity axis's version of the `min` entry directly above it.
  - **THE CONTROL DOES NOT STOP IT EITHER, and the app already knows the fix.** All three typed quantity controls — `app/prs/new/PRForm.js`, `app/invoices/new/InvoiceForm.js` and `app/invoices/[invoiceId]/edit/EditInvoiceForm.js` — are `type="number"` and `required` with no `min`, so a typed `0` satisfies the browser and then satisfies `isWholeQty`. Two controls in this app already carry `min="1"`: the tool-registration count and the delivery form's quantity. Those are the precedent and the counted exception the `min` entry above records, so the work here is to say why a request, an order and an invoice may not use it.
  - **THE JUDGMENT IS WHETHER ZERO IS EVER A THING SOMEBODY MEANS**, and unlike the negative question above it it looks answerable. A vendor does not invoice a quantity of none, and a request for none is a row that should not have been added — `isEmptyItemRow` already takes an untouched row out before the merge, so a `0` is a row somebody typed into. **What has to be checked before a `min` goes on is the DRAFT path**, since `/prs/new` saves without per-item validation and a half-filled Draft is a state that screen supports on purpose.
  - **NOTHING IS WRONG ON THE BASE, counted 2026-09-18:** `Qty` is `0` on 0 of 24 invoice items and 0 of 39 ordered items, and blank on none of either.
  - **#409's SIGNATURE MOVES WITH THIS VALUE, WHICH IS WHY IT IS FILED RATHER THAN LEFT.** `splitSignature` reduces a folded item's per-order quantities by their greatest common divisor, and a one-order item therefore reduces to `1` — which is what makes an invoice charging one order silent without a clause saying so. A charge of `0` reduces to `0` instead, so a one-order invoice mixing a zero-quantity item with a real one signs `A:0` beside `A:1` and DRAWS the list, where #409 says it stays silent. **Refusing `0` closes that gap with no change to the judgment**, which is the outcome to aim for. Both repairs inside the judgment were worked out in #409 and both NARROW it somewhere else — dropping zero shares from the key silences an item that touched an order its neighbour did not, and dropping zero-total items silences an item that named an order alone — so neither was taken, and whoever fixes the value should not reach for them. `docs/notes/deliveries-and-invoices.md` carries that reasoning under #409.
