# Materials and the item axis — the reasoning

Governs `app/materials/**`, `lib/material*.js`. **Read this before editing there** — CLAUDE.md carries only the rules that bind code outside this area; the derivation, the evidence and the alternatives weighed are here.

Moved verbatim out of CLAUDE.md — nothing in this file was rewritten. The migration was audited line by line and the result is in the pull request that created this file.

### Material price screens (#19)

`/materials` (search, grouped by item with a row per vendor) and `/materials/[materialId]` (one item's full purchase history, newest first). Both are pages, not modals — this repo's modals are confirmation dialogs (`modalStyles.js`) and every reading surface is its own route.

- **It reads the item axis, not PR Items.** Comparison figures come from **Material Prices**, history from **PO Items**, both reached through #18's `Material` link — never by matching `Item Name` text. A PR Item is a *requested* price, and an unapproved PR's price is one nobody ever paid.
- **Any active user, no Job scoping** — what a material costs is not a per-Job secret, and site staff pricing a job need it as much as the office. **The exception is document identifiers:** PO ID, PR ID and Job are shown only to a viewer who passes `canViewPR` on the source PO's parent PR, the same gate `app/pos/[poId]` uses. Price, vendor, date, quantity and PO status are open. A refused row renders `—` and still shows its price.
  - Enforced in `lib/materialHistory.js`, which builds an `identifiers` object or `null` per row. The gated PO ID is stripped from the history row after sorting, so no ungated copy of an identifier leaves the module even as a sort key.
- **The gate costs no per-row query.** `canViewPR` is pure and takes an already-loaded user and PR, so the module fetches whole levels — Materials, Material Prices, POs, PO Items, PRs, Vendors, Jobs — keyed on ids gathered from the level above. **Measured, not argued:** 7 Airtable operations for a 1-material/2-row search and **the same 7** for a 2-material/3-row one; history is 5 selects + 1 find (the material itself) regardless of ordered item count. `scripts/tests/verify-material-price-19.mjs` Part E re-measures it.
- **Search matching** uses #18's `normalizeItemText`, so the typed string and the stored value cannot disagree on case or spacing. Tokens are AND-ed as case-insensitive substrings of `Material Label`, so word order does not matter (`ball valve 2"` = `2" ball valve`) and each extra word narrows. A token can match the size or unit segment — a consequence of matching the label, accepted rather than fixed. Results are capped (25) and truncation is reported, because the follow-up batched queries fan out from these rows. **The shape of the label is unchanged and where its words come from is not: it was `Item Name_Size_Unit` with the name typed by a requester, and it is `<category path>_Size_Unit` since #356.** The section at the bottom of this file is what #357 measured about that and what it changed.
- **The date on a history row is the PO's `Created Date`.** A PO Item carries no date. `Created Date` is the moment the price was frozen onto the document, it is always present, and it is the same field `upsertMaterialPrice` stores as `Material Prices."Latest Date"` — so the comparison row and the history row cannot disagree about when a price happened. `President Signed At` was rejected because an Awaiting Signature PO has none, which would leave rows undated. It is calendar-only, so same-day rows tie; the tie-break is PO ID descending, monotonic within a day by construction.
- **Newest first, with the lowest price marked** rather than sorted to the top: a three-year-old price that happens to be lowest would otherwise take the most prominent row. The mark is a fact, not a recommendation — ties mark every tied row, and it is **omitted entirely when there is one vendor**, since "lowest of one" dresses a single data point as a comparison. When the rows' quantities differ the screen says the unit prices are not directly comparable and leaves the judgment to the reader.
- **Withdrawn and unsigned prices are shown with their status, not filtered.** `upsertMaterialPrice` writes at PO-generation time, so a vendor's newest price can come from an order later withdrawn — verified: a withdrawn PO's 41.00 is what the vendor's row carries. Whether an ordered item counts toward the order book is #18's `Committed Qty`, read via `countsAsOrdered`, never re-derived from the status string; the status tag is the *label* and comes from `PO Status`. The two deliberately come from different fields, each from where the fact lives.
- **The status tag is shown only for `Awaiting Signature` and `Withdrawn`; silence means `Signed`.** Nearly every ordered item is Signed, so tagging it puts noise on every row and buries the two states a reader actually has to account for. The rule is one pure function, `materialPriceView.js:statusTag`, shared by both screens.
- **The tag sits beside the VENDOR, not beside the PO ID it describes, and that is a measured layout decision.** In the Order column it wrapped: 168px of room against 214px needed for a PO ID plus a tag (and 228px on the history screen, where a Job code shares the cell) — visible only to a viewer who passes the identifier gate, since a refused row shows a short `—` instead. Reserving the width was the wrong fix because the majority of rows carry no tag at all. The Vendor column already had ~212px unused behind the longest vendor name, so the tag moved to where the slack was: nothing is reserved, and a tagged row is one line like every other (measured 29px throughout, with a full-length PO ID injected to reproduce the Admin view). The consequence "not counted as ordered" left the history rows for the same reason and is now stated once, as a footnote naming what the dimmed rows mean.
- **Every label therefore names its subject — `PO unsigned`, `PO withdrawn` — and that is the price of the move above, not decoration.** Beside a vendor name a bare `Withdrawn` reads as a fact about the VENDOR, i.e. a supplier we no longer buy from, which is a different and wrong claim. `Awaiting Signature` is not used verbatim because the label has to stay short enough that a long supplier name plus a tag still fits one line; the prefix costs ~18px, which is why the history screen's numeric columns were trimmed to give Vendor 272px against the 249px a 24-character name plus `PO withdrawn` needs. An **unrecognized** status renders as `PO: <status>` rather than being swallowed, so an option added to the Airtable field later shows up instead of vanishing — the failure mode #144 recorded for a denylist that admits whatever it does not name. The colon form is used there because an arbitrary option name cannot be relied on to read grammatically after a bare `PO`.
- **An empty query is a BROWSE, not an empty search.** The screen lists every indexed item under the search bar before anything is typed, so `searchMaterials` skips `filterByFormula` entirely rather than asking `andSearchAll` for a match-all — that builder's empty case is `FALSE()` on purpose, the right contract for a predicate but the wrong answer here. Browse order is alphabetical by `Material Label`, sorted **server-side** so the 25-row cap takes the first N of a stable order rather than an arbitrary N. Most-recently-priced would be more useful, but the dates live one level down in Material Prices, which is fetched *after* the cap, so ordering by them would mean capping on a figure that query cannot see.
- **That leaves three empties since #357, and none may read alike:** the query matched no item and no category carries its words, the query matched no item and a category does, and nothing is indexed at all. The third only renders while `Materials` is genuinely empty and explains that the list is built as new POs are generated — because "no results" here does **not** mean the item was never bought. ordered items created before #18 carry no `Material` link and were not backfilled, so an empty screen is the expected state on a base whose PO Items table is not empty. **The third is suppressed under a miss**, since both of the first two carry that same reason for the query the reader actually typed.
- **The `Lowest` tag sits before the price, and that is an alignment fix rather than a preference.** With the tag *after* the price in a right-aligned cell it pushes the badged row's number left of its neighbours — measured at 596.05 against their 600.05, a visible 4px break in the column. Before the price, the tag grows leftwards into the column's slack and every row's number ends on the same edge (measured identical to 2dp across every group).
- **Both screens' tables are `table-fixed` with a declared `colgroup`, so no cell's content can decide a column's width.** The search page renders one table PER item group, and an auto-layout table sizes columns from its own rows, so three groups came out three different shapes. Declared widths make them identical across groups — measured `[352, 144, 64, 112, 160]` for all three, with every price and every quantity ending at the same x — and they also mean a status tag or a long vendor name cannot move a column. Widths were set from measured content rather than guessed: every column clears its widest realistic cell (a 24-character supplier name plus a tag, a full PO ID, a `$40,959.00`) by 11–103px, and `Unit price` is sized by its HEADER rather than its figures.
- **Column order differs between the two screens on purpose.** The search table runs `Vendor | Unit price | Qty | Date | Order`; the history table, like `app/prs/[prId]`, `app/pos/[poId]` and `app/invoices/[invoiceId]`, runs `Qty | Unit price | Amount`. Those three carry an **Amount** column, so qty-then-price reads as the equation `Qty × Unit Price = Amount` — the history table has Amount and follows them. The search table has no Amount and exists to compare prices, so the price leads and the quantity follows it as the caveat that qualifies it. Adjacency is the shared property; the order within it is decided by whether an Amount column is there to close the equation.
- **Both tables also carry `min-w-[52rem]`, and dropping it breaks them in a way that is easy to miss.** `w-full` alone lets the table shrink below the sum of its declared columns, and the one flexible column (Vendor) absorbs the shortfall — at 375px it collapsed to nothing and every vendor name wrapped, taking rows from 29px to 69px. The minimum keeps the desktop layout intact and hands the overflow to the `overflow-x-auto` wrapper each table already sits in, so the page body never scrolls sideways (measured at 375px). Consequence: below roughly a 900px viewport the table scrolls horizontally, since `max-w-4xl` minus `p-8` leaves exactly 832px.
- Reached from the home page; the app has no navigation shell, so one link there rather than inventing a nav bar.

**Material Prices**: item × vendor (#18). Natural key = Material + Vendor. `Price Label` (primary, formula over the two links), `Material` / `Vendor` (links, single), `Unit Price`, `Latest Date` (calendar), `Latest PO` (link), and `Material Record ID` / `Vendor Record ID` lookups. Those two lookups are what make a row findable at all — `filterByFormula` cannot compare a link field to a record id, the same exception already recorded for parent-link filtering. Still a latest-value cache, not history.

### Materials

- **Why the split.** The three things Phase 4 serves have two different axes. Price is only meaningful per vendor — "what does this cost" has a different answer per supplier. Purchase history and on-order quantity are the opposite: they must aggregate *across* vendors, because "how much of this do we have on order" does not care who supplies it. One table cannot be keyed both ways, so identity + cross-vendor quantity live here and the per-vendor price lives in **Material Prices**.
- **`PO Items.Material` is what makes the item axis exist**, and the only alternative was matching on `Item Name` text — the approach `getInvoicingStatusByPO` cites "no name/similarity matching" as its own justification for avoiding. Its consequence: the quantity rollups traverse `Materials."PO Items"`, so **an ordered item that is never linked contributes nothing** — invisible on the item axis while looking correct on the document axis. That is why `lib/materialsCache.js` links *every* ordered item of a material, not just the one whose price won its dedupe.
- **Written in exactly two places (#18):** `upsertMaterial` (identity, find-or-create) and `upsertMaterialPrice` (price). Both go through `lib/materialsCache.js`, whose only caller is PO generation.
- **NEITHER TABLE IS THE PRICE-HISTORY SOURCE, and saying so is what stops a reader taking `Material Prices` for one.** History is read from **PO Items** through #18's `PO Items` link (#19) — see "Material price screens" above, where the same sentence appears as the rule the screens obey. `Material Prices` is a latest-value cache: one row per item × vendor, overwritten. The two lookups on it, `Material Record ID` and `Vendor Record ID`, are what make a row findable at all, because `filterByFormula` cannot compare a link field to a record id — the same exception CLAUDE.md records once for parent-link filtering and does not repeat per table. Moved out of CLAUDE.md's Data model in the routing pass after #263, where it was rationale under a list that carries name, type and link topology.
- **`Item Name` was not rewritten on a match — the first spelling recorded won, and #356 ended the rule by ending the field.** A name is not a latest-value field: rewriting it per PO would let one requester's capitalization overwrite another's and change the row's label under anything referencing it. An item catalog with a dropdown would become the authority; until then first-seen is at least stable, and the lookup was case-insensitive precisely so the two need not agree. **That catalog exists**, so `Item Name` is a lookup through `Category` and the catalog IS the authority — a path HQ renames renames every material under it, which is the behavior first-seen-wins was standing in for. Kept rather than deleted because it is the argument that decided the shape of the replacement, and because the same reasoning still governs `Size`.
- `Unit: ""` is not "no value" on a single select but a request to create an empty option, refused with `Insufficient permissions to create new select option ""` (measured), so the key is omitted instead, exactly as prItems.js/poItems.js do (#111). **`typecast` is deliberately not used on this path**: it would make that write succeed by inventing an option, which is how a canonical list silently gains a 20th value.
- `getMaterialByKey` interpolates the key into a `filterByFormula` string, so it escapes through `formulaString` — this company writes pipe sizes as `2"` / `4"`, and an unescaped quote closes the formula early (422 `INVALID_FILTER_BY_FORMULA`).
- **A unit-less item is skipped by the cache, not cached (#18).** Nothing is lost — the cache holds only latest values and the history is in PO Items — while a unit-less row would be unusable on #19's price screen, since a unit price without a unit compares to nothing. Reachable today only because a PR Item's `Unit` is not required at final submission; when it is, the branch becomes unreachable and the skip can be tightened into a throw. Deliberately not a throw today: a reachable throw there would fail a legitimate approval.
- **`Signed Qty` HAS NO READER AND IS KEPT, WHICH IS THE ONE AUDIT ANSWER THAT IS NEITHER A DELETION NOR A CALLER (#182).** Measured on the base: `Materials."Signed Qty"` is referenced by no formula, rollup or lookup, and `recordToMaterial` carries it to `signedQty`, which nothing under `app/` or `lib/` reads — its only reader anywhere is `verify-materials-cache-18.mjs`, which asserts the rollup is the signed subset. **#18 created it to keep a decision open for #20**, which is still open and is the issue before inventory: the materials cache is written at PO-GENERATION time, before the President signs, so `Committed Qty` counts an order that may never be signed and `Signed Qty` is the subset that has been. Committed minus Signed is the quantity awaiting signature. Which of the two "on order" should mean is exactly #20's question, and deleting the field would answer it by removing one of the options — for a rollup that costs nothing to keep, on a base with no production data. **What makes this a decision rather than a deferral is that it ends:** #20 picks one, and the field either gains a reader or goes in that issue. `offline/unread-exports.mjs` does not flag it — a field is not an export, and the property has a reader in the credentialed tier — so this paragraph is the whole of what holds it.
- **`Uninvoiced Qty` = Committed − Invoiced, and the name is the subtraction rather than a hope about it (#181).** It was `Outstanding Qty`, which named what someone wanted the figure to mean — ordered but not yet arrived — while the subtraction is the invoice one; and the same word was doing duty for a different subtraction on the delivery entry screen. **It remains an approximation of "ordered but not yet arrived", not a fact about it.** An invoice is an invoicing event, so goods can arrive before or after one. Packing lists would give the real delivery signal, and **when they exist this one formula is the single place that changes** — which is why the approximation is a formula over two rollups rather than a figure computed in JS at each reader. A negative value means more was invoiced than ordered and callers must surface it distinctly rather than folding it into "still uninvoiced", the same distinction `lib/poItemQty.js` makes per ordered item.

### Material categories (#354)

**HQ already maintains the tree, and this issue only moves it into the base.** 777 paths, four levels deep, one row per path with a code and an English name at every level. One flat table rather than four levelled ones: each row states its whole path, so a form narrows a level at a time from rows it already holds and no walk is needed. The source is `scripts/import/material_categories.csv`, committed, and `scripts/import/create_material_categories_354.mjs` is what puts it on the base — re-runnably, because the base is wiped and rebuilt and 777 rows re-entered by hand is 777 rows entered wrong.

- **THE CODES ARE TEXT AND THE REASON IS 427 ROWS.** Every level's code is fixed-width and zero-padded — `01`, `0101`, `0101001`, `0101001001` — and 427 of the 777 rows carry a leading zero at *every* level. A numeric column drops it, which makes `01` and `1` the same category and misfiles everything under it, and nothing downstream would say so: the import writes strings, Airtable stores strings, and a wrong string looks exactly like a right one. This is also the whole argument for creating the table through the API rather than uploading the CSV in the browser, since Airtable's own CSV import type-detects a column of digits as a number. The fields are declared `singleLineText` in the create payload, no `typecast` is used anywhere on the path, and both the offline and the credentialed check count the 427.
- **A LEAF CODE DOES NOT ENCODE ITS ANCESTORS, WHICH IS MEASURED RATHER THAN ASSUMED.** 11 of the 777 rows break prefix nesting outright: `4001001018` sits under a level-3 code of `4001003`, and the whole `95 Miscellaneous Construction Materials` branch carries level-2 codes from other branches' ranges (`1501`, `2404`, `2405`). So "the categories under this branch" cannot be answered by slicing a string, and a category is narrowed by the stored level columns instead — which is what the issue means by a form narrowing "from rows it already holds". `offline/material-categories.mjs` asserts the 11 by count so the day somebody reads these codes as hierarchical they are told otherwise; if HQ ever regularizes the tree that assertion fails, which is the right outcome, because reading codes as a path should be a decision rather than an inheritance. The tree is well-formed in the way that matters: every code has exactly one parent code, at all three levels.
- **THE SEPARATOR IS ` > ` AND THE ALTERNATIVE WAS MEASURED, NOT ARGUED.** 28 of the 770 distinct category names already contain a spaced slash — `Bolts / Nuts / Washers`, `Slip On / RF`, `Machined / Fabricated` — spread across 85 rows, so a slash-joined path reads as more levels than it has: `Stainless Steel (SUS) / Pipe / SUS 304 / Machined / Fabricated` is four levels wearing five, on the document a vendor reads. The 14 names carrying an *unspaced* slash (`AP/MP`, `NBR/EPDM …`, `S/W 3000#`) collide with neither candidate and are not the reason. What settles it is not readability alone: no name contains an angle bracket at all, so joining with ` > ` is injective and two rows can share a label only by sharing all four segments. Under ` / ` today's 777 labels are also unique — but that is a property of today's data, and `["X / Y", "Z"]` against `["X", "Y / Z"]` is a collision waiting for a row HQ has not added yet. The base's other `X Label` formulas join with `_` (`Material Label`, `Discipline Label`); this one is read by a vendor rather than by a lookup, and the underscore form was rejected for that reason.
- **THE LABEL IS A FORMULA BECAUSE PATHS ARE ADDED BY HAND.** #355 records that a path the tree does not have is asked for by the site and added to the catalog directly — so a stored text label would have to be typed by whoever adds the row, and typed wrong eventually. A formula means the person adding a path fills in eight columns and the label follows. That is also why the label is the PRIMARY field: a link renders its target's primary, and `Materials."Category"` showing `0101002002` instead of the path would be useless in the UI and in every `getLinkedRecords` result.
- **WHICH FORCES ONE HAND STEP, AND IT IS THE ONLY ONE.** Airtable documents `formula`, `rollup`, `count` and lookup as read-only field types, so a formula field cannot be CREATED through the Metadata API (**the lookup half of that reading is false and #356 measured it — see `airtable-access.md`'s tenth entry; the formula half stands, which is what this paragraph rests on**); and a field's TYPE cannot be PATCHed either (422, "Changing a field's type or number precision is not currently supported"). But an existing formula field's `options.formula` PATCHes cleanly — 200, measured in #281 on `PO Items."Signed Qty"`. So the run is two phases: the script creates `Category Label` as `singleLineText`, Soo converts it to a formula in the UI with any expression at all, and the second run PATCHes the real one and loads the rows. **The script refuses to write rows while the field is still text**, because 777 rows with an empty primary is a worse state than none — and no API deletes a table.
- **THE RULE IS IN TWO PLACES AND THE DUPLICATION IS STRUCTURAL.** `lib/materialCategory.js` holds it in JavaScript and generates the Airtable expression from the same three constants, so the two cannot drift by an edit; the base computes every label from the expression and nothing in this repository ever writes one. `filterByFormula` cannot call JavaScript and a formula cannot call `composeCategoryLabel`, so there is no measurable condition whose lifting would merge them — the same shape #244 recorded for `PO Items."Has Uninvoiced Qty"` against `lib/poItemQty.js:hasUninvoicedQty`, and the same answer: nothing re-derives the rule, and a credentialed check compares the two on live rows every run. `verify-material-categories-354.mjs` reads each row's four level values and its stored label and asks whether the JS rule composes the same string — the two sides were produced by different implementations on identical inputs, which is the only reason the comparison says anything.
- **THE RULE ITSELF, and the clause the two readings disagree about.** First level always; then each following level unless it is blank, is `Standard` or `Other`, or repeats **the segment last kept** — not the previous level, which may itself have been dropped. `Standard` fires 141 times and `Other` 51. The two readings agree on all 777 rows committed today and diverge only on a path like `PVC / Pipe / Standard / Pipe`, where segment-last-kept gives `PVC > Pipe` and previous-level gives `PVC > Pipe > Pipe`; the first is what the issue states and is also the reading that cannot emit two identical adjacent segments. It costs the formula its size — Airtable has no variables, so the last-kept expression is substituted rather than named, and the fourth level's clause carries three copies of the second's. 1,162 characters, which is affordable precisely because it is generated: nobody edits it in the Airtable UI.
- **NOTHING TRIMS, ON EITHER SIDE.** An Airtable formula comparing two text fields does not trim, so trimming in JavaScript would make the two disagree on a value with a stray space — the one class of divergence the credentialed check exists to catch. The invariant is put on the DATA instead: the offline check asserts the committed CSV carries no leading, trailing or doubled whitespace in any of its 3,108 name cells, and the import script refuses a row that does, before its first call to the base.
- **WHAT #354 DELIBERATELY LEFT TO #356, and the name it fixes anyway.** `Materials` gains nothing here. Its `Category` link, its lookup of the leaf code, and the retype of `Item Name` from text to a lookup all land in #356 because the retype breaks `upsertMaterial`, `getMaterialByKey`, `recordToMaterial` and the `Material Label` formula the moment it happens — putting it here would leave `main` broken between two issues, which is the same-commit rule read from the side it is actually about. Adding a field breaks nothing, so the link and the lookup could have come early; they do not, because #356 has to open the Airtable UI for the retype regardless and there is no trip to save. **The leaf-code lookup is `Materials."Category Code"`**, recorded here rather than in #356's body so the name is fixed before four issues depend on it: on a `Materials` row there is only one code, so no qualifier is needed, and `Level 4` is the tree's word rather than the material's — "level 4 of a material" means nothing. `Material Label` becomes `ARRAYJOIN({Item Name}) & …` in the same issue; the bare form works too, since `Discipline Label` already concatenates a link field directly, but the explicit form does not rest on how a single-element array renders in string context. **#356 MEASURED IT AND LEFT THE FORMULA ALONE** — see the section below; the sentence stays because the reasoning it gives is the reasoning that was wrong, and knowing which half was wrong is what stops the next person re-deciding it from the documentation.

### A path this branch adds takes the 900 block (#355)

**A leaf the branch creates is its parent's `Level 3 Code` plus a three-digit number from 901 up** — `0101002` becomes `0101002901`, then `0101002902`. The site asks the office for a path the catalog does not have and the office adds it in Airtable, which is the normal way one arrives; this is what it types into the code cell.

- **THE SENTENCE LIVES ON THE FIELD, because that is where the person is.** `Material Categories."Level 4 Code"` carries it in its Airtable description, written by `create_material_categories_354.mjs` rather than typed into the browser — and that script SYNCS descriptions on every run now, not only on create. `naming.md` records why: three field descriptions written by `create_direct_purchases_272.py` still say a word the app retired, and editing the script alone would have left the two disagreeing forever. A description PATCHes at 200 (#283), so the sync costs one call per field that has drifted and none when nothing has.
- **AND NOT IN `lib/materialCategory.js`, WHICH IS WHERE IT WAS EXPECTED TO GO AND IS NOT WHERE IT WENT.** #355 implemented none of this: no code computed the next number, so a rule in that module's header would have been a claim its contents did not support. **#368 built the arithmetic and it is `lib/categoryCreation.js`** — the screen that narrows to a parent and computes the leaf needed a module of its own, the way `lib/addressCreation.js` and `lib/toolRegistration.js` did, and `lib/materialCategory.js` keeps the label rule and the walk. The field's description still says it, because that is where the person adding a path by hand is standing.
- **THREE REASONS, AND THE FIRST IS THE ONE THAT DECIDES.** HQ's tree is re-received periodically, and after a re-import there has to be a way to tell a branch-made path from an HQ one; the code is the only carrier, because Korean names are deliberately not stored and the mapping workbook's KR-EN sheet is keyed on codes — that sheet is the whole remaining correspondence and a later Korean label depends on it. Second, the code has to be typed anyway, so following the rule costs nothing and no cell can be forgotten. **A `Source` field was considered and rejected**: a blank on 777 imported rows would mean "HQ" only by convention, and a convention carried by an empty value is one nobody can read. Third, the rule appends to the parent, so every path this branch adds is prefixed by its level-3 code.
- **THE MARGIN IS MEASURED, NOT ASSUMED. HQ's highest last-three is 033** — not one of the 777 leaves reaches 100, let alone 900. `offline/material-categories.mjs` asserts the PREMISE rather than the practice: no committed leaf uses the 900 block, and the highest HQ tail is 33. Asserting the practice against live rows would be a false claim about HQ's tree the day HQ uses the range; asserting the premise fails exactly when a future import reaches into it, which is the moment to re-decide.
- **THE THIRD REASON IS MEASURED TOO, and it runs the opposite way from the 11.** Of the 777 rows, 11 break prefix nesting — but only **2 break it at the LEAF** (`4001001018`, `4001001020`); the other nine are at levels 2 and 3. So 775 of 777 leaves already begin with their level-3 code, and appending to the parent makes the leaf level MORE conformant rather than adding an exception. **HQ's 11 are not renumbered**: they have no symptom, `offline/material-categories.mjs` already blocks the prefix lookup that would care, and renumbering would spend the workbook correspondence to restore a rule nothing uses.
- **NOTHING ENFORCES UNIQUENESS, AND THAT IS WHY THE READ REFUSES.** Airtable cannot make a text field unique — the limit `tools.md` records for `Tools."Tool Name"` — and this app never writes a category row, so there is no write to serialize and none of `upsertMaterial`'s normalize-lock-compare shape can attach. Two rows sharing a leaf code would have been silent in the worst way: the picker dedupes by code and keeps the row whose label sorts first, while the write path's query has no sort at all, so the requester could pick one path and the link could point at the other — and `Item Name`, frozen from that row's label, is what the vendor reads. `getCategoriesByLeafCode` therefore throws and names both records. **#368 made that rare and not unnecessary:** an admin screen computing the number means nobody types one on the usual path, but hand editing the table stays possible, so the guard is no longer the common case and is the last net under it.

### Keying the material cache on the category (#356)

`upsertMaterial` found or created a material from the item name, size and unit a requester typed, so a material's identity was a spelling. Two typings of one thing were two rows, with separate price histories and separate quantity rollups behind them. Identity is `Category` + `Size` + `Unit` now; `Materials` gains a `Category` link and a `Category Code` lookup of the leaf code, and `Item Name` becomes a lookup of the composed label.

- **THE RETYPE IS THE FIRST TIME THIS PROJECT CHANGED AN EXISTING FIELD'S TYPE, AND THE RISK IS A DIFFERENT KIND.** Adding a field breaks nothing; a retype breaks every reader at the same instant — `upsertMaterial`, `getMaterialByKey`, `recordToMaterial` and the `Material Label` formula, which is the list #354 wrote when it deferred this. Airtable refuses a type change through the Metadata API (422, "Changing a field's type or number precision is not currently supported"), so it is a hand step in the UI, which is where the window comes from.
- **THE WINDOW COLLAPSES TO NOTHING BECAUSE THE CODE TAKES BOTH SHAPES, and the ordering is what buys that.** `Category` and `Category Code` are ADDITIVE and go on the base first, with the 34 existing rows backfilled from the name each already carried; the commit lands next and reads them; the `Item Name` retype comes last. In between, the committed code is already correct: it matches on `Category Code`, never writes `Item Name`, and reads it through a coercion that takes a string or a single-element array. A material created in that window has a blank `Item Name` and a `Material Label` of `_Size_Unit` — and the retype fills both, because nothing stores either. **The reverse order is strictly worse:** the old code writes `Item Name`, Airtable 422s on a computed field, `refreshMaterialsCacheForPO` catches it per entry, and `PO Items."Material"` silently stops being written — an order correct on the document axis and absent from the item axis.
  - **NO FROZEN COPY IS AT RISK, AND THAT IS A TRACE RATHER THAN AN ASSUMPTION.** The window's blank name is on `Materials` only. Every item table's `Item Name` is frozen from the one above it — `PR Items` from the category label at save, `PO Items` from the PR item, `Delivery Items` and `Invoice Items` from the ordered item — and the chain never passes through `Materials`. `Materials."Item Name"` is read by two screens and copied nowhere; the demo seeds take `material.id` and never its name.
- **THE BARE FORM STAYS AND `ARRAYJOIN` WAS NOT USED, WHICH IS A MEASUREMENT REVERSING A PRE-MEASUREMENT JUDGMENT.** #354 recommended `ARRAYJOIN({Item Name}) & …` on the ground that the bare form "does not rest on how a single-element array renders in string context" — but this base already rests on exactly that, load-bearingly. `PO Items."PO Status"` is a lookup whose raw value is `["Withdrawn"]`, and `Committed Qty` is `IF({PO Status} & "" = "Withdrawn", 0, {Qty})`. Measured on live rows across all three statuses: `["Withdrawn"]` gives `Committed 0` against `Qty 10`, `["Signed"]` gives `10`, and `["Awaiting Signature"]` gives `Committed 10` with `Signed 0`. A bracketed or quoted rendering would make that equality false and leave `Committed Qty` at 10 on the withdrawn row. So a single-element lookup concatenates BARE, the formula needs no change at all, and `verify-materials-cache-18.mjs` Part A2 asserts on a live row that the composed label carries no `[`.
- **A LOOKUP FIELD CAN BE CREATED THROUGH THE METADATA API, WHICH THIS PROJECT BELIEVED IT COULD NOT.** `airtable-access.md` read Airtable's "read-only field type" as "not creatable"; `add_material_category_356.mjs` attempted it and got 200, with `options.recordLinkFieldId` and `options.fieldIdInLinkedTable`. Read-only means no record write may carry a value, not that the field cannot be declared. That removed one of the three hand steps. The attempt stays in the script rather than becoming an unconditional create, because a refusal there prints the response and falls through to the hand step instead of failing the run.
- **THE CATEGORY REACHES THE CACHE IN MEMORY AND `PO Items` GAINS NO FIELD.** `lib/poGeneration.js` pairs each created ordered item with the `Category` link of the request item it was copied from, in the loop that creates it, so the pairing needs no read and cannot pair the wrong two; `lib/materialsCache.js` then resolves those record ids to leaf codes in ONE batched query per order, because the key is the code and a request item stores the id. A `PO Items."Category"` field was weighed: it would follow the frozen-copy convention, but the order already reaches its catalog path in one hop through `Material`, and it would be a fourth schema change and a second hand toggle for no reader today. **The condition for adding it is a second consumer that needs an order's catalog path without loading its material.**
- **THE FIND-OR-CREATE NOW FILTERS ON A COMPUTED FIELD, AND THAT IS THE ONE BEHAVIOR CHANGE WORTH MEASURING RATHER THAN ARGUING.** `getMaterialByKey` matched a plain text field before; it matches the `Category Code` LOOKUP now, and a `filterByFormula` over a computed field is answered from the query index this file's own client note says can briefly miss a just-written record — so a second `upsertMaterial` seconds after the first could in principle create a duplicate. Measured directly: a fresh key, the create, then the read with nothing awaited between. **The row came back on the FIRST read and the second upsert returned the same row.** `verify-materials-cache-18.mjs` Part A re-measures it every run through the same pair of calls. This is the same answer #244 Part E got one level up for a rollup, and the reachable case is covered by `withKeyLock` regardless.
- **THE CASE-INSENSITIVE COMPARISON SPLIT THREE WAYS RATHER THAN GOING.** The code is compared EXACTLY — it is picked from the tree and typed on no path this app offers, which is the whole point of keying on it. `Size` keeps `normalizeItemText` plus `LOWER(TRIM(...))` on both sides, because it is still free text and is where the remaining duplication lives; `lib/prItemMerge.js` had already said so from the request side. `Unit` keeps the fold too, and that one is deliberate rather than inherited: the 19-value select makes variance unreachable through the app, but `DRUM` is the precedent for an option added by hand in Airtable that no file-only check can see, and the lock key and the formula have to normalize alike or two concurrent creates stop serializing against each other.

The formula TEXT stays in `materials.js`: `offline/formula-escaping.mjs` accepts a whole-formula builder only from `lib/airtableFormula.js`, so a complete predicate built in the identity module would fail it closed — correctly, since the check cannot see whether anything inside was escaped. So this module owns the VALUES and the query owns the text that escapes them.

The guarantee is one-directional and both halves are worth stating: since #356 a material's identity IS its category, so **if there is a material it has a category** — but `collectMaterialsCacheEntries` skips an ordered item with no Unit or no numeric Unit Price, so there may be no material at all. ### Matching the search against the composed path (#357)

`searchMaterials` AND-s typed tokens as case-insensitive substrings of `Material Label`, which held the requester's own words until #356 and holds a composed category path now. So a word found a row because somebody had typed it on a request; it finds one because HQ's tree uses it. The rule itself is unchanged, and the three things that had to change around it are here.

- **THE RULE STAYS, AND THE ALTERNATIVE WAS MEASURED RATHER THAN ARGUED AWAY.** A substring token reads differently against a path: `tee` matches 426 of the 777 committed paths and every one of the 34 rows on the base, through `s-tee-l` in the level-1 name every row carries. That is not rare — 50 of the 643 catalog words of three letters or more pull in rows that do not contain them as a word, and the collisions are words the tree itself uses (`lug` inside `Plug`, `male` inside `Female`, `din` inside `Welding`, `ring` inside `Measuring`). A word-boundary rule halves the damage: summed over all 643 words, free substring matches 1,406 rows that do not carry the word and a word-prefix rule matches 682. **It was rejected anyway, because it zeroes the queries a piping buyer actually types** — `304l` 32 paths → 0, `40` 41 → 0, `10` 67 → 7, since a grade reaches the tree only as the tail of `WP304L`, `F304L` and `SCH40`. A prefix-or-suffix rule keeps the grades and gives back most of the accidents (905). **What decides it is the asymmetry, not the totals: a false match is narrowed by typing another word, because every token narrows, and a missing match is recoverable by nothing.** The screen already carries the recovery — the truncation line asks for another word — which is why that sentence moved into the copy constant and is pinned.
- **THE SEPARATOR IS NOT A WORD.** ` > ` is on 765 of the 777 paths, so a token of `>` narrows nothing while spending a token slot, and the path is exactly what a reader has to paste: `Item Name` is frozen onto `PO Items` and printed on the purchase order the vendor reads, so looking a price up from a PO in hand means pasting a path. `buildSearchTokens` drops it, derived from `CATEGORY_LABEL_SEPARATOR` rather than written as a literal.
- **THE TOKENIZER ITSELF LEFT THIS SCREEN IN #325 AND THE TWO STEPS ABOVE STAYED.** The four document lists got a search box of their own, matching by the same rule, and writing a second tokenizer beside this one is the duplication CLAUDE.md forbids — so the fold, the AND, the substring and the empty case moved to `lib/searchTokens.js` and `buildSearchTokens` became a call to it. **What it passes are the two arguments that are this screen and not the rule:** the separator drop above, and `MAX_SEARCH_TOKENS`, whose derivation is a formula-length bound and so binds nothing for a box matching in the browser. `/materials` behaves identically and `offline/material-price-view.mjs` was not touched; `offline/search-tokens.mjs` is what holds the two callers to one rule.
- **THE TOKEN CAP WAS 6 AND TRUNCATED FROM THE WRONG END.** A path is a median of 9 words and up to 19, so a pasted one overflowed the cap — and the cap keeps the FIRST tokens, which are the outermost levels shared by every row in the branch, and drops the leaf, which is the only part that identifies. Measured on the base: the whole of `Stainless Steel (SUS) > Tee > SUS 304 > PTFE Lined` returned 25 rows and its last three words returned 2. The cap is 20 now and the figure is the longest label a reader can paste back — 16 distinct words in the longest committed path, plus the longest size on the base (`M16 x 1m`, three words) and a unit. `offline/material-price-view.mjs` re-derives the path half from the committed CSV and the assertion is exactly tight, so a deeper path from a future import fails the check instead of truncating a query in silence.
- **A MISS SAYS WHICH OF TWO THINGS IS TRUE, AND THE SPLIT WAS MEASURED BEFORE IT WAS BUILT.** The catalog can be asked whether the words name a category, which the label could not answer while it held what a requester typed. The worry was that one branch would never render on a base of 34 rows all under one level-1 branch, which would make the distinction code with no reader. Measured against what this company's people actually typed — the 41 item names the demo seeds carried before #358 replaced them with categories — **33 are misses and they split 17 to 16**; by single words, 43 misses split 31 to 12. Neither branch is rare, and the no-category side is not typos: `Cable Tray`, `EMT Conduit`, `Junction Box`, `Base Plate` and `Gate Valve` are ordinary materials whose words are absent from HQ's stainless-piping tree outright, and `Flange Gasket` is two words the tree does use with no single path carrying both. The two states have different next actions — ask the office to add a path, against wait until somebody buys one — which is the test a distinction has to pass.
- **THE PROBE IS ONE OPERATION AND ONLY ON A MISS**, `anyCategoryMatches` with `maxRecords: 1` and the same `andSearchAll` builder the materials query uses, so "the catalog has one" cannot disagree with "the search would have found it". Loading the tree to answer instead would be `getCategoryTree`'s 8 operations against a screen whose whole budget is 7.
- **A SIZE ALWAYS LANDS ON THE NO-CATEGORY SENTENCE, AND THE COPY SAYS WHAT TO DO ABOUT IT.** The tree names no dimension — 0 of the 777 paths carry `2"` or `3/4"` — so `pipe 2"` reaches that sentence even though 70 paths carry `Pipe`. **Narrowing the probe to the tokens that are category words was weighed and rejected**: nothing distinguishes a size from a word the tree simply does not use, so it would send `cable tray` to the in-catalog sentence, which is the one case the two states exist to keep apart. The sentence therefore tells the reader to try fewer words without a size, which is true whichever of the two put them there.
- **THE CATEGORY TREE IS NOT OFFERED AS A FILTER HERE, AND THE CONDITION FOR ADDING ONE IS RECORDED RATHER THAN LEFT TO TASTE.** `Materials` is 34 rows and every one of them is under `Stainless Steel (SUS)`, so a level-1 filter would offer exactly one option; the tree holds 777 paths of which at most the bought ones would return a row, so most options would lead to an empty result and teach the reader not to use the control; and `getCategoryTree` costs 8 operations against this screen's 7, paid on every load whether or not anyone narrows. **The condition is that `Materials` carries rows under more than one level-1 branch. When it does, the filter's options come from the materials already fetched and not from the tree** — that costs nothing, and it cannot offer a branch with no rows behind it.
- **WHAT NO OFFLINE CHECK CAN ASK, and the first version of the check pretended it could.** Whether an example query finds a ROW is a fact about the base: `pipe 2"` was the search box's example and matched nothing the moment the label became a path — not because `Pipe` is missing from the tree but because nothing at that size had been bought. The first draft of `offline/material-price-view.mjs` appended a synthetic `_2"_EA` to every committed path so a size token would have somewhere to land, which handed it a match for free and passed on the very example it was written to catch. What is offline is whether an example is made of the catalog's words and spans the size segment; the rest belongs to the browser.

The field's own description on the base says so, because that is where the person adding a path is standing.
- **THE `Template` COLUMN IS CARRIED IN THE CSV AND NOT IMPORTED.** It records which of the eight shapes produced a name, which is provenance for whoever maintains the catalog and not a value this app has any reading of. ### Naming a material by its item name everywhere a document shows one (#416)

An ordered item froze `Category Label` as its name, so a purchase order sent a vendor `Stainless Steel (SUS) > Tube > SUS 304 > AP` and every document downstream carried the same string. `categoryItemFields` freezes the category's `Item Name` now — `Tube, SUS 304, AP` — `Materials."Item Name"` looks that field up rather than the label, and the 127 rows already frozen are rewritten to match.

- **ONE EXPRESSION CARRIED BOTH SCREENS, WHICH IS #367's PROPERTY PAYING OFF ON ITS FIRST TEST.** That issue paired the category link and the name into `categoryItemFields` so the two writes could not disagree; the request form's save and the signing chain's edit turn both go through it, so changing WHICH field is frozen was one line and both screens followed. None of the three reads a name, so nothing about what counts as one material, one merged request row or one folded invoice item moved.
- **THE PO PDF NEEDED NO WORK AND THE ARGUMENT IS RELATIVE.** `cellItem` is 27% of the content width and `Text` wraps, so a long name grows the row rather than overflowing — and **0 of the 777 names are longer than the path they replace** (99 characters at the longest against 146, 30 at the median against 55), so the column can only have got easier. What has never been measured is the ABSOLUTE question: how many lines the longest one takes and whether that is acceptable. That gap is recorded in `lib/poPdf.js`'s header rather than filed, because it is a risk nobody has observed.

### Adding a path from the app (#368)

A path the tree did not have was added by hand in Airtable: four codes, four names and an item name in a person's typing, with three rules held nowhere but in a note and in `Level 4 Code`'s own field description. `/admin/categories/new` applies them — the parent is picked, the codes are computed, the name is drafted and typed over, and the two strings a document will carry are shown before the row is written.

- **THE SCOPE IS A LEAF UNDER AN EXISTING LEVEL 2, AND THE BOUNDARY IS THE CODE WIDTH RATHER THAN A PREFERENCE.** The codes are 2, 4, 7 and 10 digits, so a level-3 or level-4 code's tail is three digits and a level-2 code's is two — and HQ already numbers into the 9 range at level 2. **Read off the live base rather than off the CSV:** `9591`, `9593`, `9594`, `9595` and `9797` are live level-2 codes, so the 900 block does not exist at that depth and a new level 1 or level 2 has no free range to take. Adding one is a different issue with a convention to decide first.
- **THE PREMISE WAS RE-MEASURED ON THE BASE BEFORE ANY OF THIS WAS BUILT, and every figure `offline/material-categories.mjs` holds over the CSV holds over the live table too:** 777 rows, 777 distinct leaf codes, 777 distinct item names — **distinct case-insensitively as well**, which is what makes this issue's case-folded duplicate gate admit no pair of existing rows — 0 leaf tails and 0 level-3 tails at 900 or above, and HQ's highest tail 33. `Item Name` is `singleLineText` and `Category Label` is a 1,205-character formula, both as the import script left them.
- **THE ARITHMETIC IS `nextSequence`'s RULE INSIDE A BLOCK.** The next code is the highest tail **at or above 901** plus one, or 901 when the parent has none; HQ's own numbering below the floor is not counted, so the block is numbered independently of whatever HQ put under the same parent. A gap in the middle is a free number rather than a wrong record — and reusing one is worse here than for a document id, because `Materials."Category Code"` looks a leaf code up, so re-issuing a deleted row's code would point a material's identity at a category it was not keyed on.
- **THE TAIL IS THE LAST THREE DIGITS AND NOT THE DIFFERENCE FROM THE PARENT**, because 11 of the 777 rows break prefix nesting and 2 of those break it at the leaf. So a sibling is read for the number in its own last three digits, which is its number within its parent whether or not the prefix agrees.
- **WHICH IS ALSO WHY THE COMPUTED CODE IS RE-ASKED OF THE BASE BEFORE THE WRITE, and that is a different question from the one the plan already answered.** The plan numbers the code among the chosen parent's CHILDREN; what has to be true is that no row anywhere carries it, and the same 11 rows are the reason those are different populations. The re-check also narrows the window `withKeyLock` cannot close. **It cannot close it either, and the copy says so**: the ordinary cause of a collision is a concurrent submission, where re-submitting works, and the other is a row filed under another branch carrying the code, where it does not — so the sentence does not promise that a second attempt succeeds.
- **THE END OF THE BLOCK IS A REFUSAL AND NOT A FOURTH DIGIT.** `Level 4 Code` is ten digits on every row and the offline check asserts that per level, so widening would break the assertion that makes these codes readable as text at all. Unreachable in practice — 99 slots under every parent against HQ's own 33 — and the alternative to refusing is writing a shape nothing else on the base has.
- **ONE LOCK FOR THE WHOLE TABLE, WHERE THE TWO MATERIAL LOCKS ARE PER KEY, AND THE REASON IS WHAT THE INVARIANTS ARE ABOUT.** `upsertMaterial` locks on a material's own key because two different materials must not serialize against each other. Both invariants this write defends are table-wide — a leaf code names one category, and an item name names one category — so there is no second key to split on, and two people adding paths under two different branches serializing costs nothing: one office, one screen, and a path arrives when the site asks for one. It also keeps the write to a single lock, which is what CLAUDE.md's no-nesting rule needs; nothing on the path takes a second, since `Material Categories` mints no `X ID` and `generateChildId` is never reached.
- **RESOLVE-OR-MINT AT LEVEL 3, AND A MEASUREMENT DECIDES IT RATHER THAN THE ISSUE BODY'S WORDING.** A new leaf needs a level-3 code as well as a level-4 one, so the obvious reading of "the codes are computed from the parent and the 900 block" is that both are minted. **No parent in the committed tree carries two children of the same name, at any level** — 0 of 225 level-2 parents, 0 of 513 level-3 parents, 0 at level 1 — and the requester's picker narrows on the CODE while showing the NAME, so a second `Pipe Hanger` under one level 2 would put two indistinguishable options in front of every requester and the link would follow whichever the picker's tie-break kept. So a level-3 name that matches a sibling takes that sibling's code, which is the one code on this screen that is read rather than computed. Nothing is typed either way, which is what the body's sentence is about.
- **AND THE SAME RULE COVERS THE MARK, WHICH IS WHY THERE IS ONE CLAUSE AND NOT TWO.** "No division at this level" is exactly the set of names the label formula drops — `CATEGORY_LABEL_SKIPPED`, which is `Standard` and `Other` — so a mark matches a sibling carrying EITHER and mints `Standard` only when the parent has neither. A parent already carrying HQ's `Other` therefore does not gain a `Standard` beside it: both drop out of the path, so two of them are two options that mean the same thing. **What this office writes is `Standard` alone**, because nothing in the data says how the two differ: 126 rows fill level 3 or level 4 with one of them (L3 `Standard` 32, L3 `Other` 16, L4 `Standard` 107, L4 `Other` 13).
- **THE SCREEN NEVER SAYS `Standard`, AND THE READER'S EVIDENCE IS THE PATH.** The option and the checkbox both read `No division at this level` — the meaning the word actually carries — and one sentence under either says `A level with no division below it is left out of the path.` The preview's second line is where the consequence is visible. The stored word is in this file, in the module, and in the base; a screen that offered it as a choice would be asking a person to pick a placeholder.
- **A LEVEL-4 NAME THAT ALREADY EXISTS IS A REFUSAL WHERE A LEVEL-3 ONE IS A CHOICE, and that asymmetry is the shape of the screen.** At level 3 an existing child is what the new leaf hangs off; at level 4 it means the row is already there — all four names equal is one path and would be two rows carrying one label, and the 777 labels are distinct. So the level-3 control offers the parent's children and the level-4 control lists them instead, `/addresses/new`'s panel one axis over: the person is one keystroke from a path that already exists, and the empty case is a sentence because an absent list cannot be told apart from one that looked and found nothing.
- **THE DRAFTED NAME IS HQ's COMMONEST TEMPLATE, READ OUT OF THE CSV RATHER THAN INVENTED.** The `Template` column records which of eight shapes produced each name and 360 of 777 are shape A, which is the level names below the first joined with `, ` — the same three clauses the label rule drops. So `draftItemName` is `keptCategorySegments` without its first element, which is why the draft and the label cannot disagree about which levels count, and why `composeCategoryLabel` was split rather than copied. **Measured: it reproduces the stored name on 347 of the 777, and on 285 of the 360 written with that template** (27 of 27 of template E, 22 of 63 of F). **That is the whole argument for a draft rather than a computation** — 430 names are not what any rule produces, which is #415's finding and the reason the field is stored at all. It is empty on 12 rows, whose label collapses to a single segment.
- **THE BOX MIRRORS THE DRAFT UNTIL SOMEBODY TYPES IN IT AND IS THEIRS AFTER THAT**, and a line under it says so while it is still the draft. The alternative — a draft that keeps overwriting as the levels change — is a form that silently edits what a person wrote, and the alternative to that is a button nobody would press twice.
- **THE PREVIEW IS THE PLAN, WHICH IS WHAT MAKES IT HONEST.** The form runs the same `planCategory` the action runs, against the tree the page loaded, so the two lines are the values that will be written rather than a second derivation of them — and the refusals the loaded tree can already see (an existing path, a parent with no code left) are said while there is still time to act on them. `resolveCategoryNames` is split out of the plan because the item name is drafted FROM the four names, so a form that could only reach them through the plan would need a name before it could propose one.
- **TWO LINES, AND THE PATH IS ON PURPOSE.** The first is the string every document will freeze (#416); the second is where the row sits, which reads differently from the four chosen names because a placeholder and a repeat drop out. No document screen carries a path and `/materials` searches one without showing it — **this screen is the exception, because it is the only place a row is planted in the tree and there is no other way to see where.**
- **AND THE COMPUTED CODE IS DELIBERATELY NOT IN THE PREVIEW.** The server settles it inside the lock, so a line promising `…901` would be contradicted by a row landing on `…902` the first time two people add a path under one branch — a preview that cannot keep its promise is worse than no preview. The account of what was written names the code instead, where it is a fact rather than a forecast, and where it is what somebody looks the row up by in Airtable.
- **ADMIN, AND `/addresses/new` IS THE CONTRAST RATHER THAN THE PRECEDENT.** Gating to Admin scopes a screen to the office; #384 put address creation outside `/admin` because where material goes is the site's own fact. The catalog is the opposite — the site asks for a path and the office adds it, which is what #355 already recorded as how one arrives. **There is deliberately no path from inside the request form**, per the issue: a requester who cannot find a category asks, and a requester editing the catalog is a different job.
- **THE DUPLICATE-NAME REFUSAL NAMES THE CATEGORY THAT HOLDS THE NAME, AND THAT WAS CHECKED AGAINST THIS APP'S SCOPE RULES RATHER THAN ASSUMED.** CLAUDE.md's rule that a refusal must not confirm a record exists outside somebody's scope is about the three documents that carry a per-record gate. **`Material Categories` carries no gate anywhere in this app, and there is no field a scope could be computed from** — the live table holds `Category Label`, the eight level columns, `Item Name` and the two reverse links, and no owner, job or user among them, where `canViewPR` reads a requester and a job and `canAccessJobDeliveries` reads a job. **It is also already fully readable by every active user:** `getCategoryTree` has two callers, `/prs/new` and `/prs/[prId]`, both gated by `requireUser()` and neither filtering rows, and it hands all 777 rows' labels, item names and level names to a Client Component — the picker renders the names at every level and the resolved item name beside them. So the sentence tells its Admin reader nothing they could not read from the request form, which is what lets it name the useful thing instead of a not-found.

It can now, so the base can diverge from the file, and `verify-material-categories-354.mjs` asserts both clauses over live rows as well: one field added to a projection it already makes, for no extra operation.
