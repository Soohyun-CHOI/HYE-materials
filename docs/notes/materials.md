# Materials and the item axis — the reasoning

Governs `app/materials/**`, `lib/material*.js`. **Read this before editing there** — CLAUDE.md carries only the rules that bind code outside this area; the derivation, the evidence and the alternatives weighed are here.

Moved verbatim out of CLAUDE.md — nothing in this file was rewritten. The migration was audited line by line and the result is in the pull request that created this file.

### Material price screens (#19)

`/materials` (search, grouped by item with a row per vendor) and `/materials/[materialId]` (one item's full purchase history, newest first). Both are pages, not modals — this repo's modals are confirmation dialogs (`modalStyles.js`) and every reading surface is its own route.

- **It reads the item axis, not PR Items.** Comparison figures come from **Material Prices**, history from **PO Items**, both reached through #18's `Material` link — never by matching `Item Name` text. A PR Item is a *requested* price, and an unapproved PR's price is one nobody ever paid.
- **Any active user, no Job scoping** — what a material costs is not a per-Job secret, and site staff pricing a job need it as much as the office. **The exception is document identifiers:** PO ID, PR ID and Job are shown only to a viewer who passes `canViewPR` on the source PO's parent PR, the same gate `app/pos/[poId]` uses. Price, vendor, date, quantity and PO status are open. A refused row renders `—` and still shows its price.
  - Enforced in `lib/materialHistory.js`, which builds an `identifiers` object or `null` per row. The gated PO ID is stripped from the history row after sorting, so no ungated copy of an identifier leaves the module even as a sort key.
- **The gate costs no per-row query.** `canViewPR` is pure and takes an already-loaded user and PR, so the module fetches whole levels — Materials, Material Prices, POs, PO Items, PRs, Vendors, Jobs — keyed on ids gathered from the level above. **Measured, not argued:** 7 Airtable operations for a 1-material/2-row search and **the same 7** for a 2-material/3-row one; history is 5 selects + 1 find (the material itself) regardless of ordered item count. `scripts/tests/verify-material-price-19.mjs` Part E re-measures it.
- **Search matching** uses #18's `normalizeItemText`, so the typed string and the stored name cannot disagree on case or spacing. Tokens are AND-ed as case-insensitive substrings of `Material Label` (`Item Name_Size_Unit`), so word order does not matter (`2" pipe` = `pipe 2"`) and each extra word narrows. A token can match the size or unit segment — a consequence of matching the label, accepted rather than fixed. Results are capped (25) and truncation is reported, because the follow-up batched queries fan out from these rows.
- **The date on a history row is the PO's `Created Date`.** A PO Item carries no date. `Created Date` is the moment the price was frozen onto the document, it is always present, and it is the same field `upsertMaterialPrice` stores as `Material Prices."Latest Date"` — so the comparison row and the history row cannot disagree about when a price happened. `President Signed At` was rejected because an Awaiting Signature PO has none, which would leave rows undated. It is calendar-only, so same-day rows tie; the tie-break is PO ID descending, monotonic within a day by construction.
- **Newest first, with the lowest price marked** rather than sorted to the top: a three-year-old price that happens to be lowest would otherwise take the most prominent row. The mark is a fact, not a recommendation — ties mark every tied row, and it is **omitted entirely when there is one vendor**, since "lowest of one" dresses a single data point as a comparison. When the rows' quantities differ the screen says the unit prices are not directly comparable and leaves the judgment to the reader.
- **Withdrawn and unsigned prices are shown with their status, not filtered.** `upsertMaterialPrice` writes at PO-generation time, so a vendor's newest price can come from an order later withdrawn — verified: a withdrawn PO's 41.00 is what the vendor's row carries. Whether an ordered item counts toward the order book is #18's `Committed Qty`, read via `countsAsOrdered`, never re-derived from the status string; the status tag is the *label* and comes from `PO Status`. The two deliberately come from different fields, each from where the fact lives.
- **The status tag is shown only for `Awaiting Signature` and `Withdrawn`; silence means `Signed`.** Nearly every ordered item is Signed, so tagging it puts noise on every row and buries the two states a reader actually has to account for. The rule is one pure function, `materialPriceView.js:statusTag`, shared by both screens.
- **The tag sits beside the VENDOR, not beside the PO ID it describes, and that is a measured layout decision.** In the Order column it wrapped: 168px of room against 214px needed for a PO ID plus a tag (and 228px on the history screen, where a Job code shares the cell) — visible only to a viewer who passes the identifier gate, since a refused row shows a short `—` instead. Reserving the width was the wrong fix because the majority of rows carry no tag at all. The Vendor column already had ~212px unused behind the longest vendor name, so the tag moved to where the slack was: nothing is reserved, and a tagged row is one line like every other (measured 29px throughout, with a full-length PO ID injected to reproduce the Admin view). The consequence "not counted as ordered" left the history rows for the same reason and is now stated once, as a footnote naming what the dimmed rows mean.
- **Every label therefore names its subject — `PO unsigned`, `PO withdrawn` — and that is the price of the move above, not decoration.** Beside a vendor name a bare `Withdrawn` reads as a fact about the VENDOR, i.e. a supplier we no longer buy from, which is a different and wrong claim. `Awaiting Signature` is not used verbatim because the label has to stay short enough that a long supplier name plus a tag still fits one line; the prefix costs ~18px, which is why the history screen's numeric columns were trimmed to give Vendor 272px against the 249px a 24-character name plus `PO withdrawn` needs. An **unrecognized** status renders as `PO: <status>` rather than being swallowed, so an option added to the Airtable field later shows up instead of vanishing — the failure mode #144 recorded for a denylist that admits whatever it does not name. The colon form is used there because an arbitrary option name cannot be relied on to read grammatically after a bare `PO`.
- **An empty query is a BROWSE, not an empty search.** The screen lists every indexed item under the search bar before anything is typed, so `searchMaterials` skips `filterByFormula` entirely rather than asking `andSearchAll` for a match-all — that builder's empty case is `FALSE()` on purpose, the right contract for a predicate but the wrong answer here. Browse order is alphabetical by `Material Label`, sorted **server-side** so the 25-row cap takes the first N of a stable order rather than an arbitrary N. Most-recently-priced would be more useful, but the dates live one level down in Material Prices, which is fetched *after* the cap, so ordering by them would mean capping on a figure that query cannot see.
- **That leaves two empties, and they must not read alike:** nothing matched what was typed, and nothing indexed at all. The second only renders while `Materials` is genuinely empty and explains that the list is built as new POs are generated — because "no results" here does **not** mean the item was never bought. ordered items created before #18 carry no `Material` link and were not backfilled, so an empty screen is the expected state on a base whose PO Items table is not empty.
- **The `Lowest` tag sits before the price, and that is an alignment fix rather than a preference.** With the tag *after* the price in a right-aligned cell it pushes the badged row's number left of its neighbours — measured at 596.05 against their 600.05, a visible 4px break in the column. Before the price, the tag grows leftwards into the column's slack and every row's number ends on the same edge (measured identical to 2dp across every group).
- **Both screens' tables are `table-fixed` with a declared `colgroup`, so no cell's content can decide a column's width.** The search page renders one table PER item group, and an auto-layout table sizes columns from its own rows, so three groups came out three different shapes. Declared widths make them identical across groups — measured `[352, 144, 64, 112, 160]` for all three, with every price and every quantity ending at the same x — and they also mean a status tag or a long vendor name cannot move a column. Widths were set from measured content rather than guessed: every column clears its widest realistic cell (a 24-character supplier name plus a tag, a full PO ID, a `$40,959.00`) by 11–103px, and `Unit price` is sized by its HEADER rather than its figures.
- **Column order differs between the two screens on purpose.** The search table runs `Vendor | Unit price | Qty | Date | Order`; the history table, like `app/prs/[prId]`, `app/pos/[poId]` and `app/invoices/[invoiceId]`, runs `Qty | Unit price | Amount`. Those three carry an **Amount** column, so qty-then-price reads as the equation `Qty × Unit Price = Amount` — the history table has Amount and follows them. The search table has no Amount and exists to compare prices, so the price leads and the quantity follows it as the caveat that qualifies it. Adjacency is the shared property; the order within it is decided by whether an Amount column is there to close the equation.
- **Both tables also carry `min-w-[52rem]`, and dropping it breaks them in a way that is easy to miss.** `w-full` alone lets the table shrink below the sum of its declared columns, and the one flexible column (Vendor) absorbs the shortfall — at 375px it collapsed to nothing and every vendor name wrapped, taking rows from 29px to 69px. The minimum keeps the desktop layout intact and hands the overflow to the `overflow-x-auto` wrapper each table already sits in, so the page body never scrolls sideways (measured at 375px). Consequence: below roughly a 900px viewport the table scrolls horizontally, since `max-w-4xl` minus `p-8` leaves exactly 832px.
- Reached from the home page; the app has no navigation shell, so one link there rather than inventing a nav bar.

**Material Prices**: item × vendor (#18). Natural key = Material + Vendor. `Price Label` (primary, formula over the two links), `Material` / `Vendor` (links, single), `Unit Price`, `Latest Date` (calendar), `Latest PO` (link), and `Material Record ID` / `Vendor Record ID` lookups. Those two lookups are what make a row findable at all — `filterByFormula` cannot compare a link field to a record id, the same exception already recorded for parent-link filtering. Still a latest-value cache, not history.

### Materials

- **Why the split.** The three things Phase 4 serves have two different axes. Price is only meaningful per vendor — "what does this cost" has a different answer per supplier. Purchase history and on-order quantity are the opposite: they must aggregate *across* vendors, because "how much of this do we have on order" does not care who supplies it. One table cannot be keyed both ways, so identity + cross-vendor quantity live here and the per-vendor price lives in **Material Prices**.
- **`PO Items.Material` is what makes the item axis exist**, and the only alternative was matching on `Item Name` text — the approach `getInvoicingStatusByPO` cites "no name/similarity matching" as its own justification for avoiding. Its consequence: the quantity rollups traverse `Materials."PO Items"`, so **an ordered item that is never linked contributes nothing** — invisible on the item axis while looking correct on the document axis. That is why `lib/materialsCache.js` links *every* ordered item of a material, not just the one whose price won its dedupe.
- **Written in exactly two places (#18):** `upsertMaterial` (identity, find-or-create) and `upsertMaterialPrice` (price). Both go through `lib/materialsCache.js`, whose only caller is PO generation.
- **NEITHER TABLE IS THE PRICE-HISTORY SOURCE, and saying so is what stops a reader taking `Material Prices` for one.** History is read from **PO Items** through #18's `PO Items` link (#19) — see "Material price screens" above, where the same sentence appears as the rule the screens obey. `Material Prices` is a latest-value cache: one row per item × vendor, overwritten. The two lookups on it, `Material Record ID` and `Vendor Record ID`, are what make a row findable at all, because `filterByFormula` cannot compare a link field to a record id — the same exception CLAUDE.md records once for parent-link filtering and does not repeat per table. Moved out of CLAUDE.md's Data model in the routing pass after #263, where it was rationale under a list that carries name, type and link topology.
- **`Item Name` is not rewritten on a match — the first spelling recorded wins.** A name is not a latest-value field: rewriting it per PO would let one requester's capitalization overwrite another's and change the row's label under anything referencing it. An item catalog with a dropdown would become the authority; until then first-seen is at least stable. The lookup is case-insensitive precisely so the two need not agree.
- `Unit: ""` is not "no value" on a single select but a request to create an empty option, refused with `Insufficient permissions to create new select option ""` (measured), so the key is omitted instead, exactly as prItems.js/poItems.js do (#111). **`typecast` is deliberately not used on this path**: it would make that write succeed by inventing an option, which is how a canonical list silently gains a 20th value.
- `getMaterialByKey` interpolates the key into a `filterByFormula` string, so it escapes through `formulaString` — this company writes pipe sizes as `2"` / `4"`, and an unescaped quote closes the formula early (422 `INVALID_FILTER_BY_FORMULA`).
- **A unit-less item is skipped by the cache, not cached (#18).** Nothing is lost — the cache holds only latest values and the history is in PO Items — while a unit-less row would be unusable on #19's price screen, since a unit price without a unit compares to nothing. Reachable today only because a PR Item's `Unit` is not required at final submission; when it is, the branch becomes unreachable and the skip can be tightened into a throw. Deliberately not a throw today: a reachable throw there would fail a legitimate approval.
- **`Uninvoiced Qty` = Committed − Invoiced, and the name is the subtraction rather than a hope about it (#181).** It was `Outstanding Qty`, which named what someone wanted the figure to mean — ordered but not yet arrived — while the subtraction is the invoice one; and the same word was doing duty for a different subtraction on the delivery entry screen. **It remains an approximation of "ordered but not yet arrived", not a fact about it.** An invoice is an invoicing event, so goods can arrive before or after one. Packing lists would give the real delivery signal, and **when they exist this one formula is the single place that changes** — which is why the approximation is a formula over two rollups rather than a figure computed in JS at each reader. A negative value means more was invoiced than ordered and callers must surface it distinctly rather than folding it into "still uninvoiced", the same distinction `lib/poItemQty.js` makes per ordered item.

### Material categories (#354)

**HQ already maintains the tree, and this issue only moves it into the base.** 777 paths, four levels deep, one row per path with a code and an English name at every level. One flat table rather than four levelled ones: each row states its whole path, so a form narrows a level at a time from rows it already holds and no walk is needed. The source is `scripts/import/material_categories.csv`, committed, and `scripts/import/create_material_categories_354.mjs` is what puts it on the base — re-runnably, because the base is wiped and rebuilt and 777 rows re-entered by hand is 777 rows entered wrong.

- **THE CODES ARE TEXT AND THE REASON IS 427 ROWS.** Every level's code is fixed-width and zero-padded — `01`, `0101`, `0101001`, `0101001001` — and 427 of the 777 rows carry a leading zero at *every* level. A numeric column drops it, which makes `01` and `1` the same category and misfiles everything under it, and nothing downstream would say so: the import writes strings, Airtable stores strings, and a wrong string looks exactly like a right one. This is also the whole argument for creating the table through the API rather than uploading the CSV in the browser, since Airtable's own CSV import type-detects a column of digits as a number. The fields are declared `singleLineText` in the create payload, no `typecast` is used anywhere on the path, and both the offline and the credentialed check count the 427.
- **A LEAF CODE DOES NOT ENCODE ITS ANCESTORS, WHICH IS MEASURED RATHER THAN ASSUMED.** 11 of the 777 rows break prefix nesting outright: `4001001018` sits under a level-3 code of `4001003`, and the whole `95 Miscellaneous Construction Materials` branch carries level-2 codes from other branches' ranges (`1501`, `2404`, `2405`). So "the categories under this branch" cannot be answered by slicing a string, and a category is narrowed by the stored level columns instead — which is what the issue means by a form narrowing "from rows it already holds". `offline/material-categories.mjs` asserts the 11 by count so the day somebody reads these codes as hierarchical they are told otherwise; if HQ ever regularizes the tree that assertion fails, which is the right outcome, because reading codes as a path should be a decision rather than an inheritance. The tree is well-formed in the way that matters: every code has exactly one parent code, at all three levels.
- **THE SEPARATOR IS ` > ` AND THE ALTERNATIVE WAS MEASURED, NOT ARGUED.** 28 of the 770 distinct category names already contain a spaced slash — `Bolts / Nuts / Washers`, `Slip On / RF`, `Machined / Fabricated` — spread across 85 rows, so a slash-joined path reads as more levels than it has: `Stainless Steel (SUS) / Pipe / SUS 304 / Machined / Fabricated` is four levels wearing five, on the document a vendor reads. The 14 names carrying an *unspaced* slash (`AP/MP`, `NBR/EPDM …`, `S/W 3000#`) collide with neither candidate and are not the reason. What settles it is not readability alone: no name contains an angle bracket at all, so joining with ` > ` is injective and two rows can share a label only by sharing all four segments. Under ` / ` today's 777 labels are also unique — but that is a property of today's data, and `["X / Y", "Z"]` against `["X", "Y / Z"]` is a collision waiting for a row HQ has not added yet. The base's other `X Label` formulas join with `_` (`Material Label`, `Discipline Label`); this one is read by a vendor rather than by a lookup, and the underscore form was rejected for that reason.
- **THE LABEL IS A FORMULA BECAUSE PATHS ARE ADDED BY HAND.** #355 records that a path the tree does not have is asked for by the site and added to the catalog directly — so a stored text label would have to be typed by whoever adds the row, and typed wrong eventually. A formula means the person adding a path fills in eight columns and the label follows. That is also why the label is the PRIMARY field: a link renders its target's primary, and `Materials."Category"` showing `0101002002` instead of the path would be useless in the UI and in every `getLinkedRecords` result.
- **WHICH FORCES ONE HAND STEP, AND IT IS THE ONLY ONE.** Airtable documents `formula`, `rollup`, `count` and lookup as read-only field types, so a formula field cannot be CREATED through the Metadata API; and a field's TYPE cannot be PATCHed either (422, "Changing a field's type or number precision is not currently supported"). But an existing formula field's `options.formula` PATCHes cleanly — 200, measured in #281 on `PO Items."Signed Qty"`. So the run is two phases: the script creates `Category Label` as `singleLineText`, Soo converts it to a formula in the UI with any expression at all, and the second run PATCHes the real one and loads the rows. **The script refuses to write rows while the field is still text**, because 777 rows with an empty primary is a worse state than none — and no API deletes a table.
- **THE RULE IS IN TWO PLACES AND THE DUPLICATION IS STRUCTURAL.** `lib/materialCategory.js` holds it in JavaScript and generates the Airtable expression from the same three constants, so the two cannot drift by an edit; the base computes every label from the expression and nothing in this repository ever writes one. `filterByFormula` cannot call JavaScript and a formula cannot call `composeCategoryLabel`, so there is no measurable condition whose lifting would merge them — the same shape #244 recorded for `PO Items."Has Uninvoiced Qty"` against `lib/poItemQty.js:hasUninvoicedQty`, and the same answer: nothing re-derives the rule, and a credentialed check compares the two on live rows every run. `verify-material-categories-354.mjs` reads each row's four level values and its stored label and asks whether the JS rule composes the same string — the two sides were produced by different implementations on identical inputs, which is the only reason the comparison says anything.
- **THE RULE ITSELF, and the clause the two readings disagree about.** First level always; then each following level unless it is blank, is `Standard` or `Other`, or repeats **the segment last kept** — not the previous level, which may itself have been dropped. `Standard` fires 141 times and `Other` 51. The two readings agree on all 777 rows committed today and diverge only on a path like `PVC / Pipe / Standard / Pipe`, where segment-last-kept gives `PVC > Pipe` and previous-level gives `PVC > Pipe > Pipe`; the first is what the issue states and is also the reading that cannot emit two identical adjacent segments. It costs the formula its size — Airtable has no variables, so the last-kept expression is substituted rather than named, and the fourth level's clause carries three copies of the second's. 1,162 characters, which is affordable precisely because it is generated: nobody edits it in the Airtable UI.
- **NOTHING TRIMS, ON EITHER SIDE.** An Airtable formula comparing two text fields does not trim, so trimming in JavaScript would make the two disagree on a value with a stray space — the one class of divergence the credentialed check exists to catch. The invariant is put on the DATA instead: the offline check asserts the committed CSV carries no leading, trailing or doubled whitespace in any of its 3,108 name cells, and the import script refuses a row that does, before its first call to the base.
- **WHAT #354 DELIBERATELY LEFT TO #356, and the name it fixes anyway.** `Materials` gains nothing here. Its `Category` link, its lookup of the leaf code, and the retype of `Item Name` from text to a lookup all land in #356 because the retype breaks `upsertMaterial`, `getMaterialByKey`, `recordToMaterial` and the `Material Label` formula the moment it happens — putting it here would leave `main` broken between two issues, which is the same-commit rule read from the side it is actually about. Adding a field breaks nothing, so the link and the lookup could have come early; they do not, because #356 has to open the Airtable UI for the retype regardless and there is no trip to save. **The leaf-code lookup is `Materials."Category Code"`**, recorded here rather than in #356's body so the name is fixed before four issues depend on it: on a `Materials` row there is only one code, so no qualifier is needed, and `Level 4` is the tree's word rather than the material's — "level 4 of a material" means nothing. `Material Label` becomes `ARRAYJOIN({Item Name}) & …` in the same issue; the bare form works too, since `Discipline Label` already concatenates a link field directly, but the explicit form does not rest on how a single-element array renders in string context.
