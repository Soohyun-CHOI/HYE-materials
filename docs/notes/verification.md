# Verification — the reasoning

Governs `scripts/**`. **Read this before editing there** — CLAUDE.md carries only the rules that bind code outside this area; the derivation, the evidence and the alternatives weighed are here.

Moved verbatim out of CLAUDE.md — nothing in this file was rewritten. The migration was audited line by line and the result is in the pull request that created this file.

### Verification tiers (#152)

Checks are split by **cost of execution**, not by issue. A cheap check welded into a script that writes to the shared base costs credentials and fixtures to reach, so it does not get run — and a check nobody runs is not a check. #152 is the precedent: six assertions sat invalidated for weeks, in two scripts reporting `SOME CHECKS FAILED` at exit 0.

- **`scripts/tests/offline/` — the standing tier.** Plain `node`, no env vars, no Airtable, no Blob, no dev server, no module loader, creates nothing. `npm test` runs all of it; `.github/workflows/checks.yml` runs `npm test` on every push and PR.
- **`offline-checks` is a required status check on `main`**, so this tier passing is a merge condition rather than advice. The name is the **job key** in `.github/workflows/checks.yml` — renaming that job renames the check GitHub reports, while the branch protection rule keeps waiting for the old name, and a PR then sits permanently "Expected — waiting for status to be reported" with nothing failing and no obvious cause. If the job is ever renamed, update the required-check setting in the same change. Each file exports `title` and `run({ check, log, assert })` and also runs standalone (`node scripts/tests/offline/source-shape.mjs`). The runner **scans** the directory rather than listing files, so a new check is in CI automatically — same reasoning as #147's enumerated inventory: anything that has to be registered somewhere can be forgotten. Files beginning with `_` are shared helpers (`_harness.mjs`, `_ast.mjs`). `fixture-cleanup.mjs` (#171) is the newest check: it walks every `verify-*.mjs` on the AST and requires each one that creates records to go through the fixture helper, with no `Promise.allSettled` whose results are discarded, no empty `catch`, and no `process.exit` above its cleanup call. **It carries no exemption list on purpose** — a script that cannot use the helper is evidence the helper is wrong, not a line to add. `product-name.mjs` (#201) is the second check with none, and it gets there a different way: it scopes itself to `app/` + `lib/` so that every legitimate spelling of a superseded name is outside it rather than excused within it. `us-english.mjs` (#215) is the third, by the same move and for the same reason — a British spelling has one legitimate use, being cited as the form not to write, and every site that cites one is documentation. Its cost is stated in its header rather than hidden: 69 of #215's 114 fixes were outside that scope, so CLAUDE.md, `docs/notes/` and `scripts/` are swept but not guarded.
- **`scripts/tests/verify-*.mjs` — the credentialed tier.** Needs `.env.local` and the loader, writes throwaway fixtures to the shared base, and some need `npm run dev`. Human-initiated on purpose and deliberately not in CI: one shared base means concurrent workflow runs would create and delete records against each other. These no longer contain their offline parts — run `npm test` for those.
- **Where a new check goes:** if it needs no credentials it goes in `offline/`, otherwise it goes in the credentialed tier. The boundary is not a judgment call — `lib/airtable/client.js` throws `Missing AIRTABLE_API_KEY` at module load, so importing it, or anything that imports it, puts a check in the credentialed tier. Offline-safe today: `lib/prVisibility.js`, `lib/authzWrap.js`, `lib/units.js`, `lib/editLogFields.js`, `lib/variance.js`, `lib/prSigning.js`, `lib/itemNaming.js`, `lib/poItemQty.js`, `lib/airtableFormula.js`, `lib/materialPriceView.js`, `lib/deliveryAccess.js`, `lib/deliveryAllocation.js`, `lib/idSequence.js`, `lib/deliveryStatus.js`, `lib/overage.js`, `lib/invoiceItemFold.js`, `lib/productName.js`, `lib/authTokenState.js`, `lib/airtableOps.js` (#190 — importable under plain `node` because `node:async_hooks` is a built-in; it is nonetheless server-only, and for the browser it is a forbidden root, which is a different boundary from this one), `lib/poListView.js`. **An offline-safe module must have no UNRESOLVABLE imports, which is stricter than "pure" (#19):** the tier runs under plain `node` with no loader, and node cannot resolve the extensionless intra-lib imports the rest of the app leaves to Next. So an offline-safe module either imports nothing, or spells the extension out: `lib/materialPriceView.js` imports `"./itemNaming.js"` that way, because the alternative was inlining #18's naming rule — a second implementation, which is worse than deviating from an import style. `lib/deliveryAllocation.js` is the second such case (#162), importing `"./materialPriceView.js"` for `countsAsOrdered` rather than re-typing `committedQty > 0`. **That friction is resolved as of #169**, the third consumer and therefore the condition above firing. `countsAsOrdered` now lives in `lib/poItemQty.js` (per-line quantity judgments, dependency-free) and both `lib/deliveryAllocation.js` and `lib/deliveryStatus.js` import it from there. The condition was only ever written HERE — neither module carried it — so a reader of either file had no way to know the move was pending. Leaving it would have made a delivery-STATUS module import a material-price-VIEW one. Not: `lib/poWithdraw.js`, `lib/blobIngest.js`, `lib/ids.js`, `lib/materialsCache.js`, `lib/deliveryCandidates.js`, `lib/deliveryReconciliation.js`, `lib/overagePR.js`. #18 is the worked example of one concern splitting across both tiers rather than picking a side: the two Unit lists are files, so comparing them is offline (`offline/unit-options.mjs`); what the Airtable fields actually hold needs the Metadata API, so that is credentialed (`verify-unit-options-18.mjs`). Neither subsumes the other — a hand-added option passes the first and fails the second.
- **Exit codes are mandatory for anything that computes a verdict**, in the shape #147 set: **0** all clear, **1** something failed, **2** no failures but a part could not run. A script that prints its verdict and returns 0 regardless makes a failure indistinguishable from a pass to anything but a reader. **A LEAK IS 1, NOT 2 (#171)** — a run that left rows on a shared base needs a hand, which is the same criterion that made 1 right for a failure, while 2 means a part could not run and needs none. Two meanings for 2 would demand two different human responses. Every script that creates records therefore carries two verdicts and two sentences: `pass` about the feature, and `fixtures.describe()` about the run's effect on the base. **One file computes no verdict about its subject and still has an exit code** — `verify-variance-15.mjs` prints variance figures for a human to compare and returns 1 for a leak and nothing else, because that is a fact about the run rather than a judgment about variance; its header says so. `verify-detect-po-92.mjs` remains the one file with no exit code at all, and it creates nothing.
- **Source-shape checks belong in `offline/source-shape.mjs`**, together, on the AST. "This call site calls X before Y" is unreachable behaviorally for a Server Action (iron-session cookie, request scope), so it has to be asserted on the source — but keep it in one file and parse it: matching on source text decays whenever an export changes shape. `_ast.mjs` documents what it still cannot prove: source order is not execution order.
- **What a green CI run does NOT mean.** It means the cheap tier passed. It does not mean authorization is enforced, and putting these checks behind a CI badge lends them an authority they haven't earned — the same correction #147 had to make about its own Part A. `source-shape.mjs` proves a gate call appears earlier in the file than the call it guards; a gate inside `if (false)`, or after an early return, satisfies it. `authz-structure.mjs` proves each endpoint export is wrapped, and for an exempt export only that its helper is named somewhere inside — order is not checked there at all. Only `authz-wrappers.mjs` proves behavior, and only of the wrappers themselves. Everything that proves a real refusal against real data still lives in the credentialed tier and still has to be run by hand. Green means "nothing cheap regressed", not "the system is safe."
- **Airtable formulas, rollups and lookups are outside CI entirely — treat them as a third tier that no test can reach cheaply.** They are not in the repo, they are not in git history, and `npm test` cannot see them — and it makes no difference that Claude can now edit them directly (see "Editing the Airtable schema"), because the edit still leaves no diff: a formula can be rewritten between two green CI runs with nothing in the diff. `DRUM` is the precedent — a 20th Unit option appeared on PR Items, held by no record and creatable by no code path here, and every file-only check stayed green. **The convention that follows: when a judgment rule lives on the Airtable side, a credentialed check must read the live schema or the live values and compare them against what the code assumes.** Five exist now — `verify-unit-options-18.mjs` for the five Unit option lists, `verify-edit-log-fields-181.mjs` for `Edit Log."Field"`'s option list against `lib/editLogFields.js` (schema **and** rows, because whether an unwritable choice is legitimate depends on whether any row holds it — see Edit Log), `verify-materials-cache-18.mjs` Part E for `PO Items.Committed/Signed Qty` across all three PO statuses (the only thing that would notice if the `& ""` coercion stopped turning the `PO Status` lookup into text), and `verify-deliveries-162.mjs` Parts A–B for `PO Items."Delivered Qty"`, `verify-overage-167.mjs` Part A for #167's two link fields and both symmetric sides — a link field renamed in the UI makes `record.get()` return `undefined`, which every banner would then render as nothing at all — and `verify-delivery-status-166.mjs` Part A for the two reverse-links #166's join walks plus `Invoiced Qty` on the first read after an invoice line is created — that join has no stored link, so those three are the whole of what it rests on and none is visible to a file-only check. That last one is the sharpest illustration of why this tier has to exist: **the Metadata API does not expose a rollup's aggregation function at all**, so SUM and COUNT are indistinguishable from any schema dump, and the only way to know which one the field is doing is to write two rows and look at the number. None run in CI, all must be run by hand, and that is the cost of putting a rule where the UI can edit it.
- **The tier boundary is enforced, not just documented.** `run-all.mjs` catches a load failure per file and names it: a check that reaches `lib/airtable/` is reported as "is NOT offline" with the rule, and a missing `acorn`/`acorn-jsx` is reported as dev dependencies not installed. Both would otherwise surface as a raw module-resolution or `Missing AIRTABLE_API_KEY` stack, which reads as broken tooling rather than as a misplaced check — and a CI failure that looks like an environment problem is precisely what trains people to ignore CI. One unloadable file also cannot hide the other checks' results.

### Directories

- scripts/tests/ — verification. **The fixtures such a script creates are deleted within the run that created them, and since #171 that is a CONTRACT rather than a convention**, owned by `scripts/tests/_fixtures.mjs` and adopted by all sixteen scripts that create records. What it guarantees: cleanup survives a throw in the body; each record is reported by id when its delete fails; a failed CHILD delete keeps its parent, so a recoverable pair is left instead of an orphan; a failed PARENT read skips the parent, because the child list is then unknown rather than empty; a leak reaches the run's verdict and its exit code; and the deletion is MEASURED — a tag census before and a residue check after, since "found 0" is also what a query against the wrong field returns. `scripts/tests/offline/fixture-cleanup.mjs` pins the shape in CI; only the credentialed run proves a row is gone. This is a statement about a script's own fixtures, not a standing license to clean the base — see the dummy-data note below.
- scripts/import/ — reusable one-time backfills. Python via `requests` + `.env.local` (import_jobs.py, add_unit_options.py).
- scripts/demo/ — kept in repo, NOT deleted from Airtable: seed_demo_fixtures.mjs (demo Job 26-DEMO-01 + Line/Vendor/Address, skip-if-exists), make-invoice-pdf.mjs (demo invoice PDF from a real PO), seed_material_prices.mjs (#19 — five PRs through the real approve-and-generate flow so `/materials` has something to show, plus a third demo Vendor), seed_over_delivery_165.mjs (#165 — four backdated orders on 26-DEMO-01 plus one delivery that fills two of them, so `/deliveries/new` can show an over-delivery attaching to the last order filled and one attaching to the most recent order when everything is already delivered; skip-if-exists on its own Materials row), seed_delivery_status_166.mjs (#166 — one scenario per state on 26-DEMO-01, since NONE of them existed on this base beforehand and the feature had nothing to show; each scenario gets its own material, which is load-bearing because allocation matches on the `Material` link and sharing one would make the scenarios each other's candidates; skip-if-exists, and every delivery goes through the production `planDelivery` so the rows are what the app would have written; **#181 gave scenario A's delivery a `Packing List PO`**, the only seeded record that carries that field, because nothing else covered its read path). Demo runs from one account standing in for every role; President access via temporarily flipping Role.
  - **ADDING COVERAGE TO A SEED DOES NOT COVER AN ALREADY-SEEDED BASE, and that is worth saying because it is easy to assume otherwise.** Every seed here is skip-if-exists, so a field a seed learns to populate appears only from the next CLEAN seed onward — measured on #181's own change: the run exited at "Already seeded", printed its guide, and created nothing, so `Deliveries."Packing List PO"` is carried by no stored record on this base even though the seed now writes one. The two ways out both cost something a reader should weigh rather than have chosen for them: deleting the seed's own Materials rows re-seeds cleanly but leaves the previous generation of orders, deliveries and invoices standing beside the new one, and setting the field by hand on the record the seed would have set it on is truthful (allocation already happened; the value is that delivery's own single order) but is a hand edit to stored demo data. **A seed change is therefore a claim about future coverage, not a verification of the present one.**
  - **Each of these prints a WHERE TO LOOK guide, and the guide is part of the script's job rather than decoration** — #166's own copy defect ("nothing delivered yet" on an invoice where 10 of 13 had arrived) was caught by reading a seeded row, not by a check. Which is also why `seed_delivery_status_166.mjs`'s skip path had to be fixed to reach that guide at all: `printGuide` is a hoisted function declaration but `ids` was a `const` below it, so a re-run — the only way to reach the skip path — died in the temporal dead zone before printing anything. The guide's `?? "A"` placeholders exist for exactly that path, where the scenarios are on the base but their ids are not in hand.
  - **`seed_material_prices.mjs` generates every PO before backdating any of them, and that order stopped being load-bearing in #164.** `lib/ids.js` used to number a PO by counting the POs whose `Created Date` is today, so backdating one inside the creation loop hid it from the next call's count — the first version of the script did exactly that and produced **five POs sharing one PO ID**, which makes `/pos/[poId]` ambiguous. The counter now counts the ID prefix and reads no date field, so that failure is unreachable; the generate-then-backdate order and the script's assertion that the IDs are distinct both stay, because they cost nothing and the assertion is what would catch a regression. This is the incident #164 cites as evidence that a counter reading an app-written date field is only conditionally correct, and it is reproduced against the live base in `verify-invoice-ids-164.mjs` Part D.
  - **`seed_over_delivery_165.mjs` builds its orders through the real approve-and-generate flow for one specific reason**, not just realism: PO generation is what writes each PO line's `Material` link (#18), and allocation matches candidates on that link and never on `Item Name` text. A hand-created PO Item would be invisible to `getDeliveryCandidates`, so the seeded orders would not appear in the item dropdown at all. It backdates the four `Created Date`s afterwards so "oldest first" and "most recent" are visible rather than decided by a same-day `PO ID` tie-break, and it fills two of the orders through the production `planDelivery` so the fully-delivered branch has real rows behind it.
  - It backdates at all so the price screens' newest-first ordering is visible instead of every row reading the same day, and it moves `Material Prices."Latest Date"` with each PO — production writes the two together (`upsertMaterialPrice` copies the PO's Created Date), so leaving them disagreeing would misrepresent the feature. Both are direct field writes, which is why they live in a demo script and not in `lib/`.
- **TWO PERMANENT FIXTURE ACCOUNTS (Users), and they are a PAIR — do not delete either, and do not change their flags.** They answer the two questions this app's visibility model asks separately: does a gate REFUSE, and does a row-scoped surface ADMIT AND RENDER. One account cannot do both, which is what #205 was raised to fix.

| Account | Flags | Proves | Use it for |
|---|---|---|---|
| `authz-fixture@hanyangengusa.com` | Employee, non-Admin, Active, **no `Assigned Jobs`** | a refusal, and nothing else | Admin/President gates: `/invoices`, `/admin/*`, the Admin API routes |
| `scoped-fixture@hanyangengusa.com` | Employee, non-Admin, Active, **`Assigned Jobs`: 26-DEMO-01** | that a row-scoped surface admits, and what it renders | `canViewPR` rows on `/prs`, `/pos`, `/pos/[poId]`; `/deliveries` and everything under it |

- **`authz-fixture@hanyangengusa.com`.** Created by #147 through the real magic-link path, so `createUser` gave it Role: Employee, Is Admin: false, Status: Active. It exists because the only two other users are both Admins, and proving an Admin gate refuses needs an active non-Admin session; keeping it means no one has to flip a real user's `Is Admin` to run the check. #143 needs a non-Admin session too. `scripts/tests/verify-authz.mjs` Part E logs in as it by minting a token with `createAuthToken` and letting `/api/auth/verify` consume it (a form POST since #203) — the email step is skipped because nothing here can read a delivered inbox, and no route exists in the app for issuing sessions any other way. (That clause used to read "because Resend is still in sandbox mode", which stopped being the reason when the domain was verified; the step is skipped either way, so only the stated reason was wrong.)
  - **What it CANNOT be used for, which is more than it sounds:** it has no `Assigned Jobs`, so on top of being non-Admin it is outside every row-level scope as well. That rules it out for both halves of this app's visibility model at once — it cannot reach a President-or-Admin surface (the PO detail's `Invoiced`/`Uninvoiced` columns, the invoice list's payment column and the invoice detail's Payment section) **and** it cannot reach a Job-scoped one (`/deliveries` and everything under it, and since #211 the invoice ROWS themselves, both of which are Job membership rather than role). So it proves a refusal and nothing else. **#211 narrowed the role half of that list**: the invoice list and detail used to be entirely President-or-Admin and are row-scoped now, so what `authz-fixture@` proves there is the empty state and the not-found refusal rather than a route gate — and #166's invoicing column left the list entirely, since every viewer gets it. Three passes ran into that before #205: #166 could not demonstrate its own withholding with it, #181 could not open a single one of the screens whose renamed fields it needed to look at, and #169 could not render `/pos/[poId]` as the viewer the privilege split exists for — it forced `isPrivileged` in source instead, which shows what the branch draws but not that a real viewer reaches it. **`scoped-fixture@` is the answer to all three**, and #205 re-ran #169's case with a session: 9 columns rather than 11, `Invoiced`/`Uninvoiced` absent, `Delivered`/`Undelivered` present.
  - **ADDING JOBS TO `authz-fixture@` IS STILL NOT THE FIX, and #205 is why the rule finally has an alternative rather than only a prohibition.** Its whole value is being the account that fails every gate; a fixture that passes one is no longer that. So #205 added a SECOND account rather than widening the first, and the flags of both stay as they are.
- **`scoped-fixture@hanyangengusa.com` (#205) is created and assigned by `scripts/demo/seed_demo_fixtures.mjs`**, so a clean seed produces the usable pair with no hand step left over — a fixture that needs one is missing exactly when somebody reaches for it. The seed calls `createUser`, which is the app's own path: the single function `verifyMagicLink` calls on a first sign-in and the only thing that writes Role, Is Admin and Status, so the record is the one a real first-time signer gets. Signing in afterwards finds it rather than creating a second.
  - **`lib/airtable/users.js:addAssignedJob` is the only writer of `Assigned Jobs` and did not exist before #205.** `createUser` never set it, there is no `updateUser`, and no route or Server Action touches it — assignment has always been a hand edit in Airtable, which is right for real staff and wrong for a fixture. It is additive and idempotent, never a replacement, so re-running the seed cannot drop an assignment somebody made by hand.
  - **THERE IS NO USER-CREATION SCREEN: a Users record is created as a side effect of a first magic-link sign-in and in no other way.** `app/admin` holds three create-forms — Jobs, Vendors and Lines — and none of them is for a user. The Phase 0 milestone description used to name Job, Vendor and User as the three creatable through the app, and of those three only the first two had a form; #205 found that and the description was corrected, so it now says a user record appears on its owner's first sign-in rather than through a form. CLAUDE.md's own Phase 0 line was accurate throughout — it lists Jobs/Vendors/Lines and no User.
- **An Admin account that is also assigned to a Job** is `soo@hanyangengusa.com` (`Is Admin: true`, `Assigned Jobs`: 26-DEMO-01 + TESTQA-01), which is what to use when a check needs BOTH at once. A session for any of the three is minted the same way: `createAuthToken`, then a form POST to `/api/auth/verify`.
- **Dummy records already in the base are deliberate, not leftovers.** Test PRs/POs and their attachments that are still there are kept for development, the same as the scripts/demo/ fixtures: do not delete them and do not treat them as residue from earlier work. Nothing in this base is to be removed as tidying-up — a record that looks orphaned is either in use or someone's decision, and neither is yours to reverse. The one deletion this file does describe is a script cleaning up fixtures it created itself, in the same run. **WHAT KEEPS THAT NARROW IS ONE CHARACTER-FOR-CHARACTER PROPERTY: a verification run's tag must be unique to that run** (`V###-${Date.now().toString(36)}`). The fixture helper's `discoverByTag` path is the only place it deletes a row the script never held an id for, so the prefix is the whole of what stops it reaching someone else's records — widen it to a fixed `V140-` and it silently becomes the base sweep this paragraph forbids. **Measured, not hypothetical (#171):** a fixed `V140-` prefix matches two hand-entered dummy invoices on this base, `HYE-INV-260727-03` and `-04`, the second of which this file already documents by name for its variance-flag anomaly. The rule lives in `scripts/tests/_fixtures.mjs`'s header where a bucket is configured; it is repeated here because it is what enforces the sentence above it.
- lib/airtable/addresses.js has createAddress() (writer) for the demo seed script.
