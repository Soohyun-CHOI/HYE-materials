# Naming — the reasoning

Governs `lib/airtable/**` (with `airtable-access.md`), and any renaming of a field, a screen word or an identifier. **Read this before editing there** — CLAUDE.md carries only the rules that bind code outside this area; the derivation, the evidence and the alternatives weighed are here.

Moved verbatim out of CLAUDE.md — nothing in this file was rewritten. The migration was audited line by line and the result is in the pull request that created this file.

### Screen words and the fields behind them

**A screen word is not a field name, and this table exists so nobody searches the base for one and concludes it is missing.** Three relationships appear here and they are not the same kind of thing: a word that maps to one field, a word that deliberately differs from the field it reads, and a word that is no field at all. Where the relationship is not 1:1 the row says so rather than picking the closest field.

**A CODE IDENTIFIER that diverges on purpose belongs here too (#181), not only a screen word** — the last row is one, and the reason is the same: someone reads `resolveOriginalPOItem`, searches the base for "original", and finds nothing.

| Screen word or identifier | What it actually reads |
|---|---|
| `Ordered` (invoice detail box) | `PO Items."Qty"`. **NOT `Committed Qty` or `Signed Qty`** — those two are the which-POs-count *judgment* (#18), read as a predicate by `countsAsOrdered` and never rendered as a figure. What "ordered" should MEAN as a quantity is #20's decision, which is why the pair exists and why no screen names either yet. |
| `Billed` (invoice detail box) | `PO Items."Invoiced Qty"` — the ordered item's total across every invoice, not this invoice's own item. A different word from the field on purpose: on an invoice screen "Invoiced" would read as "this invoice". |
| `Delivered` (invoice detail box) | the SUM of that ordered item's `Delivery Items."Qty"`, computed in `lib/deliveryReconciliation.js`. **Deliberately not `PO Items."Delivered Qty"`**, even though a field of exactly that name exists: the rollup adds within-order and beyond-order quantity together and only the rows carry `Over Delivered` (#166). |
| `Delivered` (deliveries list column) | no field — `summarizeDelivery` folds a delivery's `Delivery Items` into "first item + a count". |
| `Invoiced` (deliveries list column) | no field — a chip from `summarizeDeliveryInvoicing`, which since #210 compares, per ordered item this delivery filled, what the invoices NAMING it charge against what it brought. It asked whether that ordered item carried any `Invoice Items` at all until then, which is a level shared with every other arrival on the same order. |
| `Invoiced` (PO detail column) | `PO Items."Invoiced Qty"`. Same word, same field — the one place they agree. |
| `Uninvoiced` (PO detail column, and the invoice form's `(Uninvoiced: N)`) | `PO Items."Qty"` − `Invoiced Qty` (`lib/poItemQty.js:uninvoicedQty`). **Was `Remaining` until #181**, which said a quantity was left over without saying left over from what. Same word as `Materials."Uninvoiced Qty"` on purpose: same subtraction, one level up — the symmetry `Invoiced Qty` already has on both tables. |
| `N undelivered` / `fully delivered` (delivery entry dropdown) | `PO Items."Qty"` − `Delivered Qty` (`lib/deliveryAllocation.js:undeliveredQty`). **Was `N outstanding` / `none outstanding` until #181**, which is the other word that named two subtractions. `fully delivered` rather than `none undelivered` for the zero case, because the double negative is unreadable and the positive is the same fact. |
| `Amount Due (vendor's stated total)` | `Invoices."Amount Due"`. The gloss is on screen because this base carries two totals and the field name only distinguishes them by convention. |
| `Calculated Total` | `Invoices."Calculated Total"` = Items Subtotal + Shipping Fee + Tariff. The PR and PO call the same shape `Total Amount`; the invoice needs two names because it has two totals. |
| `Over-delivered` (tag) | `Delivery Items."Over Delivered"`, a checkbox. **Was `Over Delivery` until #181** — a noun for a condition, which reads as though the column held an event rather than a yes/no about this row. Hyphenated on screen, hyphen-free in the field, per the field convention; the noun "an over-delivery" stays in prose, where it names the event. |
| `PO on packing list` (delivery detail row) | `Deliveries."Packing List PO"`. **Was `PO` until #181.** A bare `PO` reads as the order the arrival was recorded against, which is `Delivery Items."PO Item"` on another table, one per slice, reached through the `Material` link rather than from this number. Paired with `Packing List File`: both are facts copied off the same document. |
| `Order` (materials search column) | no single field — a composite cell: the PO ID, plus the Job on the history screen, both behind #19's per-row identifier gate. |
| `Job / Line` (PR list column) | two fields — `Purchase Requests."Job"` (a lookup) and `"Line"` (a link). |
| `Delivered` / `Awaiting delivery` (invoice list and detail) | whether `Invoices."Delivery"` is set — the one place on either axis where a chip reads a field rather than a computation (#210). **Was `Delivered` / `Partly delivered` / `Awaiting delivery` and computed**, with no link stored and deliberately none; the middle word left with the estimate that produced it, because it read as progress toward a whole while the fact it named was a vendor shipping less than it billed. `Partly delivered` survives on the PO detail's own axis, where an order really is filled item by item. |
| `Mismatch: …` (invoice list marker) | no field — `lineStatus`'s `billedNotArrived` over the shipment the invoice names, rolled up per invoice by `summarizeInvoiceStatus.mismatch` (#210). A MARKER rather than a chip, so it composes with `Delivered` instead of doubling the set. |
| `Paid 2026-07-27` (invoice list) | `Invoices."Paid"` and `"Paid Date"`, rendered as one cell — **President-or-Admin since #211**. The column header is `Status` for them and `Variance` for everyone else, since for an employee the cell holds only the variance badge and a `Status` heading over it would name a subject that is not there. |
| `changed Unit Price: "30.18" → "33.18"` (PR detail history) | `Edit Log."Field"` — the stored option value, printed verbatim, so it reads as the same word the items table above it uses. It said `changed Rate` until #181: that column points at a field's IDENTITY rather than at the label in use when the row was written, so #78's rename of `Rate` → `Unit Price` took its three log rows with it. See Edit Log for the field-id test that decides when rows follow a rename and when they do not. |
| `⚠ Variance` (invoice items table, and a charge on the PO detail's invoice list) | `Invoice Items."Variance Flag"`. One word for one field at both places it is shown (#233). |
| `⚠ Total variance` (PO detail invoice list) | `Invoices."Variance Flag"` — the invoice's stated total against its calculated one. **A different word from the bare `⚠ Variance` above because the two share a screen there** (#233), which is the one place they do: `/invoices` shows the header flag alone and the invoice items table shows the item flag alone, so both say `⚠ Variance` unqualified. The PO detail said `Header Variance` and `Line Variance` until #233 — one a database word, the other the word reserved for a Job's `Lines` row. |
| `⚠ Header Variance` (invoice detail) | `Invoices."Variance Flag"` — **a different fact from the field of the same name on Invoice Items**; #179 owns that pair. |
| `HYE USA Portal` (browser tab, `/login`'s heading, the From name and subject on every email) | no field — `lib/productName.js:PRODUCT_NAME` (#201), and nothing in Airtable carries it. **Not `HANYANGENG USA INC.`**, which is `lib/poPdf.js:HYE_BUYER_NAME` and is what a vendor reads on the purchase order: the product's name is this app's to choose, the company's legal name is not, so the two are separate constants on purpose and a rename of one is never a rename of the other. |
| `resolveOriginalPOItem` (identifier, `lib/overage.js`) | `Delivery Items."Former PO Item" ?? "PO Item"`. **A third adjective on purpose.** The FIELD is named for what it stores, always a past value; the FUNCTION is named for the answer it computes — which ordered item this delivery was originally allocated against — and of the three candidates only `original` is true in both states: `former` is false for a row that never moved, `current` is false for one that did. The two are interchangeable only under the premise on the field's description (see Delivery Items). |
| `plan.over` / `rows[].over` / `hasOverDelivery` (identifiers, `lib/deliveryAllocation.js`) | nothing — **not named after `Delivery Items."Over Delivered"`, and deliberately not renamed with it (#181).** A plan is computed before any row exists, so `over` is allocation's own word for "this slice is the excess" and it is the INPUT the field is written from, not a copy of it. `hasOverDelivery` is a summary flag over a delivery, where the English noun is right. Renaming these to match the field would claim they read it. |
| `poRecordId` (parameter, `planDelivery` / `selectCandidates`) | nothing — "narrow the candidates to this order", not `Deliveries."Packing List PO"` (#181). The value comes off the packing list today because that is the only thing that narrows; the parameter is about narrowing. `createDelivery`'s parameter, which really is that field, is `packingListPORecordId`. |
| `lineStatus` (identifier, `lib/deliveryStatus.js`) | one `PO Items` row — an ordered item, NOT a `Lines` row under a Job. **A departure from the word rule below, recorded here rather than renamed.** The module states that rule in its own header, two screens above the function that breaks it, and `offline/delivery-status.mjs` enforces the word only inside #166's copy — so nothing catches an identifier, and this one seeded a family: `poLineDelivery`, an allocation row's `line`, `getDeliveryCandidates`'s `lines`. Renaming them moves code and needs a judgment about how far the family reaches, which is #184's question and not a correction to make in passing. |

**Divergences that are deliberate rather than drift**, recorded here because the audit that found them is now #181's and this table is where the reasoning belongs: `Amount` is a live formula on PR/Invoice Items and a static currency on PO Items (same meaning, frozen versus live); `Status` names five different value sets on five tables and is unambiguous within each; `Remark` is free text on PR Items and a discrepancy note on Invoice Items. None is a candidate for renaming.

**The rule #181 applied, so the next name has one to follow: a subtraction is named for what it subtracts.** `Outstanding` and `Remaining` were two words for one subtraction and one of them was also doing duty for a second, so three surfaces read as three quantities when there are two. Naming each for its subtrahend collapses them correctly — `uninvoiced` on `Materials` and on the PO detail (same subtraction, two scopes, one word, exactly as `Invoiced Qty` already spans both), `undelivered` on the delivery side. It also PINS THE NAME TO THE ARITHMETIC: if #20 changes `Materials."Uninvoiced Qty"` to subtract delivered quantity, the field has to be renamed in the same edit. That is the point rather than a cost, and it does not pre-empt #20's decision about what "outstanding" should mean — it frees the word by stopping a field from claiming it.

**A FILE NAME IS THE SAME DRIFT ONE LEVEL UP, and the test that kept #181 out of #184's way was "does the name make a claim the contents contradict".** Narrow is not the same as wrong. Two files failed it and were renamed. The old names are spelled here without backticks, because a later sweep for either string must leave this paragraph alone: app/components/DeliveryChips.js → `DeliveryStatusMarks.js`, because the marker beside the chips is documented at length as deliberately NOT one (`InferredMarker` then, `QualifierMarker` since #210 — see below); and scripts/tests/offline/guard-placement.mjs → `source-shape.mjs`, because its own exported `title` had already moved to `Call-site shape` and half of what it holds — `Quotations.File` has one writer, `Packing List File` has exactly two — is a writer count rather than a guard, in the category this file is named as the home of. Two were considered and left, with the reasons, because "rename it" is not the fix: `lib/materialsCache.js` describes two of its three writes (the third, `PO Items.Material`, is a link and not a cache), but whether that write belongs in a cache module at all is #184's question; and `lib/overagePR.js` also writes an invoice line and a delivery row, yet the whole correction hangs off that PR — it is even the field name on `Delivery Items` — so the name states the subject rather than one write.

**#210 RAN THAT SAME TEST ON AN EXPORT AND RENAMED IT: `InferredMarker` → `QualifierMarker`.** The component is a `!` in a circle whose whole meaning is the sentence handed to it, and it carried exactly one meaning while there was exactly one qualifier in the app. #210 removed the invoice axis's inference and put a MISMATCH label through the same component, while #167's overage attribution kept an `inferred` one — so the old name would have been false at one of its two call sites the moment it was reused. It is named for its shape now and the label says what it means, which is what `StatusChip` beside it already does. The test is #181's unchanged: does the name make a claim the contents contradict.

**`line` NAMES A `Lines` ROW UNDER A JOB AND NOTHING ELSE — a `PO Items` row is an `ordered item`.** The base has one table whose rows are lines, `Lines`, reached as the `Line` link on `Purchase Requests`, and a word that already names a table cannot be spent on a second thing one level down: "this job's lines" and "this order's lines" are then two different sets and the sentence carrying either one no longer says which. `lib/deliveryStatus.js` settled this for #166's copy and stated it in that module's header; what it never got was a statement anywhere a person naming something would look, which is why this is the rule that keeps coming back. It comes back through the CODE — `lineStatus` and the family in the table above say `line` for an ordered item, so anyone writing a comment or a doc beside them picks the word up from what is on the screen in front of them rather than from a convention they have not read. Recording the identifiers is therefore half the fix and this paragraph is the other half; the rename itself is #184's. The rule reaches prose, documentation and screen copy, and it is not retroactive on its own: a sweep of what is already written is its own change, and the count that would size one is in the pull request that added this paragraph.

**The `Qty` symmetry these must not break.** Every child row's own quantity is plain `Qty` (`PR Items`, `PO Items`, `Invoice Items`, `Delivery Items`); only an aggregate or a derived figure takes a modifier (`Invoiced Qty`, `Delivered Qty`, `Committed Qty`, `Signed Qty`, `Uninvoiced Qty`). Any rename has to keep that shape, which is why the audit's recommendations are all of the form `X Qty`.

**A checkbox takes a participle, not a noun.** It states a condition about the row, so: `President Signed`, `Paid`, `Used`, and `Over Delivered` since #181 — which was `Over Delivery` and read as though the column held an event. Hyphen-free per the field convention; the screen tag stays `Over-delivered` and the noun "an over-delivery" stays in prose, where it names the event rather than the flag. **This lived only on that one field's Airtable description until #181 moved it here**, which is the wrong place for a convention: a rule about how every checkbox on the base is named cannot be found by someone naming a different one.
