# Uploads and Draft re-save — the reasoning

Governs `lib/blobIngest.js`, `lib/prDraft.js`, `app/prs/new/**`. **Read this before editing there** — CLAUDE.md carries only the rules that bind code outside this area; the derivation, the evidence and the alternatives weighed are here.

Moved verbatim out of CLAUDE.md — nothing in this file was rewritten. The migration was audited line by line and the result is in the pull request that created this file.

## File uploads (Vercel Blob -> Airtable)

Every file — quotation files, invoice files, generated PO PDFs — is written to Vercel Blob first and then handed to Airtable as an attachment URL, which Airtable fetches to keep its own copy. **Airtable's copy is the copy of record**; the Blob object exists only so Airtable has something to fetch. One lifecycle (#140), and the table below is the set of write paths #140 knew — it predates the delivery photo (#162) and the direct purchase claim (#272), which follow the same lifecycle and are not listed. **The current inventory of client-upload paths is the size limit section below**, and `offline/upload-limit.mjs` fails on one it has not been told about, which is why this table is not the thing to trust for completeness.

| Path | Blob write | Ingested by | Cleanup scheduled in |
|---|---|---|---|
| Quotation file, PR form | client `upload()` (PRForm.js) | `createQuotation` in `persistPRFromForm` | `saveDraftAction` / `createPRAction`, after their last write |
| Quotation file, Edit and continue | client `upload()` (EditAndContinueForm.js) | `createQuotation` | `editAndContinueAction`, right after its try/catch |
| Invoice file | client `upload()` (InvoiceForm.js) | `createInvoice` | `createInvoiceAction`, after the last write |
| PO PDF | server `put()` (lib/poPdf.js) | `updatePO` | `generateAndAttachPOPdf` itself |
| Quotation file, overage PR (#167) | server `put()` (lib/overagePR.js), of bytes fetched from the invoice's own attachment | `createQuotation` | `createOverageDraftAction`, after its last write |

- **The fourth path is the only one with no client upload at all (#167).** The bytes come from Airtable's copy of the invoice file, so the reason for a server `put()` is not that we generated them but that re-submitting the url Airtable gave us is #142's silent data loss. It still ends at `createQuotation`, which stays the one writer of `Quotations.File`; the `after()` sits at the end of `createOverageDraftAction` rather than inside the module, because that action rolls back and a retry has to be able to re-submit the same url.
- `lib/blobIngest.js:confirmIngestThenDelete` owns the sequence. Call sites pass `{ table, recordId, field, blobUrl, attachmentId }` and never restate it.
- **One size ceiling for every user upload (#146)** — `lib/uploadLimit.js`, read by all three token routes and by all five forms. See the section below for where the figure came from and why the refusal is minted rather than measured. The three server `put()` paths have no ceiling and are deliberately outside it: the PO PDF, the overage request's re-fetched quotation and the direct purchase claim are all bytes we generated or read back out of Airtable, not something a person picked.
- **Cleanup is scheduled at the END of the enclosing action, never straight after the attachment write.** All four actions roll their writes back on failure, and the user's retry re-submits the same Blob URL from the still-open form — deleting at ingest time would charge the user for a failure they didn't cause. The rule is "no Blob object outlives its ingest *and the action that ingested it*".
- **It is scheduled, not awaited**: all four sites wrap the call in `after()` from `next/server`, so the confirm poll runs once the response is on its way instead of adding ~1s per file to the user's wait. Ordering still holds — `after()` can only run after the writes that scheduled it succeeded — and if it never runs the result is one orphan, the same outcome as a failed `del()`. It also keeps the cleanup independent of placement: three of these actions end in `redirect()`, which throws, so an awaited call would only work while it sat above that line. `generateAndAttachPOPdf` defers too: being non-fatal to a signature doesn't take it off the clock, since `signPOAction` awaits the whole function. Consequence to know about: that function now expects a request scope.
- **Blob's `onUploadCompleted` callback is not relied on** by either client-upload token route. The client already has the Blob URL from `upload()`'s return value and carries it through the form submission, so nothing needs the callback to learn it — and in local dev it can't arrive at all, since receiving it needs a tunneling service (Vercel can't reach localhost). Nothing in that handler is load-bearing.
- **Confirmation signal**: the attachment no longer carries the URL we submitted (Airtable replaces it with its own). Deliberately not Airtable's CDN hostname (versioned) and not a populated `size`. An empty field counts as NOT ingested: an attachment write pointing at a URL Airtable can't fetch **returns success and silently leaves the field empty** (measured — a write against a deleted object was still empty 30s later).
- Observed ingest latency on this base: 825/890/913/959/943 ms (5 samples). Hence poll every 300 ms (stays inside Airtable's ~5 req/s per-base budget, ~3 polls to confirm) with a 10 s ceiling (~10x the slowest observed, so it fires on breakage rather than slowness). Targets are confirmed one at a time — a multi-quotation PR takes ~1 s per file, off the response path but still spread out rather than parallel, so three files can't burst against the per-base budget.
- **Timeout keeps the object** and logs it: a late ingest must not find a deleted URL. One orphan beats an empty attachment. Only the PO PDF path offers a user-facing retry for the not-confirmed case (`Regenerate PDF`) — the other paths have no regeneration path to offer, so they just log.
- On a *failed* attachment write the object is deleted immediately (no ingest can follow) — the two failure directions are opposite, see `generateAndAttachPOPdf`.
- Cleanup is **best-effort**: a failed `del()` is logged and nothing more, since Airtable already holds the file and failing the user's action over housekeeping would be backwards. So an orphan is still possible; this is a convention, not an absolute invariant.
- **The one orphan source that survives by design**: a file uploaded and then abandoned (form closed before submit). It was never ingested, so it has no ingest to outlive, there is no record to hang cleanup on, and finding it needs the store sweep #140 excludes.
- Airtable's own attachment URLs are short-lived signed URLs (**~2h**, confirmed empirically), so nothing durable may store one — re-read the record instead. Every in-app link (PR detail Quotations, invoice detail, PO PDF) renders Airtable's URL and can go stale on a page held open past that window. Rendering a stale one is a visible, recoverable annoyance; **re-submitting one as an attachment is data loss**, which is what #142 was (see "Draft re-save" below).

### The upload size limit (#146)

**Three token routes and five client call sites, one ceiling.** The routes are `/api/quotations/upload`, `/api/invoices/upload` and `/api/deliveries/upload`; the call sites are `PRForm`, `EditAndContinueForm`, `InvoiceForm`, `DeliveryForm` and `DeliveryEditForm`. Both inventories are enumerated in `offline/upload-limit.mjs` rather than described, so a route or a form added later fails until it is classified.

**The issue said two limits and there were three by the time it was picked up, which is the whole argument for the inventory.** #146 was opened because the invoice route held the only ceiling as a literal and the quotation route held none. While it sat open, #162 added the delivery route and copied that literal — and its comment cited #146 while doing it. So the defect the issue names ("a second literal") had already happened once, by an author who had read the issue, in the interval between the issue and the fix. Three assertions about three routes would not have seen the fourth; an inventory that fails on an unclassified route does.

**Where 20 MB came from: nowhere, and the module says so.** Nothing on either platform forces it. Vercel Blob takes a single blob up to 5 TB and recommends multipart above 100 MB; Airtable accepts up to 5 GB per attachment when handed a URL, which is our path (its 5 MB figure belongs to the `uploadAttachment` endpoint, which this app does not use). Every real ceiling is between five and a quarter-million times the one we set, so the figure is a product bound and what it actually protects is the base's attachment storage allowance. A scanned invoice, an emailed quotation and a phone photo of a packing list all run 1–10 MB, so 20 MB refuses no real document and does refuse a runaway. **What the module records beside the number is that raising it is not blocked by anything** — #296 established that a figure is the first thing here to go stale, and a reader who cannot tell an arbitrary bound from a platform one cannot change it.

**One constant rather than two, and the condition that would split them.** The three paths accept the same three content types and hold the same kind of artifact — a vendor-issued document captured as PDF, JPEG or PNG — and nothing measured separates a quotation from an invoice from a packing list. CLAUDE.md's "one rule, one implementation" asks that keeping two be justified by a measurable condition, and there is none. The condition that would create one is a path's accepted content types diverging: a packing list route that took HEIC, or a multi-page scan class, would be holding a different kind of file. Recorded in the module header so the split has somewhere to start.

**The refusal is minted into the token, never measured after the bytes land — this is the part that touches #140.** `onBeforeGenerateToken` cannot see the file's size; what it can do is put `maximumSizeInBytes` into the token, which Blob HMAC-signs with the server-only read-write token. A caller who skips the form still receives our ceiling and Blob refuses the oversized `PUT`. **No object is created, so there is nothing to clean up and this path never reaches `confirmIngestThenDelete` at all** — the rule that no Blob object outlives its ingest and the action that ingested it is untouched, because no object exists to outlive anything. The alternative considered and rejected was measuring server-side after the upload, with `head()` inside the Server Action: that refuses *and leaves an object*, so the refusal needs a best-effort `del()` that can fail, which is the rollback shape #296 put on the backlog. Moving the measurement in front of the upload is the only way to have no cleanup rather than cleanup that usually works.

**The client half is what the requester actually gets, and it is one line in five places.** Without it an oversized file travels to Blob and comes back with the SDK's own English; with it the refusal is instant and in our words. It is `refuseOversizeUpload(file)` as the first statement inside the try each `upload()` already sits in, so every form reaches its existing error slot through its existing catch — no new state shape, no new branch, and no new place on any of the five screens for a design to have to account for. Both `setState` calls happen in one synchronous handler tick, so the `uploading` line set immediately above never renders. **It throws rather than returning for that reason alone**: a returning predicate would have been five different state updates, which is one rule with five implementations a byte apart, and `offline/upload-limit.mjs` pins the call rather than the outcome so a form that inlines `file.size > …` fails even while it refuses the same files.

**Strictly greater, to match Blob.** The SDK compares `computeBodyLength(body) > options.maximumSizeInBytes`, so a file of exactly 20 MB is accepted there. A `>=` in the browser would refuse what the server takes, and the boundary is the one input nobody uploads by accident, so the disagreement would sit unnoticed.

**The figure in the sentence rounds UP.** `This file is larger than the upload limit — 24.3 MB against 20 MB`. A file of 20 MB plus a byte rendered to the nearest tenth reads `20.0 MB against 20 MB`, which describes a file at a limit it was just refused for. The limit's own label is derived from the constant by the same function, so there is one figure in the module and not two.

**THE SIGNED CEILING DOES NOT BIND A MULTIPART UPLOAD, and that was measured rather than reasoned about.** The forged caller above, run again with `multipart: true` in the generate-client-token payload, received a token whose payload still read `maximumSizeInBytes: 20971520` and then uploaded 21 MB successfully. So the server half — the only half that exists on a directly-called route, which is the half this issue is about — was something a client could opt out of by setting one flag. The fix is `refuseMultipartUpload`, called by all three routes with the flag `onBeforeGenerateToken` is handed: the request is refused at token issue, with a 400 and no token minted. **Refusing costs nothing because nobody asks** — the SDK defaults `multipart` to false and not one of the five call sites passes it. If a path ever needs multipart, what to reopen is the ceiling rather than this refusal; `@vercel/blob` recommends multipart above 100 MB, five times what we allow, so the two would have to move together.

This is also the answer to a question the design pass left open as unprovable. It was going to be reported as "not verified" — the probe was cheap, it was run, and it found a hole rather than a reassurance. Worth keeping as a note about the practice: the thing that was almost left unmeasured is the thing that was wrong.

**What the offline tier still cannot reach here.** It cannot call Vercel Blob, so it asserts that the ceiling reaches the token and that a multipart request is refused before one is minted — not that Blob honors the ceiling it is given. That was forged and watched, and is in the pull request.

### Draft re-save (#142)

`persistPRFromForm` rebuilds a Draft's children from form state, so a re-save handed Airtable whatever url the form was carrying. For a quotation hydrated from a re-opened Draft that url is Airtable's own signed one, and past its ~2h life the attachment write **succeeds and lands empty** — re-saving a Draft the next morning deleted the quotation file, with no error anywhere. Re-submitting a real ingested attachment's own url with its signature invalidated is accepted and empties the field.

- **The rule is "an attachment that did not change is not rewritten"**, not "refresh the url just before re-submitting". Refreshing narrows the window without closing it and leaves "re-upload on every save" as the design.
- The judgment is `lib/quotationReuse.js:shouldReuseQuotation`, on three facts about one form entry: it names a Quotation record, that record is still among the PR's Quotations, and its url is not one of ours. `lib/prDraft.js` supplies the `recordId`; `PRForm.js` round-trips it in `quotationsJson`. They travel in the same object — replacing a file keeps `recordId` and swaps the url, removing an entry splices the whole object — so they cannot come to describe different records.
- **Where the judgment is wrong:** a `recordId` that has gone stale is not reusable, and that entry falls back to the create path with an expiring url — the original bug, in a corner. It does **not** need anyone editing Airtable: the same Draft open in two tabs, one of which **replaces a file** and saves, is enough, because a replacement is a destroy-and-create and the other tab's copy of that record id is dead from then on. #142 narrowed this rather than introducing it — before, every re-save rebuilt every Quotation, so a second tab's save re-submitted a stale url unconditionally. Left as-is rather than given a new error message; see the follow-up below.
- **Quotations are the only child this reconciles.** PR Items and PR Signers are still destroyed and recreated on every re-save, which is safe because neither holds an attachment. Item→Quotation links are re-pointed at the reused record, so a regenerated item keeps its quotation.
- Rollback is unchanged: only records this pass created are torn down, so a reused record — which belongs to the previous generation — survives a failure. Vendor Quotation Code edits on reused records are applied after the new generation is fully in place, for the same reason, and are best-effort (the file is safe either way).
- `editAndContinueAction` does **not** share the defect and was not changed — and it was not fixed for free either, since it doesn't call `persistPRFromForm` (that function, and `collectChildIds`/`destroyChildren`, exist only in `app/prs/new/actions.js`). It has no destroy-and-recreate generation: items are diffed and updated in place by record id, and its only `destroy` calls are its own rollback. Nor does its form hand it a stored url — `EditAndContinueForm` reads existing quotations only to build dropdown options, an item's choice is `existing:<id>`, and `newQuotationsJson` is serialized from a list that starts empty and only grows by this session's uploads. The one-writer rule above covers both paths anyway.
- `Purchase Orders."Quotation File"` is a Lookup chain (PR -> Purchase Requests."Quotation Files" -> Quotations.File) exposing attachment objects on the PO. Mapped in `recordToPO`, read by nothing — not a dependency.

### Draft save and submit share one path

**Merged — PR Draft Support (milestone):** save-as-draft, resume-prompt on re-entry, drafts list (open/delete). Save and submit share `persistPRFromForm` (`app/prs/new/actions.js`); submit promotes the same Draft record to In Review (PR ID/Created At/history continuous); `lib/prDraft.js:loadPRDraft(prId)` hydrates the form. After a successful save the form shows a confirm modal and leaves to the PR list (#124).
