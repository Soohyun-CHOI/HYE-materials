# Tools — the reasoning

Governs `lib/tool*.js` and `app/(tools)/**`. **Read this before editing there** — CLAUDE.md carries only the rules that bind code outside this area; the derivation, the evidence and the alternatives weighed are here.

The index row named only `lib/tool*.js` until #336, because `offline/notes-index.mjs` fails a glob that matches nothing and there was no `app/tools/` for one to match. #336 created the directory and widened the row in the same commit.

`lib/airtable/tool*.js` is additionally governed by `airtable-access.md` and `naming.md`, as all of `lib/airtable/**` is.

## What this track is (#334)

The company buys drills, grinders and the like, hands them out to sites, and gets them back when a project ends. None of that is recorded anywhere today — the only account of where a tool is, is whoever remembers carrying it. Each physical tool gets a QR label; a scan on a phone moves it between `In Stock` and `Out`, and the app can then answer what is where.

**It is not a second product.** Same app, same domain, same Airtable base, same login, same `Users` and `Jobs` as everything on the materials axis. One difference, and it is a real one: a scan happens on a phone, on site, possibly by someone wearing gloves, so the tools screens assume a mobile width while every screen above them assumes a desk (#336).

**IT DOES NOT PASS THROUGH THE OFFICE, AND THAT IS THE FACT MOST OF THIS SCHEMA FOLLOWS FROM.** A site person buys the tool, registers it, keeps it and scans it. There is no purchase request, no approval chain and no invoice; nothing here is Admin-gated, and everyone who scans needs an account only because the scan records who performed it (#337). The materials axis is the opposite shape — an order the office places and reconciles — which is why almost nothing is shared between the two beyond people and jobs.

## Where the screens stand, and the one place a width is decided (#336)

`app/(tools)/layout.js` wraps the whole axis; `app/(tools)/tools/page.js` is the first screen on it. **Both stood under `app/tools/` until #348** put the axis in a route group, which moved the files and moved neither URL.

**NOTHING ABOVE THE TOOLS TRACK MOVED, BECAUSE THERE WAS NOTHING TO MOVE.** The screens on the materials axis share no layout file at all — `app/layout.js` was the only one in the tree — and each declares its own container inside its own page instead: eighteen of those twenty-one pages carry an `mx-auto w-full max-w-* p-8`, twenty-two declarations in all, four pages carrying two. So "the layout the materials screens share" was a repeated habit rather than a file, and giving the tools screens one of their own displaced nothing and needed no rearrangement of the axis above.

**WHAT THE TOOLS AXIS DOES DIFFERENTLY IS HOLD THAT CONTAINER ONCE.** A width settled above lands in as many places as there are pages, which is why #258 has to visit each of them; a width settled here lands in one file. That is the single structural claim this issue makes, and the layout's own header is where a reader editing a tools page meets it — a page that declares a width of its own puts the axis back to two containers, and nothing fails when it does.

**THE CONTAINER IS EMPTY, AND THE EMPTINESS IS THE POINT RATHER THAN AN UNFINISHED EDGE.** #336 decides where a width is decided and decides no value: no width, no padding, no color, no type. The reason is `docs/briefs/_shared.md`'s opening claim — nothing about this app's appearance was designed, and there is no version of it to preserve — so a value chosen here to make the first screen look finished would become the baseline a design has to justify departing from, which is the one outcome the whole design milestone is arranged to avoid. #258 fills it. The visible consequence is recorded rather than smoothed over: the first tools screen renders with no styling at all, at a phone width and at a monitor width both.

**THE ROOT LAYOUT GAVE NOTHING UP.** Everything it holds is needed by both axes — the document shell, the two font variables, `globals.css` with its `color-scheme: light`, and the `title` template that lets every page state only its own name. **And the one thing that would have had to come down is not there:** this app has no navigation shell, so there was no nav to split into a desk shape and a phone shape. The links on `/` are that page's own content, added one at a time by the issue that added the screen behind each, and #336's is the fifth by the same precedent.

**THE SHORTEST ADDRESS ON THE AXIS BELONGS TO WHATEVER A LABEL CARRIES, AND THE QR IS WHY.** How many characters that string has decides the symbol's version, and each version step adds four modules to every side — so at the size a sticker is printed, a longer address is a symbol whose modules are thinner, and thinner modules are a worse scan in a gloved hand on a site. #336 read that as "the tool item's page takes the flat slot under `/tools`", and #339 and #340 were built on it; **#348 separated the printed address from the screen, and the section at the foot of this file is where that goes.** What survives from here is the premise rather than the arrangement: the printed address is a budget, and the screen behind it is not.

**THE FIRST SCREEN IS ONE HEADING, AND IT READS NO TOOL TABLE.** `getAllTools` names `/tools` in its own docstring as the list of kinds, and #339 is what puts that list there; a list invented ahead of it would be a shape that issue has to argue its way out of. So the page carries the heading its table's name gives it and nothing else, and the one operation it makes is the session's user read. What it does prove is the thing #334 and #335 could not: a tools screen renders, at both widths, inside a layout of its own.

**WHO REACHES IT IS #337'S DECISION APPLIED HERE, NOT A SECOND ONE.** `requireUser()`, which is every signed-in user with no Role and no Job scoping — that issue's body states it as a fact about the axis, and a page has to name a reader before its brief can. What stays with #337 is how the person holding the phone arrives and the signal for a scan on a job the scanner is not assigned to.

**THE CHANGE OF PREMISE IS RECORDED IN `docs/briefs/_shared.md` RATHER THAN HERE**, as a fifth entry in its constraints. That file is the design work's only input and it runs in a tool that does not read this repository, so a premise recorded only here would have to be inferred from a screen brief nobody has written yet. The half that belongs in this file is the derivation above; the half that constrains a drawing — that breakpoints, touch targets and a spacing scale are being chosen with a phone case beside them rather than widened into one afterwards — belongs where the design meets it.

## The first write screen: one form, two writes, no rollback (#338)

`/tools/new` takes a tool's name and a quantity and produces one `Tools` row, that many `Tool Items` rows, and a `Registered` row in `Tool Log` for each of them. It is the first screen on this base that creates a `Tools` row, and #339 and #340 had nothing to render before it.

**THE FORM IS ONE FORM, AND THE FIND-OR-CREATE IS WHAT MAKES THAT POSSIBLE.** Naming a tool the company already owns is the ordinary case rather than an error — buying six more of a drill is the same act as buying the first six — so there is no "new tool" path beside an "add to existing tool" path. Two forms would be two write paths for one rule, which is the duplication CLAUDE.md's own section is about, and the person filling one in would have to know which of the two they were in before they knew whether the name existed.

**WHAT THE ONE FORM OWES THEM INSTEAD IS THE MATCH, STATED BEFORE THEY SUBMIT**, and it costs no query: the page loads the whole `Tools` table in one operation — `getAllTools`, the `Vendors` shape, bounded by what the company has bought — and `lib/toolRegistration.js:matchExistingTool` applies the same key in the browser. That is `lib/prItemMerge.js`'s arrangement exactly: one pure module holds the key, the action applies it, the form previews it. **The preview is not the verdict and the module's own header says so** — the list is as old as the page, so the write asks Airtable again through `getToolByName`.

**THE DUPLICATE GATE IS `upsertMaterial`'S SHAPE DOWN TO THE LOCK KEY, AND FOLLOWING IT WAS THE WHOLE DECISION.** Both tables carry a human-typed natural key Airtable cannot make unique. So: normalize inside the writer so no caller can create an unnormalized row, compare case-insensitively at the lookup, lock on the normalized lowercased key so names Airtable would call equal serialize against each other, and **do not update the name on a match** — the first spelling wins, for `upsertMaterial`'s own reason that rewriting it lets one person's capitalization overwrite another's under everything already linked to the row. The residual is `withKeyLock`'s standing one: two concurrent Vercel invocations can both read "nothing exists yet". Unlike the tool item family, the repair here is cheap — `Tools` mints no id, so a duplicate row merges by hand with no printed label going wrong.

**`/tools/new` IS SAFE BESIDE THE DYNAMIC SEGMENT AND THE ARGUMENT IS THE ID FORMAT RATHER THAN THE FRAMEWORK'S RULE.** Next.js matches a static segment ahead of a dynamic one, measured rather than read off the documentation: with a temporary page at `app/tools/[toolItemId]/page.js` alongside the form, `/tools/new` rendered the form and `/tools/HYE-TL-260909-001` rendered the dynamic page. **But precedence is not what makes this settled** — the id that slot holds could never equal a static segment this app would add. **It holds a `Tools` record id since #348** rather than a `Tool Item ID`, which strengthens the same argument instead of changing it: Airtable mints those as `rec` and fourteen characters.

**A TOOL'S NAME NEVER APPEARS IN A PATH, AND THE CONCLUSION OUTLIVED THE REASON THIS PARAGRAPH GAVE FOR IT.** The reason was that the flat slot under `/tools` belonged to the tool item, so nothing else could have it. #348 moved the tool item off that slot and the conclusion did not move with it: a tool's name is human-typed and could be any string, so `/tools/[toolName]` is unavailable on its own terms — a name is not URL-safe and a rename would move the address. That is also what stops a tool somebody names `new` from colliding with this form. The slot holds the tool's RECORD ID now.

**THE TWO WRITES RUN IN SEQUENCE AND ARE NEVER NESTED, WHICH THE CONCURRENCY RULE DECIDES RATHER THAN A JUDGMENT ABOUT DAMAGE.** `createToolItems` holds the day-prefix lock across its whole batch; `createToolLogEntry` takes a per-tool-item lock of its own through `generateChildId`. Writing each log row inside the batch would bound the damage to one unlogged tool item and would nest two `withKeyLock` calls — which CLAUDE.md forbids and `lib/materialsCache.js` is the precedent against. So the log pass runs after the batch, and a failure in it can leave several tool items without a `Registered` row.

**WHAT AN UNLOGGED TOOL ITEM IS, AND WHY IT IS NOT REPAIRED.** The row is complete and usable — it has its printed id, `In Stock`, and a job — and what is missing is the moment it came into existence. `Tool Items` carries no `Created At` on the ground that the log's first row holds the instant, so there is no second place holding it and no way to recover it. **Writing a late `Registered` row is refused on purpose**: its `Event At` would state a time that is not when the tool item was created, and an append-only log whose rows record what was true at a moment cannot carry a row that does not. So the screen names those ids separately and the state stands. The log pass also STOPS at its first failure rather than trying the rest, which is `createToolItems`' own posture and reason: a log write that fails is failing systemically far more often than per row.

**NOTHING BATCHES A CREATE, AND THIS IS THE ISSUE `createToolItems` NAMED AS OWNING THAT DECISION.** The figure it asked for, **measured on a dev server against the live base**: `registerToolItemsAction` costs **5 + 3N operations** for a new tool and 4 + 3N for one that already exists. Confirmed at three sizes — 1 tool item under a new tool was **8** (3 list, 3 create, 2 find), 2 under an existing one **10**, and 12 under a new one **41**. The three per tool item are its own create plus the parent find and the create `generateChildId` makes for its log row; the fixed term is the session find, the two lists the page's own picker needs, and the duplicate lookup.

Batching the tool item creates ten to a request, which is Airtable's limit, takes 3N to about 2.1N — **the log rows cannot be batched at all**, since `generateChildId` mints one id per parent under one lock, so the un-batchable term dominates and the order of magnitude does not move. Against that, a failed batch of ten spends ten ids at once and makes the account the screen owes coarser. **The measurable condition for revisiting it:** if the log row ever stops needing a per-parent mint — a `Tool Log ID` that is not `{Tool Item ID}-{seq}` would do it — the un-batchable term goes and batching the creates becomes the whole cost.

**SO ONE SUBMISSION IS CAPPED, AND THE NUMBER COMES FROM ONE INVOCATION'S BUDGET.** Measured at 12 tool items: **9.0 seconds, so 0.75 s each**, which puts `MAX_TOOL_ITEMS_PER_REGISTRATION` at 100 around 75 seconds against a Vercel function's 300-second ceiling — a fourfold margin, and the figure the cap is chosen from rather than a round number. It is a local measurement and the real rate depends on the round trip, which is what the margin is for. **The refusal is not a dead end** — it tells the reader to register up to the cap and repeat, and the find-or-create path is what makes the remainder land under the same tool, so the cap costs a second submission and nothing else.

**THE IDS ARE REACHABLE FROM THE SUBMISSION'S ANSWER AND FROM NOWHERE ELSE IN THE APP YET, AND THAT IS ACCEPTED RATHER THAN OVERLOOKED.** The account names every minted `Tool Item ID` rather than counting them, because the id is what gets printed onto a sticker and a count cannot be acted on. It arrives as the action's return value, so **a reload loses it** — the rows are on the base and #339 is what lists them. It is written down because the alternative reading is that somebody forgot. **THE SENTENCE THAT SAID THIS WAS AFFORDABLE BECAUSE PRINTING LABELS IS A LATER PHASE IS GONE (#353):** that phase arrived, and the account being the only place the ids appear together is now the reason the link to the label sheet has to leave from it. Losing them on a reload costs a page of the tool's own screen rather than nothing.

**AND THE JOB IS THE ACTOR'S OWN, WITH NO OFFICE CLAUSE, WHICH IS A SECOND PREDICATE ON PURPOSE.** `lib/toolRegistration.js:assignedJobsFor` is not `lib/deliveryAccess.js:accessibleJobs`: that one admits President and Admin to every job because invoicing and reconciliation are office work. This track does not pass through the office, and `Tool Log."Job"` is the job the event HAPPENED on — so an Admin assigned to no job has no such job and is refused, on the same screen and in the same words as anybody else with no assignment. `offline/tool-registration.mjs` holds the disagreement between the two predicates as an assertion, so a later pass that aligns them fails rather than quietly widening a write path.

## The tool item's own page, and the address it spends (#340)

`/tool-items/[toolItemId]` renders the tool, the printed id, the status, the job and the whole of `Tool Log`. It is the first screen on this base reached by a machine rather than from a list. **It stood at `/tools/[toolItemId]` when #340 shipped** and that is what the next two paragraphs were written about; #348 moved it and gave the printed address a route of its own.

**THE BUDGET IS REAL AND IT IS NO LONGER THIS PAGE'S.** A QR carries the whole address, host included, and the symbol steps up a version as that string grows — printing finer modules on a sticker of the same size, which reads worse through oil and wear. None of the steps within reach is unreadable, so it is a budget rather than a limit; what makes it spent-once is that moving it means reprinting every label already glued to a tool. #348 handed that budget to `/t/[toolItemId]`, which is what freed this page to be named for what it shows.

**AND NO LABEL IS PRINTED BEFORE THE APP HAS THE HOST IT WILL KEEP.** The host is part of the string the symbol encodes, so a move from a preview domain to a permanent one is the same reprint as a moved path. **The host is settled as of #348 — `hyeusa.com`** — and the app will run on a Vercel preview domain for a while yet, which is the state this paragraph is about: a label printed from a preview host encodes that host. It binds Phase 2 rather than this one.

**THE LOOKUP IS CASE-INSENSITIVE AND THE PAGE REDIRECTS TO THE CANONICAL ID.** The label prints the id in readable characters beside the QR code, and that is not decoration: it is the fallback for a symbol somebody has scratched or painted over. A bare `=` — which #338 measured to be case-sensitive on a text field — made `hye-tl-260909-001` a miss, so the fallback amounted to demanding exact capitals from a gloved hand on a site. `getToolItemByToolItemId` now compares through `LOWER(TRIM(…))`, which is `getMaterialByKey`'s and `getToolByName`'s comparison rather than a third one.

**THE REDIRECT IS WHAT KEEPS THE CONCESSION FROM COSTING THE ADDRESS ITS UNIQUENESS**, and when #340 wrote this it was **the only page in the app that redirected at all**: every other `redirect()` under `app/` was in a Server Action or a Route Handler. `/t/[toolItemId]` is the second, for a different reason and with a different status. The mechanism does reach a page render — `requireUser()` sends a reader with no session to `/login`, on every page — so what is new is a page deciding its OWN address needs to change. It is `permanentRedirect`, because the mapping is stable for good: a `Tool Item ID` is minted once and printed, the app offers no deletion, and `Retired` is what takes a tool out of the count while keeping its row, so nothing reassigns the string a cached redirect names. It runs after `requireUser()`, so a reader with no session learns nothing about which strings resolve.

**FIVE OPERATIONS PLUS ONE PER 50 LOG ROWS.** The session find, the tool item lookup, its tool, its people and the job list are each one, and only the log walk grows — in steps of 50 through `findChildRecords`, not per row, and skipping the parent find because the tool item record already carries its `Tool Log` array (#193). People and jobs are read once for the whole history rather than per row, so a tool item with two hundred events costs four operations there and nothing more on either. That shape is the point rather than the figure: this becomes the most frequently rendered screen on the axis the moment a scan opens it. **The one read that could be removed is the tool's**, by putting a `Tool Name` lookup on `Tool Items` — refused, because this base keeps removing that third copy rather than adding one, and the condition for revisiting it is #339's list needing the same read per row.

**THE PAGE READS THE CACHED `Status` AND `Job` AND COMPARES NOTHING.** It has the last log row in hand, so deriving them would be free — and it does not, for two reasons. They are what every other tools surface shows, so deriving here would let two screens say two things about one tool item; and they are present when the history is not, which is a state #338 can leave behind. **A comparison was designed and then removed before it was built.** A disagreement is reachable only by editing Airtable by hand, which this base forbids, since the only writer of the caches is the code that writes the row — and a sentence for it would need a reader who knows what a cache is, a design for where it sits, a brief entry and a check, all for a state no path produces. Code for an unreachable state outlives everyone's memory of why it is there.

**ALL FOUR OF A ROW'S FACTS ARE ON EVERY ROW**, which `lib/toolItemView.js:logRowFacts` states in code rather than only in the brief. `Event` is a closed select written with no `typecast`, `Event At` is stamped by the writer, `Job` is never blank and `Recorded By` is written on every path that appends — so a design hiding one, or folding a repeated `Job` away, is undoing a decision rather than styling one. **THIS SAID FOUR OF FIVE, WITH `Notes` AS THE ONE THAT DROPS, UNTIL #363 DELETED THAT FIELD** — see the retirement section for why the rule it was carried for went with it.

**A TOOL ITEM WITH NO HISTORY IS A REAL STATE AND THE PAGE SAYS SO.** #338's registration writes the tool item and then its first `Tool Log` row, reports a failure between the two, and repairs nothing — so a row can exist whose history is empty. `Tool Items` carries no `Created At`, so what is missing is the moment it came into existence, and there is nowhere else holding it. The sentence says that rather than that something failed: the row itself is sound, with its printed id, its status and its job.

**OLDEST FIRST, AND NOTHING SORTS.** `getToolLogByToolItem` returns the link array's order — creation order, which for an append-only table is chronological — and `/prs/[prId]`'s history, the only other one in the app, sorts ascending too. So the first entry is always the registration and the history begins where the tool item does. **A repeated `Job` down the list is the normal reading** rather than something to collapse: a tool item that never left its job carries the same job on every row, and that absence of blanks is what makes the previous row's job the previous job.

**`getToolItemByRecordId` WAS DELETED IN THIS COMMIT, AND `getToolItemsByRecordIds` WAS KEPT.** Both were written in #334 with no caller, which CLAUDE.md names as the shape `upsertMaterial` sat in from Phase 0 to #18 carrying three defects. The first has no foreseeable caller: this page and a scan both arrive with the PRINTED id, #339 reads a tool's items in a batch, and #341 is closed. The second is #339's — the count per status comes from flattening the `Tool Items` link arrays `getAllTools` already returns, which is one batched read rather than one call per tool, and that is what makes the no-rollup decision above affordable. Its docstring says so, so a later sweep for uncalled readers leaves it.

### The symbol on this page, and what it is for (#352)

The page draws the tool item's QR symbol and links to the sheet screen to print its label. Nothing new was written for either: the symbol comes from `buildToolItemQR` (#351) and the size from `labelBudget` and `symbolBox` (#353).

**BUILT HERE RATHER THAN FETCHED, AND THE ARITHMETIC IS THE WHOLE ARGUMENT.** #351's endpoint spent two operations a symbol — a session read and a tool item read — and this page has both in hand several lines earlier. Inlining costs **zero** operations: measured at 6 for a tool item with one log row, which is exactly #340's recorded `5 + one per 50 log rows` and unchanged by the symbol. The endpoint's second operation existed to refuse an id with no row, and the not-found return above has already refused it. So the page pays nothing and asks nothing twice, and the section above records what that did to the endpoint.

**IT IS DRAWN AT ITS PRINTED SIZE, WHICH IS THE ONE SIZE THAT NEEDED NO CHOOSING.** The alternative was to invent an on-screen size, and #353's own rule against that applies: a value chosen to make an undesigned screen look finished becomes the baseline a design has to argue with. The printed size is not invented — it is the same module size the stock derives and the same per-symbol box the sheet uses, so **the screen becomes a preview of the physical object** and a reader can hold the worn sticker against it. Measured the same way on both screens: 21.089 mm at 0.57 mm a module on the tool item page, on the sheet with one label, and on all four labels of a four-label sheet. That equality is the issue's claim and it is now a measurement.

**THE SYMBOL IS NOT HERE TO BE SCANNED OFF THE SCREEN, AND SAYING SO IS WHAT SETTLES ITS SIZE.** A reader who typed the id because the sticker had worn through has already arrived; a scan of the screen would return them where they are. The scan that does work is Phase 3's, against a label on a tool. So the symbol carries **no legibility floor of its own** — unlike the readable id on the label, whose floor #353 set because it is a functional fallback — and nothing here invents one. Scanning the screen is not forbidden, merely not what the size answers to.

**PRINTING GOES THROUGH THE SHEET SCREEN AND THIS PAGE PRINTS NOTHING.** The control is a link carrying this one tool item. Two reasons, and the second is the stronger: the sheet screen owns the layout, the page box and the print rule, so a print path here would be a second implementation of one rule — and **printing one label is the archetypal part-used sheet**, which is exactly what #353's start position is for. Printing from here would either lose that control or rebuild it, and the app's most common print would become its worst sheet-waster. It also makes "the same physical object as the original" true by construction rather than by comparison: there is no second layout to drift. `offline/tool-item-view.mjs` holds that this page names no stylesheet, no page box and no print call.

**THE `alt` IS THE FAILURE STATE, WHICH IS WHY IT IS NOT EMPTY.** A symbol duplicating an id already on the page reads as decorative, and the accessible answer for decoration is an empty `alt` — refused, because the one way this image fails is a session that expired between the render and the fetch, and an empty `alt` makes that silent on the screen whose subject it is. It names the thing rather than describing the picture, and it comes from `TOOL_ITEM_COPY` because `offline/tool-list-view.mjs` fails an `alt` literal on this axis.

**THE CONTROL SAYS `Print the label` AND NOT `Reprint`, AND THE REASON IS THAT THE SCREEN CANNOT KNOW WHICH IT IS.** It said `Reprint this label` until this was read on a screen: the page is reached by somebody whose sticker has worn through, so a re-print is the case that motivated the control — but **nothing in this base records whether a sticker was ever printed or stuck on**, so a control promising one states what the app cannot check, and the reader printing a label for the first time meets a word that is wrong for them. The two want the same act. `offline/tool-label-sheet.mjs` pins the string and holds that no opener claims a re-print, since the word is the kind that comes back.

**AND A LOG ENTRY'S MOMENT IS A DATE AND A TIME TO THE MINUTE, WHICH WAS THIS PAGE'S LAST UNRENDERED FACT.** It printed the stored value — a UTC instant to the millisecond, the most machine-shaped string on the page — and its brief had recorded the rendering as open since #340. The five parts are `/prs/[prId]`'s history's, the only other history in the app, so this followed rather than chose. **That makes a fourth inline copy of those five options and the duplication is kept on purpose**: extracting one formatter would edit two screens in another area to serve this one, so `EVENT_AT_FORMAT` is named here and `offline/tool-item-view.mjs` reads the options off `/prs/[prId]`'s own call site and requires the two to agree. The measurable condition for merging is a fifth site or the first screen wanting a different resolution.

**WHAT THAT COSTS IS THE ZONE, AND IT IS RECORDED RATHER THAN SOLVED.** Both pages are Server Components, so `toLocaleString` resolves against wherever the render happened — UTC on Vercel — and the string no longer carries the `Z` the stored value had, so a reader on a site cannot tell from the page which zone they are reading. **The check cannot hold the rendering either**: `toLocaleString` depends on the runtime's locale and timezone, so a pinned string would pass where it was written and fail in CI. What is pinned is the option set, the absence of `second`, and that the formatter honors the exported object rather than passing its own.

**AND AN UNPARSEABLE INSTANT COMES BACK UNCHANGED RATHER THAN AS `Invalid Date`.** A log row's four facts never drop, so there is always a pair to fill, and a stored string the formatter cannot read is more honestly shown as itself than as the formatter's complaint. A blank stays blank.

**AND THERE IS NO TOOL ITEM WHOSE LABEL IS MISSING**, which looks like a state and is not. A symbol is a pure function of the id and the host, so every tool item that exists has one; what can be missing is a sticker on the drill, and nothing in this base records whether one was printed or stuck on. The page therefore has two states rather than three — a tool item with its symbol, or the not-found refusal with neither symbol nor print control.

## The two list screens, and the app's first paging (#339)

`/tools` is every tool with a count per status. `/tools/[toolRecordId]` is one tool's tool items, ten at a time — **it stood at `/tools/tool/[toolRecordId]` until #348**. `lib/toolListView.js` holds both screens' rules and every word either says.

**THE TOOL'S SCREEN WENT A LEVEL DEEPER RATHER THAN INTO A QUERY PARAMETER, AND THE DEPTH IS THE ONLY HALF #348 UNDID.** The extra segment was forced by the flat slot being spent; the argument against a parameter was not, and it is why this is still a route rather than a state of `/tools`. #336 and #340 left the choice open and named both options. `offline/url-parameters.mjs` inventories every parameter the app carries, and before this issue they were three kinds: a filter narrowing which rows appear, a navigation opening a form on a record, and a one-time account of something the arrival does not say. **None of them changes what the page is a list of** — `/materials?q=` searched still lists materials. `/tools?tool=rec…` would have made one route render two different tables, which no screen in this app does and which the brief system cannot describe: a brief is one file per page with a section for what the page carries only sometimes, and neither of those two lists is the other's exception. Against that, every list-to-one-record pair in this app is a route rather than a state, five for five. So the tool's screen is a route, `page` is the axis's first parameter, and it is a fourth group in that inventory — a SLICE. A filter is a question and a page is an answer too long to hand over at once.

**THE SEGMENT IS AIRTABLE'S RECORD ID, WHICH IS `/materials/[materialId]`'s ANSWER TO THE SAME PROBLEM.** `Tools` mints no id for the reason above — nothing prints a tool — and the primary field is a name a person typed. A name is not a path: it can hold any character, and the first spelling wins only because nothing renames a tool yet, so a route built on it would move the day something does. Giving `Tools` a minted ID was the other option and is refused: its only purpose would be a prettier URL, against a decision this file already records with its reasons.

**BUT THE PARAMETER IS `toolRecordId` AND NOT `toolId`, WHICH IS WHERE THIS DEPARTS FROM THE PRECEDENT IT FOLLOWS.** There is no `Tool ID` field and there is no `Material ID` field either — `/materials/[materialId]` names its segment after a field that does not exist, which is exactly the failure `naming.md` opens by describing: somebody reads the identifier, searches the base for it, and finds nothing. Following the shape without repeating the defect costs one word. The row is in `naming.md`'s table.

## The four addresses, and the one a label prints (#348)

`/tools` is the tool list, `/tools/[toolRecordId]` is one tool, `/tool-items/[toolItemId]` is one tool item, and `/t/[toolItemId]` is what a label encodes and redirects to the third. All five pages sit in the `app/(tools)/` route group so one layout still holds the axis's width. `lib/toolRoutes.js` holds every one of those addresses; `offline/tool-routes.mjs` holds it to what the app serves.

**THE CONDITION FOR REACHING FOR A ROUTE GROUP, WHICH IS THE USEFUL FORM OF THIS.** A route group buys one thing: a layout over a set of routes that do not share a URL prefix. While every screen on an axis hangs off one segment, the directory that names the segment already is that set, and a group adds a level of nesting and a hole in every derivation that reads a path — so it is not free and there is nothing to buy. **Reach for one when a second top-level collection joins the axis**, which is what happened here: `/tool-items` and `/t` are not under `/tools` and must not be, and all three want the layout #336 put the width in. That is the whole test, and it is why this arrived at #348 rather than at #336.

**WHAT THE GROUP COST, AND IT IS ONE FUNCTION PLUS FOUR READERS.** `routeTemplate` derived a route by stripping the `app` prefix, which is exact only while every directory is a URL segment. A parenthesized directory is not, so it strips those too now. Four files take that function's word for what a route is and each wanted something different from the answer:

- `offline/airtable-ops.mjs` derives the ops label a page must open its scope with. Nothing in the check changed; the pages now write `/tool-items/[toolItemId]` and `/t/[toolItemId]`, and a label carrying `(tools)` would have failed the comparison — which is the check working, since the label is a bucket a human reads.
- `offline/screen-briefs.mjs` derives a brief's FILENAME from the route, so the group is what keeps `tools-toolRecordId.md` from becoming `tools-tools-toolRecordId.md`. Two briefs were renamed and one added by the routes moving, and none by the group.
- `offline/url-parameters.mjs` attributes a parameter to a route, both from a page's own path and by walking up from a component. Its `CARRIED` row moved with the route.
- `scripts/screen-strings.mjs` needed the INVERSE, and it is the one that actually broke. It rebuilt a directory as `"app" + route`, which pointed at `app/tools` for a page living in `app/(tools)/tools` — every tools screen would have reported no strings at all, silently, since a screen with no strings is a legitimate answer. It maps a route back through the page files now, so the two directions cannot disagree.

CLAUDE.md's index glob moved to `app/(tools)/**` in the same commit, because `offline/notes-index.mjs` fails a row matching nothing — which is the mechanism catching the edit rather than a courtesy.

**`/t/` REDIRECTS RATHER THAN RENDERING, BECAUSE ONE PAGE HAS ONE ADDRESS.** A rewrite would have served the tool item's page under the short path at no hop at all, and it would have made two addresses for one screen — the thing #340's canonical redirect exists to prevent one level down. So `/t/` is an entry point that leaves.

**AND IT IS `redirect` (307) WHERE #340 IS `permanentRedirect` (308), WHICH IS A DIFFERENCE IN WHAT IS BEING MAPPED.** #340 maps a VARIANT of an address onto that address: a property of the id, true for as long as the id exists, so a 308 cached in a browser forever is correct. `/t/` maps a printed ENTRY POINT onto a SCREEN, and the screen's address is the app's to move — that separation is the entire reason this route exists. A permanent redirect would weld the two back together inside every scanner's cache, where nothing shipped later can reach them, and the app would have bought the freedom and then given it away. The cost is a round trip per scan.

**THE CASE IS NORMALIZED AT `/t/` AND THE RULE IS THAT A SCAN NEVER REDIRECTS TWICE.** The tool item's page redirects when the id it was handed is not the stored spelling, so handing it a typed `hye-tl-…` would cost a second hop on the one path that is measured in gloved hands. `canonicalToolItemId` trims and uppercases with no read behind it, which is sound because every `Tool Item ID` is minted uppercase — asserted against `formatSequentialId` rather than assumed, so the two cannot drift. The two are LAYERS rather than two rules: a cheap string transform in front, and the stored-value comparison behind it as the authority on what exists. Direct traffic to `/tool-items/…` still meets the second, at one hop.

### What the QR carries, calculated — and then measured (#351)

**These were character counts and capacity-table lookups when #348 wrote them, and #351 encoded a real address against them. Two survived and one was wrong; the section below this one carries the measurements and is the authority where the two disagree.** The host is `hyeusa.com`.

| What the code encodes | Characters |
|---|---|
| `https://hyeusa.com/t/HYE-TL-260909-004` | 38 |
| `https://hyeusa.com/tools/HYE-TL-260909-004`, the address before this issue | 42 |
| `https://hyeusa.com/tool-items/HYE-TL-260909-004`, had the screen kept the printed job | 47 |

At byte mode and error correction M, a version 3 symbol holds 42 bytes and version 4 holds 62 — so the third row is what this issue avoided rather than the second. **The lever that actually pays is the character set.** A QR code's alphanumeric mode holds digits, capital letters and `$ % * + - . / :` and packs them far tighter than byte mode, and `HTTPS://HYEUSA.COM/T/HYE-TL-260909-004` is entirely inside it. Against the published capacity table that is one version smaller at every error-correction level — at M, 38 alphanumeric characters fit version 2 (25 modules a side) where 38 bytes need version 3 (29). At a fixed sticker size that is a module about a sixth larger.

**SO THE LABEL PRINTS THE URL IN CAPITALS, AND `/T/` RESOLVES.** The scheme and host are case-insensitive per RFC 3986 and the path is not, so the uppercase spelling needs an answer of its own. It is a rewrite in `next.config.mjs` rather than a second route: **two directories differing only in case cannot coexist** — measured on this machine, `mkdir T` beside `t` was refused with `File exists` — and even where they could, two pages for one entry point would be two briefs and two entry points. A redirect was the other option and is refused for the reason above: it would make an uppercase scan cost two hops.

**TWO THINGS PHASE 2 STILL DECIDES, AND NEITHER IS THE ENCODING.** What the label prints beside the code — the readable id, a tool name, a job — and the physical size and error-correction level, which is where the version arithmetic above gets used. **What it does not have to re-open is the address or the character set.** **THE ERROR-CORRECTION LEVEL LEFT THAT LIST IN #351** and is settled at M, measured rather than derived from the arithmetic; the physical size is #353's alone, and what it gets handed is a module count.

**AND THE SEQUENCE IS NOT CAPPED AT THREE DIGITS.** `nextSequence` widens past its pad rather than wrapping, so the thousandth tool item of one day is `HYE-TL-260909-1000` and every figure above is one character longer. **THIS SENTENCE SAID THAT WAS INSIDE VERSION 2 AT M WITH TWO CHARACTERS TO SPARE, AND IT IS NOT (#351).** Measured: version 2 at M holds exactly 38 alphanumeric characters, the 38-character address uses all of them, and 39 steps to version 3. Where the two characters were read from is not recoverable and is not worth guessing at; what matters is that the address sits exactly on the boundary, which the next section records with what it costs.

### The symbol itself, encoded rather than looked up (#351)

`GET /api/tool-items/[toolItemId]/qr` returns one tool item's QR symbol as SVG. `lib/toolLabelQR.js` is the pure half — the address, the level, the quiet zone and the figures — and `offline/tool-label-qr.mjs` is what encodes and reads the answers back.

**THIS IS THE FIRST ISSUE ON THE AXIS WHOSE NUMBERS ARE MEASUREMENTS, AND ONE OF THEM CAME BACK DIFFERENT.** The section above was capacity-table arithmetic. Encoding the real address confirmed two of its claims and broke a third: the route move to `/t/` does buy a version at M (42 characters needs version 3), the uppercase spelling does buy a version (the same 38 characters in lowercase segment into `Byte:20 + Alphanumeric:18` and need version 3), and **the four-digit sequence does not fit with two characters to spare.** Both figures were produced by two independent encoders — `qrcode` and `qrcode-generator` agree on every row — so the disagreement is with the earlier reading rather than with one library.

| Error correction | Version | Modules a side | What version 2 holds at that level |
|---|---|---|---|
| L, 7% | 2 | 25 | 47 alphanumeric characters |
| **M, 15%** | **2** | **25** | **38 — and the address is 38** |
| Q, 25% | 3 | 29 | 29 |
| H, 30% | 4 | 33 | 20 |

**M, AND THE DECIDING MEASUREMENT IS NOT THE PERCENTAGE.** L and M produce the same version and the same 25 modules, so the level is free in printed density — and a solid blot painted over the data region kills L at 5x5 while M still decodes at 7x7. That is the whole argument for taking M over L. The argument against Q and H is the other measurement: **one flipped module inside a finder pattern leaves no symbol to find at L, M, Q and H alike.** Error correction protects the data region and does nothing for the corners, which is where a sticker peels and abrades first — so paying a version for Q (16% thinner modules at a fixed sticker size) or two for H (32%) buys recovery in the region that was not the failure mode and loses module width, which is what a gloved hand at arm's length actually depends on. The issue said to choose against a worn label rather than against capacity; this is that choice, and the cost is the zero headroom in the table.

**THE VERSION IS RECORDED AND NOT PASSED TO THE ENCODER, WHICH IS THE ONE DECISION HERE THAT COULD REASONABLY HAVE GONE THE OTHER WAY.** Passing `version: 2` makes the encoder refuse an address that no longer fits, which sounds like the safe direction: every printed symbol would then be exactly the geometry #353 measured. It is refused because the address is not fixed — the thousandth tool item of one day is one character longer and needs version 3 — so the pin turns a benign geometry change into a tool that cannot be labeled at all, and a row nothing can reach is what registration exists to prevent. So the encoder chooses, `buildToolItemQR` reports what it chose, and the pin lives in CI: `offline/tool-label-qr.mjs` encodes `https://hyeusa.com` and fails if the answer is not version 2 at 25 modules. A drift in the address, the host, the level or the library is a failing check, which is earlier and louder than a runtime refusal.

**WHICH MAKES ONE THING #353'S OBLIGATION RATHER THAN A PREFERENCE: SIZE BY THE MODULE, NOT BY THE SYMBOL.** A version step adds four modules to a side, so a fixed-width box renders them 16% thinner while a per-module width renders a larger label. Only the second stays scannable. What this issue hands over is therefore a count and not a millimeter: **25 modules of symbol, 4 of quiet zone on each side, 33 on a side of the `viewBox`** — and the SVG carries no `width` or `height` at all, so a consumer cannot accidentally inherit a size. `QR_SIDE_MODULES` is a constant as well as a value on the builder's return, because a number reachable only through an async call is one a label layout cannot read while it is being drawn.

**THE QUIET ZONE IS INSIDE THE SVG, AND NO CHECK IN THIS REPOSITORY CAN JUSTIFY IT.** The `viewBox` covers the symbol plus four modules on each side and the renderer paints white across the whole box, so a colored label stock or a mark printed beside it cannot bleed into the margin — and #353's obligation collapses to "do not print over this box". What cannot be shown is that the four are needed: **a software decoder reads the same symbol rendered with no margin at all**, measured, so a passing round trip is not evidence for them. The four rests on the specification and on a camera having to separate the symbol from everything printed around it. The check asserts the zero-margin decode explicitly, so the limit is in the tier rather than only in this paragraph.

**THE ENDPOINT IS GONE, AND #352 IS WHERE IT WENT.** Three paragraphs stood here describing `GET /api/tool-items/[toolItemId]/qr` — that it read the record to refuse an id with no row, that its two operations per symbol are what barred a sheet from it, and that it was gated on `getActiveUser()` and cached for a year. **What killed it is that the caller it was built for turned out not to want it.** #351 named the tool item's own page as the single-label consumer, and when that page came to render one it had already read the session and that very record — so the endpoint's two operations were the same two facts asked a second time, and the read that justified one of them (refusing a missing id) had already been performed by the page's own not-found return. With the sheet importing the builder and the page importing the builder, nothing called the address. This axis deletes those rather than keeping them: #340's own commit deleted `getToolItemByRecordId` for exactly this and kept `getToolItemsByRecordIds` because it had a caller.

**WHAT DIED WITH IT AND WHAT SURVIVED, because most of #351 was never about the route.** Gone: the endpoint, its `authz-structure.mjs` exemption (a stale one fails, so the deletion was forced to be complete), `QR_ROUTE` and `toolItemQRPath`, and `offline/tool-routes.mjs`' six assertions about that address — replaced by one asserting the axis serves no Route Handler at all, since an address deleted for having no caller is one a later pass could reintroduce by habit. Surviving untouched: the version, the error-correction level, the quiet zone, the library choice, the independent decode, and every figure in the table above — **all of it belongs to `lib/toolLabelQR.js`, which now has two real callers instead of one endpoint and one prediction.** The one piece of reasoning worth carrying forward from the exemption is a general rule rather than a fact about a route, and `authorization.md` keeps it: one gate and no field to select is what makes an exemption the whole coverage.

**AND THE ARGUMENT THAT BARRED A SHEET FROM THE ENDPOINT DID NOT DEPEND ON THE ENDPOINT.** Two operations per symbol against a base limited to five requests a second is why a hundred labels could not be fetched one at a time — and what that really established is that a screen showing many symbols reads its tool items in ONE batched query and builds the symbols itself, which is `getToolItemsByToolItemIds` and is #193's standing ban on per-record reads. That shape stands whether or not an address exists to be barred from.

**A `Retired` TOOL ITEM STILL GETS A SYMBOL**, which the endpoint's paragraph used to say and is now the page's: its label may be on the object, and a reprint is the same act whatever the status says.

**A SYMBOL LOOKED AT LOCALLY IS NOT THE ONE A LABEL CARRIES.** The origin comes off the request, so `HTTP://LOCALHOST:3000/T/HYE-TL-260909-004` is 41 characters and encodes as **version 3, 29 modules, 37 on a side** — measured, and asserted in the check so the two figures cannot be confused. That is the honest consequence of a label encoding where it was printed from, and it is also the second reason a label may not be printed from a preview host: a Vercel preview domain is longer still.

**THE LIBRARY IS `qrcode`, AND THE THING IT WAS CHOSEN FOR IS THE READ-BACK.** `create()` reports the version, the module count and the segment modes, so the mode is a measurement rather than an instruction — which is what turned #348's alphanumeric claim into evidence. `qrcode-generator` was the other candidate, zero-dependency and agreeing on every version, and it lost because its mode is an argument the caller passes: there is nothing left to measure. The cost is recorded rather than glossed: `require("qrcode")` pulls `dijkstrajs` and `pngjs` into the server graph (59 modules) for renderers this app never calls, and `yargs` sits in the install tree reachable only from the package's CLI. Its own SVG renderer is used rather than a hand-rolled one — 1210 bytes against 2346 for a path we would write ourselves, with the margin and the absent `width`/`height` already right, and rendering from `create`'s matrix would be a second implementation of one rule. The two encodes per call that costs (114us and 104us, measured) are noise against an Airtable round trip.

**THE DECODE IS A DIFFERENT LIBRARY, AND THAT IS THE POINT.** `jsqr` is a devDependency for the offline tier alone, the way `acorn` is: an encoder decoding its own output proves only that it is self-consistent. jsQR reads the format information, corrects with its own implementation, and reports version 2 and an `alphanumeric` chunk — its answers are compared against the encoder's rather than assumed to match, and six minted ids round-trip. **What that does not cover is the rendering**, because the check decodes the MATRIX and not the served SVG bytes; the browser measurement in #351's pull request is what closes it, by painting the real response and decoding the pixels.

### The sheet the symbol is printed on (#353)

`/tool-items/labels` takes printed ids in its address and draws a sheet of adhesive stock at its true size. `lib/toolLabelSheet.js` holds the stock, the arithmetic and the words; `offline/tool-label-sheet.mjs` holds the figures by value.

**THE STOCK IS NOT CHOSEN, AND THAT IS THE CONSTRAINT THE WHOLE FILE IS SHAPED BY.** Nobody has confirmed which printer the site has, so no stock has been bought. The layout is therefore built against `Avery 5160` — 30 labels of 25.4 x 66.675 mm on US Letter, the sheet an office printer takes — with every figure in `LABEL_STOCK` and none of them written twice. **The test that matters is whether the real stock costs a layout edit, and it does not: one object changes.** The single exception is `@page size`, which the language will not let a custom property reach, so `labels.css` carries the keyword and the check compares the two — the arrangement `LABEL_REWRITE` already has with `next.config.mjs` (#348).

**THE MODULE SIZE IS DERIVED FROM THE STOCK AND THE VERSION HEADROOM, NOT CHOSEN.** #351 handed over a count rather than a millimeter, and the arithmetic that turns one into the other is: the label's height less two safe insets, divided by the widest symbol the printed size must absorb, rounded down to a hundredth. That is **0.57 mm per module** on this stock, which puts today's version-2 symbol at 18.81 mm and the version-4 symbol two steps above it at 23.37 mm inside a 23.4 mm budget. Choosing a millimeter figure instead would have meant re-deriving it by hand for the real stock, which is the edit this file exists to avoid.

**TWO VERSIONS OF HEADROOM, AND THE REASON IS #351's MEASUREMENT RATHER THAN CAUTION.** The printed address uses exactly version 2's capacity — 38 alphanumeric characters of 38 — so a four-digit daily sequence is already version 3, and the production host is not settled either: the app is on a Vercel domain today and every character of a longer host counts against the same budget. Sizing per module for the largest of the three means a longer address prints a bigger symbol rather than a denser one, which is the only version of that trade where the label still scans.

**0.57 mm IS ABOVE A FLOOR THAT IS A CITATION AND NOT A MEASUREMENT, AND THAT IS THE ONE NUMBER HERE STILL OPEN.** `MIN_MODULE_MM` is 0.4 mm, the practical minimum published for a phone camera reading a printed symbol; **nothing in this repository measured it and nothing in this repository can.** What would settle it is printing a sheet on real stock and scanning it with a real phone, and neither has happened — so the module size rests on arithmetic above a cited bound. **The day somebody prints a sheet and scans it, this number reopens**, and both the derivation and the floor are the things that would move. The check holds the derived module above the floor, which turns "this stock is too small for a scannable symbol" into a failing check rather than a discovery on paper.

**THE READABLE ID HAS A FLOOR AND NO CEILING, WHICH IS WHERE THIS ISSUE'S AUTHORITY STOPS.** That the id must be legible is functional — it is the only path from a scratched or painted-over symbol back to the record — so `MIN_ID_FONT_MM` is set here and the check requires the id to fit beside the widest symbol at that size. Everything above the floor is the design's: how much larger, where it sits, what it is set in. It renders AT the floor today, and that is the constraint with no design applied rather than a chosen size — `docs/briefs/_shared.md`'s rule about not letting an unconsidered default become the baseline.

**THE FIT IS THE ONE PHYSICAL CLAIM AN OFFLINE CHECK CAN HOLD.** Whether a label overlaps its neighbor, whether ink lands in the quiet zone, whether a browser scaled the page — none of that is visible to a tier that never renders. What is arithmetic is whether the pieces fit: the widest symbol plus a gap plus the id at its floor against the label's usable width, and the widest symbol against its usable height. **If they do not fit, no layout can stop them overlapping**, and ink inside the quiet zone is exactly what #351 asked this issue not to produce. So `labelBudget` returns the parts and the check adds them up.

**AND THE STOCK'S OWN GEOMETRY IS ADDED BACK UP RATHER THAN TRUSTED.** The published numbers are a margin, a pitch and a count, and they only reach 215.9 x 279.4 mm if every one was transcribed correctly — so the check requires the left margin plus the pitches plus the last label's width to land the same margin on the right. **The first version of that assertion rounded to hundredths and failed on its own arithmetic**: 3/16 of an inch is 4.7625 mm and 1/8 is 3.175, and two decimals destroy both. It rounds to four now.

**THE FIGURES ARE ASSERTED BY VALUE, WHICH IS #351's LESSON APPLIED BEFORE IT COULD BE REPEATED.** That issue expressed every quiet-zone assertion in terms of `QR_QUIET_ZONE_MODULES` and measured the consequence: changing 4 to 2 moved the constant, the derived side, the SVG's margin and the builder's report together, and all 47 assertions passed. Every figure on this screen is reachable from `LABEL_STOCK`, so the same trap is larger here — a check written against it would pass for any stock, including one too small to print. So the literals are typed out, and changing stock changes them in the same commit.

**THE SELECTION CROSSES A NAVIGATION, WHICH IS WHY THE IDS ARE IN THE ADDRESS.** A registration's minted ids live in the action's return value and nowhere else — a reload loses them — so the link that leaves the account is the only way they reach another screen. They are the PRINTED ids rather than record ids, because that is what the account holds, what a person reads off a sticker, and what one batched query can look up. `id` is repeatable and is **a fifth kind of URL parameter** in `offline/url-parameters.mjs`' inventory: not a filter (there is no list without it), not a navigation onto a record, not a slice, and not an account. **It is clear of #321 on that last distinction** — it says what the next act is for, so a copied link is a good request to print those labels again rather than somebody else's confirmation.

**AND THE SCREEN SELECTS AMONG THEM RATHER THAN PRINTING WHAT IT WAS HANDED.** The address carries candidates and a per-label include decides. That is the app's first row selection: every checkbox on every other list in this app is a FILTER — `over` on the deliveries list, `mine` on the two document lists — and none of them selects a row. Which also settles the cap: `MAX_LABELS_PER_REQUEST` is `MAX_TOOL_ITEMS_PER_REGISTRATION` rather than a number of its own, because a cap below it would silently drop the tail of the largest registration anybody can make.

**THE START POSITION IS NOT AN EDGE CASE, AND THE ARITHMETIC IS WHY IT EXISTS.** A registration is usually a handful of tools, so a run of six on a thirty-label sheet leaves twenty-four positions — and printing always from the top would throw away most of a sheet every time somebody registers anything. The control is a POSITION rather than a count of labels to skip, because a person looks at a part-used sheet and counts across to the first one still attached. It clamps rather than refusing, which is `pageOfToolItems`' shape (#339) for the same reason: the value comes from a control somebody types into.

**THE HOST IS NAMED ON THE SCREEN, AND THIS IS WHERE A RULE BECAME A RISK.** #340 recorded that no label may be printed before the app has the host it will keep, and until this screen existed that was a rule with nothing to attach to. A symbol encodes the host it was printed from, so a sheet printed on a preview domain is thirty stickers pointing at somewhere that stops resolving — and **the app is on a Vercel domain today, so it is the live case rather than a hypothetical.** The screen states the host and says so, on screen and never on the label. It does not refuse: nothing in the app knows which host is the permanent one, and a guard that guessed would block every local check.

**THE PRINT PATH IS THE APP'S FIRST, MEASURED BEFORE IT WAS WRITTEN**: no `@page`, no `@media print` and no physical unit anywhere under `app/` or `lib/`. Three rules carry it. `size: letter` makes the page box match the paper, so the browser's default scale is already correct and there is nothing to fit. `margin: 0` is load-bearing rather than tidy — a default page margin of about half an inch would push every label off its die-cut by more than a label's height, and the stock's own top and left margins are what position the first one. And `@media print` hides the picker, the position control and all three sentences, so the paper carries labels and nothing else. **What no CSS can do is refuse a reader who prints at `Fit to page`**, which is stated in the stylesheet's own header where somebody debugging a wrong size will meet it.

**A SHEET IS ABSOLUTE PLACEMENT AND NOT A GRID.** The offsets belong to the die-cut, and a grid would distribute the gaps that the cut has already fixed. Each label is positioned from the page corner by `cellPosition`, which is the only place the pitches are read.

**AND THE FIRST REAL PRINT FOUND WHAT NONE OF THAT COULD.** The print rule hid `.label-controls`, which is the sheet component's picker — and the `<h1>` is rendered by the PAGE, so it printed: 24 pixels of heading took page one, and every sheet moved down by a page. The stylesheet's own comment claimed to hide the heading and the navigation, which made it a false comment sitting directly above the rule that did not. **The lesson is the arithmetic rather than the oversight**: a sheet is exactly one page tall against a page box with no margin, so the set of things hidden at print has to be exhaustive rather than nearly so, and "nearly" is invisible until paper comes out. The class is named for the property now — everything that is not a label is inside one `label-screen-only` wrapper on both files — and `offline/tool-label-sheet.mjs` walks the JSX of both, requiring every heading, sentence, link and control to have that class above it. That check is structural because it has to be: nothing in this tier renders, and the browser pane cannot reach a print preview.

**WHAT NOBODY HAS DONE, AND IT IS THE HALF THAT DECIDES WHETHER THIS WORKS.** No sheet has been printed on paper, no ruler has been put to one, and no phone has scanned a printed label. What was checked is the browser's own layout measured back in millimeters and its print preview; #353's pull request carries both and says what they are. **The gap is not a disclaimer but the condition on two numbers above** — the module size and its floor — and closing it is a physical act this repository cannot perform.

### The screens the labels come from are desktop first

**`/tools`, `/tools/new` and `/tools/[toolRecordId]` are drawn for a desktop and `/tool-items/[toolItemId]` for a phone**, and each brief now says so beside its reader. Both widths still have to work on all of them; the priority says which one is drawn first and how the other folds out of it.

## Three tables, and what each is for

`Tools` is the KIND. `Tool Items` is the object. `Tool Log` is the history.

**A tool is bought BY THE KIND and tracked ONE AT A TIME.** A company buys six of the same drill and then needs six labels, six locations and six histories under one name that a person typed once. Folding the kind and the object into one table gives you either six rows repeating the name — which is how two spellings of one kind appear and a count splits in two — or one row that cannot say where any individual drill is.

**`Tools` takes no minted ID, the way `Vendors` and `Materials` take none.** Nothing prints a kind and nobody quotes one, so the name a person types is the identity. The cost is a uniqueness rule the schema cannot hold, since Airtable has no unique constraint: `upsertTool` enforces it, find-or-create under a lock, and `getToolByName` is the comparison it makes — `Impact Driver` and `impact driver` are one tool whose count must not split.

**THIS PARAGRAPH SAID THAT LOOKUP WAS CASE-INSENSITIVE BECAUSE AIRTABLE'S `=` IS, AND AIRTABLE'S `=` IS NOT (#338).** Measured read-only against this base before anything was written: `{Vendor Name} = "brazos metals"` returned 0 rows against a stored `Brazos Metals`, the uppercased form returned 0, and `LOWER(TRIM({Vendor Name})) = LOWER(TRIM(…))` returned 1 for both. So the gate as #334 wrote it would have created a second tool under a differently cased name — the exact split this paragraph says it prevents, in the one table where the name IS the identity. The claim was in `lib/airtable/tools.js`'s header too and both are corrected. **Neither form collapses an internal whitespace run** (`Brazos  Metals` matched 0 rows either way), which is why the write side normalizes: `LOWER(TRIM(…))` is enough only because `normalizeItemText` has already collapsed the runs on both the stored value and the argument, which is exactly what `itemNaming.js` says about `Materials`.

**`Tool Items.Tool Item ID` is different in kind from every other minted ID on this base**, and it is worth saying why once. A PR ID is read on a screen; a PO ID is read on a document. This one is encoded into a QR code, glued to a drill and carried onto a site. Two rows sharing it means two tools wearing the same label, and the repair is reprinting both — see the ID section below for the width and how a batch stays contiguous.

**`Tool Log` exists because a status field answers where a tool is now and nothing about the project that just ended.** The question a site asks when a job closes is which tools went out on it — a question about the past, which the current status cannot answer once the tool has moved on. It is append-only in the shape `PR Edit Log` already has: a row records what was true at a moment, a moment does not change, so there is no update function and correcting a mistaken scan is another row.

### The name is #333's rule applied, not a coincidence

`Tools` → `Tool Items` is a child table taking its parent's name. `Tool Log` is an append-only event table taking its subject and `Log`, which is the second half of the same rule and is why it is not `Tool Item Log`: `PR Edit Log`'s subject is a PR edit rather than a `Purchase Requests` row spelled out, and the pattern is a short form of the subject plus `Log`.

`Tool Items` is also a fifth item table under #303's rule, so a row of it is a **tool item** — never a bare `item`, which on this base already names a row of `PR Items`, `PO Items`, `Invoice Items` or `Delivery Items`.

**AND A `Tools` ROW IS A `tool`, WHICH #338 SETTLED BECAUSE IT WAS ABOUT TO BE SETTLED BY ACCIDENT.** The same rule decides it — a row takes its own table's name in the singular — and nothing else may borrow the word, so a tool item is never "a tool". What made this worth writing down is that `kind` had begun to look like the answer: this file, `getAllTools`'s docstring and #336's own brief all say "kind", which is the right EXPLANATORY word for what distinguishes the two tables and the wrong one for a screen. A brief handed to the design work saying "a list of tool kinds" invites `Kind` as a column head, and that brief is corrected in #338's commit. `kind` stays in prose here, where it is explaining the split rather than naming a row.

## Status is written by this app, not computed by Airtable

`Tool Items."Status"` is a cache of the last `Tool Log` row, written by `lib/toolStatus.js`'s mapping in the same operation as the row that moved it. That is a decision rather than a limitation worked around, and **#335 removed one of the three grounds it rested on — the conclusion survives on the other two.** The removal is recorded rather than quietly dropped, so nobody re-derives the argument from a premise that is gone.

**THE GROUND THAT DIED.** #334's first and strongest reason was that a last row is not a status: the vocabularies were different sizes and `Job Changed` was a last row that left the status alone, so reading the last row's `Event` into `Status` would have written a value the option list did not contain. #335 removed that event, `STATUS_AFTER_EVENT` has no `null` entry any more, and every event now moves the status. A formula that copied the latest event's status would, on today's vocabulary, be correct.

**Airtable has no argmax.** A rollup's `MAX` is numeric, and there is no aggregation that returns the value of a field on the row where another field is highest. "The status implied by the row with the latest `Event At`" is not expressible. The workaround is to lean on rollup ordering — the link cell's order — which is not a documented guarantee, so a history that reordered for any reason would silently rewrite every tool's status.

**A formula field cannot be a `singleSelect`.** The closed option list goes, the colors go, and #339's count per status would be computed over free text. `Tool Items."Job"` has the same problem one step worse: a formula cannot be a link either, so the job cache could not exist at all on that route.

Neither of the two is checkable in this repository — both are facts about Airtable — which is why this paragraph is prose and `offline/tool-status.mjs` says so in the assertion that replaced #334's.

## Why the vocabulary is four events and three statuses

**Statuses: `In Stock`, `Out`, `Retired`. Events: `Registered`, `Checked Out`, `Checked In`, `Retired`.** #334 shipped five and eight; #335 cut them to this before a single row existed, which is the only reason it was affordable — an existing select's option list cannot be PATCHed at all, so the repair was deleting two tables and running the creation script again.

**`In Repair`, `Lost` and `Found` are gone because those things do not happen here.** A tool that breaks is thrown away and replaced rather than repaired, and nobody reports an individual tool item missing. The cost of modelling them anyway is not neutral: a status nobody will ever designate is a permanent blank in the per-status count, a dead option in the list filter, and an entry in `STATUS_AFTER_EVENT` that no code path reaches. If repair ever starts, adding an option is a hand edit in the Airtable UI — known, and cheaper than carrying three dead values until then.

**`Retired` stays because without a terminal status the count goes wrong.** A discarded tool would sit `In Stock` for good, and the only other way to correct that is deleting the record, which takes its whole log with it. It covers a tool found missing at a stock check as well as one thrown away, because on this axis those are one fact — the company no longer holds it.

**AND NOTHING RECORDS WHICH OF THE TWO IT WAS, WHICH IS A DECISION AND NOT AN OMISSION (#363).** This paragraph used to end "and which of the two it was goes in `Tool Log."Notes"`", and that field is deleted. The question to ask of the distinction is what would read it, and the answer is nothing: every question this axis serves — where is this tool, what went out on that job, how many of this tool does the company still hold — is answered by the status and the log's jobs, and none of them changes if the tool was skipped or stolen. What a stored reason would have bought is a report nobody has asked for, against a required field on the one transition that has to be quick enough to actually get used. **So if somebody later asks why there is no `Lost` status and no lost-versus-discarded reason, the answer is that both were weighed — `Lost` in #335, the reason in #363 — and both were found to have no reader.** What would reopen it is a real question that needs the difference, and the repair is cheap: `Retired` stays one status and a `Lost` one is a hand edit to an option list, exactly as this file already records for `In Repair`.

**`Job Changed` is gone for a different reason: the fact it recorded is already in the log.** A manager scans out their own job's tools to workers; a worker may carry one to another site; whoever manages the site it reaches scans it back in. So a tool moving between jobs shows up as a check-out on one job and the next check-in on another, and a separate event adds nothing those two rows do not already carry. **That is what makes `Tool Items."Job"` a cache rather than an attribute** — see below.

**`Registered` was added, and the deciding reason is a field that is not there.** #334 left `Created At` off `Tool Items` on the ground that the log's first row holds the instant. Without an event naming registration there is nowhere at all that answers when a tool item came into existence, and `Created At` would have to come back. `Checked In` was the alternative and reads wrong: it means a tool came back into stock, and one being registered has never been out. It is also not a fiction — the label still has to be printed and stuck on, so the `In Stock` it leaves behind describes a real tool sitting on a bench.

**The naming shapes.** A transition a person designates is named for the state it leaves the tool in, so the event and the status are the same string: `Retired`, the only one of that kind left. A transition that happens by scanning carries an action name, because the person is performing an act rather than declaring a state: `Checked Out`, `Checked In`. `Registered` is a third case — an act with no status of its own name — which is why `STATUS_AFTER_EVENT` is a map rather than something derivable from the two lists.

**What the check can and cannot hold.** `offline/tool-status.mjs` asserts that every status is produced by at least one event, which catches a dead option. It is **not** the rule applied above: what was removed were statuses nobody would ever DESIGNATE, and `In Repair` was perfectly reachable from `Sent to Repair` right up until it was deleted. The assertion would have passed on the old vocabulary and passes on the new one. Whether an event describes something that happens on a site is not a property of this source tree, and a green run is not evidence that the vocabulary is justified.

## The job is a cache on the tool item and a fact on every log row

`Tool Log."Job"` is filled on every row and never blank. It holds the job the event happened on, which is where the tool item is immediately after it.

**`Tool Items."Job"` IS A CACHE OF THAT COLUMN ON THE LATEST ROW — the same kind of value as `Status`, from the same row.** #334's description called it the job the tool belongs to, a durable attribute, and #335 corrected that: a tool does not belong to a job, it was last scanned on one. Nothing in the flow ever reassigns a tool; it moves because somebody carries it and somebody else scans it in.

It is still REQUIRED and still app-enforced, since Airtable cannot make a link field required (the limit `Invoice Items."PO Item"` lives with, #278). Never empty, because every event carries a job and registration is an event.

### Where the job comes from

**Registration, check-out and check-in all take it from the `Users."Assigned Jobs"` of whoever performs the action.** One assigned job and it is used without asking; several and it is a dropdown; there is no path anywhere that types a job.

**IT IS STORED ON THE LOG ROW AT THAT MOMENT AND NEVER LOOKED UP AFTERWARDS.** `Assigned Jobs` changes when a person moves site, so a log row that referenced the session or the user's current assignment would make an old check-out describe today's posting. That is the precise thing the per-row copy exists to prevent, and referencing it at read time would undo the whole reason `Tool Log` carries a job of its own. The screens are #338 and later; the rule is here because it constrains all of them.

### `Former Job` was considered and refused

With no blanks, the PREVIOUS row's `Job` is unambiguously the previous job — a check-in on a different job than the check-out before it IS the record of a tool changing site. Storing the pair would be one fact in two places, derivable from an ordering the log already has, and #340 renders the whole history at once so it holds both rows.

The counter-precedent is `Delivery Items."Former PO Item"` (#167), which IS stored — and the difference is the reason: there is no log on that axis, so the re-attachment destroys the only record of where the row came from. Here the log is the record.

## What the schema deliberately does NOT carry

- **No `Created At` on `Tool Items`.** The `Tool Item ID` carries the day and the log's first row carries the instant; a third copy is the shape this base keeps having to remove. **That omission is what forced the `Registered` event** — with no such row there would be nowhere left holding the instant, and the field would have to come back. The two decisions hold each other up, so neither can be undone alone.
- **No `Created At` on `Tools`.** `Vendors` and `Materials`, the two tables it is modelled on, have none, and `/tools` orders by name. An Airtable `createdTime` can be added in one field CREATE if #339 wants a tiebreak.
- **No per-status rollup on `Tools`.** #339 needs a count per status and can have it from the `Tool Items` link array `getAllTools` already returns for free. The measurable condition for changing that: if `/tools` measures above roughly ten operations because of the tool item walk, the count moves into a rollup and `Purchase Orders."Uninvoiced Items"` (#244) is the worked example of the move. Five rollups nothing reads would be five fields to keep in step for nothing.
- **No `{Parent} Record ID` lookup on either child table.** After #334 deleted the seven that existed, `Material Prices` holds the only two left on the base, and those are CLAUDE.md's stated exception — a price row is keyed by two links and has no parent whose reverse-link would do. See below.
- **No `Unit` field anywhere.** A tool item is one object, not a quantity, so `add_unit_options.py` stays a five-table script — the same note `create_direct_purchases_272.py` makes for its own table.

## The tool item ID: width, and how a batch stays contiguous (#335)

`HYE-TL-YYMMDD-###`, minted by `lib/ids.js:generateNextToolItemIds`. Same daily-reset shape as every other document in the system, counting the rows whose ID carries the same prefix and never a date field (#164) — the rule that matters more here than anywhere else, because a duplicate is two labels already stuck to two tools and the repair is reprinting both.

**THE WIDTH IS 3 AND IT IS THE FIRST PER-FAMILY WIDTH ON THIS BASE.** Every other family takes `SEQ_PAD_LENGTH`, which is 2 and stays 2: `formatSequentialId` reads `padLength` through a default, so `ID_KINDS.TOOL_ITEM` declaring one leaves the other five untouched. That mechanism is not new — `CHILD_KINDS` already carries a width per relation — and it is the reason widening this sequence changed no document ID.

Three, because one registration creates many. Every other family is a document somebody raises one at a time and none has ever needed more than a handful in a day; a tool registration takes a quantity, and the first day of use is a warehouse's whole stock arriving at once. It is also not a new number — seven of the nine child relations already pad to 3.

**IT IS NOT A CEILING, WHICH IS WHY THE CHOICE IS CHEAP.** `padStart` does not truncate and `nextSequence` parses the whole tail, so the 1000th tool item of one day is `-1000` rather than a collision. The width is a statement about how the common case reads.

**A BATCH IS ONE LOCK, ONE QUERY AND N CONTIGUOUS IDS.** `mintDailyIds` holds the critical section across the whole registration; `mintDailyId` is that function with a count of 1. Minting one at a time would be wrong twice: a lock acquisition and a full day-prefix query PER tool item, which grows with the day, and — worse — two people registering at once would interleave, so one registration's tool items would come back with another's numbers scattered through them.

The direction of the delegation is forced rather than chosen: `offline/id-sequence.mjs` asserts `lib/ids.js` builds exactly one `filterByFormula` and that it is a bare `prefixMatch` call, so a batch helper with a query of its own fails CI. Two queries for one rule is how the two drift.

**AN ISSUANCE HELPER NARROWER THAN A WRITER IS NOT AVAILABLE**, and it is worth knowing before someone tries. `mintDailyIds` calls its callback INSIDE the lock, because reading the highest sequence and writing the rows that claim it must be one critical section — a helper that returned ids would hand them out with the lock already released. So `createToolItems` mints and creates in one function, exactly as `createToolLogEntry` does one level down, and for the same reason.

**WHAT THE LOCK DOES NOT COVER** is `withKeyLock`'s standing residual: it serializes within one process or invocation only, so two concurrent Vercel invocations can still read the same highest sequence and both create. Every family has lived with that window; what differs here is the repair. No distributed lock is built — that is new machinery against a risk this base has never been observed to hit — and the frontend disable-on-click guard remains the other half. The module header says so where a reader of the code will meet it.

**A DELETED TOOL ITEM FREES ITS NUMBER IF IT WAS THE HIGHEST OF ITS DAY, WHICH IS THE ONE HAZARD ON THIS AXIS WORTH KNOWING.** `nextSequence` is MAX + 1 over the live rows, so deleting the top row lowers MAX and the next mint re-issues that number — measured, not reasoned: with `HYE-TL-260908-001..009` on the base, destroying `-009` and minting again produced `-009`. That is MAX + 1 working as specified, and for an invoice it is the accepted behavior #164 settled; here the number is on a sticker, so the same behavior would put one label on two tools with nothing to notice.

**WHAT CLOSES IT IS THE VOCABULARY, NOT THE GENERATOR.** The app offers no way to delete a tool item and must not: `Retired` exists so a tool can leave the count while its row and its whole log stay, which is the same argument that kept `Retired` when `In Repair` and `Lost` went. The only remaining exposure is a hand deletion in Airtable, which this base already forbids — nothing here is removed as tidying-up. A high-water mark in place of MAX + 1 would remove the hazard outright and is refused in `id-generation.md`, with the trade written down.

**NOTHING ROLLS BACK A PARTIAL REGISTRATION.** `createToolItems` returns what it created and what it did not, and a failed create simply stops the rest. Undoing the rows before it would free ids the counter has already spent, and a later registration would re-issue them; `nextSequence` is MAX + 1, so the gap costs nothing while a reused number costs two labels on two tools. What the submission says about a short count is #338's.

**#313 IS OPEN AND THIS FAMILY DOES NOT TOUCH IT.** That issue moves `Purchase Orders`' four-digit year onto the two-digit form everything else writes; the tool item family took the two-digit form from the start, so it adds nothing to that work. `offline/id-sequence.mjs` pins the split — five families on two digits, `PO` the one that is not — so the claim stays checkable rather than remembered.

## The reverse links needed no disambiguation, and that is worth recording

Five link fields, five auto-created inverses, and all five are the name we would have chosen, so none was renamed: `Tools."Tool Items"`, `Jobs."Tool Items"`, `Tool Items."Tool Log"`, `Jobs."Tool Log"`, `Users."Tool Log"`.

Two links land on `Jobs`, which looks like the case `Users."PR Edit Requests (Initiated)"` and `"(Sent To)"` exist for. It is not. **Every disambiguated inverse on this base is two or more links from ONE source table** — `Purchase Orders (as PIC / as Manager / as Sender)`, `Jobs (as PIC / as Manager)`, the `PR Edit Requests` pair. Airtable names an inverse after the SOURCE TABLE, so two links from two different tables land already distinct.

## The ninth child relation, registered before anything writes a row

`"Tool Items::Tool Log"` is in `CHILD_KINDS` from the commit that creates the table, and `lib/airtable/toolLog.js:createToolLogEntry` is the `generateChildId` call site that makes it legal. Deferring the registration to #338 was proposed and reversed: the alternative was stating `{Tool Item ID}-{seq}` in the Airtable field description and having the next issue read it back out, which is one rule written twice in two places neither of which can check the other.

**`offline/id-sequence.mjs` requires a CALL SITE, not a writer with a screen behind it.** Its walker finds any `generateChildId(...)` under `lib/` and never asks whether anything calls that function in turn — measured by running it, 110 of 110 with the ninth relation registered and nothing but the credentialed check calling it.

**An issuance helper narrower than a writer is not available**, which is worth knowing before someone tries. `generateChildId` calls `createFn` INSIDE the per-parent lock, and that is the whole mechanism preventing two concurrent scans from minting one id; a helper that returned an id for the caller to use would hand it out with the lock already released. Minting and creating are one function by construction.

The relation shares its name from the moment it exists, which is the composite-key census confirming itself: `Tool Log` is carried by `Tool Items`, `Users` and `Jobs` the moment it exists, so a registry keyed on the bare field name would have had three candidates to be wrong about. See `id-generation.md`.

## The seven parent Record ID lookups deleted alongside (#334)

`PR Signers`, `PR Items`, `Quotations`, `PR Edit Requests` and `PR Edit Log` each carried a `PR Record ID` lookup, and `Invoice Items` carried `Invoice Record ID` and `PO Record ID`. All seven are gone; `Material Prices."Material Record ID"` and `"Vendor Record ID"` stay, are read by `getMaterialPrice`, and must not be swept with them.

**Nothing read the seven** — measured across `lib/`, `app/` and `scripts/`, the three names survive only in comments — and **no formula, rollup or lookup on the base referenced them**, measured by field id against the whole schema before the deletion. Each of the six tables had exactly one default `Grid view`.

**Deleting a lookup destroys nothing**, which is the fact that made this safe rather than merely tidy: a lookup stores no value, so recreating it with the same configuration restores the same cells. CLAUDE.md's warning that a type change can silently drop values is about a data field and does not reach this.

**The positive reason, which the `_Record ID` formulas do NOT share:** these seven existed only to support filtering a child table by its parent's record id, which this repository forbids — that lookup is computed asynchronously and undercounts siblings created right after the parent, reproduced for PO Items (`lib/ids.js:generateChildId`). Deleting them makes the banned query unwritable rather than merely forbidden. `PO Items."PO Record ID"` had additionally been MISCONFIGURED for as long as it existed (see `purchase-orders.md`), which is the same hazard one step further along.

**The six `_Record ID` formulas were examined and all six kept.** `Materials._Record ID` and `Vendors._Record ID` are load-bearing for the two `Material Prices` lookups. The other four — `Users`, `Purchase Requests`, `Purchase Orders`, `Invoices` — have no consumer at all now, and are kept anyway: they sit on the PARENT table so they enable nothing wrong, they are a human affordance for copying a record id out of the grid into a `verify-*` run, they cost nothing as formulas, and deleting four of six would leave an asymmetry the next reader has to re-derive.

`offline/table-field-names.mjs` gained the three names. They are **the first `RETIRED` entries with no successor field at all** — a third kind after a rename (#280, #333) and a replaced field (#318's `Paid` → `Paid Date`) — because what replaces the query is a method rather than a name: read the parent's reverse-link, which `getLinkedRecords` has always done.
