# ID generation — the reasoning

Governs `lib/ids.js`, `lib/idSequence.js`. **Read this before editing there** — CLAUDE.md carries only the rules that bind code outside this area; the derivation, the evidence and the alternatives weighed are here.

Moved verbatim out of CLAUDE.md — nothing in this file was rewritten. The migration was audited line by line and the result is in the pull request that created this file.

### The daily counter counts the ID prefix, never a date field (#164)

`mintDailyId` is the one implementation behind every generator: lock on `{table}:{prefix}`, select the rows whose ID field starts with today's prefix, take the highest sequence, add one, create. **The pure part is `lib/idSequence.js`** — each family's token, year width and ID field name, the stamp, the prefix, `nextSequence` and `formatSequentialId`. That module imports nothing, which is the whole reason it exists separately: `lib/ids.js` reaches `lib/airtable/client.js` and its module-load throw, so a rule kept inside it cannot be pinned offline. Same split, same measured reason, as `lib/airtableFormula.js` (#159) and `lib/authzWrap.js` (#147); same shape as `lib/itemNaming.js`. **`lib/ids.js` is still the only place an ID is generated** — it owns the lock, the query and the create, and no counting reaches a call site.

- **The defect this replaced.** `generateNextInvoiceId` built `HYE-INV-{today}-{seq}` while counting `IS_SAME({Issue Date}, TODAY(), 'day')` — the **vendor's** date off their document, human-entered and almost never today — so the count was almost always 0 and **every invoice entered on one day got `-01`**. Measured read-only twice, on 2026-07-31 and again on 2026-08-03: that filter matched 0 of 5 invoices. It had not fired only because all five happened to be entered on their own issue date, which real vendor invoices are not.
- **All four converted, and the reason is that they share one rule** rather than that the other three were broken. PR counted `{Created At}` and PO `{Created Date}`, both app-written, both correct — **conditionally on nobody writing those fields with anything but now.** That condition has already been broken by a committed script: `scripts/demo/seed_material_prices.mjs` backdated `Created Date` inside its creation loop and produced **five POs sharing one PO ID**. The ID prefix needs no such condition — it is the population the sequence must be unique within by definition, and nobody can backdate it. `verify-invoice-ids-164.mjs` Part D reproduces that incident against the live base and shows the new rule is immune to it.
- **Not `LEFT({Invoice ID}, 13)`, the form the issue was filed with.** Measured: 0 rows, because the prefix is 14 characters, not 13. A hard-coded length is a per-family magic number (PR 13, PO 15, Invoice 14, Delivery 13) and that one was already written down wrong in two places. The predicate is `lib/airtableFormula.js:prefixMatch` → `FIND("<prefix>", {Field}) = 1`, which takes the anchor from the string itself. It lives with the escape for #19's reason — the alternative was a per-call-site exemption — and is registered in `offline/formula-escaping.mjs`, which fails closed on the call site if it is not (verified by mutation).
- **`nextSequence` is MAX + 1, not count + 1.** A count is the next free number only while nothing has been deleted, and deletion is normal here. Measured on this base: `HYE-INV-260716` held seqs [02, 03] and `HYE-INV-260727` held [03, 04] — three invoices had been deleted, and in **both** namespaces count + 1 is a number that already exists.
- **Child IDs use the same rule, and the boundary that once excluded them is gone.** It was recorded as deliberate — a parent's link array holds record ids rather than child IDs, so the highest sequence is not readable from it without another query — and that was true but was a statement about cost, not about correctness. The sentence above applies to children unchanged, and worse: **a child is deleted by an ordinary Draft re-save, not by anyone choosing to.** `persistPRFromForm` creates the new generation before destroying the old one, deliberately, so a failed re-save never loses saved children; the consequence is that every re-save shifts the sequence upward and frees the numbers below it. One item and one re-save leaves `[002]`. Measured on the live base: `HYE-PR-260722-09` held exactly one PR Item, `-002`, and exactly one Quotation, `-Q02`, so under count + 1 the next child of either kind re-issued a number already on a live row — **and for the Quotation that was reachable with a mouse**, since the PR is In Review and Edit and continue creates Quotations. So `generateChildId` now reads the array, resolves it through `findByRecordIds` and takes `nextSequence`. That second query is the whole cost.
  - **Why the parent's array and not a `prefixMatch` on the child table**, which would be one query instead of two and was measured ~2× faster (112–197ms against 289–709ms). **Not because it lagged** — it was measured seeing a just-created sibling in 6 of 6 rounds. Because of what each option makes ID uniqueness *depend* on. The array depends on a link being visible on both sides immediately, which `generateChildId` already depended on, which `client.js` records as measured, and which `canViewPR` clauses 5–6 also rest on — so the fix adds no new consistency assumption. Filtering the child table would newly make uniqueness depend on the search index being read-your-writes consistent for a plain text field: a guarantee nothing else here relies on, supported only by a negative measurement of a timing window. The one thing the filter is genuinely better at — seeing an **orphaned** sibling whose parent link is gone, like the two parentless `HYE-PO-260727-05-001` rows the #140 script left — stopped mattering when #164 made a parent's own ID no longer re-mintable, since no future parent carries a dead parent's ID.
  - Still **not** the child table's `{Parent} Record ID` lookup: that one is genuinely computed asynchronously and undercounts when siblings are created right after the parent, reproduced for PO Items. That prohibition is unchanged.
  - **The ID shape is a registry, not a call-site argument.** `CHILD_KINDS` in `lib/idSequence.js` holds all nine relations (ID field, pad width, optional `seqPrefix`), so "a Quotation is `{PR ID}-Q##`" is stated once rather than at one of nine call sites — and the ID field name, the one value a caller must not get wrong, is not a caller's to supply. A wrong field name would read `undefined` off every sibling, look exactly like a childless parent, and mint a duplicate; `generateChildId` throws on that instead. An unregistered relation throws too, and `offline/id-sequence.mjs` enumerates every call site in `lib/` rather than listing them, so a tenth child table cannot ship unregistered or still passing a shape of its own. **Six prose counts read `eight` or `ninth` until the CLAUDE.md routing pass after #354** — two here, three in `lib/idSequence.js`'s `CHILD_KINDS` docstring, one in CLAUDE.md. #334 registered the ninth relation and moved the count in that docstring's first line and in the check's hard-coded figure, but not in the sentences around them, and "a ninth child table" went on meaning "the next one" after the ninth had shipped. **The 2026-08-03 census figures are left as measured**, and that is the distinction to apply to the next one: a record of what was observed keeps its number, a count of what exists does not.
  - **The registry key is `Parent Table::Link Field`, and the pair is not caution — the field name alone is measurably not unique.** Counted against the live schema on 2026-08-03 (21 tables, 84 `multipleRecordLinks` fields, 50 distinct names): **7 of the 8 registered names are carried by more than one table**, and 18 of the 50 names base-wide are. Only the link that is `PR Edit Requests` since #333 is unique — it was `Correction Requests` when the census was taken, and the rename moved that name and no figure in this paragraph. Nothing collided because exactly one table per name is a *registered* relation — a property of which call sites exist, not of the schema, and `Materials."PO Items"` and `PO Items."Delivery Items"` are already sitting there one `generateChildId` call away from clashing. **The failure a collision causes is silent:** two identical keys in an object literal are not an error in JS, the later wins at parse time, and `Object.keys` then reports one entry — so a check that imports the object agrees with the bug. Demonstrated by mutation: a duplicated key left the imported object with 8 keys and `PO Items` carrying `Delivery Item ID`, i.e. the wrong field, which is the childless-parent read above. It is caught by counting `Property` nodes on `lib/idSequence.js`'s **AST**, which is the only place the duplicate still exists.
    - The offline enumeration resolves each call site's `TABLES.X` by parsing `lib/airtable/client.js`'s own object literal, since importing it would need credentials. A `TABLES.X` that does not exist is caught by the same step.
    - `verify-invoice-ids-164.mjs` Part A re-measures the census and asserts each registered pair still exists in Airtable. That is not cosmetic: a link field renamed in the UI makes `parentRecord.get()` return `undefined`, `generateChildId` reads it as a childless parent, and a live sequence restarts at 1.
  - **One `nextSequence` covers both shapes**, and `seqPrefix` is what makes that work: with `""` a `-Q01` is not a sibling of `-001`, and with `"Q"` the reverse. Two independent sequences under one parent, which is what the live rows showed — `HYE-PR-260722-09` carried `-002` and `-Q02`, neither aware of the other. So `lib/idSequence.js` has its second consumer rather than a near-copy.
  - **No existing duplicate was repaired.** Measured across all eight child tables: 0 duplicate child IDs, 0 parentless PO Items (the two the #140 script stranded were hand-deleted in #162), and exactly the two gapped groups named above. A gap is a free number, not a wrong record.
- **THE FIFTH FAMILY IS `HYE-DP`, AND IT IS THE ONE WITH THE MOST TEMPTING DATE FIELD ON ITS OWN RECORD (#272).** A `Direct Purchases` row is recorded off a vendor's invoice, so it carries that document's `Issue Date` — a date somebody else wrote, routinely weeks or months old, and the office records several in one sitting. Counting it would be #164's defect with a worse input than the one that produced it: the invoice generator at least counted a date that was sometimes today. Nothing here can point at it, because the population is the rows whose `Direct Purchase ID` carries today's prefix and the family declares that field rather than a call site passing one. The prefix is 13 characters, the same as PR and Delivery, and no length is written down anywhere.
- **A TABLE RENAME MOVED TWO CHILD FAMILIES AND NO MINTED VALUE (#333), WHICH IS WORTH RECORDING BECAUSE THE ISSUE WAS RAISED ASKING WHETHER A PREFIX HAD TO MOVE.** `Correction Requests` → `PR Edit Requests` and `Edit Log` → `PR Edit Log`, so `CHILD_KINDS` gained two new keys and two new `idField`s — and neither family has a token of its own. A child ID is `{PR ID}-###`; the only prefix in it is the parent's, so **no stored value ever contained the retired word.** Measured read-only before the rename: the request table held one row, `HYE-PR-260819-02-001`, the log table held none, and 0 values matched either old name. So the rename cost no data migration and no fixture regeneration, which is the answer to "does the prefix move too" — there was none to move.
  - **A `seqPrefix` WAS THE ONE CHANGE THAT WOULD HAVE TOUCHED VALUES, AND IT WAS REFUSED.** Giving an edit request a letter the way a Quotation carries `Q` is the obvious symmetry to reach for, and it breaks a different one: `PR Items`, `PR Signers`, `PR Edit Requests` and `PR Edit Log` all mint `{PR ID}-###`, and `nextSequence` counts each table's own field, so the four sequences are independent and unaware of each other. A letter on one of the four makes them read as three of a kind plus one, changes live values, and fixes no defect. `Q`'s own reason does not transfer — a Quotation is a LABELED SUB-SEQUENCE of the request (see `CHILD_KINDS` above), which is a claim about what the row is, not a way of telling two child tables apart.
- **THE NINTH CHILD RELATION WAS REGISTERED BEFORE ANY SCREEN WROTE A ROW, AND THE CHECK IS WHAT MADE THAT LEGAL (#334).** `"Tool Items::Tool Log"` went into `CHILD_KINDS` in the commit that CREATES the table, with `lib/airtable/toolLog.js:createToolLogEntry` as its call site and nothing calling that in turn until #338. The first reading of `offline/id-sequence.mjs` said this was impossible — its three Part 3 assertions do require every registered key to be used — and that was a misreading of what "used" means: the walker finds any `generateChildId(...)` under `lib/` and never asks whether the enclosing function has a caller. **The alternative was worse and is why the point was worth settling:** stating `{Tool Item ID}-{seq}` in the Airtable field description and having the next issue implement it from there is the same rule written twice, in two places neither of which can check the other, one of them outside the repository entirely. Only the hard-coded `8` in that check had to move.
  - **A HELPER NARROWER THAN A WRITER IS NOT AVAILABLE, which is worth knowing before somebody tries to build one.** `generateChildId` calls `createFn` inside the per-parent lock, and that is the whole mechanism: a helper that minted an id and returned it would release the lock before the row existed, which is precisely the gap the callback shape closes. So "an issuance helper" and "the writer" are one function by construction, and registering a relation early means shipping its writer early.
  - **It arrived already sharing its name, which is the census above confirming itself rather than a coincidence.** `Tool Log` is carried by three tables the moment it exists — `Tool Items."Tool Log"` is the registered parent, `Users."Tool Log"` and `Jobs."Tool Log"` are the inverses of `Recorded By` and `Job` — so the count reads 8 of 9 and a key on the bare field name would have had three candidates to be wrong about. The 2026-08-03 base-wide figures are left as measured; three tables and five link fields have been added since.
- **THE SIXTH FAMILY IS `HYE-TL`, AND IT IS THE FIRST TO CARRY A WIDTH OF ITS OWN (#335).** Every family above pads to `SEQ_PAD_LENGTH`, which is 2 and stays 2. A tool item pads to 3, and the mechanism is that `formatSequentialId` reads `padLength` through a DEFAULT — so `ID_KINDS.TOOL_ITEM` declaring one changes nothing for a family that declares none, and widening this sequence moved no document ID by a character. That is the same shape `CHILD_KINDS` has used per relation since #164, reached for a second time rather than invented. **3 because one registration creates many**: every other family is a document somebody raises one at a time and none has needed more than a handful in a day, while the first day of tool use is a warehouse's whole stock. **It is not a ceiling** — `padStart` does not truncate and `nextSequence` parses the whole tail, so the 1000th of a day is `-1000`, and the width is a statement about how the common case reads rather than a limit.
  - **A BATCH IS ONE LOCK, ONE QUERY AND N CONTIGUOUS IDS, WHICH IS WHY `mintDailyIds` TAKES A COUNT.** Minting one at a time is wrong twice over: it costs a lock acquisition and a full day-prefix query PER record, and that query grows with the day, so a bulk registration is quadratic; and it is not contiguous, because two people submitting together interleave and one registration's ids come back with another's scattered through them. `withKeyLock` holds until its callback settles whatever the callback does, so the whole batch fits in one critical section. `mintDailyId` is `mintDailyIds(..., 1, ...)`.
  - **THE DELEGATION DIRECTION IS FORCED BY A CHECK, not chosen.** `offline/id-sequence.mjs` asserts this file builds EXACTLY ONE `filterByFormula` and that it is a bare `prefixMatch` call. A batch helper with a query of its own therefore fails CI — correctly, since two queries for one rule is how the two drift. Demonstrated by mutation: giving `mintDailyId` its own query back fails that assertion and nothing else.
  - **THE OFF-BY-ONE LIVES IN THE PURE MODULE.** `formatSequentialIds(prefix, startSeq, count)` returns `startSeq` through `startSeq + count - 1`, and the check pins it as a ROUND TRIP rather than as literals: what one batch writes, the next batch's `nextSequence` must read back as the number after it, which is "no gap and no overlap" stated once. A count below 1 throws rather than returning `[]`, since a caller asking for zero has computed a quantity wrong and an empty array would let a registration report success having created nothing.
  - **A PARTIAL BATCH LEAVES A GAP AND THAT IS FINE**, which is the MAX + 1 rule paying for itself a second time. `createToolItems` stops at the first failed create and returns what it made; rolling back would free ids the counter has spent, and a later registration would re-issue them. A gap costs nothing; a reused tool item id costs two labels already stuck to two tools.
  - **MAX + 1 RE-ISSUES A DELETED TOP NUMBER, AND #335 IS WHERE THAT WAS FINALLY MEASURED.** Everything written above about gaps concerns a gap in the MIDDLE — `HYE-INV-260716` holding [02, 03], `HYE-PR-260722-09` holding one item — and the argument is that MAX + 1 steps over those where count + 1 would collide. **The top of the range is not a gap**, so deleting the highest row lowers MAX and the next mint re-uses that number. Measured against the live base rather than reasoned: with `HYE-TL-260908-001..009` present, destroying `-009` and minting again produced `-009` (`verify-tool-item-ids-335.mjs` Part D). **This is not new behavior and not a regression** — it has been true of all six families since #164, and for a document it is fine, because an ID freed by a deleted invoice is genuinely free.
    - **THE FAMILY IT IS NOT FINE FOR IS THE ONE WHOSE ID IS PRINTED.** A tool item's number is on a sticker, so a row deleted after the label went on leaves that number for the next registration to put on a different tool — and there is no string collision to notice, just two tools wearing one label. What closes it is that **the app offers no deletion at all** and the supported exit is the `Retired` status, which keeps the row and its log precisely so the count can be corrected without freeing an id. The remaining exposure is a hand deletion in Airtable, which this base already forbids as tidying-up.
    - **WHY NOT A HIGH-WATER MARK.** Storing the highest number ever issued, rather than the highest currently live, would remove the hazard for every family. It is a schema change plus a second write inside the lock, changing a rule all six share, against a hazard that requires somebody to break a standing rule first — and it would have to be paid for by every document ID in the system. Recorded here so the trade is visible if a tool item ever IS deleted by hand.
    - **THE TEST THAT NEARLY MISSED IT.** #335's first plan deleted the MIDDLE of a batch, which only distinguishes MAX from COUNT and passes cleanly under both readings of the top-of-range case. Deleting the highest row is the boundary; a check aimed at the wrong one would have reported green over the whole question.
  - **#313 HAS SINCE CLOSED THAT EXCEPTION, AND THIS FAMILY NEVER ADDED TO IT.** `HYE-TL` took the two-digit form from the start; `Purchase Orders` was the one family that did not, and that issue moved it. **The check that pinned the split — five families on two digits and `PO` the one that is not — could not survive the fix**, since counting families per width needs two widths to exist. It was replaced rather than deleted: `yearDigits` is gone from the registry and the assertion is now that no family declares one and that every family's prefix is token-dash-six-digits. See the #313 section at the end of this file.
- **The formula narrows; the pure function decides.** `prefixMatch` exists to avoid reading the whole table, but membership is re-tested in `nextSequence`, so a formula that over-matches costs rows and cannot corrupt a number. Past 99 the sequence widens to three digits rather than wrapping or colliding. The hand-made `-99` fixtures on this base sit on prefixes no generator can produce (`HYE-PR-TESTQA` has no digit date segment; `HYE-PO-260715` is past).
- **One clock now.** The stamp comes from the JS clock while `TODAY()` evaluated in GMT — they agree on Vercel, where the process clock is UTC, and need not agree anywhere else. Airtable is no longer asked what day it is.
- **What each tier proves.** `offline/id-sequence.mjs` pins both rules and asserts, on the AST, that `lib/ids.js` names no date field in a formula, that `TODAY()`/`IS_SAME` are gone, that every generator delegates to the one helper, and that `generateChildId` reads its siblings' IDs rather than the link array's length — so neither date counting nor length counting can come back without failing CI. It also enumerates every `generateChildId` call site in `lib/` rather than listing them, so an unregistered tenth child table fails too. It does **not** prove the queries selected the right rows, nor that a link array is populated in time to be counted: those are Airtable's properties and live in `verify-invoice-ids-164.mjs`, which creates two invoices in one run with backdated Issue Dates, creates three children and deletes the middle one, and re-measures the link array on the first read after a child is created. Both halves were confirmed by mutation against the live base — reverting either rule makes the corresponding Part fail, and the child mutation minted a real duplicate.

Naming: auto-generated -> `X ID`. Human-typed -> `X Label`/plain name. Calendar-only -> `X Date`. Time-meaningful -> `X At`.

### One year width for every family (#313)

`Purchase Orders` numbered itself `HYE-PO-20260819-12` while the other five families wrote `YYMMDD`. The generator moved, and the 37 orders and 39 ordered items already carrying the long form were rewritten, so nothing this app stores is written two ways.

- **THE OLD WIDTH HAD A REASON AND IT WAS RECORDED, WHICH IS WHY THE ISSUE BODY WAS REWRITTEN BEFORE THE WORK STARTED.** `lib/idSequence.js` said the company's own purchase order numbers, issued before this app existed, carry a four-digit year — confirmed from real invoice samples — and the generator was given `yearDigits: 4` so a generated ID would match them. The body's first draft said nothing had decided it and that each family had copied whichever neighbor was open; that was false about this one. **The observation is true and stays in the module**; what does not survive is calling it a constraint. A PO ID is a number we assign and send out, the vendor transcribes what is printed on the document, nothing outside this company parses the format, and those vendors already deal with customers whose numbers look nothing alike. It was our convention agreeing with our own older convention.
- **`yearDigits` IS GONE FROM THE REGISTRY RATHER THAN SET TO 2 SIX TIMES.** It was a per-family width with exactly one family turning it; with that family moved it became a knob nobody turns, and the one exception could have come back as a single character. `dailyStamp` takes no width either. **If a family ever needs its own, `padLength` is the mechanism to copy** — declared per family, read through a default, so `TOOL_ITEM`'s 3 changes nothing for the five that declare none.
  - **THE CHECK THAT PINNED THE SPLIT COULD NOT SURVIVE THE FIX, and was replaced rather than deleted.** `offline/id-sequence.mjs` counted families on each width, five against one, which is a shape that needs two widths to exist. What it asserts now is stronger: no family declares a year width, and every family's prefix matches `token-\d{6}`. A family re-declaring a width fails the first; one reaching a longer stamp some other way fails the second.

- **THE REWRITE IS TOTAL, AND ORDERING IS WHY.** `/pos` leaves its ordering to Airtable on the ID string and `lib/poListView.js` records that a fixed-width zero-padded ID sorts as its date. `"2026…"` sorts before `"26…"` because `'0' < '6'`, so a half-migrated table puts every long-form order below every short-form one whatever its date; `PO Item ID` is a sort key too (`lib/deliveryAllocation.js`). The script refuses to start unless every row can move.
- **TWO FIELDS, AND THE SCAN THAT ESTABLISHED THERE WAS NO THIRD.** All 65 text fields across the base's 26 tables were read and searched for `HYE-PO`: `Purchase Orders."PO ID"` (37 rows) and `PO Items."PO Item ID"` (39) were the only hits. Every other reference to an order is a LINK — `Deliveries."Packing List PO"`, `Material Prices."Latest PO"`, `Invoice-PO Link`, `Invoice Items."PO"` and `"PO Item"`, `Delivery Items."PO Item"` — and a link carries a record id, which no rename touches.
  - **`Deliveries."Packing List PO"` LOOKS LIKE A COUNTEREXAMPLE AND IS NOT.** #181's body describes it as holding "the number the packing list printed", which reads as free text; the field is `multipleRecordLinks`. The form does take a typed number, and `app/deliveries/new/actions.js` resolves it with `getPOById` and stores the record id — so the string a person typed is never stored anywhere. That sentence is about the value's PROVENANCE rather than the field's type.
- **NO SCHEMA CHANGE AND NOTHING FOR THE UI.** Both fields are `singleLineText`. All 20 formulas on the base were dumped through the Metadata API and **none references `PO ID`**, so there is no computed value to follow, no field type to change and no link to toggle — the whole migration is ordinary record updates.
- **WHAT CANNOT MOVE, AND IT IS TWO FILENAMES.** `PO PDF File` attachments are named `{PO ID}.pdf` and the document prints the number twice; renaming needs a re-upload and the PDF's own text would still disagree, and #281 refuses to regenerate a document that exists because regeneration misstates history. Two orders on this base carry a PDF. **Zero orders have been sent to a vendor**, so no document outside this company quotes a number at all.
- **THE SCRIPT IS DRY-RUN BY DEFAULT AND REVERSIBLE BY LEDGER.** `scripts/import/rewrite_po_year_313.mjs` prints all 76 before/after pairs and writes nothing without `--apply`; with it, a JSONL of `{table, field, id, before, after}` is written **before the first patch**, so a run that dies halfway has still recorded every value it was about to touch, and `--revert <ledger>` puts them back. Three refusals run before any write: a value that is not a PO ID, two rows that would land on one id, and — checked on this base — **zero collisions**, because dropping `20` cannot make two same-day orders share a sequence.
- **ORDER OF OPERATIONS.** Merge first, then run. The generator mints from `ID_KINDS.PO`, so running before the merge is followed by new long-form rows; merging first leaves old rows long only for as long as the run takes, and with nobody deployed that window has no reader.

- **THE DETECTION REGEX NARROWED RATHER THAN ACCEPTING BOTH WIDTHS.** `app/api/invoices/detect-po/route.js` scanned a vendor's invoice text with a hand-written `/HYE-PO-\d{8}-\d{2}/g`. It takes the shape from `idPattern(ID_KINDS.PO)` now, because a hand-written width is the reader a width change breaks most quietly: a stale pattern matches nothing a generator mints, detection returns an empty list, and the form looks like it simply found no order. **Keeping `\d{8}` was weighed and protects nothing**: every match is looked up with `getPOById`, and a pre-app company number has no record in this base — those orders were never in the app — so a long-form match can only resolve to null and be dropped. The app-generated long forms it used to catch are the ones this issue rewrote.
  - **THE SEQUENCE WENT FROM `{2}` TO `{2,}` IN THE SAME EXPRESSION**, which corrects the hand-written version rather than reproducing it. `formatSequentialId` pads with `padStart` and `nextSequence` parses the whole tail, so the 100th order of a day is `-100` — and a fixed-width pattern matched `-10` of it and looked that up as a different order. Greedy, so a quoted `HYE-PO-260911-33-001` still resolves to the order it belongs to.
- **NO TRANSITIONAL ACCEPTANCE WAS BUILT, AND THE POPULATION IS WHY.** The first plan had `getPOById` accept both widths behind one predicate. It was dropped: the app is not deployed, there are no real users, no order has been sent and no vendor invoice has arrived, so the set of people who could quote a long-form number is empty today and there is no path for it to grow before deployment. Building an option for a state nobody has met is what this repository declines to do elsewhere. **The acceptance becomes real work when the system this app replaces starts having its numbers quoted into it** — that is a different question from this one, and `docs/notes/backlog.md` carries it with that condition.
- **THE LONG FORM WAS SWEPT OUT OF THE REPOSITORY TOO — 160 ids and 5 format specs across 33 files**, because a check holding an id by value guards a shape the app can no longer mint while still passing, and a note quoting one sends a reader to the base to find nothing. **Two places kept the long form on purpose**: `app/pos/POListClient.js` and `purchase-orders.md` both record that `HYE-PO-20260805-02` rendered at 141px, which is what an 18-character id measured. The id is 16 characters now and the column was not re-cut — that is a width the design pass owns, and a migration is not the place to spend slack it happens to create.
