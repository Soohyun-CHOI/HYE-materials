# Authorization — the reasoning

Governs `lib/authz*.js`, `lib/prVisibility.js`, `lib/invoiceVisibility.js`, `app/api/**`. **Read this before editing there** — CLAUDE.md carries only the rules that bind code outside this area; the derivation, the evidence and the alternatives weighed are here.

Moved verbatim out of CLAUDE.md — nothing in this file was rewritten. The migration was audited line by line and the result is in the pull request that created this file.

### Row visibility — `canViewPR` (lib/prVisibility.js)

In order, first match wins:

1. **A `Draft` is visible only to its Requester** — ahead of everything, including President/Admin (#143). Every other Draft surface is already private that way (the resume prompt and the drafts list both read `getDraftsByRequester`), and nothing in the app links to someone else's Draft. An unsubmitted PR is not yet a record of anything, and its assigned signers have nothing to sign.
2. **President/Admin** see every submitted PR.
3. The **Requester** sees their own.
4. Anyone **assigned to the PR's Job** sees it.
5. A **signer on this PR's chain** sees it (#143).
6. The **recipient of an edit request on this PR** sees it (#143).

Clauses 5 and 6 are not generosity — without them the gate cuts the signing chain. Neither a signer nor an edit-request recipient is guaranteed to be assigned to the PR's Job, and a participant who cannot open the PR cannot take their turn, so the chain stops with nothing to explain it. Both are **status-agnostic**: a signer who already approved, one pushed back to Pending by an edit request, and the recipient of an already-`Resolved` one all keep access. Being locked out of a document you signed would be strange, and every chain action ends in `redirect()` back to this same page, so access that expired at the moment of acting would bounce the actor into a refusal.

**How 5 and 6 cost no queries.** Both sides of each relation already carry the child row ids as link arrays, so membership is a set intersection: `Users."PR Signers"` × `Purchase Requests."PR Signers"`, and `Users."PR Edit Requests (Sent To)"` × `Purchase Requests."PR Edit Requests"` (both renamed from `Correction Requests` in #333, with the reverse link on `Users` the one of the five a rename could actually have broken). `recordToUser`/`recordToPR` expose them as `signerRowIds`/`editRequestRowIds` — the same reverse-link trick `purchaseOrders` already used, and confirmed on a freshly created row to be populated on both sides immediately, with no propagation lag. So the PR list stays one pass over rows it already has, with **no per-row round trip**, and the detail page adds nothing either. The cost is that an intersection cannot read a child's fields, so clause 6 *cannot* filter on `Status` — which is free here, because status-agnostic is what we want anyway.

**`Sent To` ambiguity does not reach this.** The `PR Signers` section of `purchase-requests.md` records that it holds one user id and cannot say whether an edit request went to someone *as a signer* or *as the Requester* when they are both. That is about the recipient's capacity; clause 6 only asks whether they are the recipient at all.

**`Withdrawn` takes no special path** — #122 keeps a withdrawn PR on record and in the list, so it is judged like any other submitted PR.

**A missing link array throws rather than refusing.** Once clauses 1–4 have not decided, the answer depends on `signerRowIds`/`editRequestRowIds`, and a caller that omitted them is a bug rather than a denial. Refusing would look like the safe direction and would in fact be the stalled chain 5 and 6 exist to prevent — a signer locked out of the PR they are meant to sign, with no error to trace. Both mappers default the fields to `[]`, so `undefined` can only mean the object never went through one; every production caller does today, which makes the throw unreachable now and a tripwire for the next call site. It fires only where the arrays are actually needed, so a decision already reached by clauses 1–4 still works on an object without them. What it cannot catch: Airtable omits an empty link field, so "no signers" and "field not selected" are indistinguishable downstream — the mappers' `|| []` is what turns both into `[]`, and a field-limited select would pass this check while silently disabling both clauses. No such select produces a `canViewPR` input today (the only ones are in `lib/ids.js`, for sequence numbering).

**Guard wrappers (#147) — the expected way to gate a new endpoint.** `lib/authz.js` exports three: `withAdminApi` (Route Handler; refuses with requireAdminApi()'s own 401/403 Response), `withAdminAction` (Server Action; the call site passes its refusal as the first argument) and `withPresidentAction` (Server Action; requirePresident() throws, so there is nothing to pass). A wrapped export cannot run its body unauthorized, because the body is an argument the wrapper decides whether to call — the caller obligation below stops being a thing anyone can forget. **The refusal shape follows the call site, and #185 settled it** — the decision #147 deferred by keeping refusal as the thunk's argument. **An action whose every call site BINDS the return value returns `{ error }`; an action any call site invokes without binding throws.** Three bindings exist and two of them can observe a return: `useActionState(action, init)` makes it `state`, and `await action(...)` in a client handler makes it a value, while a bare `<form action={action}>` DISCARDS it. That third one is why the rule is not "a form returns" — `/admin/jobs/new` and `/admin/vendors/new` ARE forms and cannot see a returned refusal, because each page is a Server Component handing the action straight to the element with no client boundary and no error slot on the screen at all. **The rule is a conjunction over call sites**, and the disagreement case is part of it: one non-binding caller makes the rule say throw, which costs the binding caller its inline message, so a mixture is the signal to change that caller rather than the shape. `offline/action-refusal-shape.mjs` enumerates every wrapped action, reads each thunk's actual shape off the AST, derives the shape from the call sites and compares — so the rule is applied rather than restated, and a new action fails the tier until it is classified.

- **What the throw was actually carrying, and what took it over.** The undroppability #147 needed is the WRAPPER's, not the throw's: `createFlagGuard` calls the thunk INSTEAD of the handler, so the gate cannot be skipped whatever the thunk returns, and `offline/authz-structure.mjs` holds that unchanged. What a throw really bought was OBSERVABILITY — a refusal a caller ignores still surfaces. Converting to a return gives that up, so the new check takes it: every returning action's every observing call site must have a path from the bound value's `.error` into JSX. That is the quiet mutant this settlement creates and the assertion that answers it.
- **A THROWN REFUSAL IS NOT SCREEN COPY IN THIS APP, and the reason is a premise rather than a preference.** `app/` contains no `error.js` and no `global-error.js`, so nothing in this repository renders a thrown Server Action message; it reaches the framework's own default. So the two throwing actions' text is developer-facing, needs no copy review, and is not a string a screen shows — `scripts/screen-strings.mjs` stopped collecting thrown messages from `"use server"` files on exactly that ground (#185), which took nine strings out of its census that no reader could ever meet. **The day somebody adds an error boundary, those refusals become copy** — `action-refusal-shape.mjs` asserts the absence, so that day it fails and this paragraph is what the failure sends you back to. The count is deliberately not written down here: #272 added an action and made "four and four" false in three places at once, so what splits them is recorded and the arithmetic is left to the check.
- **The rule does not reach `withPresidentAction`.** `requirePresident()` throws inside the gate, so there is no refusal argument for a call site to supply and nothing for the rule to decide.

None of the three passes the resolved user to the handler, because no Admin/President call site reads one — every requireAdmin() site destructured only `{ authorized }` and every requireAdminApi() site used its value only for the `instanceof Response` test. Add it as a first argument if a wrapped handler ever needs it.

**Not wrapped, and why (#147).** These are the exemptions, listed with reasons in `scripts/tests/offline/authz-structure.mjs` and enforced there. The list is meant to stay short for two reasons: every entry is a precedent a future author can copy, and an exemption is verified more weakly than a wrapper (see the scope note below).
- The three magic-link auth routes — public by design; there is no caller to authorize.
- `/api/invoices/upload`, `/api/quotations/upload` and `/api/deliveries/upload` — the gate has to run inside `handleUpload`'s `onBeforeGenerateToken` callback, which rejects by throwing rather than by returning a Response, so wrapping the export would answer 401/403 where the client currently gets the 400 `handleUpload`'s catch produces. Recorded because #147 found it: `request.json()` runs at the top of all three handlers **before** authorization, so "the gate comes before the route's work" is looser here than the phrase suggests. These three are the only places in the inventory where that is true, and the shape propagates — the deliveries route (#162) inherited it by being the same kind of endpoint, which is exactly what the note about every exemption being a precedent predicted.
  - The deliveries route carries one more looseness of its own, named in its exemption: it gates on `getActiveUser()` and **cannot** check the Job, because the upload happens before the form is submitted so the route does not yet know which Job the photo belongs to. The Job check is in `createDeliveryAction`. So any active user can put an object in the store; what they cannot do is attach it to a delivery.
- `GET /api/files/[axis]/[documentId]/[filename]` (#331) — session plus one of THREE per-record gates, chosen by the axis segment. `canViewPR` for a quotation and an order document, both reached through the parent request; `getVisibleInvoiceIds` for an invoice file; `canAccessJobDeliveries` for a packing list photo and a direct purchase's file. Each is the gate that axis's own screen already uses, so the route adds no visibility rule. No wrapper fits: `withAdminApi` would refuse the site staff every one of those gates admits, and Route Handlers cannot use `requireUser()` at all.
  - **THIS IS THE ONE EXEMPTION WHOSE WEAKNESS IS ANSWERED IN ANOTHER FILE RATHER THAN TOLERATED HERE, and the reason is arithmetic.** Every other entry is one gate a wrapper does not fit. This is five fields behind three gates in one export, so "the named helper is called somewhere inside" — which is the whole of what an exemption proves, order not checked — is satisfied exactly as well by `getActiveUser()` plus ONE gate for all five. No screen would change, nothing here would fail, and a reader would open a packing list for a job they are not on because the handler asked `canViewPR` about a request they happen to be a signer of. `offline/file-route.mjs` holds it instead: the route declares each axis's gate in a map AND calls a gate inside each axis's own opener, in two places on purpose, and that check reads both off the AST and requires them to agree with each other and with its own table. Verified by mutation — a swapped declaration, a swapped call with the declaration left right, one gate for all five, and an opener pointed at `Purchase Orders."Quotation File"` all fail it.
  - **The refusal is one answer for two states**, `404 Not found.` for a record that does not exist and for one outside the reader's scope alike, which is CLAUDE.md's rule about never confirming existence. It carries more weight here than on a page: the URL holds a human document id whose neighbors a person can guess, so the indistinguishability is what makes enumeration learn nothing. Demonstrated with a real session — `authz-fixture@` (non-Admin, no assigned jobs) gets that body on all five axes, on two ids that do not exist, and on an unknown axis. `scoped-fixture@` gets 200 on the order document, the invoice file and the packing list photo, and **404 on the quotation**, because the request behind it is a Draft and `canViewPR`'s first clause admits only its requester — the same gate admitting and refusing one reader through one route.
- **AN ENTRY WAS HERE FOR #351's TOOL-LABEL QR ENDPOINT AND WENT WITH THE ROUTE IN #352**, and what is worth keeping is the rule it was written to carry rather than the route. The endpoint had no caller once the tool item's own page rendered its symbol inline — the page had already read the session and that record, which were the endpoint's two operations — so it was deleted, and a stale exemption fails this check, which is what forced the list to follow. **The reusable half: one gate and no field to select is what makes an exemption the whole coverage.** "The named helper is called somewhere inside the export" says everything there is to say about a route like that, where `/api/files` has five fields behind three gates in one export and the same sentence says almost nothing — which is why that one needed `offline/file-route.mjs` and this one needed nothing. Weigh the next exemption on that property. **The other half does not survive and should not be reached for**: the endpoint's own note argued that its response carried nothing the requester had not supplied, which is a reason to be relaxed about a gate and is the shape every author believes about their own endpoint.
- `createOverageDraftAction` (#167) — `requireUser()` plus the Job check, the same per-record axis as the other delivery actions, and **deliberately not Admin**: raising the correction is site work. It is the exception to #166's withholding described under "Overage corrections", and it re-derives eligibility from a fresh read so a correction raised in another tab lands as a refusal rather than a second Draft.
- The eight `requireUser()` Server Actions — session + per-record/per-turn ownership, not a role. `requireUser()` already cannot be dropped (it redirects), and the actual authorization is the record-by-record comparison in the body. A wrapper here would cover the half that was never at risk and leave the deciding half uncovered, while looking like coverage.
  - **THAT COMPARISON WAS CHECKED BY NOTHING, AND TWO OF THE EIGHT MADE NONE (#440).** `saveDraftAction` and `createPRAction` carried this exemption and rewrote whichever request `existingDraftRecordId` named. `offline/owner-before-write.mjs` now inventories every read of a request by id under `app/` and `lib/`, and requires each one a write follows to ask its declared judgment about that record before the first side effect — which reaches an order's writes through the request behind the order. The delivery and tool axes, which compare a job, are still held by their exemptions alone. `purchase-requests.md` has the derivation.
  - **A WRITE'S REFUSAL CONFIRMS NOTHING EITHER.** The not-found rule was written for a page, and #440 applied it to the three draft writes: somebody else's request, in any status, is refused in the words an id that resolves to nothing gets, because identity is asked before status. Four refusals elsewhere still answer the two differently, and `backlog.md` holds them.

**TWO OF THE FOUR STOPPED BEING CALLABLE FROM OUTSIDE `lib/authz.js` (#182), AND THE RULE THEY ILLUSTRATE IS UNCHANGED.** That issue audited `lib/` for exports nothing outside their own file imports and found `requireRole` and `requirePresident` among twenty. Neither had ever had an outside caller: `requireRole` is what `requirePresident` narrows, and `requirePresident` is the argument `createThrowingGuard` takes to build `withPresidentAction`. Both keep the `export` keyword off now, which makes "gate a new endpoint with a WRAPPER, not a bare call" structural rather than advisory — a President-gated PAGE would carry its gate in its own body and is the one shape that would want the export back, and none exists. The paragraphs below describe all four because the failure modes are what a reader needs; only reachability changed.

**Caller obligation:** requireRole()/requireAdmin() only *report* the decision — a caller must destructure the returned `{ authorized }` and short-circuit on false (throw, return `{ error }`, or render a refusal). Calling one without acting on the flag protects nothing (the code runs on). requirePresident() and requireAdminApi() are both preferred over the flag helpers for the cases that use them, but they are not equally undroppable, and the difference is the return: requirePresident() *throws*, so control cannot continue past a refusal and there is nothing for a caller to ignore; requireAdminApi() *returns* the 401/403 Response, which is a value the handler has to return for anything to be blocked — the call on its own refuses nothing, so leaving its result unassigned is still a way to lose the gate. What it removes versus `{ authorized }` is the flag to misread, not the caller's obligation.

**Re-authorization rule (#134):** every directly-callable endpoint re-authorizes to the level of the strictest page that renders its UI — a page being the only caller isn't a substitute, since Route Handlers and Server Actions are reachable directly. Server Actions use the wrappers above (signPOAction/regeneratePDFAction are `withPresidentAction`; generatePOAction, the PO-generation retry, is `withAdminAction` with a matching isAdmin render gate on app/prs/[prId]). withdrawPOAction (#138) is the per-record variant: requireUser() only settles "is this an active session", and the actual authorization is an ownership comparison against the parent PR's Requester inside lib/poWithdraw.js — no role helper fits, since the requester is typically neither President nor Admin. `/api/*`: the magic-link auth routes are intentionally public, /api/quotations/upload is any-active-user (matching the PR form that consumes it); /api/invoices/upload, /api/invoices/detect-po, /api/pos/search, /api/pos/[poRecordId]/items are Admin-only via requireAdminApi() (their sole consumer is the Admin-only invoice form). Any route that fetches a caller-supplied URL also restricts it to our Vercel Blob host (detect-po's SSRF guard), independent of auth. **Since #438 that reaches every action that hands a caller's URL to Airtable as an attachment**, which fetches it on the app's behalf just as a route would, and "our" host means our own store rather than any host ending in the Vercel suffix, which is what the predicate had admitted — `uploads-and-drafts.md` has the inventory and the measurement.

**What enforces the rule (#147).** `scripts/tests/offline/authz-structure.mjs` is a structural check over an **enumerated** inventory — enumerated because a hard-coded path list is blind to any route added later: it walks every `app/api/**/route.js` and every `"use server"` file under `app/` and `lib/`, parses each with acorn (so a comment can satisfy nothing), and requires each export to be either wrapped by one of the three wrappers or listed as an exemption with a reason. It also flags a function-level `"use server"` directive anywhere in those trees — an inline Server Action is directly callable too, and none exist today, so one appearing should fail rather than pass by not being looked for. A file it cannot parse fails; an unparsed file is an unchecked file. A stale exemption (the export is now wrapped, or no longer exists) fails too, so the list can't rot into a blanket permission.

**What a pass proves, per case.** For a **wrapped** export: the gate cannot be skipped and cannot run late, because the handler is an argument the wrapper decides whether to call — ordering is structural, so there is nothing left for the check to assert or for an author to get wrong. For an **exempt** export: only that the named helper is called somewhere inside the exported function. **Order is not checked** — the old check's `gateIdx < workIdx` comparison has no counterpart, so an exempt route that does work before its gate still passes. That is not hypothetical: `/api/invoices/upload` and `/api/quotations/upload` both call `request.json()` before authorizing, which is why that fact is written into their exemption reasons. This is the check's exact scope rather than a defect in it, and it is the reason an exemption is worth less than a wrapper.

**It is a standing check, not issue evidence.** It runs with no env vars, no Airtable, no dev server and no module loader, writes nothing, and exits non-zero when it fails — so since #152 it sits in the offline tier that `npm test` and CI run on every push (see "Verification tiers" below). `scripts/tests/verify-authz.mjs` keeps only what genuinely needs credentials: the Blob host predicate, PO-generation idempotency against a throwaway PR+PO, and real HTTP 401/403 refusals. That one needs `.env.local`, the loader, and a dev server, and it exits 2 when a part could not run so an incomplete run never reads as a pass. Adding an endpoint without a gate fails the offline tier without anyone remembering to register it, which is the property the old check didn't have.

### Invoice visibility (#211)

**The two invoice routes were President-or-Admin and NO REASON FOR THAT WAS EVER RECORDED.** #132's "the invoice pages stay President-or-Admin" scoped *that* issue rather than deciding this one, and #166 withheld vendor invoice figures from the delivery screens without saying why either. So there was no argument to overturn, and the reason this file now carries is the pair that replaced it.

- **The boundary was already leaking.** #167 hands a site employee the vendor's own invoice PDF as the quotation on a corrective request and puts its number in `Vendor Quotation Code`; `/pos/[poId]` shows that same employee the `Amount` column. What the company agreed to pay was fully in view while what the vendor charged was not — not a line anyone would draw on purpose.
- **The person who counted the material is the only reader positioned to notice that a vendor invoiced for thirteen and shipped ten.** Withholding the invoiced quantity from them removes the one check that catches it.

**The rule is `canViewPR`, reached through the order.** President and Admin see every invoice; anyone else sees one whose items sit on a PO whose parent PR they raised or whose parent PR sits on one of their assigned Jobs. `lib/invoiceVisibility.js` owns the WALK and no predicate of its own — `offline/invoice-visibility.mjs` asserts on the AST that it imports and calls `canViewPR` and that it touches none of that function's own inputs, because a second predicate would not fail anything for as long as the two happened to agree.
- **ANY line is enough.** A multi-PO invoice is real, so one document can charge an order the viewer raised and one they have never heard of. The viewer is looking for the line that is theirs, and refusing the whole document because it also covers someone else's order would hide the thing they can actually check.
- **An invoice with no resolvable order is REFUSED**, which is the opposite direction from `canViewPR`'s own throw-on-missing-data — there, refusing would stall a signing chain; here it just means an employee does not see a document, which is the pre-#211 state. Measured on this base: `scoped-fixture@` sees fewer invoices than an Admin, and the excluded ones were the hand-entered dummies with no `PO` link (`HYE-INV-260727-03` rendered the `None linked.` empty state, which #278 removed along with the state that reached it — the refusal itself is now a fail-closed default rather than a described case).
- **Two operations for a page of any size, and ZERO for the office WHERE THE VERDICT IS ALL THAT IS WANTED** — the privileged answer needs no `canViewPR` call, so `getVisibleInvoiceIds` returns it without reading anything. **#314 narrowed that sentence**, which used to state it of the walk itself: `resolveInvoiceScope` is the same walk with its orders and requests handed back, and it walks whoever is reading, because the invoice list needs a request's `Job` for its own column and resolving a rendered fact from a walk one reader skips is a column whose value depends on who is looking at it. So the list costs 14 operations for the office and 14 for a site employee, up from 12 and down from 15 — one budget, which is what #309 gave the columns. The other three call sites take the verdict-only shape and are unchanged. The list still runs the reconciliation over the GATED rows, so a refused invoice's items never reach the wire either (#169's shape).

### Payment was President-or-Admin (#211) and is open to every reader of the row (#309)

**#211's line was drawn deliberately rather than inherited**, and the reason it gave was that whether a vendor has been paid is the one fact on these screens a recorder has no use for and a vendor's own staff might ask about on site. **The office asked for the opposite**, so the line is reversed: the gate deciding whether a document is visible is the only gate on reading it, and payment carries none of its own. Recording it did not move — the checkbox and the date are still President-or-Admin, which is the split #211 never had to make while reading and writing stood behind one answer.

**THAT SPLIT IS THE WHOLE OF THE RISK, AND IT IS STRUCTURAL RATHER THAN WRITTEN DOWN.** `seesEveryInvoice` answered two questions — may the walk be skipped, and may the payment line render — so the read gate and the write gate were one nesting apart with one predicate behind both. Collapse them and opening the read opens the control, with every check still green. `offline/invoice-visibility.mjs` assertion 3 is the answer: **a branch whose test asks a PRIVILEGE question may not have the payment fact on one side only.** `{privileged && <Payment/>}` fails; a ternary stating the fact on both sides passes, because a reader who cannot record it still reads it. **#318 left that screen with no such branch at all** — the section states the fact unconditionally and hands the privilege answer to its Client Component as `canEdit` — and added assertion 3b, which runs the same rule over branches on the section's open/closed state, where the identical mutant can now be written. Assertion 4 keeps the FILE inventory (`PAID_READERS`) — a new reader of `.paid` fails CI until registered — and the two are needed together: a file list cannot see one screen left gated, which is exactly what `/pos/[poId]` was.

## Auth (lib/auth.js, lib/session.js, lib/email.js, lib/authz.js)

- A magic link, or the code the same email carries (#471). requestMagicLink() domain-checks, holds the request to #148's ceilings, emails both and binds the asking browser to the row; verifyMagicLink() and signInWithCode() spend that one row under one withKeyLock key and end in one startSession(), which finds-or-creates the User. See "Signing in with a code" below.
- **THE LOCAL PART OF AN ADDRESS IDENTIFIES A PERSON ONLY BECAUSE ONE DOMAIN IS ADMITTED, AND A SECOND DOMAIN WOULD BREAK THAT SILENTLY.** `ALLOWED_EMAIL_DOMAIN` is one variable holding one value and `isCompanyAddress` (`lib/companyEmail.js`, #473) admits an address only when everything after its `@` is that domain, so no two users can share a local part. ### The destination a sign-in carries (#373)

A reader who follows any address in this app while signed out is redirected to `/login`, signs in, and lands on the root screen; the address they asked for is gone and they have to type it again. **The scan is what made that expensive rather than annoying**: the person is holding a phone in front of a tool, the root screen was then the app's only navigation and is drawn for a monitor, and there is no way back to the tool item from it except scanning the label again. The flow now carries the address through both of its steps and returns to it.

**THE FLOW IS TWO STEPS AND THAT IS #203's DOING, so the destination has to survive a mail round trip.** `/login` requests the link, the link lands on `/login/confirm`, and only the button there mints the session — because a mail scanner following a link must not spend the token. Nothing between `requireUser()` and that button held the address.

#### Capture: what the framework offers, measured rather than assumed

`requireUser()` runs inside the page the reader asked for and is the only point that knows the address. It cannot ask Next for it, and this was read off 16.2.10 rather than off the documentation:

- `next/dist/server/request/pathname.js` exists and is `createServerPathnameForMetadata`, reachable only from metadata resolution.
- `headers()` carries no path on a document request. `next-url` is set by the CLIENT router on RSC navigations, so a hard navigation — which every scan is — has none.
- `x-matched-path` is Vercel's own and is absent under `next dev`, so anything resting on it could not be checked locally.
- `unauthorized()` with `app/unauthorized.js` would render the sign-in screen AT the original address and solve capture outright. It is still experimental in 16.2.10 — the framework throws "`unauthorized()` is experimental and only allowed to be used when `experimental.authInterrupts` is enabled" — which is not a flag to turn on under a production sign-in.

So the address has to be put onto the request, which is `proxy.js`. **The alternative was an argument at every call site**, `requireUser({ destination })` at about twenty-five pages, and it is refused on the shape rather than on the count: a page added later that forgets the argument loses the destination and nothing fails, which is the same silence CLAUDE.md's rule about a new record-showing surface is written against. A check could require the argument to be PRESENT and could never say the value is right.

#### `proxy.js` against #46, which refused one deliberately

**The compressed line in this file said "No proxy.js/middleware", and the decision behind it was narrower than that.** `f650eca` (#46) reads: *"Deliberately not adding one: since Role/Is Admin/Status can never be cached in the cookie, the only check a `proxy.js` could do cheaply (per Next's own guidance: avoid DB calls in Proxy, it runs on every request including prefetches) is 'is there a session cookie at all' — which doesn't save anything over each page just calling `requireUser()` itself."* **It was refusing a GATE, and it left a revisit condition** — "enough protected pages that a first-line must-be-logged-in gate becomes worth the added layer" — which is the sentence this issue has to answer, because a reader who finds the file will reasonably conclude the condition fired. It did not.

**The condition should not fire even when somebody decides it has, and the reason is stronger than #46's.** This app's real authorization is per record: `canViewPR` admits the requester, anyone on the job, a signer on the chain. None of that is knowable without reading the record, which a proxy must not do. So a gate there could only ever ask the weakest question the app asks, in front of the page that already asks it, and its true effect would be to make a page whose own `requireUser()` was dropped look covered. The file's header carries that argument where somebody about to add a gate will meet it, and `offline/login-destination.mjs` holds it structurally: no authorization helper is named in `proxy.js`, and it imports nothing that reaches `lib/airtable/` or `lib/session.js`.

**Two facts about the file itself.** A proxy in Next 16 always runs on Node — a route segment config naming a runtime there is a build error, so nothing declares one. And the matcher excludes `/api`, on the fact that a Route Handler cannot call `requireUser()` at all; the check holds that from the other side, so the day a handler does, the exclusion is re-opened by a failure rather than by somebody noticing.

#### Carriage: the URL, and what that costs

Three ways across the mail hop were weighed.

- **The URL, which is what shipped.** `/login?destination=…` → the request body → the link in the mail → a hidden field on the confirmation → the redirect. Every hop is in the repository, and `offline/url-parameters.mjs` already holds both directions of a parameter's life, so a hop that stops carrying it fails a check that existed before this issue.
- **A field on the `Auth Tokens` row.** The confirmation and the verify body would not change at all and the mail would stay short. **Refused on what this tier can see**: it is a schema change on the production base for a value that lives fifteen minutes, and `verification.md` records that the offline tier is blind to the base in both directions — a field renamed in the Airtable UI would land every sign-in on the root screen with every check still green. The comparison is recorded here rather than dismissed, because it is the better design on every axis except that one.
- **A cookie set at the request step.** Refused on a measured property of the reader rather than on taste: a QR scan opens the phone's browser and the mail link opens in the mail client's own web view, so the two are frequently not the same cookie jar — the destination would be lost in exactly the case this issue exists for. Binding it to the TOKEN, as both other designs do, is what makes the device irrelevant.

**THE COST OF THE URL IS THAT THE DESTINATION IS IN THE EMAIL**, and it is recorded in `lib/loginDestination.js`'s header where the link is built, because that is where somebody asking why the sign-in link got longer will be looking. It sits in the recipient's mailbox for as long as they keep the message, in whatever their provider retains, and mail gets forwarded — so an internal address of this app is readable outside it. The constraint that follows is on that module: whatever those builders put in a link is in a mailbox forever, so nothing else goes in one.

#### The judgment, and the one outcome for two cases

`safeDestination` is the only predicate, and it is applied wherever a destination is accepted rather than once: both path builders call it, so no caller can put an unjudged value into a URL; both screens call it before rendering one; and `POST /api/auth/verify` calls it again before redirecting, **which is the call that actually protects anything** — that endpoint is reachable without the page that renders the form.

**What it accepts is origin-safety and not existence.** A path within this app, parsed against a probe origin and required to come back with it, which is what refuses `//host`, a backslash a browser reads as a host, and an embedded scheme. `/nothing-here` passes and resolves to this app's own not-found screen: the property being defended is that a destination cannot become a way OUT of the app. **Matching against the app's route templates was the alternative and is refused** — `lib/` holds no list of them, so it would be a second copy of the route table, and a page added later would be dropped by a check nobody can see firing. Two addresses inside the app are barred anyway: `/login` and everything under it, so a sign-in cannot deliver the reader back into the sign-in flow, and `/api`, which no capture can produce.

**A refused destination and no destination are one outcome** — both land on `/`, and no screen says a word about either. Telling them apart would need a sentence naming the address that was refused, which is copy this app does not have, and `/login` is reachable by anyone, so a shared link would show a stranger where somebody else was going. The briefs record that silence as deliberate so a design does not read it as a missing state.

**A refusal from the verify endpoint keeps the destination**, including the one with no token at all, so a reader who has to request another link does not lose where they were going — and the confirmation's own `Request a new sign-in link` carries it too, which is the last step where it could quietly be dropped.

**One line of the mail changed with it.** The link now has two parameters, so the `&` joining them sits inside an `href` in hand-written HTML, where it is an entity start; `lib/email.js` escapes the URL into the attribute, which is what stops the correctness of a sign-in link depending on what a parameter is called.

#### What the check holds, and what a browser had to prove

`offline/login-destination.mjs` asserts the predicate by behavior and everything else by CALL SITE AND ARGUMENT, because the trap here is sharper than usual: `proxy.js` and `lib/authz.js` import the header's NAME from one module, so an assertion naming that header would be worth nothing — rename it and both sides move together, green. It asserts instead that the stamping call takes the imported identifier, that the reading call takes it too, that the redirect's argument is a value the predicate produced, and that the confirmation's hidden field is named by the shared constant. Eight mutations were run against it and all eight failed it, including two that leave the app working: a proxy stamping its own literal, and a proxy that drops the query.

**What it cannot see is the arrival**, so the walk was made in a browser at 375px with a real fixture session: signed out at a tool item, the sign-in screen carrying the destination, the link, the confirmation, and the tool item's own page. Both sign-in screens were measured there rather than eyeballed — 375px viewport, no horizontal overflow, the form 311px inside the page's padding. **The one hop no check and no browser reached is the delivered message**: nothing here can read an inbox, and what closes it is that `lib/auth.js` builds the mail's URL from the same builder the check holds.

### Taking a person's name at their first sign-in (#381)

Nobody was ever asked their name. `createUser` wrote `email.split("@")[0]` into `Users."User Name"`, and that field is the primary — so every link to a person rendered a login handle, and a request was waiting on `bsws9803` while an edit log said `hkahn` changed something. The field is `First Name` with `Last Name` beside it now, both typed by their owner, and `lib/userName.js` owns which of them a surface prints.

#### The schema, and why a rename was the only shape

**The primary could not be deleted, for a broader reason than the one that was assumed.** The Metadata API has no field DELETE at all — measured in #363 and recorded in `airtable-access.md`: a DELETE against a real field id answers 404 and the field survives — so no field on this base is removable through the API, primary or not, and Airtable's UI refuses a primary on top of that. A rename in place was therefore not the cheap option but the available one, and it is also the right one: the field id is preserved, so the **14 link fields on this base that point at a `Users` row** went on rendering the same cell with nothing to fix. Measured before the edit: no formula, rollup or lookup anywhere on the base references that field id.

**Joining two names into a formula primary was refused on a measured limit rather than on taste.** A field's TYPE cannot be PATCHed (422, `Changing a field's type or number precision is not currently supported`), so it would be a hand conversion in the UI that drops every stored value, and the base would carry three name fields where two say everything.

**Both halves shipped from one script, `scripts/import/rename_user_name_381.mjs`** — one PATCH for the primary's name, one POST for `Last Name` — with one cosmetic hand step left over, since a field created through the API is appended at the end of the field list.

#### Where the question is asked, and the two places it is not

`/login/name` is the third step of the sign-in flow, after the token has been spent. The two earlier positions were both weighed and both fail on the same axis:

- **On `/login`, before the link is sent.** The person has not shown they control the address, and the answer would then have to cross the mail round trip — in the link, which `lib/loginDestination.js` bars anything else from riding (whatever goes in one is in a mailbox forever), or on the `Auth Tokens` row, which #373 already weighed and refused for a value that lives fifteen minutes. It also cannot ask only new people without telling an unauthenticated caller whether an address has an account.
- **On `/login/confirm`, before the button.** The same problem one step later, and on the one page a mail security scanner opens. It would also put a two-field form inside the VALID branch of a screen the briefs describe as five mutually exclusive states whose whole feature is one extra click.

**The gate is `askForNameIfMissing`, which `requireUser()` calls, and it costs no Airtable operation.** `getActiveUser()` has already fetched the record, so `needsName` is a property test on an object in hand. Route Handlers are deliberately not gated on it: they call `getActiveUser()` or `requireAdminApi()`, and a name is a display fact rather than an authorization one, so a nameless session may still fetch a file it is entitled to.

**IT IS EXPORTED BECAUSE ONE PAGE CANNOT CALL `requireUser()` AND STILL BE ITSELF, AND THE BROWSER IS WHAT FOUND THAT.** The gate lived inside `requireUser()` and the walk that created a real account through the real sign-in path landed on `/` and was asked nothing — because the root screen resolves the session with `getCurrentUser()` so it can draw a signed-OUT state of its own (`Not signed in.`, and a way in), and a helper that redirects on a missing session would delete half of what it renders. So the one page the gate did not reach was the first page a new colleague sees, `DEFAULT_DESTINATION` being exactly that address. The rule is now one implementation at two call sites, and `offline/user-name.mjs` enumerates the pages that resolve a session WITHOUT `requireUser` and requires each to call it — one today, and a second added later fails until it asks. **No check could have found this**: every assertion about the gate read `requireUser`'s own body, and the page that skipped it never called that function.

### Signing in with a code (#471)

A sign-in link signs in whichever browser opens it. Somebody who asks on a phone and opens the email on a computer is signed in on the computer, and so is somebody who opens it in the phone's mail app, whose own browser does not share the phone browser's cookies — which is the case a QR scan produces, since the scan opens the phone's browser. Found testing on a phone. The email now carries a six-digit code beside the link, and the screen that asked takes it.

#### One row, two ways in

**The link and the code are two ways of spending ONE `Auth Tokens` row, and `Used` ends both.** #203's structure is untouched: the link still lands on the confirmation, which reads and never spends, and `POST /api/auth/verify` still spends. What the two share is exactly what has to be one thing for "either one finishes the same request" to hold — one lock key per row, keyed on the row's token (`rowLockKey`); one write that ends the row (`spendAuthToken`, the only `Used: true` in the module); and one session start (`lib/auth.js:startSession`), so what follows a sign-in cannot differ by the way in: the reader lands where they were going, and a first-time signer meets the name step there because `requireUser()` asks. The code path reads the row by id first to learn its token, then takes that lock and reads again inside it — one read more than the link path, which is unchanged.

#### Finding the row: bound to the asking browser, not looked up by address

Two designs were weighed. **Looked up by address**: the screen sends the address and the code, and the row is found by address. **Bound to the browser**, which shipped: the request step seals the new row's record id into a second cookie in the browser that asked (`lib/session.js`, `hye_sign_in`), and a code is checked against that row and no other.

- **A code seen by anybody else is worthless.** A lock-screen preview, a forwarded email, a colleague reading over a shoulder: the code works only in the browser holding the binding. Looked up by address, address plus code is a credential from anywhere for fifteen minutes.
- **Nobody can spend somebody else's five tries.** Looked up by address, anyone who knew an address could guess at it and lock that person's code while they were signing in.
- **Every refusal is about a row the asking browser requested**, which is what keeps the refusals from saying anything about an address — below.
- **The code step survives a dropped tab.** The page reads the binding, so a phone that discards the tab while its owner reads the email reopens on the field the code goes in.

**#373 REFUSED A COOKIE FOR THE DESTINATION, AND THIS IS NOT THAT.** That refusal was about the LINK: the value had to be present wherever the link opens, and a scan's browser and a mail client's own view often do not share cookies, so a value set at the request would be missing where the link lands. A code is typed into the browser that asked, so the binding never has to cross into another cookie jar — which is also where the code's value comes from.

**What the binding holds is the row's record id and the address, and never the token or the code.** The token in the asking browser would sign it in without anybody opening the email, which is the one thing the email exists to prove; the code there would be the same mistake. It is sealed with `SESSION_SECRET`, httpOnly, and lives as long as the row. Because it sets a cookie, the request POST refuses a cross-origin submission since #471 — a page elsewhere must not leave a visitor waiting on the page author's own email — and `Change`, at the end of the address chip (`Use a different email` until #473), forgets it through `DELETE /api/auth/request`, the only way back to the address step before it expires, since the page reopens on the code step by design.

#### An earlier email's row is left alone

**Retiring the earlier rows on a new request was weighed and refused, on what it would hand out.** Anybody can ask for an email to any company address, so a request that ended the earlier rows would let a stranger end somebody's sign-in in progress by asking once more — a sign-in denial that does not exist today, and that #148's ceilings would bound rather than prevent.

**And under the binding it would buy nothing.** A guess is compared against exactly one row, the one the guessing browser's binding names, so other live rows do not raise the odds of any guess. A new request replaces the binding, so an earlier email's code stops working in that browser; its link goes on working until it expires, as links always did. The cost is a reader who asked twice and types the older email's code: it does not match, and a try is spent. Until #473 the screen said after `Send a new email` to use the newest email's code; the design draws `Email sent` for three seconds after `Resend email` and no sentence, so the rule is the brief's (`docs/briefs/login.md`) and the older code is answered as any wrong one is.

#### Stored as it is

**The code is stored as is, beside a token stored as is, and the pairing is the argument.** The token is the stronger credential for the same row: it works from any browser, where the code needs the asking browser's sealed binding. So anybody who can read the row can already sign in with the token, and hashing the code alone protects nothing; an unkeyed hash of a six-digit space is reversed by trying a million values in any case. A keyed hash matters only once the token is hashed too, which is a change to how the link is stored and not this issue's. **The condition is in `lib/airtable/authTokens.js`'s header: the day the token is hashed, the code is, and with a key.**

**Deriving the code from the token was weighed too** — an HMAC of the token, cut to six digits, would need no field. It hides the value behind a secret that already has a job (sealing sessions), ties every pending code's validity to that secret's rotation, and leaves the base unable to say what code went out, which is what a person sorting out a sign-in by phone would need to know.

#### Made and compared

- **Drawn with `crypto.randomInt(0, 1000000)`**, which rejects rather than folds the values past a whole multiple of the range, so every code is equally likely; zero-padded, and stored as text so the leading zero survives. It is drawn on its own rather than derived from the token or the clock.
- **Compared in constant time** — `timingSafeEqual`, once both sides are six digits, which is what makes the lengths agree. The row is found by its record id, so a code never enters a `filterByFormula` and the base never compares one.
- **A value that is not six digits is not an attempt.** It cannot match, so refusing it uncounted gives a guesser nothing, and it keeps a typo from spending one of the reader's five. Whitespace is taken out first, so a pasted `123 456` is a code.

#### The count, and why the row can hold it

**`Code Attempts` counts every attempt, the right one included, and it is written in the same write as the attempt's outcome, before the attempt is answered.** That order is what makes a broken field fail closed: renamed or deleted in the Airtable UI, the field refuses the write for the right code and the wrong one alike, so no attempt is answered while counting nothing. It is why every attempt is counted rather than only the wrong ones — a right one that skipped the write would be the one answer given without a count — and why the field is written as 0 when the row is made, so a rename fails every request loudly at the start.

**The row holds the count without a new store, with one qualification.** Within one process it is exact: attempts on a row take the row's lock and re-read the count inside it. Across two concurrent invocations it is best-effort, because Airtable has no atomic increment and two attempts on two instances can read the same count. The ceiling on that is the base's own rate — about five requests a second, shared with everything — against three operations an attempt: at worst about 1,500 comparisons over a row's fifteen minutes, roughly 0.15%, while every other screen waits. No distributed lock is built, which is this app's standing answer to the cross-invocation window (`airtable-access.md`).

**The larger term is the number of rows, and #148 bounds it.** Each request makes a fresh row with five fresh tries — 1 in 200,000 per email — so the guesses at one address are five times the emails sent to it, which #148 holds to twenty a day (below). #471 deliberately built no limit of its own.

**Five wrong codes end the code and not the row.** The link keeps working: it is unguessable, so wrong codes say nothing about it, and killing it would turn five bad guesses into a denial of the real sign-in.

#### What the code step says, and what it cannot tell a stranger

The states are `malformed`, `missing`, `invalid`, `used`, `expired`, `locked`, `wrong` and `valid`, in that order of precedence. **`used` and `expired` are the link's own judgment** (`rowLife` in `lib/authTokenState.js`), so the two ways in cannot disagree about whether a row is alive — held by `offline/auth-token-state.mjs` over every combination of the two facts.

**None of them says anything about an address.** Each describes the row the asking browser requested, and a row exists for any company address from the moment anybody asks for one — the request step creates it without reading `Users`. Looked up by address, `used`, `expired` or `locked` for an address the asker never requested would have said somebody signed in there recently, and `used` would have said the address has an account, since a first sign-in creates one.

**`used` is the one state somebody else can influence**: it appears when the email's link was used, which only the mailbox's owner can do. So a person who asks for an email to somebody else's address can learn that its owner confirmed an email they did not request. That needs the owner's own action, so it is no way to go through a list of addresses, and it signs the owner in on the owner's device. ### How often a sign-in email may be asked for (#148)

`requestMagicLink` took any number of requests for any company address. Each one mails somebody, spends the Resend quota the order mail shares, and hands its asker five tries at a fresh code. A request is now held to three ceilings, and one over a ceiling is told so and when it may ask again. `lib/signInLimit.js` owns the ceilings, the rest between two emails and the judgment; its header carries what they do not bound.

#### What is counted: the rows the requests already make

**No counter of its own, because every request already writes one row.** `requestMagicLink` makes an `Auth Tokens` row for any company address without reading `Users`, so a count of rows treats an address with an account and one without alike. That is what let the issue's first answer — the same response whether or not a ceiling was reached — give way to telling the asker: the ceiling cannot say who has an account, because it counts every company address the same way.

**One read before the row.** The rows of the last day that share the request's mailbox or its IP, newest first, one page — a send costs two operations where it cost one, and a refusal costs one and writes nothing. A full page cannot cut a verdict short: the day's two ceilings together are below it, so a full page already holds a ceiling's worth of one of them.

**A row made a moment earlier is in the next read, and why that holds.** Every field the read filters on — `Created At`, `Mailbox`, `IP Hash` — is written in the call that creates the row, and none is computed by Airtable. What `client.js:getLinkedRecords` records as briefly invisible to a filter is a computed field; a written one is what `lib/ids.js:mintDailyIds` already relies on to see the day's last id. Were a row missed, the cost is one email past a ceiling, never a refusal that should not be. `verify-sign-in-limit-148.mjs` Part C measures it.

**A row a script mints is not counted.** It carries no `IP Hash`, since only a request names an IP, and the read takes only rows that carry one. Such a row sends no email, and its code is bound to no browser, so it is nothing a ceiling exists to bound — and the sessions the credentialed tier mints for `soo@` cannot use up that address's allowance.

#### The mailbox and the IP

**The mailbox is the address lowercased with its `+` tag cut.** Another case signs in as the same person — `getUserByEmail` compares `LOWER()` on both sides — and a tag lands in the same inbox: #471's and #473's walks received their codes at `soo+code471@` and `soo+name473@`. Counted by `Email` as typed, every spelling would be a fresh allowance into one inbox. It is stored on the row as `Mailbox` rather than computed by an Airtable formula: a formula field cannot be created through the API, a computed field is the kind a filter can briefly miss, and the rule would then be implemented twice.

**The IP is the first entry of `x-forwarded-for`.** Vercel overwrites that header with the address that connected (its request-header reference, read 2026-10-05), so deployed it cannot be chosen by the caller; `next dev` fills it from the socket when it is absent (`base-server.js` in 16.2.10), so a local walk counts the way a deployed request does. `x-real-ip` carries the same value on Vercel and nothing under `next dev`. An IPv6 address counts as its /64, since one subscriber can take any address in it; an IPv4-mapped one as its IPv4 address; and a header that is no IP shares one key with every other such request rather than having no ceiling.

**What the row stores is a keyed hash, never the IP.** HMAC-SHA256 under a key derived from `SESSION_SECRET` with a label of its own, so no new variable has to be set where the app runs, and the base holds nothing a reader could turn back into an address by trying all four billion IPv4 ones. The hash never leaves `lib/airtable/authTokens.js`: the read hands back which of the two each row shares.

#### The ceilings and `Resend email`'s rest

| Per | Window | Emails | What it bounds |
|---|---|---|---|
| mailbox | 10 minutes | 11 | a burst into one inbox |
| mailbox | 24 hours | 20 | guessing at one address's code |
| IP | 24 hours | 50 | one host mailing many addresses |

**`Resend email` rests a minute after every email, `Continue`'s included, and the ten-minute ceiling is set from it.** An email at most once a minute leaves no more than ten in any ten minutes, so pressing the control each time it comes back never reaches eleven — even if the first press comes the moment the code step opens. Pressed that way, the first request refused is the twenty-first, by the day's ceiling; `offline/sign-in-limit.mjs` holds both by simulation as well as by the arithmetic.

**Twenty a day per mailbox is at most a hundred guesses a day at one address**, about one in ten thousand, and a month of it would be six hundred emails to the address's owner. **Fifty a day per IP** lets an office behind one IP sign everybody in on two devices in one day, and holds one host to half of what Resend's free plan sends in a day (100 a day and 3,000 a month on its pricing page, 2026-10-05). For scale, the busiest this base has been: seven rows for one mailbox in ten minutes, during #471's walk, and nine in a day since #471 — rows a script minted included, since nothing then told them apart.

**Nothing caps the app as a whole.** Many IPs can still use the quota up, and a cap of that kind would turn it into a sign-in outage for everyone — the trade the module header names.

#### The answer

**`429`, a `Retry-After` and `{ limited: true, retryAt }`, and nothing else.** `retryAt` is the time of the row that brought a ceiling's count to the ceiling plus its window, the latest over every ceiling reached, and it comes from the rows alone. Which ceiling was reached is left out: naming the mailbox's would tell a caller that somebody else has been asking for that address. The time itself says nothing a caller could not learn by asking again every so often, and nothing about an account.

**A refused request makes no row, sends nothing and leaves the binding alone**, so the code of an email the browser already holds still works — which is the way through for an owner whose allowance a stranger has spent.
